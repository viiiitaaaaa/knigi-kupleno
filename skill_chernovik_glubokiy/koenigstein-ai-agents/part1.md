## Гл. 1. От языковой модели к агенту

- Хочу понять, чем агент отличается от обычной модели — правило: обычная модель (LLM) знает только то, чему училась, не помнит прошлого и отвечает за один проход; агент имеет память, вызывает инструменты и работает по кругу «подумал → сделал → получил ответ» (стр. 8) [01]
- Хочу собрать управляемый поток агента — шаги: 1) описать «состояние» (словарь: контекст, история сообщений, служебные метки) 2) разбить задачу на этапы-«узлы» (планирование, действие, разбор результата) 3) написать на Python обычные проверки, куда идти дальше 4) подключить инструменты (функции/API), их результат возвращается как новое событие 5) сохранять состояние на границах шагов (checkpointing — «точки сохранения»), чтобы после сбоя продолжить (стр. 8) [01]
- Сопоставление с LangGraph (библиотека для графов агента): родительский граф = «суперсостояние», подграфы = вложенные состояния, условные рёбра = проверки перехода; `MemorySaver` делает точки восстановления (стр. 8) [01]
- Чего НЕ делать: решать сложную многошаговую задачу одним длинным промптом без управления состоянием — результат нестабильный (стр. 8) [01]
- Чего НЕ делать: давать агенту неограниченную автономию без рамок и проверок — риск зацикливания, перерасхода бюджета, нежелательных действий (стр. 8) [01]
- Управление автономным агентом — это непрерывный замкнутый цикл: телеметрия (данные о работе), границы допустимого поведения (оценки), обратная связь (стр. 6) [01]
- Главная трудность при переходе к агентам — не рабочее демо, а надёжность, безопасное хранение состояния и памяти, постоянный контроль в продакшене (стр. 6) [01]
- Книга решает реальные проблемы: сбои инструментов, управление контекстом, рост затрат, интеграции (стр. 7) [01]

### Быстрый прототип агента без памяти (stateless) — шаги [02]
- Хочу агента с инструментами за один запуск — шаги: 1) оформить каждый инструмент как функцию с декоратором `@tool` (обязательны точная сигнатура и docstring — описание функции) 2) привязать инструменты к модели `bind_tools(..., tool_choice="auto")` (модель сама решает, нужен ли инструмент) 3) цикл: вызвать модель; есть `tool_calls` — выполнить их и добавить `ToolMessage`; повторять, пока вызовов нет или не кончился лимит шагов 4) после лимита добавить инструкцию «Finish now. Give a short final answer» для гарантированного ответа (стр. нет в конспекте) [02]
- Число: лимит шагов цикла по умолчанию 8 — защита от бесконечных петель («runaway loops») (стр. нет в конспекте) [02]
- Числа из примера: `temperature=0` (одинаковые ответы), `max_tokens=800` (стр. нет в конспекте) [02]
- Без docstring у инструмента LangChain выдаёт ошибку; расплывчатый docstring ведёт к неверным вызовам (стр. нет в конспекте) [02]
- Безопасный калькулятор в примере: глобальные переменные запрещены, оставлены только константы `pi`, `e` (стр. нет в конспекте) [02]

### Агент с памятью (stateful, LangGraph) — шаги [02]
- Хочу агента, который помнит диалог — шаги: 1) тип состояния (`TypedDict`/Pydantic) минимум со списком сообщений 2) узел `llm_node` (вызывает модель) и `tool_node` (исполняет `tool_calls` из последнего сообщения) 3) роутер: есть `tool_calls` — в `tools`, иначе конец 4) собрать `StateGraph`, рёбра START → llm, tools → llm 5) компилировать с `MemorySaver` (сохраняет состояние по веткам, только в памяти) 6) задать `thread_id` (номер ветки диалога) 7) по желанию трассировка (`run_with_tracing`) для компактного журнала (стр. нет в конспекте) [02]
- Числа: лимит рекурсии в `run_with_tracing` по умолчанию 20; `_short` обрезает текст до 140 символов (стр. нет в конспекте) [02]
- Ошибки: не хранить сообщения в состоянии — контекст теряется; не задать `thread_id` — все диалоги сливаются в один; неверный роутер — зависание цикла (стр. нет в конспекте) [02]

### Сколько автономии у агента на самом деле [02]
- Правило: сегодняшний агент выбирает только между заранее заданными путями, вызывает инструменты и рефлексирует; сам не может перепроектировать свой граф и создать новые инструменты без человека (стр. нет в конспекте) [02]
- Шаги: 1) определить фиксированные пути (узлы, инструменты) 2) ограничить модель выбором между ними (роутер, проверки) 3) добавить защиту: лимиты по времени/шагам, проверка вывода инструмента (стр. нет в конспекте) [02]
- Чего НЕ делать: считать автономию полной — переоценка и небезопасное поведение; без роутера агент может застрять или вызвать лишний инструмент (стр. нет в конспекте) [02]
- Пример AI Scientist v2: подал 3 статьи на воркшопы ICLR 2025, принята 1 (воркшоп, не основная конференция); слабые места — ошибки в цитатах, вводящие в заблуждение описания рисунков, поверхностная методология, скрытые баги в коде; нужен человек для проверки (стр. нет в конспекте) [02]

## Гл. 2. Паттерны рассуждения, человек в цикле, несколько агентов

### Выбрать способ рассуждения [02][03]
- Если задача — математика, планирование, аналитика → CoT (Chain-of-Thought, «думай по шагам»). Плюсы: надёжнее, прозрачнее, годится для небольших моделей. Минусы: медленнее, многословно, может дать правдоподобную, но ошибочную цепочку (стр. нет в конспекте) [03]
- Если задача творческая или поиск стратегии → ToT (Tree-of-Thoughts, «дерево вариантов»). Плюсы: исследует альтернативы, меньше «предвзятости первого ответа». Минусы: дороже, ветвление растёт без обрезки — контролировать глубину (pruning) (стр. нет в конспекте) [03]
- Если нужны и рассуждение, и инструменты (поиск, код, API) → ReAct («думай + действуй»). Плюсы: журнал действий, адаптация к ответам. Минусы: сложное состояние, риск бесконечного цикла — нужно явное условие остановки (стр. нет в конспекте) [03]
- Общий порядок: 1) определить тип задачи 2) выбрать паттерн 3) встроить в граф LangGraph (стр. нет в конспекте) [03]

### CoT на практике [02]
- Шаги: 1) системный промпт «думай шаг за шагом, финальный ответ — только после завершения анализа», с чёткой структурой финала (в примере 3 части: описать данные, найти закономерности, итоговый вывод) 2) при нужде добавить песочницу для кода (`PyodideSandboxTool`) 3) запуск через `create_react_agent` (стр. нет в конспекте) [02]
- Ограничение: Pyodide поддерживает не все библиотеки (нет `matplotlib`) — планировать pandas и вывод в SVG (стр. нет в конспекте) [02]
- Без чёткого финального шаблона модель может отдать частичный вывод (стр. нет в конспекте) [02]

### ToT на практике (облегчённый вариант) [02]
- Шаги: 1) узел-«предлагатель» (малая модель) выдаёт фиксированное число вариантов (в примере 3) 2) узел-«рефлектор» (более сильная модель) оценивает и выбирает лучший, ответ в JSON 3) дальше узлы research и draft работают с выбранным 4) рёбра: propose → reflect → research → draft → END (стр. нет в конспекте) [02]
- Число: ширина ветвления 3 — ради экономии и читаемости; слишком большая ширина даёт взрывной рост затрат (стр. нет в конспекте) [02]

### ReAct на практике [02]
- Шаги: 1) состояние = список сообщений 2) `model.bind_tools(TOOLS)` 3) узел-политика `call_model` выдаёт либо мысль, либо вызов инструмента 4) узел `tools` исполняет и добавляет `ToolMessage` 5) условный переход `should_continue`: к `tools` или конец (стр. нет в конспекте) [02]
- Без правильного `should_continue` цикл «подумал-сделал» не кончится — нужен жёсткий лимит шагов (стр. нет в конспекте) [02]

### Человек в цикле (HITL — human-in-the-loop) [03]
- Зачем: агент останавливается, ждёт подтверждения человека, потом продолжает — надёжнее и проще аудит (стр. нет в конспекте) [03]
- Четыре вида паузы: Approve/Reject (перед критическим шагом, напр. HTTP-запрос); Review and Edit (поправить состояние); Review Tool Calls (проверить аргументы инструмента, влияющего на внешние системы); Validate Human Input (запросить у человека доп. сведения) (стр. нет в конспекте) [03]
- Шаги: 1) выбрать место в графе 2) вставить `interrupt(...)` с вопросом, схемой и текущими данными 3) получить ответ 4) `approve` → `Command(goto=следующий_узел, update=…)`; `revise` → обновить состояние и вернуться в тот же узел-«ворота» 5) продолжить (стр. нет в конспекте) [03]
- Правило: код с побочными действиями (API, база) НЕ класть в тот же узел, где `interrupt` — риск двойного выполнения; пауза всегда ПЕРЕД действием (стр. нет в конспекте) [03]
- Ошибки: забыть `Command(resume=…)` при повторном запуске — граф зациклится; JSON не по схеме — ошибка проверки; бесконечный `interrupt → resume` без изменения состояния — «залипание» (стр. нет в конспекте) [03]
- Параллельные паузы (несколько отзывов сразу): 1) отдельные узлы, каждый со своим `interrupt` 2) подключить оба к START 3) компилировать с `checkpointer` 4) при `stream` получить список `interrupts` 5) собрать ответы (пусто = оставить как было; ввод пробовать читать как JSON) 6) вернуть `Command(resume={interrupt_id: значение})`; у всех пауз уникальные `interrupt_id` (стр. нет в конспекте) [03]
- Применять: деньги, запись в базу, изменения инфраструктуры, проверка текста/кода; для параллельных — несколько проверяющих (напр. юридический + технический) (стр. нет в конспекте) [03]

### Несколько агентов [03]
- Хочу руководителя над помощниками (Supervisor) — шаги: 1) список имён рабочих 2) системный промпт «ты супервизор, выбирай, кто работает дальше, либо FINISH» 3) структура ответа `Router` с полем `next` из `["FINISH", *members]` 4) вызвать модель со структурированным выводом 5) FINISH → END, иначе переход к выбранному 6) вернуть `Command(goto=…, update={"next":…})` (стр. нет в конспекте) [03]
- Рабочий узел: `create_react_agent` с инструментами и ролью; результат возвращает супервизору как сообщение с именем рабочего (стр. нет в конспекте) [03]
- Пример команды: search (Tavily), web_scraper, exa_search, patent_research; граф: START → supervisor, каждый рабочий → supervisor, FINISH → END; запуск с `recursion_limit` 100 (стр. нет в конспекте) [03]
- Иерархия (супервизор над командами): суперграф с узлами supervisor, research_team, writing_team; запуск с `recursion_limit` 150; на выходе файл (в примере .txt) (стр. нет в конспекте) [03]
- Рой (swarm, передача управления между равными) — шаги: 1) инструменты передачи `create_handoff_tool` 2) роли (исследователь с инструментом передачи писателю; писатель с инструментом возврата) 3) `create_swarm(agents=[…], default_active_agent=…)` 4) запуск через `stream`; в примере ~30 сек (стр. нет в конспекте) [03]
- Что выбрать (табл. 2-4): Supervisor — малые команды с чёткими границами; плюс простая настройка и контроль, минус — узкое место и единая точка отказа. Hierarchical — большие процессы; плюс модульность, минус — труднее отлаживать. Swarm — когда порядок шагов заранее неизвестен; плюс гибкая обратная связь, минус — менее предсказуем, нужен надёжный механизм передачи (стр. нет в конспекте) [03]

## Гл. 3. Обучение агентов с подкреплением (RL) — только если дообучаем сами [03][04][05]

Терминология (табл. 3-1, 3-2) [03]:
- Online RL — свежие прогоны во время обучения; Offline — только готовый набор прошлых траекторий. On-policy — обучение на данных текущей версии политики; Off-policy — можно на старых логах и примерах человека. Model-free — без модели среды; Model-based — с моделью для планирования (стр. нет в конспекте)
- Reward (награда, сигнал «хорошо/плохо»); trajectory (весь путь: промпты, вызовы, ответы); rollout (полный прогон задачи); policy (правило «контекст → следующее действие»); judge-модель (LLM, скрипт или человек, превращающий оценку в число); relative evaluation (сравнение нескольких прогонов друг с другом) (стр. нет в конспекте)
- Сравнение методов (табл. 3-3): PPO — нужна обученная reward-модель и «критик», уровень токенов; DPO — без reward-модели и критика, парные предпочтения, уровень последовательности; GRPO — judge/скрипт на каждый образец, без критика, токены, нормализация внутри группы; GSPO — то же, но уровень последовательности (стр. нет в конспекте) [03]
- GRPO vs GSPO — шаги: 1) сгенерировать группу ответов на один запрос 2) нормализовать награды внутри группы 3) посчитать коэффициент важности (токен — GRPO; нормированная по длине последовательность — GSPO) 4) применить клиппинг и штраф KL-дивергенции (ограничение отхода от исходной политики). GSPO стабильнее на длинных ответах и в Mixture-of-Experts; токенный GRPO накапливает шум и может привести к коллапсу (стр. нет в конспекте; нет в тексте) [04]
- ART + RULER (обучение без размеченных эталонов) — шаги: 1) запустить агента, получить несколько траекторий 2) отдать уникальные части LLM-судье с рубрикой 3) судья ставит балл 0.0–1.0 с пояснением 4) нормализовать внутри группы и использовать как награду (GRPO). Абсолютная оценка одиночного ответа нестабильна; сравнение нескольких — надёжнее (стр. нет в конспекте) [04]
- Гибридная награда (задача Countdown) — шаги: 1) модель и инструменты 2) асинхронный ReAct-прогон с лимитом шагов 3) программная проверка правильности (0 или 1) 4) для верных — оценка RULER 5) награда = бинарный гейт + нормализованный балл RULER с весами α и β. Риски: бесконечные вызовы (нужен `recursion_limit`), деление на ноль (стр. нет в конспекте) [04]
- Дополнительное время на размышление при запуске (test-time compute) — шаги: поиск по дереву MCTS (выбор, расширение, симуляция, обратное распространение); приоритет узла по формуле UCT (средняя награда, число визитов узла и родителя) — баланс «исследовать/использовать»; промежуточные шаги оценивать reward-моделью. Простая повторная генерация без рефлексии даёт разнообразие, но не улучшает глубокие шаги (стр. нет в конспекте) [04]
- AB-MCTS (адаптивное дерево) — шаги: 1) первый вариант + оценка судьёй 2) байесовское обновление неопределённости 3) выбор: GEN (новая ветвь) или CONT (дорабатывать существующую) 4) повторять до конца бюджета. Оценки судьи — JSON 0–1; ошибки разбора судьи обрабатывать и ставить нейтральное значение по умолчанию, чтобы не сломать дерево. Библиотека TreeQuest (стр. нет в конспекте) [04]
- rLLM — обучение целых многоагентных воркфлоу — шаги: 1) класс от `Workflow` 2) логика (напр. solver–judge или planner–executor) в `run()` 3) вернуть `Episode` с траекториями и наградами 4) запустить встроенный `Trainer` (относительные преимущества, KL). Паттерн solver–judge: решатель предлагает варианты, судья выбирает лучший, обучаются вместе. Задача-пример «24»: из 4 чисел (3,3,4,5) получить 24 (стр. нет в конспекте) [05]
- Сравнение фреймворков (табл. 3-7): RULER — относительная оценка судьёй; ART — RL для агентов с инструментами; rLLM — сложные воркфлоу, рассуждение + судья + MCTS (стр. нет в конспекте) [05]
- Чего НЕ делать: дообучать модели по отдельности и потом склеивать — хуже совместного обучения всей схемы (стр. нет в конспекте) [05]

## Гл. 4. Модели под агентов: выбор и оптимизация

- Хочу выбрать модель под роль — шаги: 1) цель (генерация, классификация, поиск, несколько задач) 2) сопоставить с типами из табл. 4-1 3) учесть бюджет и масштаб 4) если оправдано, собрать «команду» из разных типов (стр. нет в конспекте) [05][a1]
- Типы: encoder-only — анализ, эмбеддинги, классификация, поиск (RAG); decoder-only — генерация, код, диалог, планирование; encoder–decoder — перевод, суммаризация; embedding-модели — поиск и RAG; MoE — масштабная генерация с экономией (стр. нет в конспекте) [05]
- Чего НЕ делать: одну большую модель на все задачи — переплата и задержка (latency) (стр. нет в конспекте) [05][a1]

### Decoder-only и память KV-кэша [05][a1]
- Правило: скорость и память упираются в KV-кэш (сохранённые вычисления внимания). Размер = длина последовательности × слои × KV-головы × размерность головы × 2 × байты точности (множитель 2 — Keys и Values) (стр. нет в конспекте) [05][a1]
- Число: Qwen2.5-7B-Instruct-1M — 28 голов Query, 4 головы KV (7:1) → ~7-кратная экономия кэша (GQA — Grouped-Query Attention) (стр. нет в конспекте) [05][a1]
- Шаги экономии в движке вроде vLLM: 1) GQA 2) Paged attention (кэш блоками, без фрагментации) 3) Prefix caching (хэш повторных промптов) и Chunked prefill (длинный промпт порциями) 4) при обрезке контекста — выборочно сбрасывать кэш по хэшу токенов 5) скользящее окно или обрезка префикса при подходе к лимиту (стр. нет в конспекте) [05]
- Проверить GQA в Hugging Face: загрузить `AutoModelForCausalLM`, посмотреть `model.config` — `num_attention_heads` и `num_key_value_heads` (стр. нет в конспекте) [05][a1]
- Следить за `cache hit ratio` и нагрузкой на память; при падении hit-ratio улучшать планировщик и не сбрасывать кэш зря; смена порядка токенов сбрасывает кэш (стр. нет в конспекте) [a1]
- Проблема «иглы в стоге сена»: на длинном контексте softmax размывает внимание, факты находятся хуже (стр. нет в конспекте) [05][a1]
- Encoder–decoder (FAT5 с Flash-Attention): может превосходить decoder-only в мультизадачном и zero-shot режимах; при beam-search общий кэш префиксов; у лимита контекста — обрезка префикса (стр. нет в конспекте) [a1] (конспект [a1] — слабое место, см. «Не дочитано»)

### Encoder-only [05][a1]
- Не генерируют, а анализируют двунаправленно; быстрее и дешевле; годятся как «аналитики» и ретриверы для RAG. Современные: NomicBERT, ModernBERT, NeoBERT (RoPE — поворотные позиции, FlashAttention) (стр. нет в конспекте)
- Числа (табл. 4-4): BERT base — 120M параметров, контекст 512; ModernBERT base — 149M, 1024–8192; NeoBERT medium — 250M, 1024–4096 (стр. нет в конспекте) [05]
- Масштаб RoPE при загрузке в vLLM: `rope_scaling={"type":"linear","factor":4.0}`; простое масштабирование может ухудшить качество — тестировать на своих данных (стр. нет в конспекте) [05][a1]
- Чего НЕ делать: использовать encoder-only для генерации текста (стр. нет в конспекте) [a1]

### MoE и модели рассуждений (reasoning) [05][a1]
- MoE: для каждого токена включается лишь часть «экспертов» — большая ёмкость без пропорционального роста затрат; риск — неравномерная загрузка экспертов (стр. нет в конспекте) [05][a1]
- Режим «thinking» (скрытая цепочка мыслей) — шаги: 1) включать для планирования, кода, сложных расчётов, проверки инструментов 2) выключать для простых быстрых шагов 3) ставить `thinking_budget` (лимит токенов на мысли) (стр. нет в конспекте) [05]
- Числа: `thinking_budget` от 1000 токенов и выше для сложных задач; токен `</think>` в примере = 151668; в [a1] примеры `thinking_budget=1024`, `max_new_tokens=32768` (стр. нет в конспекте) [05][a1]
- Как переключать: Transformers — `enable_thinking=True/False` в чат-шаблоне; vLLM — `extra_body={"chat_template_kwargs":{"enable_thinking": False}}` (стр. нет в конспекте) [05][a1]
- Предупреждения: мысли тоже считаются в токенах и задержке; слишком малый бюджет обрывает логику на полуслове; при выключенном thinking некоторые модели всё равно хранят скрытый trace (стр. нет в конспекте) [05][a1]

### Команда экспертов (сборка) [05][a1]
- Шаги: 1) роли: поиск (Exa), патенты (Google Serper), аналитик (ModernBERT + Qwen3 Thinking), конспектирование, копирайтинг, супервизор (GPT-4.1) 2) рутинным ролям — быстрая модель без мышления 3) аналитику — режим мышления с бюджетом 1536 (в примере) 4) каждого завернуть в ReAct-узел (`make_react_worker_node`) 5) таблица «роль ↔ архитектура ↔ модель» (табл. 4-5) (стр. нет в конспекте) [05][a1]
- Пример аналитика: контроллер рассуждений Qwen3 235B + энкодер ModernBERT, выдаёт числовую релевантность (напр. `score: 0.956`) (стр. нет в конспекте) [05]
- Чего НЕ делать: все задачи — одной тяжёлой думающей модели: медленно и дорого; не отключать thinking у аналитика (стр. нет в конспекте) [05][a1]

### Открытые и закрытые модели [05][a1]
- Шаги выбора: сравнить инновации, доступность, кастомизацию (PEFT/дообучение против ограниченного в закрытом API), производительность, стоимость, безопасность/комплаенс (стр. нет в конспекте) [a1]
- Стратегия: 1) старт на закрытых API или у провайдеров открытых моделей (Together.ai, Nebius) 2) при нужде контроля, приватности, экономии — перенести открытую модель на своё железо/частное облако 3) специализировать через LoRA (стр. нет в конспекте) [05]
- Числа (начало 2026): закрытые до $150 вход / $600 выход за 1 млн токенов (o1-pro); открытые в облаке ~$0.3 вход / ~$3 выход (стр. нет в конспекте) [05][a1]
- Гибрид: крупная закрытая модель — супервизор, дообученные открытые (LoRA) — исполнители (стр. нет в конспекте) [05]
- Чего НЕ делать: дообучать закрытую модель на сервере вендора — полная зависимость (vendor lock-in), веса вам не принадлежат (стр. нет в конспекте) [05]

### LoRA, адаптеры, квантование [05][06][a1]
- LoRA/адаптеры (дообучается малая часть параметров, база заморожена): полное дообучение требует ~4-кратного запаса памяти GPU на параметр; адаптеры не вызывают «катастрофического забывания» (стр. нет в конспекте) [05][06]
- LoRAX (загрузка адаптеров по мере надобности, пакетная обработка нескольких адаптеров): >100 специализированных LoRA-моделей на одном GPU; многоуровневый кэш весов (GPU/CPU/диск) защищает от нехватки памяти (OOM); экономия «десятки тысяч долларов» (стр. нет в конспекте) [06]
- Квантование (сжатие весов до 8 или 4 бит) — библиотеки `bitsandbytes`, `unsloth`; проверять качество на своей задаче (стр. нет в конспекте) [06][a1]

## Гл. 5. От прототипа к продакшену: контракты, инструменты, надёжность

- Правило: в продакшене главный враг — неуправляемое исполнение, а не «ум» модели; причина сбоев — нет проверок на границах между агентами и при вызове инструментов (стр. нет в конспекте) [06][a1]
- Три опоры: Pydantic (описание данных, «технический контракт»); Instructor (заставляет модель выдать нужную структуру, с повторами); MCP (общий разъём к инструментам, «USB-C для ИИ»); плюс «ворота валидации» до передачи данных дальше (стр. нет в конспекте) [06][a1]

### Надёжность цепочки (закон Луссера) [06][a1]
- Правило: надёжность цепочки без проверок = произведение точностей агентов. При точности одного агента 0.98: 1 агент 98.0%; 3 — ~94.1%; 5 — ~90.4%; 10 — ~81.7% (стр. нет в конспекте) [06]
- С воротами валидации (полнота обнаружения ошибок v=0.9): эффективная точность `p_eff = p + (1−p)·v` ≈ 0.998; 10 агентов ≈ 98.0%; 3 агента ≈ 99.4% (стр. нет в конспекте) [06][a1]
- Таблица 5-2 в конспекте [a1] обрезана; смысл изложен формулой выше (стр. нет в конспекте) [a1]

### Контракты и ворота — шаги [06][a2]
1. Описать вход/выход через Pydantic (пример: `user_id: int`, `age: int` в диапазоне 0–150); на границе сразу создавать объект модели — при несовпадении `ValidationError` (быстрый отказ) или автоприведение типов (строка `"123"` → число) (стр. нет в конспекте) [06][a2]
2. Правила (режим strict, минимальная длина промпта 50 симв., допустимые типы изображений `image/png`, размер 512–1536 px, максимум повторов 3) хранить в конфиге OmegaConf (YAML), а не в коде (стр. нет в конспекте) [a2]
3. Фабрика моделей создаёт Pydantic-схему «на лету» под текущую политику (`build_image_prompt_model`) (стр. нет в конспекте) [06][a2]
4. На старте запуска «закрепить» политику: хэши `policy_hash` и `schema_hash` (SHA256) в состоянии — для аудита, воспроизводимости, кэша; менять правила в середине запуска нельзя (дрейф) (стр. нет в конспекте) [06][a2]
5. Узел-ворота: построить модель из данных; успех → `prompt_ok=True`, `retry_count=0`; ошибка → записать `last_error`, увеличить `retry_count` (стр. нет в конспекте) [06][a2]
6. Модели вернуть короткое смысловое описание ошибки (одно понятное предложение), а не сырой стектрейс (стр. нет в конспекте) [06]
7. Сохранять состояние (сообщения, результаты инструментов, текущий узел, политика, хэши, `run_id`) через `MemorySaver` / `InMemorySaver` / `PostgresSaver` + `thread_id`; после сбоя вернуться к последнему стабильному узлу без повторной оплаты прошлых шагов (стр. нет в конспекте) [06][a2]
- Чего НЕ делать: жёстко зашивать правила в код; не ставить `max_retries` (бесконечный цикл и рост стоимости); не фиксировать хэши (нельзя воспроизвести, что было в проде) (стр. нет в конспекте) [a2]

### Instructor (проверка прямо при генерации) [06][a2]
- Шаги: 1) клиент `instructor.from_provider(...)` (OpenRouter и др.) с `mode=instructor.Mode.TOOLS` 2) Pydantic-модель контракта 3) `client.create(..., response_model=Модель, max_retries=N)` (пример: 3; `temperature=0.2`) 4) при несовпадении Instructor сам отправляет ошибку модели в том же вызове (стр. нет в конспекте) [06][a2]
- Два круга повторов: внутренний (Instructor) — частые, быстрые, ловит выдуманные ключи JSON и пропущенные поля; внешний (LangGraph + Pydantic) — редкие, ловит сбои инфраструктуры, таймауты, бизнес-логику; чекпоинт — возобновление после падения (стр. нет в конспекте) [06][a2]
- Число: выбор маршрутизации по задержке (latency-based) в OpenRouter снижает время отклика в 4–5 раз против выбора по минимальной цене (стр. нет в конспекте) [06]
- Чего НЕ делать: полагаться только на ворота Pydantic без Instructor (двойные запросы); писать свой парсер вместо `response_model`; ждать, что Instructor заменит таймауты и повторы уровня графа (стр. нет в конспекте) [06][a2]

### MCP (Model Context Protocol) [06][a2]
- Что это: открытый стандарт от Anthropic (передан в Agentic AI Foundation); инструменты подключаются без переписывания сервисов (стр. нет в конспекте) [06]
- Шаги: 1) Pydantic-модели запросов/ответов 2) сервер `FastMCP`, функции с `@mcp.tool()` (пример: `read_file`, `write_file`, `list_files`) 3) транспорт: `stdio` — для локальной разработки, HTTP/WebSocket/Streamable HTTP/gRPC — для продакшена 4) в LangGraph клиент `MultiServerMCPClient`, `await client.get_tools()`, привязать к модели 5) для внешних инструментов — агрегаторы (Composio, Docker-MCP) (стр. нет в конспекте) [06][a2]
- Правила: при параллельных вызовах — соединение на каждый вызов и режим SQLite WAL (журнал, чтобы запросы не блокировали друг друга); ограничивать `max_parallel_calls` (стр. нет в конспекте) [06][a2]
- Чего НЕ делать: полагаться на модель в вопросах безопасности — права и ограничения проверяет сам MCP-сервер на границе вызова; `stdio` в продакшене не масштабируется (стр. нет в конспекте) [06][a2]

### Динамический поиск инструментов (Composio) [06]
- Шаги: 1) клиент Composio с ключами 2) `composio.tools.get(search="I want to send an email")` 3) получить определения в формате OpenAI 4) передать в цикл модели; на «отправить email» вернулись GMAIL_SEND_EMAIL, OUTLOOK_SEND_EMAIL, SENDGRID_SEND_EMAIL (стр. нет в конспекте) [06]
- Правило: не давать доступ ко всем инструментам подряд (раздувается контекст, случайные вызовы); ограничивать выдачу, напр. `limit=10` (стр. нет в конспекте) [06]

### Deep Agents (планировать, потом исполнять) [06][a2]
- Шаги: 1) агент сначала строит план, потом вызывает инструменты 2) тяжёлое (веб-поиск, базы) выносить в субагентов с изолированным контекстом — главному возвращается только итог 3) контракты в файлах `SKILL.md` (какие умения и ограничения) и `AGENTS.md` (роль, стандарты качества) 4) пауза человека (HITL) перед чувствительными инструментами 5) middleware: подключение инструментов, политики, хранение промежуточных артефактов. Библиотека `deepagents`, лицензия MIT (стр. нет в конспекте) [06][a2]
- Зачем: субагенты не дают «засорить контекст» (context bloat) и ухудшить рассуждения (стр. нет в конспекте) [06]
- Чего НЕ делать: давать консоль и файлы без планирования и одобрения человека (порча данных, неконтролируемые траты токенов); раздувать системный промпт; не отделять план от исполнения; оставлять субагентов без собственного чекпоинта (стр. нет в конспекте) [06][a2]
- (Числа «3–5 субагентов», «≤5 вызовов на субагента», «≥200 симв. промпта», «≤500–800 токенов на план» стоят в [a2], но выглядят добавленными конспектом — см. «Не дочитано»)

## Гл. 6. Безопасное исполнение и управление инструментами

- Главное: инструкции в системном промпте НЕ дают настоящей безопасности; нужна глубокая защита — правила, жёсткие лимиты, песочницы, проверка путей (стр. нет в конспекте) [07]
- Общие шаги [07]: 1) отделить «решение» от «исполнения» через шлюз управления (A2A) 2) явная политика «запрещено всё, что не разрешено» (default-deny) и разделение этапов «найти инструмент» и «выполнить» 3) трекер бюджета (время, число вызовов, параллельность) 4) все вызовы инструментов — через одну функцию-шлюз с проверкой аргументов 5) для опасного — пауза человека 6) код выполнять в изоляции (Docker, Firecracker, gVisor, облачная песочница E2B) 7) при «code mode» — в интерпретаторе с нулевыми правами (Monty) (стр. нет в конспекте)
- Опасности: выход за каталог (`../../`, абсолютные пути); «pivoting» (поиск инструмента и сразу его применение за один шаг); запуск сгенерированного кода обычным `exec()` на хосте — утечка секретов при инъекции промпта (стр. нет в конспекте) [07][a3]

### Политика и бюджет [07][a2]
- Шаги: 1) `GovernancePolicy`: общее число вызовов, параллельность, время, таймаут MCP-вызова, право создавать соединения, запрет «найти + выполнить» в одном запуске, допустимые типы артефактов 2) `BudgetTracker`: время старта, счётчики, флаги фаз; на каждый запрос проверять лимиты и отклонять нарушения 3) A2A-«губернатор» как отдельный узел перед MCP: сверяет intent (что агент хочет) с политикой → разрешить / отклонить / запросить человека 4) PRP (Product Requirement Prompt) — промпт с пожеланиями к продукту: контекст (пути, версии), образцы кода, команды проверки 5) логировать `policy_decision`, `tool_call_log`, `approval_log` вместе с `run_id` и хэшами (стр. нет в конспекте) [07][a2]
- Числа: таймаут MCP-вызова 20 с; общее время 300 с; максимум 20 вызовов на задачу; параллельных 3; в `SEPARATION_POLICY` — 2 вызова и 60 с; `connection_and_execution_in_same_run=False` (стр. нет в конспекте) [07][a2]
- Время ожидания одобрения человеком вычитается из времени задачи (стр. нет в конспекте) [07]
- Чего НЕ делать: разрешать «найти + выполнить» в одном запуске; отключать лимит вызовов; не вести журнал решений; зашивать список инструментов в агента; пропускать человека для опасных операций (стр. нет в конспекте) [a2]

### Единый шлюз вызовов (`governed_call`) [a3]
- Шаги по порядку: 1) имя и категория инструмента 2) политика разрешает? (иначе отказ) 3) инструмент в списке найденных? 4) бюджет позволяет (лимит вызовов и времени)? 5) аргументы валидны? 6) записать начало вызова 7) выполнить 8) вернуть результат + снимок бюджета 9) в `finally` записать конец вызова (иначе счётчики «зависнут») (стр. нет в конспекте) [a3]
- Пауза человека для инструментов с уровнем RESTRICTED: собрать `approval_payload` (имя, аргументы, причина, время), вызвать `interrupt`, после ответа записать `approval_granted`; человек перед решением видит журнал и снимок бюджета; неограниченные инструменты в этом узле пауз не вызывают (стр. нет в конспекте) [a3]

### Изоляция выполнения [07][a3]
- Три слоя, которые складываются, а не заменяют друг друга: изоляция среды (Docker/VM), временные среды (на задачу, потом уничтожить), управляемый сервис выполнения кода (политики, бюджеты, таймауты, одобрения) (стр. нет в конспекте) [a3]
- Docker — шаги: образ `python:3.11-slim`; системные зависимости (gcc); пользователь `appuser` не root; каталоги `/app/work`, `/app/runs` с правами 755; зависимости без кэша; владелец `appuser:appgroup`; `USER appuser`; переменные `WORK_DIR`, `RUNS_DIR`, `HOME` (стр. нет в конспекте) [a3]
- Проверка пути — шаги: 1) единый корень `WORK_DIR` 2) `work_path(*parts)`: собрать путь, `resolve()`, `relative_to(WORK_DIR)`; `ValueError` → `RuntimeError` (быстрый отказ) 3) все записи — только через `work_path()`. Блокирует: directory traversal, symlink, абсолютные пути, манипуляции путём (стр. нет в конспекте) [07][a3]
- Docker сам по себе не гарантирует безопасность; для недоверенного кода — Firecracker (микро-ВМ) или gVisor (песочница системных вызовов), опасные задачи направлять только на такие узлы (стр. нет в конспекте) [a3]
- UI без секретов (Zero-Trust UI): Streamlit — только интерфейс; FastAPI (порт 8010) в контейнере хранит ключи и ходит во внешние API; UI шлёт ему запросы на старт, подтверждение, получение артефактов; секреты не держать в окружении, доступном UI (стр. нет в конспекте) [a3]
- Облачные песочницы (E2B, Runloop, Daytona) — шаги: `Sandbox.create()` → обернуть в инструмент `@tool` (возвращает stdout, stderr, error) → добавить в список инструментов; пауза/продолжение `beta_pause()` / `Sandbox.connect`; после задачи уничтожать; каждому агенту свой sandbox (стр. нет в конспекте) [a3]
- Code mode (программный вызов инструментов): модель пишет короткую программу с циклами и вызовами, программа запускается в песочнице. Плюсы: меньше задержка и токенов, промежуточные результаты не попадают в контекст. Минус: исполняется сгенерированный код — нужен надёжный sandbox (стр. нет в конспекте) [07][a3]
- Monty (минимальный интерпретатор Python на Rust, deny-by-default): шаги: 1) промпт-контракт: только объявленные функции, базовый Python, последняя строка — ответ 2) запуск `pm.Monty(program, inputs=[...]).run(external_functions={...})` 3) для контроля — `.start()` и на каждой паузе проверять `ALLOWLIST` и `CALL_BUDGET`; отказ → `PermissionError`. Пример: 16 вызовов (8 городов × 2 функции) без обращений к модели; через обычный `exec()` тот же код вытащил секрет. Monty не даёт полной гарантии от побега — добавлять Docker/Firecracker; не забывать передать все внешние функции (`NameError` иначе) (стр. нет в конспекте) [07][a3]
- Что к чему (табл. 6-4): Monty — вызов инструментов программой; Docker — внутренние/headless-задачи; облачные песочницы — недоверенный или разнородный код, параллельные запуски (стр. нет в конспекте) [a3]
- Запомнить: ошибки рассуждения можно откатить, ошибки исполнения — нет (стр. нет в конспекте) [a3]
