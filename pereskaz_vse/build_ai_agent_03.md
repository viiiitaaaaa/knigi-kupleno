## Chapter 5. Building knowledge bases with RAG / Глава 5. Создание баз знаний с помощью RAG

#### Главная мысль автора

Главная идея главы заключается в том, что языковым моделям для решения реальных задач необходим доступ к закрытым или локальным данным компании и пользователя (внутренним базам знаний, файловым системам). RAG (**Retrieval-Augmented Generation**) решает эту проблему за счёт выборочного извлечения актуальной информации и добавления её в контекст. Авторы показывают, как от фундаментальных принципов векторного поиска (векторы, эмбеддинги, разбиение на чанки, косинусное сходство) и структурного поиска по файлам перейти к гибкому расширению агента с помощью паттерна колбэков (**callbacks**), реализующего автоматическое сжатие веб-поиска и асинхронное подтверждение человеком (**Human-in-the-loop / HITL**).

#### Ключевые формулировки автора

1. "Rather than answering solely from its own knowledge, the LLM references information found in external data to formulate its response." — *«Вместо того чтобы отвечать исключительно на основе собственных знаний, LLM обращается к информации, найденной во внешних данных, для формирования своего ответа.»*
2. "Vector search quantifies the meaning of text and calculates similarity." — *«Векторный поиск количественно определяет смысл текста и рассчитывает сходство.»*
3. "Using the callback pattern, we can extend the agent's behavior without touching its core code." — *«Используя шаблон колбэков, мы можем расширять поведение агента, не затрагивая его базовый код.»*
4. "By extracting only the three most relevant chunks, we reduced the context from more than 37,000 tokens to 304, achieving a 99.2% savings rate while preserving the information most relevant to quantum computing." — *«Извлекая только три наиболее релевантных чанка, мы сократили контекст с более чем 37 000 токенов до 304, достигнув показателя экономии 99,2% при сохранении наиболее важной информации о квантовых вычислениях.»*

##### 5.1 The problem of using internal data / Проблема использования внутренних данных

* **Мысли автора по порядку**:
  * **5.1.1 A simple case: Single file / Простой случай: один файл** При работе с одним файлом (например, CSV-файл в задаче GAIA с вопросом *"В каком месяце был наибольший объём продаж в этих данных?"*) решение состоит в том, чтобы прочитать файл и целиком поместить его в контекст. Если файл содержит несколько сотен строк, он легко помещается в контекстное окно.
  * **5.1.2 Multiple files / Множество файлов** Задачи GAIA с прикреплёнными zip-архивами распаковываются во множество папок и файлов (project/, README.md, requirements.txt, src/main.py, database.py, docs/architecture.md). Чтение всех файлов неэффективно и невозможно при их росте. Требуется структурный поиск (**structure-based search**), при котором агент изучает файловую структуру и выбирает нужные файлы по именам, аналогично работе разработчиков и инструментов Claude Code, Cursor, Gemini CLI.
  * **5.1.3 Large or extensive data / Большие или обширные данные** Огромные файлы логов на десятки тысяч строк или тысячи документов в корпоративной вики-системе невозможно изучать по одному. Требуются механизмы выборочной выборки точечной информации — векторный или ключевой поиск.

##### 5.2 Types of search methods / Типы методов поиска

* **Мысли автора по порядку**: RAG состоит из поиска (**retrieval**), дополнения контекста (**augmentation**) и генерации ответа (**generation**).
  * **5.2.1 Keyword search / Ключевой поиск** Оценивает релевантность по частоте и важности слов (алгоритмы TF-IDF, BM25). Идеально подходит для точного совпадения имён функций (get_user_by_id), кодов ошибок (404) или параметров (MAX_CONNECTIONS). Недостаток: не понимает синонимы (не видит связи между sofa и couch).
  * **5.2.2 Vector search / Векторный поиск** Преобразует текст в многомерные векторы (эмбеддинги), сохраняя смысл. Позволяет находить семантически близкие фразы (sofa и couch, cat и kitten), различая контекст одинаковых слов (например, bank как финансовая организация и как берег реки). Расчёт расстояний выполняется через косинусное сходство (**cosine similarity**) или евклидово расстояние.
  * **5.2.3 Graph search / Графовый поиск** Представляет знания в виде узлов (сущностей) и рёбер (связей). В предложении *"Alice writes Python code"* узлы — Alice и Python code, ребро — writes. Подходит для сложных вопросов о взаимосвязях (зависимости в коде, структура организации).
  * **5.2.4 Structure-based search / Структурный поиск** Использует готовую иерархию папок и файлов. Имена файлов (user_service.py), папки (/services/auth/) и функций (authenticate_user) служат естественной метаинформацией.

* Паттерн колбэков позволяет расширять функциональность агента без изменения его базового кода, обеспечивая интерактивное подтверждение операций человеком (HITL) и автоматическое сжатие больших результатов поиска.

## Chapter 6. Adding memory to your agent / Глава 6. Добавление памяти вашему агенту

#### Главная мысль автора

Память превращает инструмент без состояния в интеллектуального ассистента, способного сохранять непрерывность диалога и накапливать знания. Авторы разделяют память на три шаблона использования: иерархическое управление контекстом внутри одного запуска (**in-run context management** / скользящие окна, компактификация и суммаризация), непрерывное выполнение диалогов между запусками через сессии (**continuous execution** / Session и SessionManager), поддерживающее асинхронный **HITL-паузу и возобновление**, и долгосрочную память (**long-term memory** / TaskMemoryManager с ChromaDB), автоматически извлекающую структурированные уроки из прошлых запусков и устраняющую дубликаты.

#### Ключевые формулировки автора

1. "Memory is what separates a stateless tool from an intelligent assistant." — *«Память — это то, что отделяет инструмент без состояния от интеллектуального помощника.»*
2. "The first principle of context management is separating storage from presentation." — *«Первый принцип управления контекстом — отделение хранения от представления.»*
3. "SessionManager handles horizontal continuity within sessions (conversation flow), and MemoryManager handles vertical continuity across sessions (knowledge accumulation)." — *«SessionManager отвечает за горизонтальную непрерывность внутри сессий (поток диалога), а MemoryManager отвечает за вертикальную непрерывность между сессиями (накопление знаний).»*
4. "Compaction turns 100,000 tokens of noise in every prompt into a precise, on-demand resource." — *«Компактификация превращает 100 000 токенов шума в каждом промте в точный ресурс по требованию.»*

##### 6.1 The anatomy of agent memory / Анатомия памяти агента

* **Мысли автора по порядку**:
  * **6.1.1 Limitations of the current memory architecture / Ограничения текущей архитектуры памяти** Агент из предыдущих глав заносит всё в ExecutionContext во время выполнения и всё выбрасывает после его завершения. Проблемы: 1) Проблема пространства (контекст превышает лимит модели и приводит к сбою); 2) Проблема времени (пользователь, представившийся вчера как *"Джеймс, маркетолог"*, вынужден повторять это снова).
  * **6.1.2 Three challenges of the current memory architecture / Три проблемы текущей архитектуры памяти**
    * *Ключевые понятия*: **Сессия (Session)** — единый непрерывный диалог; **Краткосрочная память (Short-term memory)** — хранит текущие события сессии в ExecutionContext.events; **Долгосрочная память (Long-term memory)** — сохраняет выжимку фактов между сессиями.
    * *Три проблемы*:
      1. *Проблема 1: Взрыв контекста (Context Explosion)* при выполнении сложного запуска run().
      2. *Проблема 2: Отсутствие непрерывности диалога (Lack of Conversation Continuity)*. Пример: Пользователь пишет *"Установи дедлайн для Project Alpha"*, агент ставит. В следующем запуске run() пользователь пишет *"Обнови прогресс"* — без сессии агент не знает, о каком проекте речь.
      3. *Проблема 3: Отсутствие персистентных знаний (Lack of Persistent Knowledge)* после закрытия сессий.
  * **6.1.3 Context engineering and memory / Контекстная инженерия и память** Три шаблона использования памяти и их связь со стратегиями из главы 1 представлены в таблицах.

##### 6.2 Managing context during execution / Управление контекстом во время выполнения

* **Мысли автора по порядку**:
  * **6.2.1 Separating storage from presentation / Отделение хранения от представления** Первый принцип: ExecutionContext.events остаётся неизменяемым эталоном (**ground truth**), а модификации перед отправкой в LLM подвергается только LlmRequest.contents (аналогия с сохранением исходной фотографии и наложением фильтров только при публикации). Осуществляется через before_llm_callback.

  * **6.2.2 Sliding-window strategy / Стратегия скользящего окна** Сохраняет первый запрос пользователя и оставляет последние N сообщений.
    * **Что делает пример кода (Listing 6.2, 6.3)**: Функция apply_sliding_window сохраняет входной вопрос пользователя и оставляет только window_size=20 последних сообщений.
  * **6.2.3 Token counting / Подсчёт токенов** Точное измерение размера контекста с помощью библиотеки tiktoken.
    * **Исследования**: Исследование Chroma "Context Rot" (2025) и опыт команды разработки Manus доказывают, что деградация работы моделей начинается задолго до официального предела контекстного окна, поэтому порог оптимизации устанавливается значительно ниже (в примерах книги — 20 000–50 000 токенов).
    * **Что делает пример кода (Listing 6.4)**: Функция count_tokens рассчитывает точное число токенов в LlmRequest.
  * **6.2.4 Compaction strategy / Стратегия компактификации** Принцип «Сфера охвата по умолчанию» (**scope by default**): замена обработанных данных лёгкими ссылками.
    * *Сжатие ToolCall*: при операциях записи (create_file с текстом на 10 000 символов) аргументы заменяются на "[Content saved to file]".
    * *Сжатие ToolResult*: при операциях чтения (read_file, search_web) результат заменяется ссылкой вида "File content from {file_path}. Re-read if needed." или "Search results processed. Query: {query}. Re-search if needed.".
    * *Взаимодействие с Prompt Caching*: Промт-кэширование дает скидку до 90% при совпадении префикса. Модификация сообщений в середине сбрасывает кэш. Компактификация запускается по порогу (например, 50 000 токенов), когда выгода от предотвращения сбоя превышает потерю кэша.
    * **Что делает пример кода (Listing 6.5)**: Функция apply_compaction сжимает вызовы и результаты инструментов по правилам TOOLCALL_COMPACTION_RULES и TOOLRESULT_COMPACTION_RULES.
  * **6.2.5 Summarization strategy / Стратегия суммаризации** Старые сообщения (кроме первого вопроса пользователя и последних keep_recent=5 сообщений) суммаризируются отдельным вызовом LLM, а краткая выжимка добавляется в системный промт [Previous work summary].
    * *Сравнение*: Компактификация детерминирована, бесплатна и обратима (можно перечитать файл), а суммаризация семантична, стоит вызова LLM и необратима.
    * **Что делает пример кода (Listing 6.6)**: Функция apply_summarization генерирует сжатый итог истории через generate_summary.
  * **6.2.6 Hierarchical context management / Иерархическое управление контекстом** Иерархия применения: 1) Измерение токенов (если ниже порога — ничего не делаем для сохранения Prompt Caching); 2) Компактификация; 3) Если токены всё ещё выше порога — суммаризация.
    * **Номера рисунков**: **Figure 6.4** (схема принятия решений иерархического контекст-менеджмента).

#### Summary / Резюме главы 6

* Память агента делится на скользящее управление контекстом внутри запуска (**in-run context management**), непрерывность сессий (**continuous execution**) и долгосрочную память (**long-term memory**).
* Иерархическое управление контекстом включает подсчёт токенов, компактификацию вызовов/результатов инструментов и суммаризацию. Разделение ExecutionContext (неизменяемый эталон) и LlmRequest (модифицируемая проекция) сохраняет историю для аудита.
* Сессии (Session и SessionManager) сохраняют диалог между запусками и позволяют реализовать асинхронный рабочий процесс **HITL** с паузой при выполнении опасного инструмента и возобновлением при получении ответа от пользователя.
* Долгосрочная память TaskMemoryManager на базе ChromaDB извлекает структурированные выжимки решений задач, проверяет их на дубликаты (ADD/SKIP) и предоставляет доступ агенту через явный MemoryTool или автоинъекцию process_llm_request().
