## Chapter 3. Enabling actions: Tool use / Глава 3. Включение действий: использование инструментов

#### Главная мысль автора

Языковые модели сами по себе изолированы от внешнего мира и не способны получать актуальные данные, производить точные вычисления или изменять состояние внешних систем. Использование инструментов (**tools**) и нативный механизм их вызова (**tool calling**) превращают модель в управляющего посредника, а внедрение открытого протокола **MCP (Model Context Protocol)** от Anthropic стандартизирует взаимодействие между агентами и инструментами, устраняя необходимость создания уникальных обёрток и исключая дублирование кода.

#### Ключевые формулировки автора

1. "On their own, large language models (LLMs) can't access external data or interact with external systems. They need tools and the ability to select and use those tools, which is central to implementing agents." — *«Сами по себе языковые модели (LLM) не могут получать доступ к внешним данным или взаимодействовать с внешними системами. Им нужны инструменты и способность выбирать и использовать их, что является центральным элементом реализации агентов.»*
2. "The LLM doesn't execute tools itself. Rather, it generates a textual specification indicating which tool should be called and with what parameters." — *«LLM не исполняет инструменты сама. Вместо этого она генерирует текстовую спецификацию, указывающую, какой инструмент должен быть вызван и с какими параметрами.»*
3. "Just as APIs established a common language for developers to communicate with services, MCP established a common language for LLM agents to communicate with tools." — *«Подобно тому как API установили общий язык для связи разработчиков с сервисами, MCP установил общий язык для связи LLM-агентов с инструментами.»*

##### 3.1 LLM tools / Инструменты LLM

* **Мысли автора по порядку**:
  * **3.1.1 Why do we need LLM tools? / Зачем нам нужны инструменты LLM?** Ограничения LLM делятся на три категории:
    1. *Временны́е ограничения (Temporal)*: модель ограничена датой среза обучающих данных и не видит изменений в реальном времени. *Решение*: информационно-дополняющие инструменты (веб-поиск, arXiv, API погоды и курсов акций, внутренние базы знаний).
    2. *Интеракционные ограничения (Interaction)*: модель не может напрямую влиять на физический или цифровой мир. *Решение*: действительно-исполняющие инструменты (системы бронирования, отправка email, управление календарем, IoT-контроллеры).
    3. *Функциональные ограничения (Functional)*: модель слаба в точных математических расчётах и узких доменах. *Решение*: специализированные инструменты (калькуляторы, интерпретаторы кода, генераторы изображений и речи).
  * **3.1.2 Types of LLM tools / Типы инструментов LLM** Инструменты делятся на пользовательские (**custom-built**) и предопределённые провайдером (**noncustom / predefined**). Предопределённые инструменты (OpenAI web search, file search, code interpreter; Anthropic computer use; Google Search) готовы к использованию, но не поддаются гибкой настройке. Пользовательские инструменты создаются под специфические задачи проекта, но требуют самостоятельного обслуживания и обеспечения безопасности.

##### 3.4 MCP: Standardizing tools / MCP: стандартизация инструментов

* **Мысли автора по порядку**:

Транспортные механизмы: **Stdio** (стандартные потоки ввода-вывода для локальных процессов) и **Streamable HTTP** (для сетевого взаимодействия).

#### Summary / Резюме главы 3

* Инструменты избавляют LLM от временных, интерактивных и функциональных ограничений, расширяя пространство действий агента.
* LLM не исполняет код инструмента сама, а лишь формирует структурированную спецификацию вызова (имя функции и аргументы), которую запускает приложение-хост.
* Качественные схемы инструментов требуют явных названий, строгих типов данных, ограничений форматов (enum) и отсутствия дублирующих параметров.
* Протокол MCP от Anthropic предлагает универсальную архитектуру «Хост — Клиент — Сервер», избавляя от написания уникальных адаптеров для каждого стороннего сервиса.

## Chapter 4. Implementing a basic ReAct agent / Глава 4. Реализация базового ReAct-агента

#### Главная мысль автора

Основополагающий шаблон ReAct (Reasoning + Acting) объединяет рассуждения и действия в итеративный цикл **think-act**, центральным звеном которого является объект ExecutionContext. Переход от хрупкого текстового парсинга к нативному вызову функций (**Tool Calling**) делает работу агента надёжной, а интеграция специального инструмента final_answer гарантирует строго структурированный вывод и повышает точность решения сложных задач из бенчмарка GAIA с 20% до 70% при использовании веб-поиска.

#### Ключевые формулировки автора

1. "ReAct is the foundational pattern behind most modern AI agents. The core idea is simple: instead of trying to answer everything at the same time, an agent alternates between reasoning about what it needs to reach an answer and taking actions to get it." — *«ReAct — это основополагающий шаблон большинства современных ИИ-агентов. Основная идея проста: вместо попытки ответить на всё одновременно, агент чередует рассуждение о том, что ему нужно для получения ответа, и выполнение действий для его получения.»*
2. "ExecutionContext serves as the central storage where all information converges." — *«ExecutionContext служит центральным хранилищем, где сходятся все данные.»*
3. "The key insight is that we can use our existing tool-calling infrastructure to enforce structured outputs." — *«Ключевое озарение заключается в том, что мы можем использовать нашу существующую инфраструктуру вызова инструментов для обеспечения структурированного вывода.»*

##### 4.1 How ReAct agents work / Как работают ReAct-агенты

* **Мысли автора по порядку**:
  * **4.1.1 The think-act cycle / Цикл think-act** Разбор решения задачи Кипчоге по цепочке ReAct:
    * *Thought*: Нужно найти рекордный темп Кипчоге -> *Action*: search_web("Kipchoge marathon world record") -> *Observation*: 2:01:09 на 42.195 км (Берлин 2022).
    * *Thought*: Нужно найти расстояние до Луны в перигее -> *Action*: search_wikipedia("Moon perigee distance") -> *Observation*: 356 500 км.
    * *Thought*: Рассчитать время -> *Action*: calculator("356500 / (42.195 / 2.0186) * 1") -> *Observation*: 17 034 часа.
    * *Thought*: Информации достаточно -> *Final Answer*: Примерно 17 000 часов.

Нативный Tool Calling перенес этап рассуждения внутрь выбора функций самой моделью, сохранив идею ReAct, но сделав её исполнение надёжным.

#### Summary / Резюме главы 4

* Шаблон ReAct объединяет рассуждение и действие в итеративный цикл think-act, а современные LLM используют для этого нативный механизм вызова функций (Tool Calling).
* ExecutionContext выступает единым хранилищем состояния, где регистрируются все события (Event), счетчик шагов и переменные состояния.
* Единая абстракция BaseTool и FunctionTool позволяет оборачивать обычные Python-функции и удалённые MCP-серверы в универсальный интерфейс.
* Слой связи (LlmRequest, LlmResponse, LlmClient) изолирует специфику API от логики агента.
* Использование Tool Calling для создания динамического инструмента final_answer позволяет гарантировать получение структурированных ответов в виде Pydantic-моделей.
* Наличие инструментов веб-поиска повышает точность решения сложных задач 1-го уровня GAIA с 20% до 70%.
