### Chapter 6. RAG and Agents / Глава 6. RAG и агенты

* **Главная мысль автора:** Для решения задачи модели нужны как инструкции по её выполнению, так и необходимая информация. Подобно человеку, модель чаще ошибается и галлюцинирует при отсутствии контекста. Инструкции общие для всех запросов приложения, а контекст уникален для каждого конкретного запроса. Две доминирующие паттерн-архитектуры для конструирования контекста — это RAG (поисково-дополненная генерация) и агенты.
* **Ключевые формулировки автора:**
  * *"Context construction for foundation models is equivalent to feature engineering for classical ML models."* — «Конструирование контекста для базовых моделей эквивалентно инженерии признаков (feature engineering) для классических ML-моделей».
  * *"An agent is anything that can perceive its environment and act upon that environment."* — «Агент — это всё, что может воспринимать свою среду и воздействовать на нее».

---

### RAG / Поисково-дополненная генерация

* **Мысли автора по порядку:**
  1. Паттерн «сначала найди, затем сгенерируй» (retrieve-then-generate) был впервые представлен в работе Chen et al. (2017) *«Reading Wikipedia to Answer Open-Domain Questions»*, где система находила 5 наиболее релевантных страниц Википедии, а модель («документ-ридер») считывала их для ответа.
  2. Термин *Retrieval-Augmented Generation (RAG)* введен в работе Lewis et al. (2020) из Meta AI как решение для задач с высокой плотностью знаний (knowledge-intensive tasks).
  3. **Почему RAG не исчезнет с ростом контекстных окон (почему бесконечный контекст не заменит RAG):**
     * Объём данных растёт быстрее, чем расширяются контекстные окна моделей.
     * Длинный контекст ухудшает точность модели (эффект «Lost in the Middle» / «Needle in a Haystack»).
     * Каждый дополнительный токен контекста увеличивает стоимость и задержку. RAG передает только самые релевантные факты, экономя токены и повышая точность.
* **Рекомендация Anthropic по Claude (2024):**
  * *"If your knowledge base is smaller than 200,000 tokens (about 500 pages of material), you can just include the entire knowledge base in the prompt that you give the model, with no need for RAG or similar methods."* — «Если ваша база знаний меньше 200 000 токенов (около 500 страниц материала), вы можете просто включить всю базу знаний в промпт, передаваемый модели, без необходимости в RAG или подобных методах».

### RAG Architecture / Архитектура RAG

* **Компоненты:** **Retriever (Поисковик)** — извлекает релевантную информацию из внешней памяти; **Generator (Генератор)** — генерирует ответ на основе найденного контекста и запроса.
* **Функции поисковика:** **Indexing (Индексация)** — предварительная обработка и структурирование данных для быстрого поиска; **Querying (Запрос)** — поиск наиболее релевантных фрагментов (чанков) по запросу пользователя.

```
┌─────────────────────────────────────────────────────────┐
│                    External Memory                      │
│             (Documents, Tables, DB, VectorDB)           │
└────────────────────────────┬────────────────────────────┘
                             │
                             ▼
┌──────────────┐     ┌──────────────┐
│  User Query  ├────►│  Retriever   │
└──────────────┘     └───────┬──────┘
                             │ Relevant Context
                             ▼
                     ┌──────────────┐     ┌──────────────┐
                     │  Generator   ├────►│   Response   │
                     └──────────────┘     └──────────────┘
```

### Retrieval Algorithms / Алгоритмы поиска

#### 1. Term-Based Retrieval (Поиск по терминам / Лексический поиск)
* **Принцип:** Поиск по точным ключевым словам и их частоте.
* **Метрики:**
  * **Term Frequency (TF):** Количество вхождений термина в документ.
  * **Inverse Document Frequency (IDF):** Обратная частота документа. Чрезмерно частые слова (стоп-слова: "for", "at", "the") имеют низкий IDF. Formula: \\(IDF(t) = \log(N / C(t))\\), где \\(N\\) — всего документов, \\(C(t)\\) — количество документов с термином \\(t\\).
  * **TF-IDF Formula:** \\(\text{Score}(D, Q) = \sum_{i=1}^{q} IDF(t_i) \times f(t_i, D)\\).
* **Решения:**
  * **Elasticsearch:** Использует инвертированный индекс (inverted index) — словарь, отображающий каждый термин на список документов, его содержащих.
  * **Okapi BM25:** Модификация TF-IDF, нормализующая частоту термина по длине документа (длинные документы содержат больше слов случайно). Является мощным базовым лайном (baseline).

#### 2. Embedding-Based Retrieval (Поиск на основе эмбеддингов / Семантический поиск)
* **Принцип:** Преобразование текста в векторы (эмбеддинги) и поиск ближайших векторов в векторной базе данных (Vector DB).
* **Алгоритмы приблизительного поиска ближайших соседей (ANN — Approximate Nearest Neighbors):**
  * **k-NN (Exact):** Медленный точный перебор всех векторов (подходит только для малых датасетов).
  * **LSH (Locality-Sensitive Hashing):** Хеширование похожих векторов в одинаковые корзины (FAISS, Annoy).
  * **HNSW (Hierarchical Navigable Small World):** Построение многослойного графа векторов. Высокая точность и скорость запроса, но долгое время построения индекса и высокая потребность в RAM.
  * **Product Quantization (PQ):** Сжатие векторов путём их разбиения на подвекторы и квантования (компонент FAISS).
  * **IVF (Inverted File Index):** Кластеризация K-means (от 100 до 10 000 векторов на кластер).
  * **Annoy (Spotify):** Построение бинарных деревьев со случайными гиперплоскостями деления.

#### 3. Comparing Retrieval Algorithms / Сравнение алгоритмов поиска
* **Таблица сравнения (Таблица 6-2):**

| Характеристика | Term-based (Поиск по терминам) | Embedding-based (Семантический поиск) |
| :--- | :--- | :--- |
| **Скорость запроса** | Намного быстрее | Медленнее (генерация эмбеддинга + векторный поиск) |
| **Точность из коробки** | Высокая точность по точным ключам, но не понимает синонимы | Отлично понимает смысл и естественный язык, но может пропускать точные артикулы/коды |
| **Стоимость** | Дешёвая индексация и хранение | Дорогие вызовы моделей эмбеддингов и хранение векторов в RAM |

* **Метрики качества поисковика:**
  * **Context Precision (Точность контекста):** Процент релевантных чанков среди всех извлеченных.
  * **Context Recall (Полнота контекста):** Процент извлеченных релевантных чанков от всех имеющихся релевантных документов в БД.
  * **Метрики ранжирования:** NDCG, MAP, MRR.
  * **Бенчмарки:** **MTEB** (Massive Text Embedding Benchmark), **BEIR** (14 бенчмарков), **ANN-Benchmarks** (оценка по Recall, QPS, Build Time, Index Size).

#### 4. Combining Retrieval Algorithms / Комбинирование алгоритмов (Гибридный поиск)
* **Hybrid Search:** Сочетание поисковика по терминам (BM25) и векторного поиска.
* **Последовательный поиск (Reranking):** Дешевый лексический поиск выбирает 100 кандидатов, а более дорогая модель-переранжировщик (Cross-Encoder / k-NN) отбирает 5 лучших.
* **Параллельный поиск и объединение рангов (Reciprocal Rank Fusion / RRF, Cormack et al., 2009):**
  * **Формула RRF:** \\(\text{Score}(D) = \sum_{i=1}^{n} \frac{1}{k + r_i(D)}\\), где \\(r_i(D)\\) — ранг документа в \\(i\\)-м алгоритме, константа \\(k = 60\\).

### Retrieval Optimization / Оптимизация поиска

1. **Стратегии разбиения на чанки (Chunking Strategies):**
   * *Фиксированный размер:* По символам, словам, предложениям или абзацам (например, 512 слов или 2 048 символов).
   * *Рекурсивный chunking:* Последовательное разбиение по разделам, затем абзацам, затем предложениям.
   * *Специализированные сплиттеры:* Для исходного кода (по функциям/классам), китайского языка, пар QA.
   * *Токенизационные границы:* Разбиение по токенам конкретной модели (например, Llama 3).
   * *Правило компромисса:* Маленькие чанки позволяют вместить больше разнообразной информации в контекст, но теряют общий контекст документа и удваивают объем векторной БД.
2. **Переранжирование (Reranking):** Позиционирование самых важных чанков в начале и в конце промпта; временное переранжирование (Time-based decay) для новостей и писем.
3. **Переписывание запросов (Query Rewriting / Reformulation):** 
   * Преобразование неполного пользовательского контекстного ввода (Пользователь: *"А как насчет Эмили Доу?"*) в самодостаточный поисковый запрос (*"Когда Эмили Доу в последний раз делала покупку?"*).
4. **Контекстуальный поиск (Contextual Retrieval, Anthropic 2024):**
   * Обогащение чанков метаданными, тегами, сущностями (например, код ошибки `EADDRNOTAVAIL (99)`).
   * **Метод Anthropic:** Перед индексацией модель Claude генерирует преамбулу в **50–100 токенов**, объясняющую связь конкретного чанка со всем документом, и подклеивает её в начало чанка (Рисунок 6-5).

### RAG Beyond Texts / RAG за пределами текстов

* **Мультимодальный RAG (Multimodal RAG):** Использование единых векторных пространств (CLIP) для совместной индексации текста и изображений.
  * *Пример из книги:* На вопрос *" Какого цвета дом в мультфильме 'Вверх'?"* поисковик находит в базе кадр с домом и передает изображение в мультимодальную модель.
* **RAG с табличными данными (RAG with Tabular Data / Text-to-SQL):**
  * 3 шага: 1) **Text-to-SQL:** Преобразование вопроса пользователя в SQL-запрос на основе схемы таблиц; 2) **SQL Execution:** Выполнение запроса к СУБД; 3) **Generation:** Формирование финального ответа по полученным табличным строкам.

### Agents / Агенты

* **Определение:** **Агент (Agent)** — это система, способная воспринимать среду (perceive environment) и воздействовать на нее с помощью набора действий и инструментов (act upon environment).
* **Пример SWE-agent (Yang et al., 2024, GPT-4):** Среда — терминал и файловая система компьютера. Набор действий: `navigate repo`, `search files`, `view files`, `edit lines` (Рисунок 6-8).
* **Почему агентам нужны более сильные модели:**
  1. *Накапливающиеся ошибки (Compound mistakes):* При точности выполнения одного шага в **95%**, на 10 шагах итоговая точность падает до **60%**, а на 100 шагах — до **0.6%**.
  2. *Высокие ставки (Higher stakes):* Доступ к действиям записи (`DELETE`, банковские переводы) делает ошибки критическими.

---

### Tools / Инструменты

* **3 категории инструментов агента:**
  1. **Knowledge augmentation (Усиление знаний):** Чтение данных — текст/аудио/фото-поисковики, SQL-выполнение, Slack/Email API, веб-поиск (Google, GitHub, Reddit API).
  2. **Capability extension (Расширение способностей):** Калькулятор, конвертер валют/часовых поясов, календарь, интерпретатор кода Python, OCR (Tesseract), DALL-E.
     * *Кейс Chameleon (Lu et al., 2023):* Агент на GPT-4 с набором из **13 инструментов** превзошел чистый GPT-4, подняв точность на бенчмарке ScienceQA на **11.37%**, а на TabMWP — на **17%**.
  3. **Write actions (Действия записи):** Модификация среды — отправка писем, выполнение модифицирующих SQL-запросов (`UPDATE`/`DELETE`), перевод денег, покупка билетов.

### Planning / Планирование

* **Разделение планирования и выполнения (Decoupling Planning and Execution, Рисунок 6-9):** Во избежание зависания модели в бесконечных циклах генератор создает план, модуль-оценщик (Evaluator / AI Judge) или человек валидирует его, и только после этого исполнитель (Executor) делает вызовы функций.

```
               ┌──────────────┐
               │  User Query  │
               └──────┬───────┘
                      │
                      ▼
               ┌──────────────┐
               │   Planner    │
               └──────┬───────┘
                      │ Generated Plan
                      ▼
              ┌───────────────┐  No   ┌──────────────────────┐
              │  Evaluator?   ├──────►│ Regenerate / Reflect │
              └──────┬────────┘       └──────────────────────┘
                     │ Yes (Valid)
                     ▼
               ┌──────────────┐      ┌───────────────┐
               │   Executor   ├─────►│ External Tools│
               └──────────────┘      └───────────────┘
```

* **4 шага замкнутого цикла агента:**
  1. *Plan generation (Task decomposition):* Декомпозиция сложной задачи на последовательность простых действий.
  2. *Reflection & error correction (Рефлексия плана):* Проверка валидности плана до запуска.
  3. *Execution:* Выполнение функций (Function Calling).
  4. *Reflection & error correction (Рефлексия результатов):* Анализ выходов инструментов, исправление ошибок и принятие решения о завершении задачи.
* **Дискуссия о способности LLM к планированию:**
  * Ян Лекун (Chief AI Scientist, Meta) утверждал, что авторегрессионные LLM принципиально не способны к планированию.
  * Суббарао Камбхампати (2023, *"Can LLMs Really Reason and Plan?"*): *"The plans that come out of LLMs may look reasonable to the lay user, and yet lead to execution time interactions and errors."* — «Планы, создаваемые LLM, могут казаться разумными неспециалисту, но приводят к сбоям и ошибкам на этапе выполнения».
* **Гранулярность планирования:** Генерация планов на естественном языке более устойчива к изменениям API инструментов, чем генерация точных имен функций. Специальный модуль-транслятор переводит естественный язык в вызов кода.
* **Порядки управления (Control Flows, Рисунок 6-11):** Последовательное (Sequential), Параллельное (Parallel — одновременный просмотр 10 сайтов), Условные операторы (If-statement), Циклы (For-loop).
* **Фреймворк ReAct (Yao et al., 2022):** Поочередное чередование мыслей, действий и наблюдений в формате `Thought 1 -> Act 1 -> Observation 1 ... -> Finish`.
* **Фреймворк Reflexion (Shinn et al., 2023):** Разделение на исполнителя, отдельный модуль оценки и модуль саморефлексии (Self-reflection), сохраняющий траектории ошибок.

### Agent Failure Modes and Evaluation / Режимы сбоев агентов и их оценка

1. **Planning failures (Сбои планирования):**
   * *Invalid tool:* Попытка вызвать инструмент, отсутствующий в инвентаре.
   * *Valid tool, invalid parameters:* Вызов корректного инструмента с неверным количеством аргументов.
   * *Valid tool, incorrect parameter values:* Вызов с неверными значениями (передача 100 вместо 120).
   * *Goal failure:* Невыполнение условий задачи или нарушение ограничений (превышение бюджета, пропуск дедлайнов).
   * *Reflection error:* Модель убеждена, что выполнила задачу, хотя сделала её частично (распределила 40 человек по комнатам вместо 50).
2. **Tool failures (Сбои инструментов):** Ошибки самих инструментов (неверный SQL-запрос, сбой OCR-парсерa), ошибки транслятора планов, отсутствие необходимых инструментов.
3. **Efficiency (Эффективность):** Количество шагов, итоговая стоимость токенов, задержка каждого действия.

### Memory / Память

* **3 механизма памяти ИИ-системы (Рисунок 6-16):**
  1. **Internal knowledge (Внутренние знания):** Веса модели, полученные при предобучении и файнтюнинге. Не меняются без переобучения.
  2. **Short-term memory (Кратковременная память):** Контекстное окно диалога. Быстрый доступ, ограниченный объём.
  3. **Long-term memory (Долгосрочная память):** Внешние базы данных (RAG), хранящие историю сессий, профиль пользователя и документы. Позволяет добавлять и удалять записи без изменения весов модели.
* **Стратегии управления кратковременной памятью:**
  * **FIFO (First-In, First-Out):** Удаление самых старых сообщений при превышении лимита контекста.
    * *Предупреждение автора:* Первые сообщения часто содержат главную цель и правила диалога, их удаление приводит к сбою системы.
  * **Суммаризация (Summarization):** Сжатие истории диалога в краткую выжимку с отслеживанием именованных сущностей (Bae et al., 2022).
  * **Рефлексивное обновление (Liu et al., 2023):** Модель анализирует новые факты, объединяет их с существующими или перезаписывает устаревшие/противоречивые данные.
