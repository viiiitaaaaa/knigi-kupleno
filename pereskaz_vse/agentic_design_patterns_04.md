## Chapter 10. Model Context Protocol (MCP) / Глава 10. Протокол контекста модели (MCP)

#### Главная мысль автора

Model Context Protocol (MCP) — это открытый клиент-серверный стандарт, который выступает в роли универсального интерфейса для взаимодействия больших языковых моделей (LLM) с внешними ресурсами, данными, инструментами и промптами, устраняя необходимость в создании отдельных кастомных интеграций под каждый сервис.

#### Ключевые формулировки автора

1. *"Imagine a universal adapter that allows any LLM to plug into any external system, database, or tool without a custom integration for each one. That's essentially what the Model Context Protocol (MCP) is."* — «Представьте себе универсальный адаптер, который позволяет любой LLM подключаться к любой внешней системе, базе данных или инструменту без кастомной интеграции для каждого из них. Это и есть суть Model Context Protocol (MCP).»
2. *"It's an open standard designed to standardize how LLMs like Gemini, OpenAI's GPT models, Mixtral, and Claude communicate with external applications, data sources, and tools."* — «Это открытый стандарт, созданный для стандартизации того, как LLM, такие как Gemini, модели GPT от OpenAI, Mixtral и Claude, взаимодействуют с внешними приложениями, источниками данных и инструментами.»
3. *"An API is only useful if its data format is agent-friendly, a guarantee that MCP itself does not enforce."* — «API полезен только в том случае, если его формат данных удобен для агента — гарантия, которую сам по себе MCP не обеспечивает.»

#### MCP Pattern Overview / Обзор паттерна MCP

##### Мысли автора по порядку

* Чтобы языковые модели эффективно функционировали как агенты, им недостаточно только генерации текста — необходимо взаимодействие с внешней средой: доступ к актуальным данным, использование ПО и выполнение операционных задач.
* MCP функционирует на базе клиент-серверной архитектуры:
  * **MCP Server (сервер):** предоставляет доступ к трём типам компонентов: *Resources* (статические данные), *Prompts* (шаблоны взаимодействия) и *Tools* (исполняемые функции).
  * **MCP Client (клиент):** хост-приложение ИИ или сам агент, запрашивающий и использующий эти компоненты.
* Автор подчеркивает: MCP является контрактом «агентского интерфейса», и его эффективность прямо зависит от качества базовых API.
* *Проблема легаси-API:* Прямое обёртывание устаревших API без адаптации неэффективно. Если API тикет-системы позволяет запрашивать детали только по одному тикету за раз, агент при суммаризации множества тикетов будет работать медленно и со сбоями. API необходимо дополнять детерминированными функциями фильтрации и сортировки.
* *Агентно-ориентированные форматы данных (Agent-friendly data):* Сам MCP не гарантирует понятность данных. Если сервер передаёт бинарные PDF-файлы, а агент не умеет их парсить, интеграция бесполезна. Сначала необходимо создать API, возвращающий текстовое представление (например, Markdown).

##### Цифры, примеры и истории

* **История с API тикетов:** Разработчик обернул легаси-API тикет-системы в MCP -> API выдавал детали строго по одному тикету -> при попытке агента обработать массив высокоприоритетных задач система работала с высокой задержкой и ошибками.
* **История с хранилищем PDF:** Сервер возвращал файлы в формате PDF -> агент не имел внутреннего парсера для этого формата -> агент не смог прочитать данные (решение: конвертация вывода API в Markdown).

#### MCP vs. Tool Function Calling / MCP против вызова функций инструментов

##### Мысли автора по порядку

* Вызов функций (Function Calling) — это прямое разовое взаимодействие «один-к-одному» между LLM и конкретной предустановленной функцией. Данный механизм часто является проприетарным и отличается у разных провайдеров.
* MCP — это открытый стандартизированный протокол клиент-серверного взаимодействия, обеспечивающий динамическое обнаружение (discovery) и повторное использование инструментов в федеративной среде.
* Аналогия автора: Function Calling подобен выдаче ИИ конкретного гаечного ключа или отвёртки под узкую задачу; MCP подобен созданию универсальной розетки, к которой можно подключить любой инструмент от любого производителя.

#### Additional considerations for MCP / Дополнительные соображения по MCP

##### Мысли автора по порядку

* **Tool vs. Resource vs. Prompt:** *Resource* — статические данные (PDF-файл, запись БД); *Tool* — исполняемая функция (отправка email, запрос к API); *Prompt* — шаблон, направляющий модель при работе с ресурсом или инструментом.
* **Discoverability:** Механизм запроса "just-in-time" позволяет клиенту узнавать о новых возможностях сервера без пересборки агента.
* **Security:** Обязательность аутентификации и авторизации.
* **Implementation:** Использование SDK (FastMCP, Anthropic SDK) снижает объем шаблонного кода.
* **Error Handling:** Ошибки вызова передаются обратно в LLM, позволяя ей выбрать альтернативный путь.
* **Local vs. Remote Server:** Локальные сервера задействуют JSON-RPC over STDIO для скорости и безопасности; удаленные — Streamable HTTP и Server-Sent Events (SSE).
* **4 компонента архитектуры:** 1. LLM; 2. MCP Client; 3. MCP Server; 4. Optional 3P Service (сторонний сервис).
* **5 шагов взаимодействия:** 1. Discovery (клиент запрашивает манифест); 2. Request Formulation (LLM формирует параметры); 3. Client Communication (клиент посылает стандартизированный вызов); 4. Server Execution (сервер исполняет действие); 5. Response and Context Update (сервер возвращает результат в контекст модели).

#### Practical Applications & Use Cases / Практические применения и варианты использования

##### Мысли автора по порядку

1. **Database Integration:** Взаимодействие с базами данных (например, использование MCP Toolbox for Databases для запросов к Google BigQuery на естественном языке).
2. **Generative Media Orchestration:** Оркестрация мультимедийных сервисов Google Cloud (Imagen для изображений, Veo для видео, Chirp 3 HD для голоса, Lyria для музыки).
3. **External API Interaction:** Стандартизированный вызов сторонних API (погода, котировки акций, CRM).
4. **Reasoning-Based Information Extraction:** Точечное извлечение точных цитат/условий из документов вместо возврата всего текста.
5. **Custom Tool Development:** Быстрое создание внутренних инструментов на FastMCP.
6. **Standardized LLM-to-Application Communication:** Унификация слоя связи между приложениями и LLM.
7. **Complex Workflow Orchestration:** Многошаговые цепочки (запрос данных клиента из БД -> генерация баннера в Imagen -> составление и отправка письма).
8. **IoT Device Control:** Управление датчиками, умным домом и робототехникой.
9. **Financial Services Automation:** Анализ финансовых рынков, исполнение сделок и автоматизация комплаенса.

## Chapter 11. Goal Setting and Monitoring / Глава 11. Постановка целей и мониторинг

#### Главная мысль автора

Для того чтобы ИИ-агенты работали автономно и осознанно, им необходима четкая постановка измеримых целей (Goal Setting) и непрерывный мониторинг состояния среды и собственных действий (Monitoring), образующие контур обратной связи для оценки успешности выполнения задач.

#### Ключевые формулировки автора

1. *"For AI agents to be truly effective and purposeful, they need more than just the ability to process information or use tools; they need a clear sense of direction and a way to know if they're actually succeeding."* — «Чтобы ИИ-агенты были по-настоящему эффективными и целенаправленными, им требуется нечто большее, чем просто способность обрабатывать информацию или использовать инструменты; им необходимо четкое чувство направления и способ узнать, действительно ли они добиваются успеха.»
2. *"This step-by-step process, often considering dependencies and constraints, is fundamentally what we mean by planning in agentic systems."* — «Этот пошаговый процесс, часто учитывающий зависимости и ограничения, по своей сути и является тем, что мы подразумеваем под планированием в агентных системах.»
3. *"Goals should be specific, measurable, achievable, relevant, and time-bound (SMART)."* — «Цели должны быть конкретными, измеримыми, достижимыми, релевантными и ограниченными по времени (SMART).»

#### Goal Setting and Monitoring Pattern Overview / Обзор паттерна постановки целей и мониторинга

##### Мысли автора по порядку

* Аналогия с планированием поездки: человек определяет пункт назначения (целевое состояние / goal state), анализирует текущее положение (начальное состояние / initial state), оценивает ресурсы (бюджет, транспорт) и строит пошаговый маршрут.
* В агентных системах агент принимает верхнеуровневую цель и самостоятельно генерирует последовательность подцелей.
* Мониторинг обеспечивает постоянную проверку промежуточных результатов, позволяя своевременно выявлять отклонения от цели и корректировать план.

#### Practical Applications & Use Cases / Практические применения и варианты использования

##### Мысли автора по порядку

1. **Customer Support Automation:** Цель — «разрешить проблему с биллингом». Мониторинг диалога, проверка записей БД, подтверждение списания и оценка отзыва клиента.
2. **Personalized Learning Systems:** Цель — «улучшить понимание алгебры учеником». Мониторинг выполнения упражнений, отслеживание точности и времени, адаптация сложности.
3. **Project Management Assistants:** Цель — «завершить этап X к дате Y». Мониторинг статусов задач, сигналы о задержках и перераспределение ресурсов.
4. **Automated Trading Bots:** Цель — «максимизация доходности портфеля при ограниченном риске». Мониторинг рынка и корректировка позиций при превышении порогов риска.
5. **Robotics and Autonomous Vehicles:** Цель — «безопасная доставка пассажиров из A в B». Мониторинг пешеходов, светофоров, скорости и остатка топлива.
6. **Content Moderation:** Цель — «удаление вредоносного контента». Мониторинг входящего потока, отслеживание ошибок 1-го и 2-го рода (false positives/negatives) и эскалация модераторам.

#### Hands-On Code Example / Практический пример кода

##### Мысли автора по порядку

  * Более надежный подход — разделение ролей между командой специализированных агентов (Peer Programmer, Code Reviewer, Documenter, Test Writer, Prompt Refiner).

## Chapter 12. Exception Handling and Recovery / Глава 12. Обработка исключений и восстановление

#### Главная мысль автора

Для работы в непредсказуемой реальной среде автономным ИИ-агентам необходимы надежные системы обнаружения ошибок, их обработки и восстановления операционной целостности (через откат состояния, самокоррекцию или эскалацию на человека).

#### Ключевые формулировки автора

1. *"For AI agents to operate reliably in diverse real-world environments, they must be able to manage unforeseen situations, errors, and malfunctions."* — «Чтобы ИИ-агенты работали надежно в разнообразных реальных условиях, они должны быть способны справляться с непредвиденными ситуациями, ошибками и сбоями.»
2. *"This pattern focuses on developing exceptionally durable and resilient agents that can maintain uninterrupted functionality and operational integrity despite various difficulties and anomalies."* — «Этот паттерн фокусируется на создании исключительно устойчивых и живучих агентов, способных поддерживать беспрерывную функциональность и операционную целостность, несмотря на различные сложности и аномалии.»

#### Exception Handling and Recovery Pattern Overview / Обзор паттерна обработки исключений и восстановления

##### Мысли автора по порядку

* В реальном мире агенты сталкиваются со сбоями API, таймаутами и невалидными данными.
* Паттерн часто сочетается с рефлексией (Reflection): при ошибке агент анализирует сбой и повторяет попытку с обновленным промптом.
* **3 ключевых компонента (Fig. 1)****:**
  1. *Error Detection (Обнаружение ошибок):* Фиксация невалидного вывода инструментов, кодов ошибок API (404, 500), задержек сети и неформатированных ответов.
  2. *Error Handling (Обработка ошибок):* Логирование (logging), повторные попытки (retries), использование резервных путей (fallbacks), сохранение частичной функциональности (graceful degradation) и уведомление оператора (notification).
  3. *Recovery (Восстановление):* Откат изменений (state rollback), выяснение причин, самокоррекция/перепланирование (self-correction) и эскалация на человека (escalation).

#### Practical Applications & Use Cases / Практические применения и варианты использования

##### Мысли автора по порядку

1. **Customer Service Chatbots:** При падении БД информирует пользователя и эскалирует тикет оператору.
2. **Automated Financial Trading:** При ошибке "insufficient funds" или "market closed" логирует сбой и меняет стратегию.
3. **Smart Home Automation:** При сетевом сбое при включении света делает ретраи, а затем просит ручного вмешательства.
4. **Data Processing Agents:** При встрече битого файла пропускает его, продолжает обработку пакета и выводит список пропущенных файлов.
5. **Web Scraping Agents:** При появлении CAPTCHA или ошибок 404/503 ставит паузу или меняет прокси.
6. **Robotics and Manufacturing:** При неудачном захвате детали перенастраивает манипулятор и просит помощи оператора.

#### At a Glance / Краткий обзор

##### Мысли автора по порядку

* **Что:** Без структуры обработки ошибок ИИ-агенты остаются хрупкими и падают при первых сетевых или форматных сбоях.
* **Почему:** Паттерн сочетает обнаружение, реактивную обработку и протоколы восстановления для сохранения стабильности.
* **Правило:** Применяйте паттерн в любых реальных средах с рисками сбоев API, сети или сторонних сервисов.
