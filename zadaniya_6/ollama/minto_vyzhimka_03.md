- Использовать модель C‑Q‑A (описание проблемы – вопрос – ответ) при формулировании гипотез (стр. 56)  
- В схеме C‑Q‑A включать буквы C, Q, A и обозначать 5 = Assumption (стр. 56)  
- Не принимать «насыщенность рынка» за данность, игнорировать управленческие факторы – это ошибка (стр. 56)  

- При построении вводной части по схеме S‑C‑Q‑A выполнить 4‑шаговый процесс: выбрать тон, переставить части S, C, Q, сформулировать каждый блок в 1‑2 предложения, убедиться, что вопрос Q явно задаёт цель текста (стр. 57)  
- Вариантов тонального оформления S‑C‑Q‑A четыре: **STANDARD**, **DIRECT**, **CONCERNED**, **AGGRESSIVE** (стр. 57)  
- Не менять порядок S, C, Q без цели – иначе тон будет несогласован (стр. 57)  

- Размещать Key Line в середине первой страницы в виде списка (стр. 58)  
- При длинных документах сразу добавить заголовок к каждому пункту Key Line и начать его раскрывать (стр. 58)  
- При коротких текстах использовать пункты Key Line как тематические предложения (подчёркнутые) (стр. 58)  
- В первых 30 секундах чтения длинного документа следует представить Key Line (стр. 58)  
- Не писать пункты Key Line как «Background», «Introduction» – это категории, а не идеи (стр. 59)  

- Длину введения определять потребностями читателя, а не размером документа (стр. 60)  
- Для Situation и Complication обычно писать 2‑3 абзаца по 3‑4 предложения; Solution – 1‑2 предложения (стр. 60)  
- При тесном контакте с читателем вводную часть можно сократить до одного предложения (стр. 61)  
- Не перегружать вводную часть фактами и экспонатами – это ошибка (стр. 61)  

- Пункты Key Line должны быть идеями, а не названиями разделов; каждый пункт сопровождается мини‑вводом S‑C‑Q‑A (стр. 62)  
- Для каждого пункта Key Line выполнить пять шагов: выбрать идею, сформулировать S, C, Q, A (стр. 64‑66)  
- Заголовок пункта должен отражать его суть (стр. 64)  
- Не начинать пункт без вводного контекста; не использовать заголовки‑категории («Background») (стр. 65)  

- В начале документа должен стоять один главный (pivot) вопрос; остальные выводятся из него (стр. 66)  
- Если нужны два вопроса, они должны логически соединяться (пример: «Войти ли на рынок? И как?» → «Как войти на рынок?») (стр. 66)  
- Выделены четыре типовых вопроса: 1) Что следует сделать? 2) Как следует/будет/было сделано? 3) Стоит ли это делать? 4) Почему это произошло? (стр. 66)  
- Два несвязанных вопроса приводят к потере логики и запутанности (стр. 66)  

- Директивный меморандум строится по схеме S‑C‑Q‑A; при вопросе “How?” ответ всегда представляет собой список шагов (стр. 67‑68)  
- Не уточнить вопрос “How?” → риск «не знаю, что писать» (стр. 68)  

- Запрос на одобрение расходов следует схеме S‑C‑Q‑A; вопрос «Should I approve?», ответ «We urge your approval» (стр. 68‑69)  
- При составлении запросов использовать четыре стандартных аргумента: 1) проблема не откладывается, 2) решение решит проблему, 3) финансовый выигрыш (экономия > стоимость), 4) дополнительные выгоды (если есть) (стр. 68‑69)  
- Не добавлять «четвёртый пункт», если он не подкреплён фактами (стр. 69)  

- «How‑to» документ строится по схеме S‑C‑Q‑A; в A приводится список шагов, сравнивающих Present Process и Recommended Process (стр. 70‑71)  
- Не раскрывать оба процесса в уме без их сравнения – можно упустить важные детали (стр. 71)  

- При выборе среди альтернатив: после S и C задать вопрос “Which makes most sense?”; перечислить варианты (A, B, C…) и критерии сравнения (быстрота, простота реализации, цель); выбрать вариант, объяснив решающий критерий (стр. 72‑73)  
- Не рассматривать альтернативы как одинаково решающие; иначе получаем лишь набор целей, а не решений (стр. 73)  

- Консультационные предложения и отчёты о прогрессе используют шаблон S‑C‑Q‑A; в A для письма‑предложения 4‑частная структура: 1) понимание проблемы, 2) подход к решению, 3) опыт компании, 4) выгодные бизнес‑условия (стр. 74‑75)  
- В Progress Review в A давать краткое резюме результатов (стр. 75)  
- Не писать длинные вводные вместо чётких S‑C‑Q‑A; не забывать выводов по каждому этапу (стр. 76)  

- В письме использовать один из двух логических шаблонов: дедуктивный (от частного к общему, завершается «therefore») или индуктивный (обобщение из фактов) (стр. 77‑78)  
- Смешивание дедуктивной и индуктивной формы приводит к «ponderous» письменной речи; использовать дедукцию в проблемо‑решении, избегая её излишней тяжести (стр. 78)
