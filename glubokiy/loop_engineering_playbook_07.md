## 1. Категория 5 – Качество и Безопасность (Patterns 61‑75) (стр. 282)  

- **Главная мысль** – набор проверок и защитных механизмов, которые позволяют агенту выдавать достоверный, непредвзятый и безопасный результат и оставлять полную историю действий.  

- **Шаблоны / примеры (по каждому пункту)**  

| № | Шаблон (кратко) | Что делает |
|---|----------------|------------|
| 61 | **Self‑Critique** – после выдачи ответа агент проверяет его на фактические, логические и полно‑текстовые ошибки. |
| 62 | **Rubric Scoring** – оценивает вывод по 4‑м измерениям (точность, полнота, ясность, формат) по шкале 1‑10. |
| 63 | **Adversarial Check** – второй LLM ищет дефекты в ответе; если находит – агент исправляет. |
| 64 | **Citation Verification** – проверяет, что каждое утверждение имеет корректный источник. |
| 65 | **Output Validation** – проверка JSON/структурных ответов по схеме; при ошибке – повторный запрос с сообщением об ошибке. |
| 66 | **Guardrails** – фильтрация запрещённого контента (регулярки, классификатор). |
| 67 | **Consistency Check** – сравнение новых утверждений с ранее сказанным, выявление противоречий. |
| 68 | **Confidence Scoring** – агент ставит оценку 0‑1; < 0.7 → человек проверяет, > 0.9 → авто‑одобрено. |
| 69 | **Bias Detection** – сканирование вывода на гендерные, расовые, подтверждающие и другие типы предвзятости (классификатор/правила). |
| 70 | **PII Scrubbing** – поиск и замена персональных данных (регекс, NER) токенами [EMAIL_1] и т.д. |
| 71 | **Audit Log** – неизменяемый журнал всех действий агента (LLM‑запросы, вызовы инструментов, изменения состояния). |
| 72 | **Rate‑of‑Change Guard** – при резком росте изменений (> 5 файлов, > 20 записей)‑пауза и запрос подтверждения. |
| 73 | **Dry Run** – полное моделирование цикла без коммита побочных эффектов, вывод пользователю «что будет, если выполнить». |
| 74 | **Canary Deployment** – 5 % трафика идёт к новой версии, 95 % – к старой; сравнение метрик 24‑48 ч. |
| 75 | **Kill Switch** – мгновенное отключение всех агентов через флаг/endpoint; обязательно тестировать ежеквартально. |

- **Ошибки / предупреждения** – не делать авто‑коррекцию при Bias Detection (требует человеческого решения); не полагаться только на один Guardrail – комбинируйте.  

- **Где пригодится** – при построении систем, где *регуляторные требования, защита данных и репутация* критичны (финансы, медицина, клиент‑поддержка).

## 2. Категория 6 – Стоимость и Производительность (Patterns 76‑90) (стр. 283)  

- **Главная мысль** – набор техник, позволяющих резко снизить токен‑ и вычислительные затраты без потери качества.  

- **Шаблоны / примеры**  

| № | Шаблон | Что даёт |
|---|--------|----------|
| 76 | **Model Tiering** – роутинг задач к самому дешёвому подходящему LLM (Haiku = кл. $0.001/вызов, Sonnet = $0.01, Opus = $0.05). Сокращение 50‑70 % расходов. |
| 77 | **Prompt Compression** – удалять лишние пробелы, сокращать повторяющиеся инструкции; пример: 2000 токенов → 800 токенов (экономия 60 %). |
| 78 | **Semantic Caching** – кэшировать ответы по смыслу (эмбеддинги, косинус > 0.95); типичный Hit‑Rate 20‑40 %. |
| 79 | **Batch Processing** – группировать запросы (10 запросов → один LLM‑вызов); уменьшает накладные токены ≈ 90 %. |
| 80 | **Lazy Evaluation** – выполнять только те ветки, которые реально нужны в текущем шаге. |
| 81 | **Streaming Response** – отправлять частичные результаты через SSE; пользователи видят прогресс сразу. |
| 82 | **Token Budget** – фиксировать процент токенов для фаз (план 30 %, исполнение 50 %, синтез 20 %). |
| 83 | **Cost Alerting** – алерты в реальном времени при достижении 50 %, 80 % и 100 % дневного бюджета; можно throttling. |
| 84 | **Prompt Template Reuse** – общие секции (формат, безопасные правила) хранятся централизовано и включаются по ссылке. |
| 85 | **Response Truncation** – лимитировать длину вывода под задачу (yes/no ≤ 100 токенов, summary ≤ 500 токенов). |
| 86 | **Parallel Tool Calls** – одновременно вызывать независимые инструменты (asyncio.gather); снижение латентности ≈ 50 %. |
| 87 | **Prefetch** – предзагружать данные, которые, скорее всего, понадобятся, пока агент «думает». |
| 88 | **Deferred Computation** – отложить тяжёлые операции в очередь, выполнять в оф‑пик. |
| 89 | **Resource Pooling** – общий пул соединений/кешей для всех агентов; уменьшает оверхед. |
| 90 | **Cold Start Optimization** – прогрев моделей и кэшей до пика нагрузки; время первой заявки < 1 сек. (сокращение 5 сек → 1 сек). |

- **Ошибки / предупреждения** – не забывать про **Token Budget** (может привести к «засорению» фазой планирования); **Prefetch** без подтверждения востребованности может наоборот увеличить нагрузку.  

- **Где пригодится** – при масштабных сервисах с высоким QPS (чат‑боты, поиск, аналитика), где *каждый токен стоит денег*.

## 3. Категория 7 – Пользовательский Опыт (UX) (Patterns 91‑100) (стр. 283‑284)  

- **Главная мысль** – улучшить восприятие и доверие пользователя к автономным агентам за счёт прозрачности, возможности отката и гибкой подачи информации.  

- **Шаблоны / примеры**  

| № | Шаблон | Кратко |
|---|--------|--------|
| 91 | **Progressive Disclosure** – показывать сначала краткое резюме, детали раскрываются по запросу. |
| 92 | **Status Updates** – выводить в реальном времени статус («поиск 3 баз…», «анализ 47 записей…»); пользователи терпят 10× более длительное ожидание, если видят прогресс. |
| 93 | **Undo Support** – каждое действие (файл, запись в БД, email) имеет возможность отката одним кликом; хранится история действий. |
| 94 | **Explanation Mode** – при запросе «почему?», агент выводит простой текстовый «trace» своего рассуждения. |
| 95 | **Preference Learning** – собирает предпочтения (формат вывода, стилистика) и автоматически адаптирует будущие ответы. |
| 96 | **Multimodal Output** – подбирает формат (таблица, график, код) под тип контента; не использовать один формат для всего. |
| 97 | **Context Persistence** – сохраняет разговор между сессиями (проект, предпочтения, последняя задача). |
| 98 | **Error Translation** – преобразует технические ошибки в дружелюбные сообщения («База недоступна, повторная попытка через 30 сек.». |
| 99 | **Feedback Loop** – лайк/дизлайк на каждый вывод; отрицательная обратная связь порождает кейс в eval‑пайплайн, инициирует автоматическое расследование. |
| 100| **Graceful Handoff** – при невозможности решить задачу передаёт полностью контекст человеку‑оператору, чтобы тот не задавал уточняющих вопросов. |

- **Ошибки / предупреждения** – не делать **Undo** без ограничения (может привести к бесконечному росту памяти); **Progressive Disclosure** требует чёткой маркировки «расширяемого» контента, иначе пользователь не поймёт, где кликнуть.  

- **Где пригодится** – в клиент‑фронтендах, чат‑ботах и любых сервисах, где *удобство и доверие* критичны.

## 4. Категория 1 – Контроль Цикла (Loop Control) (стр. 284‑286)  

**Главная мысль** – набор шаблонов, позволяющих управлять длительностью, стоимостью и стабильностью итеративных агентных циклов.  

### 4.1 Bounded Loop (1)  
- **Что делает** – ставит жёсткий максимум шагов (обычно 10‑25).  
- **Шаги**: 1) объявить счётчик; 2) в условии while проверять `counter < MAX`; 3) при превышении вернуть fallback‑ответ.  
- **Правило** – без предела агент может «сжечь» $50 токенов за минуту.  

### 4.2 Early Exit (2)  
- **Что делает** – завершает цикл сразу, как только цель достигнута.  
- **Шаги**: после каждого шага проверять `goal_met?`; если True → `break`.  
- **Эффект** – экономит 30‑50 % бюджета, устраняя «just‑in‑case»‑шаги.  

### 4.3 Cost Circuit Breaker (3)  
- **Что делает** – прерывает цикл, когда суммарные токены превышают установленный бюджет (пример $0.50 за run).  
- **Шаги**: отслеживать `total_input + total_output` токенов; при превышении выйти и вернуть лучший промежуточный результат.  

### 4.4 Convergence Check (4)  
- **Что делает** – сравнивает текущий вывод с предыдущим; если изменение < threshold → остановка.  
- **Метрика** – косинусное расстояние эмбеддингов ≥ 0.95 → output почти одинаковый → прекратить.  

### 4.5 Oscillation Detector (5)  
- **Что делает** – обнаруживает зацикливание между двумя состояниями.  
- **Шаги**: после каждого шага вычислять hash(state); если такой hash появлялся в последних 5 шагов → вставить инструкцию «выбери иной подход».  

### 4.6 Backoff Loop (6)  
- **Что делает** – при ошибках увеличивает задержку между повторными попытками (exp‑backoff).  
- **Алгоритм**: 0 сек → 1 сек → 2 сек → 4 сек … + random jitter; максимум 30 сек.  

### 4.7 Priority Loop (7)  
- **Что делает** – сортирует задачи по приоритету; при исчерпании бюджета откладывает низкоприоритетные.  

### 4.8 Checkpoint Loop (8)  
- **Что делает** – сохраняет полное состояние (сообщения, результаты инструментов, переменные) каждые 3‑5 шагов. При падении процесс восстанавливается из последнего чекпоинта.  

### 4.9 Timeout Guard (9)  
- **Что делает** – стенок‑тайм (например 5 мин) независимо от счётчика шагов; при истечении возвращает лучший частичный результат.  

### 4.10 Nested Loop (10)  
- **Что делает** – внешняя петля делит задачу на под‑задачи; каждая под‑задача имеет собственный лимит шагов и бюджет.  

### 4.11 Parallel Loop (11)  
- **Что делает** – независимые итерации выполняются параллельно (asyncio.gather); ускоряет время 60‑80 % при embarrassingly parallel‑workloads.  

### 4.12 Conditional Loop (12)  
- **Что делает** – выбирает стратегию (кол‑во шагов, модель) в зависимости от классификации задачи (simple/medium/complex).  

### 4.13 Warmup Loop (13)  
- **Что делает** – 1‑2 дешёвых шага для оценки сложности задачи, выбора инструментов, оценки количества шагов; потом переключается на основной цикл.  

### 4.14 Cooldown Loop (14)  
- **Что делает** – после главного вывода делает последнюю проверку (факт‑проверка, согласованность, валидация формата). Улавливает 10‑15 % ошибок, пропущенных основной петлей.  

### 4.15 Adaptive Step Limit (15)  
- **Что делает** – динамически меняет максимум шагов: старт ≈ 20; после 5 шагов, если ≥ 80 % работы завершено → сократить оставшиеся до 3; если ≤ 20 % → увеличить до 25.  

- **Ошибки / предупреждения** – не устанавливать слишком высокий `MAX` (рост расходов); не полагаться только на `Early Exit` без `Convergence Check` (может вернуть неполный ответ).  

- **Где пригодится** – в любой автономной системе, где необходим контроль расходов и время выполнения (скрипты‑агенты, небольшие сервисы).

## 5. Категория 2 – Работа с Инструментами (Tool Use) (стр. 287‑289)

| № | Шаблон | Кратко |
|---|--------|--------|
| 16 | **Tool Router** – лёгкая модель (Haiku) выбирает нужный инструмент до основной модели; экономия 50‑70 % на роутинге. |
| 17 | **Tool Fallback** – при ошибке основного инструмента (таймаут, пустой результат) автоматически переключается на запасной (другой поисковик, затем «использовать знание модели с дисклеймером»). |
| 18 | **Tool Composition** – объединяет последовательность инструментов в один логический вызов (например `search_and_summarize = web_search → read_page → summarize`). |
| 19 | **Tool Validation** – проверка аргументов (типы, диапазоны) до выполнения; при ошибке выдаёт ясное сообщение. |
| 20 | **Tool Caching** – кэширует результаты одинаковых входов (hash(tool+args)); типичный hit‑rate 15‑30 %. |
| 21 | **Tool Rate Limiter** – токен‑бакет/скользящее окно для ограничения количества вызовов внешних API. |
| 22 | **Tool Sandboxing** – изоляция: код‑инструменты в Docker, файловые операции в ограниченной директории, БД‑инструменты – read‑only по умолчанию. |
| 23 | **Tool Discovery** – агент запрашивает реестр доступных инструментов вместо жёсткой их прописки в системном запросе. |
| 24 | **Tool Documentation Injection** – включать полное описание инструмента в prompt только когда он нужен; экономит 40‑60 % токенов. |
| 25 | **Read‑Only First** – всегда сначала собирать информацию (чтение файлов/БД) перед любыми изменениями. |
| 26 | **Idempotent Tools** – повторный вызов той же функции (например `create_user`) не создает дубликатов, а возвращает уже существующий объект. |
| 27 | **Tool Versioning** – поддержка нескольких версий инструмента; системный prompt указывает нужную версию. |
| 28 | **Tool Health Check** – перед началом цикла пингует health‑endpoint каждого инструмента; при недоступности информирует пользователя сразу. |
| 29 | **Tool Result Summarization** – сжимает объёмный вывод (500 строк → 3‑ключевых метрики) перед добавлением в контекст; экономия 60‑80 % токенов. |
| 30 | **Confirmation Tool** – мета‑инструмент `confirm_action(description=…)` запрашивает у пользователя подтверждение перед необратимыми действиями. |

- **Ошибки / предупреждения** – не забывать о **Read‑Only First** (может привести к потерям данных); **Tool Sandboxing** обязателен при работе с файловой системой/БД.  

- **Где пригодится** – в любой системе, где агент взаимодействует с внешними API, БД, файловой системой (автоматическое обслуживание, ETL, скрипты‑агенты).

## 6. Категория 3 – Память (Memory) (стр. 290‑291)

| № | Шаблон | Кратко |
|---|--------|--------|
| 31 | **Sliding Window** – держать в контексте последние N сообщений (5‑10) – простейшая стратегия для коротких задач. |
| 32 | **Landmark Memory** – фиксировать ключевые «landmarks» (изменения плана, ошибки) и выгонять остальные в сводку‑однострочку. |
| 33 | **Semantic Recall** – хранить всё в векторном хранилище; при запросе берём top‑K похожих записей по эмбеддингам. |
| 34 | **Memory Compression** – каждые 5‑10 шагов дешёвой моделью суммировать контекст в буллет‑список (сокращение 60‑80 %). |
| 35 | **Episodic Memory** – сохранять полные эпизоды прошлых задач; при новой задачи искать похожие эпизоды и использовать как few‑shot пример. |
| 36 | **Working Memory Buffer** – отдельный «scratch‑pad» для промежуточных вычислений (под‑итоги, гипотезы), не загрязняющий основной диалог. |
| 37 | **Preference Store** – key‑value хранилище пользовательских предпочтений (например «люблю буллет‑списки», «метрические единицы»); подгружается в системный запрос. |
| 38 | **Fact Cache** – кэш проверенных фактов с источником; повторные запросы используют кэш, экономя поиск. |
| 39 | **Context Budget** – распределение % контекстного окна: 40 % working, 20 % landmarks, 20 % retrieved, 20 % system+tools. При превышении – сжимать/выгонять. |
| 40 | **Memory Eviction** – удалять наименее важные записи (оценка recency + relevance + importance); никогда не удалять пользовательские сообщения и landmark‑записи. |
| 41 | **Shared Memory** – общий стейт (Redis/БД) доступен нескольким агентам для координации. |
| 42 | **Memory Versioning** – каждый апдейт сохраняет новую версию с тайм‑стемпом и причиной; удобно для отладки. |
| 43 | **Structured State** – хранить состояние в типизированных объектах (не в свободном тексте) → программные проверки легче. |
| 44 | **State Validation** – после каждого изменения проверять правила (обязательные поля, диапазоны). |
| 45 | **Rollback State** – стек состояний; при ошибке откатываемся к последней «хорошей» версии. |

- **Ошибки / предупреждения** – слишком частая **Memory Compression** без учёта критических фактов может привести к потере важного контекста.  

- **Где пригодится** – в длительных проектах, где агент работает над одной задачей часами (исследования, код‑генерация, аналитика).

## 7. Категория 4 – Мульти‑агентные системы (Multi‑Agent) (стр. 292‑294)

| № | Шаблон | Кратко |
|---|--------|--------|
| 46 | **Supervisor** – один агент‑надзорщик разбивает задачу, распределяет под‑задачи, собирает результаты, синтезирует итог. |
| 47 | **Pipeline** – последовательный поток: A → B → C (исследование → написание → публикация). |
| 48 | **Debate** – два агента спорят, третий (или человек) выбирает лучший вариант; снижает предвзятость. |
| 49 | **Ensemble** – несколько независимых агентов решают одну задачу, выбирается лучший ответ (голосование). |
| 50 | **Specialist Routing** – классификатор направляет задачу к эксперту‑агенту (SQL‑агент, код‑агент, писатель). |
| 51 | **Reviewer‑Writer** – один пишет, другой рецензирует; итерации (обычно 2‑3) пока не достигнут требуемый уровень качества. |
| 52 | **Hierarchical Delegation** – многоуровневое делегирование (lead → senior → junior). |
| 53 | **Blackboard** – общая доска, где агенты читают и пишут задачи/результаты асинхронно. |
| 54 | **Auction** – агенты делают ставки (качество / стоимость); система выбирает лучший баланс. |
| 55 | **Consensus** – действие производится только после согласия большинства (или все) агентов. |
| 56 | **Agent Pool** – динамическое масштабирование количества агентов под нагрузкой. |
| 57 | **Agent Lifecycle** – чёткое создание‑исполнение‑завершение, предотвращает «зомби‑агенты». |
| 58 | **Message Bus** – стандартизированный протокол (типы сообщений, схемы, роутинг). |
| 59 | **Role Rotation** – периодическая смена ролей (ревьюер ↔ писатель) – проверка устойчивости процесса. |
| 60 | **Escalation Chain** – джуниор → сениор → человек, если уровень уверенности < threshold или ошибка. |

- **Ошибки / предупреждения** – не перегружать **Supervisor** слишком сложными задачами без чёткого протокола таймаутов; **Consensus** может сильно замедлить процесс, если требовать unanimity.  

- **Где пригодится** – в проектах с разнородными под‑задачами (контент‑производство, исследовательские пайплайны, автоматизация разработки).

## 11. Приложение C – Сравнительная матрица инструментов (стр. 300)  

- **Главная мысль** – оценка четырёх популярных фреймворков (LangChain, LangGraph, CrewAI, AutoGen) по 13 категориям (баллы 1‑5).  
- **Ключевые выводы**:  
  - *LangGraph* лидирует в сложных ветвлениях, управлении состоянием и кастомизации.  
  - *LangChain* лучше для простых цепочек и широкой экосистемы.  
  - *CrewAI* удобен для ролей‑ориентированных команд, но хуже в контроле стоимости.  
  - *AutoGen* хорош для экспериментальных разговорных агентов, но слаб в продакшн‑готовности и контроле расходов.  
- **Где пригодится** – при выборе базового фреймворка для нового проекта (сравнивать требуемую сложность, нужды в состоянии, стоимость).

### Как применять полученный конспект  

| Сценарий | Что использовать из конспекта |
|----------|------------------------------|
| **Создание нового автогенного агента** | Шаблоны Loop Control (Bounded Loop, Early Exit, Cost Circuit Breaker) + Tool Use (Tool Router, Validation, Caching) |
| **Оптимизация расходов** | Категория 6 (Model Tiering, Prompt Compression, Semantic Caching, Batch Processing) |
| **Повышение надёжности** | Категория 5 (Self‑Critique, Audit Log, Kill Switch, Rate‑of‑Change Guard) |
| **Улучшение UX для конечных пользователей** | Категория 7 (Progressive Disclosure, Status Updates, Undo, Graceful Handoff) |
| **Работа в мульти‑агентной среде** | Категория 4 (Supervisor, Pipeline, Debate, Escalation Chain) |
| **Выбор фреймворка** | Приложение C (матрица) + Приложение E (список фреймворков) |
| **Обучение команды** | Приложения D‑F (глоссарий, ресурсы, cheat‑sheet) |

---  

**Важно:** используйте только те паттерны, которые реально нужны в текущем проекте. Не переборщите с *Guardrails* и *Checks* – они добавляют токены и latency, но без них система может стать уязвимой. Баланс *cost ↔ quality ↔ user experience* — главный критерий выбора.
