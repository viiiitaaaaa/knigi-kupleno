## Введение (стр. —)

- **Главная мысль** – Агент не запоминает автоматически; память нужно добавить целенаправленно, иначе каждый диалог начинается «с чистого листа».  
- **Почему важно** – Память позволяет сохранять предпочтения, контекст и улучшать поведение со временем.

## Таблица 10‑1 — Типы памяти в системах‑агентах  

| Тип памяти | Что хранит | Зачем |  
|------------|-----------|-------|  
| **Short‑term (working)** | Текущее состояние разговора, последние сообщения, промежуточные шаги | Сохраняет когерентность в рамках одного сеанса |  
| **Long‑term** | Персистентные сведения: предпочтения, прошлые взаимодействия, знание | Обеспечивает непрерывность между сеансами, персонализацию |  
| **Episodic** | Конкретные прошлые события (разговоры, решения, результаты) | Позволяет вспомнить «что произошло» для будущих рассуждений |  
| **Semantic** | Факты, документы, эмбеддинги, структурированная информация о мире | Дает фактическую опору; обычно извлекается через RAG |  
| **Procedural** | Шаблоны, инструкции, рабочие процессы, выученное поведение | Делает выполнение задач стабильным и позволяет улучшаться без перепрограммирования |

## Short‑Term Memory и Time Travel (стр. —)

### Главная мысль  
Краткосрочная память — это «чекпоинтер», сохраняющий состояние графа‑потока между шагами, позволяющий откатываться и ветвить выполнение.

### Как делать  
1. **Создать чекпоинтер** – `InMemorySaver()` (или `SqliteSaver`, `PostgresSaver` в проде).  
2. **Создать хранилище** – `InMemoryStore` с функцией эмбеддингов.  
3. **Определить граф** (`StateGraph`) и добавить узлы/рёбра.  
4. **Скомпилировать граф с чекпоинтером** – `graph.compile(checkpointer=…)`.  
5. **Запустить** – `graph.invoke(initial_state, {"configurable": {"thread_id": "my‑thread"}})`.  
6. **Получить историю** – `graph.get_state_history(cfg)`.  
7. **Выполнить “time‑travel”**: выбрать нужный чекпоинт, изменить состояние, продолжить выполнение (`update_state`, `invoke`).  

### Шаблоны кода (из текста)  
```python
# 1. Чекпоинтер в памяти
CHECKPOINTER = InMemorySaver()

# 2. Чекпоинтер в продакшн
conn = sqlite3.connect("checkpoints.db")
CHECKPOINTER_PROD = SqliteSaver(conn)

# 3. Мини‑граф с чекпоинтером
ps_wf = StateGraph(PS)
...
persist_demo = ps_wf.compile(checkpointer=InMemorySaver())
```

### Ошибки/предупреждения  
- **Не использовать только in‑memory чекпоинтер** в продакшн — данные пропадут при перезапуске.  
- **Не забывать задавать `thread_id`** — иначе всё путается в одной общей истории.  

### Где пригодится  
- Для отладки сложных цепочек рассуждений, аудита решений, ветвления логики.

## Long‑Term Memory — Профессиональный агент (стр. —)

### Главная мысль  
Без долговременной памяти агент стартует каждый раз «с нуля». С ней он превращается в опытного специалиста, способного сохранять знания и привычки между сессиями.

### Сравнительная таблица 10‑2  

| Аспект | Short‑term | Long‑term |
|--------|------------|-----------|
| **Определение** | Состояние текущего сеанса | Персистентные сведения между сеансами |
| **Компоненты** | Текущее состояние, план, выводы инструментов | История решений, предпочтения, аудит‑логи |
| **Область** | Один запуск | Кросс‑сеанс |
| **Цель** | Сохранить когерентность, избежать циклов | Обеспечить непрерывность, адаптацию, обучение |
| **Хранение** | Эфемерно | Требует постоянного хранилища |
| **Типичные кейсы** | Реактивные циклы, планировщик | Персональный помощник, корпоративные знания |
| **Отказы** | Нет кросс‑сеансов, ограниченный аудит | Не валидировано, шипучий рост, устаревшие/шумные данные |

### Где пригодится  
- При построении персональных или корпоративных ассистентов, которые должны помнить предпочтения, прошлые задачи и т.п.

## Применение **Namespaces** (стр. —)

### Главная мысль  
В многопользовательском приложении память должна быть **разделена** по пользователям, организациям и типу памяти, иначе данные перемешаются.

### Как делать (шаги)  
1. Определить константы типов: `NS_SEMANTIC`, `NS_EPISODIC`, `NS_PROCEDURAL`, `NS_PROFILE`.  
2. Создать `@dataclass` `AppContext(org_id, user_id, is_admin)`.  
3. Реализовать функции формирования кортежей‑пространств имён: `ns_user`, `ns_org_shared`, `ns_profile_user`.  
4. При записи/чтении в/из хранилища всегда передавать полученный кортеж.  

### Пример кода (10‑5)

```python
NS_SEMANTIC = "semantic"
NS_EPISODIC = "episodic"
NS_PROCEDURAL = "procedural"
NS_PROFILE = "profile"
SHARED_SEGMENT = "_shared"

@dataclass(frozen=True)
class AppContext:
    org_id: str
    user_id: str
    is_admin: bool = False

def ns_user(ctx: AppContext, kind: str) -> tuple[str, str, str]:
    return (_safe_segment(ctx.org_id), _safe_segment(ctx.user_id), kind)
```

### Ошибки/предупреждения  
- **Не проверять подлинность `user_id`** – если берётся из клиентской строки, любой может писать в чужую память. Нужно использовать проверенный JWT/Auth‑токен.  

### Где пригодится  
- При построении SaaS‑приложения с несколькими пользователями и ролями.

## Сервис‑слой доступа к памяти (стр. —)

### Главная мысль  
Оборачивая хранилище в небольшую сервис‑обёртку, вы централизуете операции чтения/записи, избегаете «распыления» логики по графу.

### Шаги  
1. Создать класс `UserMemoryService` с конструктором, принимающим `BaseStore`.  
2. Реализовать методы `list_semantic`, `list_episodic`, `upsert_semantic`, `set_procedural`.  
3. Внутри методов делегировать ре‑ализацию вспомогательным функциям (`semantic_list_items`, `procedural_set_instructions` и т.п.).

```python
class UserMemoryService:
    def __init__(self, store: BaseStore):

    ...
```

## Эпизодическая память (стр. —)

### Главная мысль  
Эпизодическая память позволяет агенту обращаться к прошлым «событиям», превращая его в собственный набор тренировочных примеров (few‑shot).

### Как делать  
1. **Поиск** – `store.search(ns_user(ctx, NS_EPISODIC), query, limit)`.  
2. **Запись события** – генерировать UUID (если нет), сформировать запись `{task, outcome, mem_ix, created_at}` и `store.put`.  

### Пример (10‑7)  

```python
def episodic_search(store, ctx, query, *, limit=3):
    return list(store.search(ns_user(ctx, NS_EPISODIC), query=query, limit=limit))

def episodic_record_event(store, ctx, task, outcome, *, memory_key=None):
    key = memory_key or str(uuid.uuid4())
    store.put(ns_user(ctx, NS_EPISODIC), key, {...})
    return key
```

### Где пригодится  
- Для построения «истории решения задач», отладки и пост‑мортем‑анализа.

## Семантическая память (стр. —)

### Главная мысль  
Семантическая память хранит долговременные факты (настройки, предпочтения, справочную информацию) и извлекает их через запросы.

### Как делать  
1. **Поиск** – `store.search(ns_user(ctx, NS_SEMANTIC), query, limit)`.  
2. **Upsert** – валидировать текст (`validate_durable_memory_text`), сформировать payload `{fact, mem_ix, updated_at, …}` и `store.put`.  

### Пример (10‑8)

```python
def semantic_upsert_fact(store, ctx, key, fact, extra=None, *, transient=False, projection_of=None):
    text = validate_durable_memory_text(fact)
    payload = {"fact": text, "mem_ix": f"{text}\u200ckey:{key}", "updated_at": _utc_now_z(), **ex}
    store.put(ns_user(ctx, NS_SEMANTIC), key, payload)
```

### Где пригодится  
- При хранении пользовательских настроек (язык, тема), справочных материалов, фактов о домене.

## Процедурная память (стр. —)

### Главная мысль  
Процедурная память — живой «мануал», который агент действительно читает и применяет; пользователь может изменять инструкции «на лету».

### Как делать  
1. **Получить** – `store.get(ns_user(ctx, NS_PROCEDURAL), PROFILE_AGENT_INSTRUCTIONS)`.  
2. **Обновить** – загрузить текущую структуру, заменить только переданные поля, добавить `updated_at`, `store.put`.  
3. **Инициализация по‑умолчанию** – если записи нет, записать базовую инструкцию.  

### Пример (10‑9)

```python
def procedural_put_structured(store, ctx, fields):
    cur = procedural_read_structured(store, ctx)
    for k in ("style","workflow","safety","task_policies"):
        if k in fields and fields[k] is not None:
            cur[k] = str(fields[k]).strip()
    cur["updated_at"] = _utc_now_z()
    store.put(ns_user(ctx, NS_PROCEDURAL), PROFILE_AGENT_INSTRUCTIONS, cur)
```

### Где пригодится  
- При изменении формата вывода, правил безопасности, рабочих процессов без деплоя кода.

## Шифрование и защита памяти (стр. —)

### Главная мысль  
Данные в чекпоинтере могут содержать чувствительную информацию; их надо шифровать, а также валидировать перед записью, чтобы предотвратить **memory poisoning** (запись вредоносного контента в долговременную память).

### Как делать (пример 10‑11)  
1. Прочитать AES‑ключ из переменной окружения `LANGGRAPH_AES_KEY` (64 hex‑символа).  
2. Создать `EncryptedSerializer.from_pycryptodome_aes()`.  
3. Передать сериализатор в `InMemorySaver(serde=…)`.  
4. Скомпилировать граф с этим чекпоинтером и выполнить одно‑разовое `invoke`.  

### Где пригодится  
- При работе с персональными данными, медицинскими записями, финансовой информацией.

## Гигиена памяти — как‑не‑забиваться (стр. —)

### Главная мысль  
Память растет, если её не «чистить». Нужно регулярно удалять старое, дубли, противоречия и сжимать большие наборы.

### Политики (таблица 10‑4)

| Механизм | Описание | Пример |
|----------|----------|--------|
| **Time‑based pruning** | Удалять записи старше N дней | Keep last 30 days |
| **Importance‑based retention** | Оставлять только ценные записи | Хранить ошибки, нарушения, события с высокой уверенностью |
| **Compression** | Сжимать (например, суммировать) эпизоды | Summarize conversations |

### Пример 10‑12 — сокращение диалога

1. Собрать все сообщения, убрать команду‑сократитель.  
2. Сконкатенировать их в один текст.  
3. Отправить в LLM с инструкцией «Summarize ≤ 8 bullets, keep preferences».  
4. Сформировать `RemoveMessage`‑ы для всех старых сообщений.  
5. Вставить новый `HumanMessage` с виде «Prior conversation (summarized): …».  

### Пример 10‑13 — компакция семантики  

- Считать до `list_limit` записей.  
- Сформировать список `facts` в виде маркеров.  
- Попросить LLM «Merge…de‑duplicate aggressively».  
- Записать полученный `merged`‑текст под ключом `CONSOLIDATED_KEY`.  
- Удалить все прежние записи (кроме консолидированного).  

### Пример 10‑14 — валидация перед записью  

```python
def validate_durable_memory_text(text, *, max_chars=MEMORY_CONTENT_MAX_CHARS):
    t = (text or "").strip()
    if len(t) > max_chars: raise ValueError(...)
    if re.search(r"\b\d{3}-\d{2}-\d{4}\b", t): raise ValueError(...)
    # ... проверки на номера карт, приватные ключи, AWS‑keys, OpenAI‑secrets
    return t
```

### Пример 10‑15 — структурные обновления (удаление противоречий, дубли, порог confidence)

- Удалять `factsToRemove` и всё, что «supersedes» их.  
- По категориям (`CATEGORY_COMBINE_MODE`) либо **replace**, либо **accumulate**.  
- Отклонять новые факты с `confidence < 0.7`.  
- Ограничить общее количество фактов `max_facts = 100`.  

### Пример 10‑16 — детерминированное устранение противоречий  

- Список пар regex‑ов (`dark mode` vs `light mode`).  
- Сравнивать `updatedAt`/`createdAt`, оставлять более новое.  

### Где пригодится  
- При построении долгоживущих агентов‑помощников, где важно поддерживать чистую и актуальную базу знаний.

## Стоимость решения о памяти (стр. —)

| Подход | Доп. вызовов LLM | Точность | Стоимость |
|--------|-------------------|----------|-----------|
| **Regex / правила** | 0 | ≈ 70 % | бесплатно |
| **Embedding similarity** | 0 (GPU‑инференс) | ≈ 85 % | низко |
| **Небольшой классификатор (encoder‑only)** | 0 (GPU) | ≈ 90 % | низко‑средняя |
| **Полный LLM‑judge** | 1 LLM‑вызов / шаг | ≈ 95 % | удваивает счёт |

- **Рекомендация**: использовать каскадный подход – сначала regex, потом similarity, затем лёгкий классификатор, а LLM‑judge только для «сложных»/«высокорисковых» случаев.  

### Где пригодится  
- При планировании инфраструктуры: как избежать лишних расходов на LLM‑вызовы при управлении памятью.

## Топология памяти в мульти‑агентных системах (стр. —)

### Главная мысль  
Размещение памяти (локальная, общая, гибридная) определяет степень координации, шумов и масштабируемости.

| Топология | Плюсы | Минусы |
|-----------|-------|--------|
| **Per‑agent local** | Модульность, чистый контекст, низкий шум | Дублирование данных, дрейф представлений, сложнее согласовать |
| **Shared global** | Один источник истины, простая координация | Шум, «заполнение окна контекста», нужен строгий фильтр, синхронизация |
| **Hybrid** | Локальная авт. память + глобальная согласованность | Самый сложный в реализации, но самый практичный |  

### Где пригодится  
- При проектировании систем из нескольких агентов (супервизоры, специалисты, инструменты), где нужно сочетать автономию и общий контекст.

## Итоги для Claude (помощника‑одиночки)

| Что будет использовать Claude |  
|-------------------------------|  
| **Short‑term memory** — чекпоинтер для текущего диалога (чтобы не «забывать» где остановился).  
| **Long‑term memory** — семантические факты (настройки, предпочтения), эпизодические записи (что делал ранее), процедурные инструкции (как выполнять задачи).
