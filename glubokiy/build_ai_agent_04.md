## 1. Building tools and tool definitions for LLMs (стр. 78‑79)  
- **Главная мысль** – Чтобы LLM мог использовать внешние сервисы, нужно написать обычную Python‑функцию, обернуть её в «инструмент» (tool) и предоставить схему её параметров.  
- **Как делать**  
  1. Установить клиент API (пример — `TavilyClient`).  
  2. Написать функцию‑обёртку, принимающую запрос и возвращающую список результатов.  
  3. Протестировать её вызовом, убедившись, что результат содержит `title`, `url`, `content`, `score`.  
- **Шаблоны и примеры**  
  ```python
  from dotenv import load_dotenv
  load_dotenv()
  tavily_client = TavilyClient(os.getenv("TAVILY_API_KEY"))

  def search_web(query: str, max_results: int = 2) -> list:
      response = tavily_client.search(query, max_results=max_results)
      return response.get("results")
  ```  
  Пример вывода показан в листинге 3.13 (список словарей с полями `title`, `url`, `content`, `score`).  
- **Ошибки и предупреждения** – На этой странице ошибок не рассматривается.  
- **Где нам пригодится** – Для создания собственного инструмента поиска, который LLM будет вызывать в запросах к внешнему контенту.  

## 2. Расширение функции поиска (стр. 79‑80)  
- **Главная мысль** – Реальные запросы требуют дополнительных параметров (тип контента, время, страна и пр.). Их удобно добавить в сигнатуру функции, но это усложняет схему инструмента.  
- **Как делать**  
  1. Добавить к функции дополнительные аргументы (`topic`, `time_range`, `country`).  
  2. Прокинуть их в вызов `tavily_client.search`.  
  3. При необходимости добавить в схему параметры — указать типы и значения по умолчанию.  
- **Правила и числа** – По умолчанию `max_results=2`; в примерах могут быть `max_results=5`.  
- **Шаблоны и примеры**  
  ```python
  def search_web(
      query: str,
      max_results: int = 2,
      topic: str = "general",
      time_range: str | None = None,
      country: str | None = None,
  ) -> list:
      response = tavily_client.search(
          query,
          max_results=max_results,
          topic=topic,
          time_range=time_range,
          country=country,
      )
      return response.get("results")
  ```  
- **Ошибки и предупреждения** – Чем больше параметров, тем сложнее LLM‑модели правильно использовать инструмент; требуется тщательная документация.  
- **Где нам пригодится** – При построении агента, который должен искать только свежие новости, только в определённой стране или только в финансовой сфере.  

## 3. Обработка ошибок в инструментах (стр. 80‑81)  
- **Главная мысль** – Инструмент должен gracefully (аккуратно) реагировать на сбои API (401, 429, таймауты и пр.), иначе агент «упадёт».  
- **Как делать**  
  1. Обернуть вызов API в `try/except`.  
  2. При исключении вернуть строку‑сообщение об ошибке.  
  3. При более сложных сценариях различать типы ошибок (аутентификация, rate‑limit, таймаут) и применять специфические стратегии (повтор, уведомление человека).  
- **Шаблоны и примеры**  
  ```python
  def search_web(... ) -> list | str:
      try:
          response = tavily_client.search(...)
          return response.get("results")
      except Exception as e:
          return f"Error: Search failed - {e}"
  ```  
- **Ошибки и предупреждения** – Текущий «catch‑all» подходит лишь для обучения; в продакшене необходимо дифференцировать ошибки.  
- **Где нам пригодится** – Любой инструмент, работающий с внешним API (поиск, базы данных, CRM).  

## 4. Преобразование функций в определение инструмента (tool definition) (стр. 81‑84)  
- **Главная мысль** – Чтобы LLM «понимал», как вызвать функцию, её нужно представить в стандартизованном JSON‑Schema‑формате (tool definition). Делать это вручную сложно, поэтому пишем автоматизатор, использующий `inspect`.  
- **Как делать**  
  1. **Извлечь метаданные**: `func.__name__`, `func.__doc__`, `inspect.signature(func)`.  
  2. **Сгенерировать JSON‑Schema для параметров** через словарь‑соответствие Python‑типа → тип schema (`str`→`string`, `int`→`integer` и т.д.).  
  3. **Пометить обязательные параметры**: если у параметра нет значения по умолчанию → добавить в список `required`.  
  4. **Объединить в финальный инструмент** функцией `format_tool_definition`.  
- **Шаблоны и примеры**  
  ```python
  import inspect

  def function_to_input_schema(func) -> dict:
      type_map = {str:"string", int:"integer", float:"number", bool:"boolean",
                  list:"array", dict:"object", type(None):"null"}
      signature = inspect.signature(func)
      parameters = {}
      for p in signature.parameters.values():
          param_type = type_map.get(p.annotation, "string")
          parameters[p.name] = {"type": param_type}
      required = [p.name for p in signature.parameters.values()
                  if p.default == inspect._empty]
      return {"type":"object", "properties":parameters, "required":required}
  ```
  Конверсия `search_web` дала:
  ```json
  {"type":"function","function":{"name":"search_web",
    "description":"Search the web for the given query.",
    "parameters":{"type":"object",
      "properties":{"query":{"type":"string"},
                    "max_results":{"type":"integer"},
                    "topic":{"type":"string"},
                    "time_range":{"type":"string"}},
      "required":["query"]}}}
  ```  
- **Ошибки и предупреждения** – Если в функции отсутствуют аннотации типов, они будут считаться `string`. Необработанные типы вызывают `KeyError`.  
- **Где нам пригодится** – При быстрой генерации схем для всех ваших скриптов, чтобы не забывать обновлять описания вручную.  

## 5. Полный цикл выполнения инструмента (стр. 84‑85)  
- **Главная мысль** – Агенту нужен «мост» между LLM‑выводом (tool call) и реальным выполнением функции; цикл «LLM → инструмент → результат → LLM» продолжается, пока не получен окончательный ответ.  
- **Как делать**  
  1. **tool_execution**: принимает `tool_box` (словарь `name → function`) и `tool_call` (данные из LLM).  
     ```python
     def tool_execution(tool_box, tool_call):
         name = tool_call.function.name
         args = json.loads(tool_call.function.arguments)
         return tool_box[name](**args)
     ```  
  2. **simple_agent_loop**: собирает `system_prompt`, `question`, список инструментов, формирует список сообщений, в цикле посылает их в LLM (`completion`).  
     - Если LLM вернул `tool_calls`, вызываем `tool_execution` и добавляем в историю сообщение типа `"tool"`.  
     - Иначе возвращаем `assistant_message.content`.  
- **Шаблоны и примеры**  
  ```python
  result = simple_agent_loop(
      system_prompt="You are a helpful assistant. Use the search tool when you need current information.",
      question="Who won the 2025 Nobel Prize in Physics?"
  )
  # → ответ с актуальными данными
  ```  
- **Ошибки и предупреждения** – Цикл может зациклиться, если LLM будет постоянно запрашивать инструменты (отсутствует ограничитель `current_step`).  
- **Где нам пригодится** – Любой агент, нуждающийся в последовательном вызове нескольких инструментов (поиск → калькулятор → запись).  

## 6. Проблемы масштабирования пользовательских инструментов (стр. 85‑87)  
- **Главная мысль** – С ростом количества инструментов появляются три категории проблем: *неизвестные API*, *нормальная и надёжная обработка ошибок*, *отсутствие стандартизации* (разные команды используют разные схемы, типы данных, синхронные/асинхронные вызовы).  
- **Ключевые факты**  
  - API, не ориентированные на LLM, требуют длительного изучения (документация, модели данных, пагинация).  
  - Production‑ready error handling часто превышает 10 строк базовой реализации, доходя до 50+.  
  - Без единой схемы (интерфейса) каждую функцию приходится пере‑адаптировать под проект.  
- **Где нам пригодится** – При планировании новых интеграций (Slack, Google Drive, Salesforce) и необходимости централизованного реиспользования кода.  

## 7. Введение в MCP – Model‑Context‑Protocol (стр. 87‑90)  
- **Главная мысль** – MCP ставит задачу стандартизации описания, обнаружения и исполнения инструментов, аналогично тому, как REST стандартизировал веб‑API.  
- **Компоненты MCP**  
  1. **Host** – приложение (например, Claude Desktop) с LLM‑мозгом, принимает запросы пользователя и решает, какие инструменты нужны.  
  2. **Client** – мост, запрашивает у серверов списки инструментов и переадресует запросы на их исполнение.  
  3. **Server** – хостит инструменты, отвечает на два типа запросов: *list‑tools* и *execute‑tool*.  
- **Транспортные механизмы**  
  - `stdio` – запускает сервер как подпроцесс, общение через stdin/stdout (идеально для локальной разработки).  
  - `streamable HTTP` – позволяет удалённый доступ, подходит для продакшена.  
- **Где нам пригодится** – При построении архитектуры многокомандного проекта, где одни команды пишут инструменты, а другие используют их без написания собственного кода обёртки.  

## 8. Запуск готового MCP‑сервера (Tavily) (стр. 90‑92)  
- **Главная мысль** – С помощью `npx` можно быстро поднять готовый MCP‑сервер, который уже содержит несколько веб‑инструментов (search, extract, crawl, map).  
- **Как делать**  
  1. Установить Node ≥ 22.x (проверка `node --version`).  
  2. Экспортировать переменную `TAVILY_API_KEY`.  
  3. Запустить: `npx @modelcontextprotocol/inspector npx -y tavily-mcp@latest`.  
  4. Открыть URL‑адрес, который выведет инспектор, нажать **Connect**, перейти во вкладку **Tools** → **List Tools**.  
- **Шаблоны и примеры** – Инструменты, доступные на сервере: `tavily_search`, `tavily_extract`, `tavily_crawl`, `tavily_map`. Пример вызова `tavily_search` с запросом “2025 Nobel Physics”.  
- **Ошибки и предупреждения** – Если Node‑версия слишком старая (< 22.7.5), запуск провалится.  

## 9. MCP‑клиент на Python (стр. 92‑94)  
- **Главная мысль** – Клиент реализует запросы к серверу: список инструментов и их исполнение; он преобразует полученные MCP‑схемы в формат, ожидаемый LLM‑провайдера (OpenAI).  
- **Как делать**  
  1. Установить SDK: `uv add mcp`.  
  2. Создать `StdioServerParameters` (команда `npx`, аргументы `-y tavily-mcp@latest`, передать API‑ключ).  
  3. Открыть `stdio_client` в `async with`, затем `ClientSession`.  
  4. Вызвать `await session.list_tools()` → получить список `tool.name`, `tool.description`, `tool.inputSchema`.  
  5. Вызвать `await session.call_tool("tavily_search", {"query":"2025 Nobel Physics"})`.  
- **Шаблон функции конвертации**  
  ```python
  def mcp_tools_to_openai_format(mcp_tools):
      return [
          format_tool_definition(tool.name, tool.description, tool.inputSchema)
          for tool in mcp_tools.tools
      ]
  ```  
- **Ошибки и предупреждения** – Клиент не меняет сам формат MCP‑схем; конверсия необходима, пока провайдеры не поддерживают нативный MCP.  

## 10. Создание собственного MCP‑сервера (стр. 94‑96)  
- **Главная мысль** – С помощью библиотеки **FastMCP** любой Python‑функцию можно превратить в полностью совместимый MCP‑инструмент, лишь добавив декоратор `@mcp.tool()`.  
- **Как делать**  
  1. `uv add mcp`.  
  2. Импортировать `FastMCP` и объявить сервер: `mcp = FastMCP("custom-tavily-search")`.  
  3. Оформить функцию `search_web` (как в разделе 3) и добавить декоратор.  
  4. В `if __name__ == "__main__": mcp.run(transport='stdio')`.  
  5. Запустить сервер через `uv run tavily_mcp_server.py`.  
  6. Подключиться клиентом, изменив `StdioServerParameters` (команда — `uv`, args — `run tavily_mcp_server.py`).  
- **Шаблоны кода**  
  ```python
  @mcp.tool()
  def search_web(query: str, max_results: int = 5) -> str:
      """Search the web using Tavily API."""
      try:
          response = tavily_client.search(query, max_results=max_results)
          results = response.get("results", [])
          return "\n\n".join(
              f"Title: {r['title']}\nURL: {r['url']}\nContent: {r['content']}"
              for r in results
          )
      except Exception as e:
          return f"Error searching web: {str(e)}"
  ```  
- **Ошибки и предупреждения** – При запуске без корректного `TAVILY_API_KEY` будет ошибка 401; сервер будет завершён с исключением.  
- **Где нам пригодится** – Когда нужна фирменная логика (кастомные параметры, корпоративные API) и требуется делиться ею через стандартный MCP.  

## 11. Итоги первой части (стр. 97‑98)  
- **Главная мысль** – Инструменты расширяют возможности LLM: доступ к API, вычисления, поиск.  
- **Ключевые пункты**  
  - *Tool calling* – LLM генерирует структурированный запрос к инструменту, а не текстовое описание.  
  - *Tool definitions* – JSON‑Schema, обязательные и необязательные параметры.  
  - *MCP* – Стандартизирует обнаружение и исполнение инструментов (сервер‑клиент).  
- **Где нам пригодится** – В дальнейшем при построении многокомпонентных агентов (чтение/запись файлов, работы с базами, планирование).  

## 12. Реакт‑агент: базовый паттерн (стр. 99‑101)  
- **Главная мысль** – ReAct = *Reason + Act*: агент последовательно размышляет (think) и выполняет действия (act) через инструменты, пока не получит окончательный ответ. Современный ReAct реализуется через **tool calling**, а не через парсинг свободного текста.  
- **Как делать (think‑act цикл)**  
  1. **Thought** – LLM формулирует, какая информация нужна.  
  2. **Action** – LLM генерирует структуру `{tool: "search_web", args:{...}}`.  
  3. **Observation** – Агент получает результат инструмента и добавляет его в контекст.  
  4. Повторять шаги 1‑3, пока LLM не выдаст *Final Answer*.  
- **Шаблоны** (текстовый пример из листинга 4.1):  
  ```
  Thought: I need Kipchoge's marathon pace.
  Action: search_web("Kipchoge marathon world record")
  Observation: 2:01:09 for 42.195 km
  Thought: Need Earth‑Moon distance.
  Action: search_wikipedia("Moon perigee distance")
  Observation: 356,500 km
  Thought: Calculate time.
  Action: calculator("356500 / (42.195 / 2.0186) * 1")
  Observation: 17034 hours
  Final Answer: Approximately 17,000 hours.
  ```  
- **Ошибки и предупреждения** – Если LLM выдаёт некорректный JSON‑формат, прежний подход парсинга ломался; tool calling решает эту проблему.  
- **Где нам пригодится** – При построении любого агента, который должен последовательно комбинировать поиск, вычисления и прочие действия.  

## 13. Архитектура базового ReAct‑агента (стр. 102‑104)  
- **Главная мысль** – Для чистоты кода и масштабируемости весь процесс исполнения объединён в один объект — `ExecutionContext`, который хранит события, шаги, идентификаторы, состояние и окончательный результат.  
- **Компоненты (таблица 4.1)**  
  1. **ExecutionContext** – центральный контейнер (стр. 102‑104).  
  2. **Tool abstraction** – единый интерфейс, позволяющий передавать контекст в инструменты.  
  3. **LLM communication layer** – `LlmRequest` (выборка из контекста), `LlmClient` (вызов API), `LlmResponse` (унифицированный ответ).  
  4. **Agent** – оркестратор, который создает `ExecutionContext`, управляет цикл `think‑act`.  
- **Как делать (построение контекста)**  
  1. При старте создаётся объект `ExecutionContext`.  
  2. При каждом запросе LLM берётся нужная часть контекста → `LlmRequest`.  
  3. Ответ LLM → `LlmResponse` → сохраняется обратно в контекст (`events`).  
  4. При необходимости вызывается инструмент, которому передаётся тот же `ExecutionContext`; результат сохраняется как событие `tool`.  
  5. `current_step` контролирует максимальное количество итераций, предотвращая бесконечные циклы.  
- **Шаблон использования агента** (листинг 4.1)  
  ```python
  agent = Agent(
      model=LlmClient(model="gpt-5-mini"),
      tools=[calculator, search_web],
      instructions="You are a helpful assistant"
  )
  result = await agent.run("What is 1234 * 5678?")
  # → "7,006,652"
  ```  
- **Ошибки и предупреждения** – Без `ExecutionContext` состояние быстро рассредоточивается; без ограничения `current_step` агент может застрять в бесконечном вызове инструментов.  
- **Где нам пригодится** – При построении любого продвинутого агента (память, планирование, мульти‑агентные системы), где требуется передавать контекст между LLM, инструментами и вспомогательными подсистемами.
