## Упражнения (стр. 96)  
- **Главная мысль:** Практические задачи, позволяющие закрепить модели HITL, автотесты и построение дашбордов.  
- **Как делать:**  
  1. Реализовать трёхуровневую систему approval‑gates (auto, auto‑if‑confident, always‑approve).  
  2. Смоделировать 200 решений автоподтверждения и проверить переход «supervised → semi‑auto → autonomous».  
  3. Сгруппировать 5‑10 связанных действий в батч‑approval, измерить время time‑to‑approve.  
  4. Сконструировать детектор fatigue — сигналить, когда медиана time‑to‑approve < 3 сек (стр. 96).  
  5. Спроектировать полный HITL для e‑mail‑агента, расставив уровни одобрения для read/archive/reply/forward/delete.  
  6. Внедрить обработчик timeout по примеру Example 3 и протестировать три пути (auto‑approve, defer, reject).  
  7. Построить дашборд HITL (approval‑rate, avg time‑to‑approve, текущий autonomy‑level, топ‑5 отклоняемых действий).  
- **Правила и числа:** median time‑to‑approve < 3 сек → fatigue (стр. 96).  
- **Шаблоны и примеры:** пример‑timeout‑handler из Example 3 (стр. 96).  
- **Ошибки и предупреждения:** не проверять timeout для высокорисковых действий – может привести к пропуску критических ошибок.  
- **Где пригодится:** для построения запросов «показать approval‑gates по задачам», «отследить fatigue в реальном времени», «создать HITL‑дашборд».

## Сводка главы 9 – HITL‑паттерны (стр. 97)  
- **Главная мысль:** Выделены четыре HITL‑паттерна, подходы к approval‑fatigue, прогрессивному автопилоту и обязательному человеческому контролю в критических доменах.  
- **Как делать:**  
  1. Внедрить approval gates (авто, авто‑if‑confident, всегда‑одобрять).  
  2. Настроить confidence thresholds (уровень confidence → требуется human‑in‑the‑loop).  
  3. Вести audit trails (логировать каждое действие).  
  4. Применять progressive autonomy — супервизировано (первые 20 действий), semi‑auto (≥85 % одобрения), autonomous (≥95 % одобрения на ≥100 действий).  
- **Правила и числа:**  
  - progressive autonomy : supervised → first 20 actions, semi‑auto ≥ 85 % approval, autonomous ≥ 95 % approval over 100+ actions (стр. 97).  
  - targeted HITL ( confidence + sensitive‑topic + anomaly ) ловит 95 % ошибок, проверяя 10 % действий (стр. 97).  
  - timeout : low‑risk → auto‑approve, medium → defer, high → reject (стр. 97).  
  - в high‑stakes домена (legal, finance, medical) обязательно human review независимо от confidence (стр. 97).  
- **Шаблоны и примеры:** batch‑approval для «рутинных» действий (стр. 97).  
- **Ошибки и предупреждения:** approval fatigue («rubber‑stamping») хуже полного отказа — не допускайте median time‑to‑approve < 3 сек без контроля.  
- **Где пригодится:** для построения запросов «какие действия находятся в auto‑approve», «какова текущая autonomy‑level».

### 10.2 Обзор публичных бенчмарков (стр. 101‑103)

- **Как делать:** Для каждого бенчмарка — изучить ограничения:

  2. HumanEval/MBPP – генерация функций (90 %+ на текущих моделях) (стр. 101).  
  3. GAIA – мульти‑step reasoning (ниже 70 % на Level 3) (стр. 101).  
  4. TAU‑bench + WebArena – реальные клиентские сценарии, но узкопрофильные (стр. 102).  
- **Правила и числа:** SWE‑bench ≈ 55‑60 % solved (стр. 101); HumanEval ≈ 90 %+ (стр. 101).  
- **Шаблоны и примеры:** описание SWE‑bench (стр. 101).  
- **Ошибки и предупреждения:** не использовать HumanEval для multi‑file или performance‑optimization задач (стр. 101).  
- **Где пригодится:** запрос «какой бенчмарк показывает performance‑optimization для моего агента».  

### 10.3 Создание кастомного оценочного набора (стр. 102‑105)  
- **Главная мысль:** Кастомный eval‑suite показывает, работает ли агент в конкретных условиях.  
- **Как делать:**  
  1. **Define Success Criteria** (стр. 102): уточнить формат (exact, semantic, constraints), вредоносный вывод, латентность, стоимость, промежуточные сигналы.  
  2. **Create Test Case Taxonomy** (стр. 103): четыре категории — Happy Path (40‑50 % cases), Edge (20‑30 %), Adversarial (15‑20 %), Regression (10‑15 %).  
  3. **Build Evaluation Harness** (стр. 104‑105): реализовать EvalCase, EvalResult, AgentEvaluator (см. код).  
- **Правила и числа:** соотношения категорий — Happy Path 40‑50 %, Edge 20‑30 %, Adversarial 15‑20 %, Regression 10‑15 % (стр. 103).  
- **Шаблоны и примеры:** code‑snippet AgentEvaluator (стр. 104‑105).  
- **Ошибки и предупреждения:** не забывать задавать max_latency_seconds и max_cost_dollars в EvalCase (стр. 104).  
- **Где пригодится:** для построения запросов «создай EvalCase для моего агента с max_cost = 0.5 долл».  

### 10.4 Функции оценки (скейлинг) (стр. 106‑107)  
- **Главная мысль:** Выбор функции scoring зависит от типа задачи и качества, которое нужно измерять.  
- **Как делать:** Выбрать одну из таблицы Scoring Strategy (стр. 106) и реализовать (примеры кода ниже).  
- **Правила и числа:**   
  - Exact match → 1.0 if actual == expected, иначе 0.0.  
  - Fuzzy match → Levenshtein, BLEU, ROUGE.  
  - Semantic similarity → cosine > 0.85 (стр. 106).  
  - Constraint check → пропорционально пройденным правилам.  
  - LLM‑as‑judge → оценка 1‑10 → делить на 10.  
- **Шаблоны и примеры:** `exact_match`, `semantic_similarity`, `constraint_scorer`, `llm_judge` (стр. 107).  
- **Ошибки и предупреждения:** использовать semantic similarity только если cosine > 0.85 (стр. 106).  
- **Где пригодится:** для запросов «применить semantic similarity к моим результатам».  

### 10.5 A/B‑тестирование конфигураций (стр. 108‑109)  
- **Главная мысль:** Любое изменение агента должно проверяться через A/B‑тест на полном eval‑suite с статистической значимостью.  
- **Как делать:**  
  1. Запустить оба варианта (`agent_a`, `agent_b`) через `ab_test_agents` (стр. 108‑109).  
  2. Собирать pass_rate по runs_per_case (по умолчанию 3).  
  3. Вычислить t‑stat и p‑value (стр. 109).  
  4. При p < 0.05 и avg_b > avg_a рекомендовать деплой.  
- **Правила и числа:** p‑value < 0.05 → значимый улучшение (стр. 109).  
- **Шаблоны и примеры:** функция `ab_test_agents` (стр. 108‑109).  
- **Ошибки и предупреждения:** не тестировать только на happy‑path — это даст ложные положительные результаты (стр. 108).  
- **Где пригодится:** для запросов «запусти A/B тест мне с 3‑мя runs_per_case».  

### 10.6 Философия «Eval is the product» (стр. 109‑111)  
- **Главная мысль:** Оценочный набор — не вспомогательный, а ключевой артефакт продукта; каждый баг превращается в тест.  
- **Как делать:**  
  1. **Principle 1** — каждый баг → тест в regression‑suite (стр. 109).  
  2. **Principle 2** — деплой только после pass‑rate полного набора (стр. 109).  
  3. **Principle 3** — постоянное расширение и калибровка scoring (стр. 109).  
- **Правила и числа:** без окончательного pass‑rate деплой невозможен (стр. 109).  
- **Шаблоны и примеры:** пример Eval‑driven development (стр. 110).  
- **Ошибки и предупреждения:** нельзя откладывать eval на конец проекта (стр. 110).  
- **Где пригодится:** для построения CI/CD‑пайплайна с gate по eval.  

### 10.7 REFINE‑framework (стр. 111‑112)  
- **Главная мысль:** Пошаговый цикл Record → Extract → Formalize → Iterate → Normalize → Expand позволяет постоянно улучшать eval‑suite.  
- **Как делать:**  
  1. **Record** — логировать входы, выводы, траектории, латентность, стоимость.  
  2. **Extract** — кластераизировать ошибки, выделить 5 наиболее частых.  
  3. **Formalize** — превратить каждую ошибку в тестовый кейс.  
  4. **Iterate** — обновлять агента, проверять A/B‑тестом.  
  5. **Normalize** — отслеживать тенденции pass‑rate, latency, cost, ставить alerts.  
  6. **Expand** — добавлять ~10 новых кейсов неделю. (стр. 111‑112)  
- **Правила и числа:** 10 новых test‑cases в неделю (стр. 112).  
- **Шаблоны и примеры:** структурированный пример REFINE в текстe (стр. 111).  
- **Ошибки и предупреждения:** не пропускать record шаг – недостоверные данные.  
- **Где пригодится:** для генерации запросов «как добавить 10 new test‑cases в REFINE».  

### 10.8 Шаблоны eval для типовых агентов (стр. 112‑113)  
- **Главная мысль:** Для разных типов агентов (coding, research, data‑analysis) нужны свои scoring и test‑patterns.  
- **Как делать:**  
  - **Код‑агент:** запускать **pytest**, измерять pass‑rate (стр. 112).  
  - **Исследовательский агент:** проверять факт‑поддержку через LLM‑judge (стр. 113).  
- **Шаблоны и примеры:** `code_agent_eval` (стр. 112), `research_agent_eval` (стр. 113).  
- **Ошибки и предупреждения:** не использовать exact‑match для многофайловой реализации (стр. 101).  
- **Где пригодится:** для быстрого создания eval‑cases по типу агента.  

### 10.9 Измерение надёжности агента (стр. 113‑114)  
- **Главная мысль:** Pass‑rate не является единственной метрикой; важно разбирать категории ошибок и их опасность.  
- **Как делать:** При pass‑rate = 92 % проверить:  
  1. Категории 8 % ошибок (стр. 114).  
  2. Опасность фэйлов (грубый hallucination vs «не найдено»).  
  3. Распределение корневых причин.  
  4. Сравнение человеческой baseline.  
- **Правила и числа:** happy‑path pass > 95 %, нет dangerous failure modes (стр. 114).  
- **Шаблоны и примеры:** пример Strong Answer (стр. 114).  
- **Ошибки и предупреждения:** не принимать 92 % как «готово к продакшну» без анализа (стр. 114).  
- **Где пригодится:** для запросов «разбить 92% pass‑rate по категориям».

### 10.13 Сильные и слабые ответы (walkthrough) (стр. 122‑123)

### 11.2 Сравнение платформ трассировки (стр. 126‑128)

  - Braintrust — per‑trace pricing.

  - OpenTelemetry — free standard, backend varies. (стр. 126‑128).  
- **Ошибки и предупреждения:** не использовать две platform одновременно (стр. 126).

### 11.3 Внедрение продакшн‑trace (стр. 129‑133)  
- **Главная мысль:** Предоставлен **AgentTracer** — библиотека для создания вложенных **spans**, сборки **trace** и отправки в любой бекенд.  
- **Как делать:**  
  1. Создать `AgentTracer(backend=…)`.  
  2. Обернуть весь запрос контекстом `with tracer.trace(name, metadata)`.  
  3. Внутри – `with tracer.span(name, **attributes)` для LLM‑calls, tool‑calls и т.п. (стр. 129‑131).  
  4. При исключении span получает status "error" и event «exception».  
- **Правила и числа:** Cycle‑detection threshold = 3 повторяющихся (tool, args) (стр. 135).  
- **Шаблоны и примеры:** пример ReAct‑agent с тремя spans (стр. 131).  
- **Ошибки и предупреждения:** не передавать неструктурированные print‑выводы; их нельзя эффективно искать.  
- **Где пригодится:** для запуска `tracer.trace("my_run")` и получения JSON‑отчётов.  

### 11.4 Анализатор паттернов‑сбоев (стр. 130‑133)  
- **Главная мысль:** `FailurePatternAnalyzer` автоматически генерирует **alerts** по 5 основным типам: циклы, избыточные steps, спайки cost, доминирование tool, цепочки ошибок.  
- **Как делать:**  
  1. Инициализировать `FailurePatternAnalyzer(thresholds={…})`.  
  2. Вызывать `analyze(trace)` → список Alert.  
- **Правила и числа (стр. 130‑132):**  
  - max_steps = 20 (стр. 130).  
  - budget_warning_pct = 0.8 (стр. 130).  
  - quality_drop_pct = 0.7 (стр. 130).  
  - tool_dominance_pct = 0.6 (стр. 130).  
  - cycle_min_length = 3 (стр. 130).  
  - error_rate_warning = 0.1 (стр. 130).  
- **Шаблоны и примеры:** класс `Alert` и пример типа `budget_warning` (стр. 131‑132).  
- **Ошибки и предупреждения:** не игнорировать молчаливые циклы – они затрачивают ресурсы.  
- **Где пригодится:** запрос «создать alert при budget > 0.8 budget».  

### 11.5 Ключевые метрики (стр. 133‑134)  
- **Главная мысль:** Описан набор **Metric → Что сообщает → Триггер → Виджет** (Steps per run, Cost per run, Success rate, Tool error rate, Latency P95, Token utilization, Cycle detection, Human escalation).  
- **Правила и числа:**  
  - Steps P95 > 2 × baseline → alert.  
  - Cost P95 > 0.8 × budget → alert.  
  - Success rate drop > 10 % → alert.  
  - Tool error rate > 10 % → critical alert.  
  - Latency P95 > 3 × median → alert. (стр. 133‑134).  
- **Ошибки и предупреждения:** полагаться только на logs — нельзя построить trace и metric вместе (стр. 133).  
- **Где пригодится:** для построения дашборда «Среднее latency P95».  

### 11.6 Воспроизведение (Replay) трасс (стр. 134‑135)  
- **Главная мысль:** **LoopReplayer** позволяет точно воспроизвести продакшн‑trace в режимах recorded, live, hybrid и выявлять divergences.  
- **Как делать:**  
  1. Инициализировать `LoopReplayer(trace_data, mock_mode="recorded")`.  
  2. Вызывать `replay(agent)`.  
  3. Анализировать `divergences` (LLM‑divergence, tool‑divergence).  
- **Правила и числа:** divergence rate = len(divergences) / len(spans) (стр. 135).  
- **Шаблоны и примеры:** фрагмент `LoopReplayer` (стр. 134‑135).  
- **Ошибки и предупреждения:** не устанавливать cycle‑threshold меньше 3 (стр. 135).  
- **Где пригодится:** для создания запроса «перезапустить trace ID 1234 в live‑mode».  

### 11.7 Сценарий «дизайн observability‑stack» (стр. 136‑138)  
- **Главная мысль:** Пример сильного ответа — трёхслойный стек: (1) structured tracing (Langfuse), (2) metrics (Prometheus + Grafana), (3) alerts (PagerDuty + Slack).  
- **Как делать:** (см. сильный ответ):  
  1. Инструмент tracing — Langfuse (самохост).  
  2. Экспорт метрик → Prometheus, визуализация в Grafana (7‑дневные базовые линии).  
  3. Alerts → PagerDuty (critical), Slack (warnings).  
  4. Хранить traces 90 дн., авто‑генерировать eval‑datasets неделя.  
- **Правила и числа:** не более одной tracing‑platform (стр. 136).  
- **Ошибки и предупреждения:** просто print‑statements не подходят (стр. 136).  
- **Где пригодится:** для запроса «список метрик для observability‑stack».  

### 11.8 Сценарий «отладка падения success‑rate» (стр. 139‑140)  
- **Главная мысль:** Приведен **5‑шаговый протокол диагностики** : проверка результата, поиск точки расхождения, классификация причины, поиск схожих падений, рекомендация исправления.  
- **Как делать:**  
  1. `_check_outcome(trace)`.  
  2. `_find_divergence(trace)`.  
  3. `_classify_cause(trace, divergence)`.  
  4. `_find_similar_failures(root_cause, days=7)`.  
  5. `_recommend_fix(root_cause, similar_failures)`. (стр. 139‑140).  
- **Ошибки и предупреждения:** не начинать с ручного тестирования без сегментации (стр. 139).  
- **Где пригодится:** для создания runbook по “success‑rate drop”.  

### 11.9 Дашборд и пороги алертов (стр. 140‑141)  
- **Главная мысль:** Описаны конкретные **thresholds** для warning и critical по 8 ключевым метрикам (Success rate, P95 latency, Cost per run, Error rate, Action cycles, Budget exhaustion).  
- **Правила и числа (стр. 140‑141):**  
  - Success rate < 93 % → warning; < 85 % → critical.  
  - P95 latency > 10 s → warning; > 30 s → critical.  
  - Cost per run > 2× baseline → warning; > 5× baseline → critical.  
  - Error rate (tools) > 3 % → warning; > 10 % → critical.  
  - Action cycles ≥ 1 / hour → warning; ≥ 5 / hour → critical.  
  - Budget exhaustion > 80 % daily → warning; > 95 % → critical.  
- **Шаблоны и примеры:** таблица Alert Threshold (стр. 140).  
- **Ошибки и предупреждения:** не превышать P95 latency без анализа циклов (стр. 140).  
- **Где пригодится:** для настройки Grafana‑alerts по cost и latency.  

### 11.10 Упражнения по observability (стр. 141‑142)  
- **Главная мысль:** Практические задачи: реализовать AgentTracer, построить дашборд, расширить FailurePatternAnalyzer, создать replay‑system, настроить alerts, написать incident‑playbook, сравнить платформы.  
- **Как делать:** См. список 1‑7 в тексте (стр. 141).  
- **Где пригодится:** для планирования спринта по observability.
