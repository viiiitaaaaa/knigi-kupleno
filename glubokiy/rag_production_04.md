# Конспект: Основы и масштабирование RAG (стр. 76–98)

## Алгоритмы ANN и векторный поиск (стр. 76–78)
- **Главная мысль**: Для ускорения поиска в огромных базах данных вместо полного перебора (Brute Force/ENN) используют приближенный поиск ближайших соседей (ANN), который находит «достаточно близкий» вектор за доли секунды.
- **HNSW (Hierarchical Navigable Small World)** — основной алгоритм ANN:
    - **Как работает**: Создает многослойную структуру графа. Верхние слои — «грубые» (мало векторов, быстрые прыжки по данным), нижние — «детальные» (много векторов, точная настройка).
    - **Аналогия с поиском города**: 
        1. Слой 1: Выбор между Нью-Йорком и Лос-Анджелесом.
        2. Слой 2: Поиск по крупным городам Запада США.
        3. Слой 3: Поиск по городам залива (Бэй Эриа).
        4. Слой 4: Поиск по конкретным пригородам.
- **Правила и числа**: 
    - HNSW может вернуть не абсолютно ближайший вектор, а очень близкий к нему (цена за скорость) (стр. 77).
    - Популярная библиотека для реализации — FAISS от Meta (стр. 77).
- **Где нам пригодится**: Для настройки быстрого поиска по большой базе знаний/документов.

## Векторные базы данных (стр. 77–79)
- **Главная мысль**: Векторная БД — это не просто поиск векторов, а полноценная система с хранением, обновлением, удалением и фильтрацией метаданных.
- **Метаданные и фильтрация**:
    - **Метаданные** — это обычные поля (ID, дата, автор), как в SQL.
    - **Пре-фильтрация**: Сначала отсечь данные по метаданным (например, «только отчеты за 2023 год»), а затем делать дорогой векторный поиск. Это быстрее и качественнее (стр. 78).
- **Важные параметры**:
    - **Параметр $k$** (количество результатов): Слишком мало $\to$ пропустим ответ; слишком много $\to$ перегрузим контекстное окно LLM, добавим «шум» (лишнее) и увеличим стоимость/задержку (стр. 78).
    - **Размерность (Dimensions)**: Уменьшение размерности (Matryoshka Learning) ускоряет поиск, но может снизить качество. Пример: `pgvector` поддерживает до 2000 измерений для 32-битных float (стр. 78).
- **Где нам пригодится**: Для выбора БД и настройки фильтров (например, поиск только по конкретным папкам или датам).

## Практика с pgvector (стр. 79–81)
- **Главная мысль**: Пример интеграции векторного поиска в PostgreSQL через расширение `pgvector`.
- **Процесс реализации**:
    1. Создать эмбеддинги (например, модель `all-MiniLM-L6-v2`, размерность 384).
    2. Создать таблицу в PG с типом данных `VECTOR(384)`.
    3. Создать индекс `HNSW` для ускорения поиска (параметры в примере: $m=16, ef\_construction=64$) (стр. 79).
    4. Загрузить данные (конвертируя массивы NumPy в списки float).
    5. Выполнить поиск, используя оператор `<=>` (косинусное расстояние).
- **Ошибки и предупреждения**: В `pgvector` оператор `<=>` измеряет *диссимилярность* (различие). Чтобы получить *схожесть*, нужно использовать формулу `1 - (embedding <=> query_vector)` (стр. 81).
- **Где нам пригодится**: Для написания скриптов хранения данных в SQL.

## Генеративные LLM в RAG (стр. 81–84)
- **Главная мысль**: Финальный этап RAG — передача найденных текстовых кусков (не векторов!) и запроса пользователя в LLM для генерации ответа.
- **Оптимизация вывода (Inference)**:
    - **Квантование (Quantization)**: Снижение точности весов модели (с float32 до int8 или int4) для ускорения и экономии памяти (стр. 82).
    - **FlashAttention**: Эффективное использование памяти при вычислении внимания (стр. 82).
    - **Фреймворки**: vLLM, Ollama (стр. 82).
- **Выбор модели**:
    - Баланс «Скорость $\leftrightarrow$ Качество». Для простых задач маленькая модель часто не уступает большой.
    - Приватность: Если данные секретны, нужны open-source модели (напр., $>70$ млрд параметров) на своих серверах (стр. 83).
- **Где нам пригодится**: Для выбора между платным API (Claude/GPT) и локальным запуском (Ollama).

## Промпт-инжиниринг для RAG (стр. 83–85)
- **Главная мысль**: Правильная структура промпта помогает LLM лучше использовать найденный контекст и меньше галлюцинировать.
- **Рекомендации по шаблонам**:
    - **Порядок**: Лучше ставить запрос *перед* контекстом (стр. 83).
    - **Разметка**: Использовать XML-теги (напр., `<context>...</context>`) для разделения частей промпта (стр. 84).
    - **Борьба с галлюцинациями**: Добавлять инструкцию: «Если ответа нет в контексте, просто скажи "Я не знаю"» (стр. 84).
    - **Рассуждения**: Для сложных задач добавлять Chain-of-Thought (CoT): «Думай пошагово» (стр. 84).
- **Где нам пригодится**: Для создания системных промптов агентов.

## Оценка (Evaluation) RAG (стр. 84–87)
- **Главная мысль**: Чтобы выбрать лучшую модель/промпт, нужно измерить качество ответов на тестовом наборе запросов.
- **Критерии оценки**:
    - **Relevance (Релевантность)**: Отвечает ли ответ на вопрос?
    - **Faithfulness (Верность)**: Подтверждается ли ответ найденными документами?
- **Методы оценки**:
    1. **LLM-as-a-judge**: Использование сильной LLM для оценки слабой. Минусы: дорого, может галлюцинировать, нестабильно (стр. 85).
    2. **NLG-модели**: Специальные маленькие модели (напр., HHEM, Luna). Быстрее и дешевле (стр. 85).
    3. **Человек (Golden Standard)**: Самый точный, но самый дорогой и медленный метод (стр. 85).
- **Где нам пригодится**: Для проверки качества ответов своего бота перед запуском.

## Масштабирование RAG (стр. 89–92)
- **Главная мысль**: Переход от 10 документов к миллионам создает проблемы с задержкой (latency), стоимостью и точностью.
- **Проблемы масштаба**:
    - **Точность**: При росте числа чанков в топ-$k$ попадает больше «шума». Решение: гибридный поиск и переранжирование (reranking) (стр. 90).
    - **Свежесть данных**: Полная переиндексация миллионов документов слишком дорога. Нужны инкрементальные обновления (стр. 90).
    - **Экономика токенов**:
        - Многоуровневое кэширование (ответов, эмбеддингов, чанков) (стр. 91).
        - Динамическая маршрутизация: простые запросы $\to$ дешевая модель, сложные $\to$ дорогая (стр. 92).
- **Где нам пригодится**: Для планирования бюджета и архитектуры при росте объема данных.

## Продвинутая загрузка данных (Ingestion) (стр. 92–98)
- **Главная мысль**: Загрузка миллионов документов — это сложный инженерный процесс, а не просто «скрипт на Python».
- **Как делать правильно (Scale-up)**:
    1. **Параллелизация**: Использовать Ray, Dask или Spark для распределенной генерации эмбеддингов на нескольких GPU (стр. 94).
    2. **Оркестрация**: Использовать Apache Airflow для управления цепочкой задач (чанкинг $\to$ эмбеддинги $\to$ запись в БД). Это позволяет перезапускать упавшие задачи, а не весь процесс (стр. 94).
    3. **Принципы**: 
        - *Идемпотентность*: возможность повторного запуска задачи без дублирования данных (стр. 95).
        - *Глубокая наблюдаемость*: мониторинг зависших или отброшенных документов (стр. 95).
- **Работа с «грязными» данными**:
    - Проблемы: Ошибки OCR (замена 0 на O), шаблонный текст (футеры/хедеры), неверная кодировка (UTF-8 vs ISO) (стр. 96).
    - Решение: Многоэтапная очистка (триаж $\to$ маршрутизация $\to$ очистка) (стр. 96).
- **Огромные документы (тысячи страниц)**:
    - Ошибка: Загрузка всего файла в память $\to$ OOM (Out-of-Memory crash) (стр. 97).
    - Решение: Потоковая обработка (page-by-page) или разделение файла на диапазоны страниц для разных воркеров (стр. 97).
- **Где нам пригодится**: Для обработки очень больших PDF-файлов и автоматизации обновления базы знаний.
