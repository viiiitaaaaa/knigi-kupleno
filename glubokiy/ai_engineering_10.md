## 1. Привязка метрик оценки к бизнес‑метрикам (стр. 399‑400)  

- **Главная мысль** – Оценочные метрики модели (например, factual consistency) должны быть сопоставлены с тем, как они влияют на бизнес‑показатели (автоматизация запросов, доход, удержание).  
- **Как делать**  
  1. Выберите бизнес‑метрику, которую хотите улучшить (автоматизация запросов, DAU, MAU, удержание и т.п.).  
  2. Оцените текущий уровень выбранной технической метрики (например, factual consistency = 80 %).  
  3. Сопоставьте её с бизнес‑показателем (например, 80 % → автоматизируем 30 % запросов).  
  4. Повторите для нескольких уровней метрики, построив «таблицу эффекта».  
  5. Определите **порог полезности** –‑ минимальный уровень метрики, при котором приложение всё‑равно удобно (пример : factual consistency ≥ 50 %).  
- **Правила и числа**  
  - Пример сопоставления (стр. 399):  
    *80 % → 30 % автоматизации, 90 % → 50 %, 98 % → 90 %.*  
  - Порог полезности в примере : фактическая согласованность ≥ 50 % (стр. 400).  
- **Шаблоны / примеры** – Таблица вида:  

  | Фактическая согласованность | Автоматизируется запросов |
  |-----------------------------|---------------------------|
  | 80 %                        | 30 %                      |
  | 90 %                        | 50 %                      |
  | 98 %                        | 90 %                      |

- **Ошибки / предупреждения**  
  - Не привязывать оценку к «stickiness‑метрикам» (DAU/MAU), не учитывая риски «зависимости‑от‑добавления‑контента».  
  - Игнорировать порог полезности → продукт будет непригоден даже при «хороших» цифрах.  
- **Где пригодится** – При построении бизнес‑кейса и ROI‑модели для AI‑приложения (расчёт экономической выгоды от улучшения метрик).

## 3. Выбор методов оценки (стр. 401‑402)  

- **Главная мысль** – Разные критерии требуют разных методов (классификатор, семантическое сходство, AI‑судья). Можно комбинировать дешёвый и дорогой метод для разных частей данных.  
- **Как делать**  
  1. Для каждого критерия определите подходящий **специализированный метод** (напр., токсичность → классификатор, релевантность → семантическое сходство, factual consistency → AI‑judge).  
  2. При необходимости **смесь**: дешёвый классификатор на 100 % данных + дорогой AI‑judge на 1 % (чтобы контролировать стоимость).  
  3. Если доступны **log‑probabilities** (logprobs), используйте их:  
     - Оцените уверенность модели (пример : 30‑40 % → низкая уверенность, 95 % → высокая).  
     - Вычисляйте **perplexity** → метрика плавности и фактической согласованности.  
- **Правила и числа** – Нет фиксированных цифр, но пример сочетания: 1 % дорогой AI‑judge (стр. 401).  
- **Шаблоны / примеры** – Кратко:  

  ```
  Критерий      | Метод
  -------------|----------------------------
  Токсичность  | Малый специализированный классификатор
  Релевантность| Семантическое сходство
  Факт. соглас.| AI‑judge (дорогой)
  ```

- **Ошибки / предупреждения**  
  - Не использовать только автоматические метрики, если они дают неоднозначные сигналы — нужна Human Evaluation.  
  - Пренебрегать logprobs, когда они есть (стр. 401).  

- **Где пригодится** – При построении **pipeline** оценки качества моделей (выбор скоров и стоимости).

## 4. Автоматические и человеческие оценки, аннотирование (стр. 402‑403)  

- **Главная мысль** – Используйте автоматические метрики максимум, но в случае открытых ответов **не бойтесь** привлекать людей, даже в продакшене.  
- **Как делать**  
  1. Запустите автоматические метрики (классификаторы, лог‑пробы, perplexity).  
  2. Периодически (например, до 500 выборок в день) привлекайте **human experts** для оценки (пример : LinkedIn – 500 разговоров в день).  
  3. В продакшене готовьте **reference‑data** для экспериментов, но в реальном времени полагайтесь на **feedback пользователей** (раздел «User feedback», глава 10).  
  4. **Аннотируйте** наборы данных: используйте реальные продакшен‑данные, если есть «естественные метки», иначе – человек/AI‑генерация (см. глава 8).  
- **Правила и числа** – Пример: до 500 человеко‑оценок в день (стр. 402).  
- **Шаблоны / примеры** – Процесс «human‑in‑the‑loop» как в LinkedIn.  

- **Ошибки / предупреждения**  
  - Слишком полагаться на автоматику, игнорируя субъективный человеческий фактор.  
  - Не использовать только продакшен‑данные без аннотации – трудно измерить качество.  

- **Где пригодится** – При построении **систем мониторинга качества** в продакшене, где нужны быстрые сигналы о деградации.

## 5. Срезы (slicing) данных и парадокс Симпсона (стр. 403‑405)  

- **Главная мысль** – Делите данные на **срезы** (по пользователям, типу трафика, длине, темам) — это позволяет обнаружить предвзятость, отладить ошибки и избежать ошибки Симпсона.  
- **Как делать**  
  1. Определите **ключевые атрибуты** для срезов (тип пользователя, источник трафика, длина ввода, наличие опечаток, out‑of‑scope запросы).  
  2. Создайте **отдельные наборы** для каждого среза.  
  3. Оцените метрики **по каждому срезу** отдельно.  
  4. Проверяйте **Симпсонов парадокс**: модель может показывать лучшую агрегированную метрику, но хуже на всех подгруппах. Пример таблицы 4‑6 (стр. 404).  
- **Правила и числа** – Пример из таблицы 4‑6 (стр. 404):  

  |          | Группа 1 | Группа 2 | Итого |
  |----------|----------|----------|-------|
  | Model A  | 93 %     | 73 %     | 78 % |
  | Model B  | 87 %     | 69 %     | 83 % |

  → Model A лучше в каждой группе, но хуже в сумме.  

- **Шаблоны / примеры** – Срезы: **платные vs бесплатные**, **мобильный vs веб**, **с опечатками**, **out‑of‑scope**.  

- **Ошибки / предупреждения**  
  - Оценивать модель только на **один** общий набор – упускаете проблемы в подгруппах.  
  - Игнорировать **малые, но важные** срезы (например, нарушения у меньшинств).  

- **Где пригодится** – При построении **fairness‑оценки** и **debug‑pipeline** (разбор плохих кейсов).

## 6. Размер выборки и бутстреп (стр. 405‑406)  

- **Главная мысль** – Оценочный набор должен быть **достаточно большим**, чтобы результаты были надёжными; используйте **бутстреп** для проверки стабильности.  
- **Как делать**  
  1. Сформируйте оценочный набор (например, 100 примеров).  
  2. **Бутстреп**:  
     - Шаг 1: Смешайте 100 примеров с возвратом.  
     - Шаг 2: Оцените модель на полученной бутстреп‑выборке.  
     - Повторите N раз (N ≈ 30‑100).  
  3. Сравните полученные оценки: если разброс большой → нужен больший набор.  
- **Правила и числа** – Пример из текста:  
  - 30 % различия → ~10 примеров (стр. 406, таблица 4‑7).  
  - 10 % различия → ~100 примеров.  
  - 3 % различия → ~1 000 примеров.  
  - 1 % различия → ~10 000 примеров.  

- **Шаблоны / примеры** – Таблица 4‑7 (стр. 406) – оценка нужного количества примеров в зависимости от желаемой разницы.  

- **Ошибки / предупреждения**  
  - Считать, что 100‑200 примеров всегда достаточно – может быть ошибкой, если бутстреп показывает высокий дисперс.  
  - Не учитывать **размер эффекта** (разница в процентах) при планировании.  

- **Где пригодится** – При планировании **A/B‑тестов** и **statistical significance** в продакшене.

## 7. Оценка качества самой оценочной пайплайны (стр. 407‑409)  

- **Главная мысль** – Оценочную систему тоже нужно проверять: достаёт ли она **правильные сигналы**, насколько **надёжна**, как **коррелируют** её метрики, и сколько **стоимости/задержки** она добавляет.  
- **Как делать**  
  1. **Валидация сигналов**: проверяйте, что более качественные ответы действительно получают более высокие скоры.  
  2. **Надёжность**: дважды запустите пайплайн – сравните результаты; измерьте дисперсию при разных наборах.  
  3. **Корреляция метрик**: если две метрики полностью коррелируют → одну можно убрать; если нет корреляции → либо интересный инсайт, либо ошибка.  
  4. **Стоимость/латентность**: оцените, сколько времени и денег добавляет каждая часть пайплайна; избегайте излишних вычислений.  
  5. **Итерация**: при изменении критериев, рубрик, примеров фиксируйте **все переменные** (данные, рубрика, prompt, параметры sampling).  
- **Правила и числа** – Нет конкретных цифр, но рекомендуется **фиксировать** все переменные (стр. 409).  

- **Шаблоны / примеры** – Вопросы для само‑оценки:  

  ```
  - Даёт ли пайплайн более высокие скоры лучшим ответам?
  - Какой разброс результатов при повторных запусках?
  - Насколько коррелируют метрика A и метрика B?
  - Каковы дополнительные затраты (USD, latency)?
  ```

- **Ошибки / предупреждения**  
  - Слишком часто менять пайплайн → потеря возможности сравнивать результаты.  
  - Не фиксировать изменения → невозможность отследить, что именно повлияло.  

- **Где пригодится** – При **мониторинге** качества модели в продакшене и планировании **ресурсов**.

## 9. Введение в Prompt Engineering (стр. 416‑418)  

- **Главная мысль** – Prompt‑инженерия — это способ «настроить» модель без изменения её весов; это первая, самая лёгкая, но часто недооценённая техника адаптации.  
- **Как делать** (ключевые идеи)  
  1. Понимайте, что **промпт = инструкция** модели (запрос, роль, формат вывода).  
  2. Выделяйте основные части промпта: **task description**, **examples**, **конкретная задача**.  
  3. Проводите эксперименты так же, как любые ML‑эксперименты: фиксируйте параметры, используйте **experiment tracking**.  

- **Правила и числа** – Нет конкретных цифр, но подчёркивается необходимость **rigorous experimentation** (стр. 417).  

- **Шаблоны / примеры** – Пример простого NER‑промпта (рис. 5‑1, стр. 418).  

- **Ошибки / предупреждения**  
  - Считать, что «промпт‑инженерия – это только трепыхание словами». Нужно систематическое тестирование.  

- **Где пригодится** – На этапе **быстрого прототипирования** и **первичной адаптации** модели к задаче.

## 10. Структура промпта (стр. 418‑422)  

- **Главная мысль** – Промпт состоит из **task description**, **примеров**, **конкретного задания**; модель должна уметь **следовать инструкциям**; её **robustness** (устойчивость к небольшим изменениям) зависит от качества промпта и силы модели.  
- **Как делать**  
  1. Сформулируйте **task description** (что модель должна делать, в какой роли).  
  2. При необходимости добавьте **пример(ы)** (покажите желаемый формат).  
  3. Укажите **конкретный запрос** (вопрос, задача).  
  4. Оцените **robustness**: слегка измените промпт (замените «5» на «five», поменяйте регистр, добавьте/удалите строку) и проверьте, насколько меняется ответ.  
- **Правила и числа** – Чем сильнее модель, тем **меньше её чувствительность** к таким изменениям (стр. 419).  

- **Шаблоны / примеры** –  

  ```
  Task description: classify the sentiment of the following sentence.
  Example: "I love this product!" → Positive
  Sentence: "The delivery was late."
  ```

- **Ошибки / предупреждения**  
  - Не проверять **robustness** → модель может резко менять ответы при мелкой правке.  

- **Где пригодится** – При построении **надёжных запросов** к LLM, особенно в продакшене.

## 11. In‑Context Learning: Zero‑Shot и Few‑Shot (стр. 420‑422)  

- **Главная мысль** – Модели могут учиться *в контексте* (из примеров в промпте) без изменения весов; **zero‑shot** — без примеров, **few‑shot** — с несколькими примерами (shots). Чем больше примеров, тем лучше, но ограничивает **context length** и повышает **стоимость**.  
- **Как делать**  
  1. Определите, сколько **shots** (примеров) разумно для вашей модели и задачи.  
  2. Включите их в промпт, соблюдая лимит контекста.  
  3. Тестируйте, сравнивая zero‑shot ↔ few‑shot (напр., 5‑shot).  
- **Правила и числа** – Для GPT‑3 few‑shot дал значительный прирост; для GPT‑4 и некоторых моделей в 2023 году улучшение было небольшим (стр. 421).  

- **Шаблоны / примеры** –  

  ```
  # Zero‑shot
  Question: What is the capital of France?

  # 3‑shot
  Q: 2+2? A: 4
  Q: Capital of Italy? A: Rome
  Q: What is the capital of France? A:
  ```

- **Ошибки / предупреждения**  
  - Переполнять контекст, добавляя слишком много примеров → рост затрат и падение производительности.  

- **Где пригодится** – При **конструировании промптов** для новых задач, где отсутствуют метки для обучения.

## 12. Терминологическая неоднозначность: Prompt vs Context (стр. 422‑423)  

- **Главная мысль** – В литературе «prompt» и «context» иногда используют как синонимы, но в этой книге **prompt** = полный ввод модели, а **context** = информация, необходимая модели для выполнения задачи (например, извлечённые документы).  

- **Как делать** – При общении с API:  
  1. Понимайте, что всё, что вы отправляете, — это **prompt**.  
  2. **Context** – часть prompt, содержащая вспомогательные данные (документы, справки).  

- **Ошибки / предупреждения** – Путать термины может привести к неверному дизайну API‑запросов.  

- **Где пригодится** – При работе с разными провайдерами (OpenAI, Google, Anthropic) и их документацией.

## 13. System Prompt и User Prompt (стр. 423‑425)  

- **Главная мысль** – Многие API позволяют разделить ввод на **system prompt** (описание роли/задания) и **user prompt** (сам запрос пользователя). Это улучшает контроль над поведением модели.  
- **Как делать**  
  1. **System Prompt** — описывает роль модели, правила поведения, формат вывода.  
  2. **User Prompt** — содержит конкретный пользовательский запрос и любые дополнительные контексты (например, загруженный документ).  
  3. Объедините их в **один** ввод согласно **chat‑template** конкретной модели (пример Llama 2 в стр. 425).  

- **Пример (стр. 424‑425)**  

  ```
  System prompt:
  You are an experienced real‑estate agent. Read the disclosure, assess the property, answer succinctly.

  User prompt:
  Context: [disclosure.pdf]
  Question: Summarize the noise complaints, if any.
  ```

- **Шаблоны / примеры** – Llama 2 chat template (стр. 425):

  ```
  <s>[INST] <<SYS>>
  {system_prompt}
  <</SYS>>
  {user_message} [/INST]
  ```

- **Ошибки / предупреждения**  
  - Неправильный **chat‑template** (см. ниже) → падение качества.  

- **Где пригодится** – При построении **чат‑ботов**, где требуется стабильная «личность» модели.

## 14. Шаблоны чата моделей vs пользовательские шаблоны (стр. 426‑428)  

- **Главная мысль** – **Chat template** (определяется разработчиком модели) – это обязательный синтаксис, позволяющий модели различать system‑ и user‑сообщения. **Prompt template** (создаётся вами) – просто способ «наполнить» данные. Ошибки в шаблоне могут вести к **тихим сбоям**.  

- **Как делать**  
  1. **Изучите документацию модели** – найдите её chat‑template (например, Llama 3 использует токены `<|begin_of_text|>`, `<|start_header_id|>`, …).  
  2. При генерации запросов **строго соблюдайте** этот шаблон (например, не добавить лишний перенос строки).  
  3. **Проверяйте** финальный сформированный запрос перед отправкой (стр. 427).  

- **Шаблоны / примеры** – Llama 3 chat template (стр. 426):  

  ```
  <|begin_of_text|>
  <|start_header_id|>system<|end_header_id|>
  {system_prompt}<|eot_id|>
  <|start_header_id|>user<|end_header_id|>
  {user_message}<|eot_id|>
  <|start_header_id|>assistant<|end_header_id|>
  ```

- **Ошибки / предупреждения**  
  - Ошибки в шаблоне **не бросают исключения**, а только ухудшают ответы.  
  - Перепутать **chat‑template** и **prompt‑template** → неверные токены, ухудшение качества.  

- **Где пригодится** – При интеграции **разных моделей** (Llama 2, Llama 3, Claude) в одно приложение.

---

## 15. Почему system prompt может улучшать качество (стр. 428‑429)  

- **Главная мысль** – System prompt обычно поставлен **первым**, а модели лучше воспринимают инструкции в начале; также многие модели **пост‑тренируются**, чтобы уделять больше внимания system‑prompt (см. Wallace et al., 2024).  

- **Как делать**  
  1. При возможности **расположите** задачу/правила в system prompt.  
  2. При тестировании пробуйте менять порядок (system‑first vs user‑first) – оцените влияние.  

- **Ошибки / предупреждения**  
  - Не рассчитывать, что system prompt → 100 % улучшение; эффект может быть ограничен.  

- **Где пригодится** – При **защите от prompt‑атак** и при построении **стабильных диалогов**.

---

## 16. Длина контекста и её эффективность (стр. 428‑430)  

- **Главная мысль** – Современные модели поддерживают **очень большие контексты** (до 2 M токенов). Но не вся информация в промпте «равнозначна» – начало и конец работают лучше, середина хуже.  

- **Как делать**  
  1. Оцените **максимальный контекст** модели (GPT‑2 = 1K, GPT‑4 ≈ 8K‑32K, Gemini‑1.5 ≈ 2M).  
  2. При построении длинных запросов **распределяйте важную информацию** ближе к началу и/или концу.  
  3. Тестируйте с помощью **Needle‑in‑a‑Haystack (NIAH)**: вставьте «иголку» в разные позиции и измерьте успешность поиска (стр. 429‑430).  

- **Шаблоны / примеры** – NIAH‑тест:  

  ```
  Prompt: ... <random needle> ... (в начале, середине, в конце)
  Question: Find the needle.
  ```

- **Ошибки / предупреждения**  
  - Плотно заполнять **середину** без контроля – модель может её игнорировать.  
  - Переполнять контекст → удорожание и рост латентности.  

- **Где пригодится** – При работе с **длинными документами** (юридические тексты, коды), когда важно сохранить релевантность.

---

## 17. Лучшие практики создания промптов (стр. 432‑440)  

### 17.1 Писать **чёткие, однозначные** инструкции (стр. 432‑433)  
- **Шаги**  
  1. Определите **что** модель должна сделать (например, «оценить эссе по шкале 1‑5»).  
  2. Укажите **формат вывода** (число, JSON, «без предисловий»).  
  3. При необходимости добавьте **ограничения** (например, «только целые числа»).  

- **Пример** – Таблица 5‑1: без примера → «Santa …», с примером → нужный стиль ответа.  

### 17.2 Использовать **персону** (стр. 433‑434)  
- Добавьте к system prompt роли/личности (например, «ты учитель первого класса»), чтобы влиять на тон и критерии оценки.  

### 17.3 Приводить **примеры** (стр. 434‑436)  
- Пример формата:  

  ```
  Q: Is the tooth fairy real?
  A: Of course! … 
  Q: Will Santa bring me presents?
  A: …
  ```

- При ограничении токенов выбирайте **короткие** примеры (стр. 437).  

### 17.4 Указывать **формат вывода** и использовать **маркеры** (стр. 438‑440)  
- Пример: «Output JSON with keys `score` и `reason`».  
- Для структурированных задач ставьте маркер конца входа (например, `---`).  

- **Ошибки / предупреждения**  
  - Пропуск маркера → модель продолжает генерировать ввод (таблица 5‑3).  
  - Не указывать ограничения → модель пишет лишние предисловия, удорожает запрос.  

- **Где пригодится** – При **интеграции** модели в автоматизированные пайплайны, где требуется строгий формат (парсинг, базы данных, API‑ответы).

---

## 18. Обеспечение достаточного контекста (стр. 440)  

- **Главная мысль** – Как у студента, модель работает лучше, если ей дать **нужный контекст** (документы, выдержки). Это снижает галлюцинации.  
- **Как делать**  
  1. Включайте в промпт все необходимые факты (текст статьи, таблицу, код).  
  2. Если контекст велик, используйте **RAG** (retrieval‑augmented generation) или веб‑поиск (см. глава 6).  

- **Ошибки / предупреждения**  
  - Отдавать модель без контекста в задачах, где нужны точные данные → повышенный риск галлюцинаций.  

- **Где пригодится** – При построении **вопрос‑ответ** систем, **анализе документов**, **поддержке клиентов**.
