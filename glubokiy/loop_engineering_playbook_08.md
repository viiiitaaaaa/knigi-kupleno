## 1. STAR‑формат для интервью (стр. 317‑317)  
- **Главная мысль** – в ответе на вопрос о сбое агента расскажите коротко по‑модели **S‑T‑A‑R** (Situation, Task, Action, Result).  
- **Как делать**  
  1. **S** — опишите, что делал агент и в каком контексте.  
  2. **T** — укажите, что именно пошло не так (тип сбоя).  
  3. **A** — расскажите, как вы обнаружили проблему (мониторинг, репорт пользователя, алерт по затратам) и какое системное исправление применили.  
  4. **R** — подведите итог: чему вы научились, как изменились процессы.  
- **Правила и числа** – в примерах указывайте:  
  * конкретный **режим сбоя** (hallucination, infinite loop, cost explosion);  
  * **метод детекции** (monitoring, user report, cost alert);  
  * **системное решение** (не только «заплатить» симптом).  
- **Шаблоны и примеры** – «*Situation: агент обрабатывал запрос клиента, Task: выдача неверных цен, Action: обнаружил галлюцинацию модели через cost‑alert и добавил проверку фактов, Result: уменьшил количество ошибок на 70 %*».  
- **Ошибки и предупреждения** – не давайте ответов‑«патчей», без указания корневой причины; слишком общие описания («проблема решена») считаются слабым.  
- **Где пригодится** – при подготовке к интервью, при документировании инцидентов в базе знаний, при обучении новых агентов (пример / проверка).

## 2. Критерии выбора — строить с нуля или использовать фреймворк (стр. 317‑317)  
- **Главная мысль** – есть чёткая матрица, когда удобно брать готовый фреймворк, а когда лучше писать свой код.  
- **Как делать**  
  1. Оцените **время**: если проект < 4 недель — можно использовать фреймворк.  
  2. Проверьте **стандартность задачи**: подходит ли она под типовые паттерны фреймворка?  
  3. Оцените **размер команды**: небольшая команда → фреймворк.  
  4. Если **необходимо >30 % обходных решений** в фреймворке → строить с нуля.  
  5. Если нужен **мелкий контроль над каждым шагом** → строить.  
  6. При **масштабе ≥ 100 K запросов/день** → своё решение.  
  7. **Всегда** оборачивайте выбранный фреймворк **абстракцией** (слой‑wrapper) для будущей миграции.  
- **Правила и числа** – сроки < 4 нед., > 30 % workarounds, ≥ 100 000 req/день.  
- **Шаблоны и примеры** – *«Мы использовали CrewAI, потому‑что проект был 3‑недельный, команда из 2 человек, задачи типовые»*.  
- **Ошибки и предупреждения** – не берите фреймворк, если планируете более 30 % кастомизации; не забудьте слой‑wrapper, иначе миграция будет дорогой.  
- **Где пригодится** – при планировании нового продукта, выборе стека для MVP, построении дорожной карты разработки.

## 3. Quick Reference — ключевые метрики (стр. 317‑317)  
- **Главная мысль** – есть набор измерений, к которым нужно стремиться, иначе агент будет «плох».  
- **Как делать** – проверяйте каждую метрику в рамках CI/CD и реального сервиса.  
- **Правила и числа**  

| Метрика | Типичное значение | Целевой показатель |
|--------|-------------------|--------------------|
| **ReAct‑шагов на задачу** | 3‑8 | 3‑5 (простые), 6‑10 (сложные) |
| **Точность вызовов инструментов** | 85‑95 % | ≥ 95 % (при хороших описаниях) |
| **Стоимость простого запроса** | $0.01‑0.05 | ≤ $0.03 (с кешированием) |
| **Стоимость сложной задачи** | $0.10‑0.50 | ≤ $0.20 (с tier‑pricing) |
| **Успешность агента** | 85‑95 % | ≥ 98 % (продакшн) |
| **Использование контекстного окна** | 40‑80 % | ≤ 70 % (на рассуждения ≤ 30 %) |
| **Размер набора оценки** | 20‑50 кейсов | ≥ 50 (полный охват) |
| **Задержка на шаг** | 2‑10 сек | ≤ 5 сек (p95) |
| **Успех при первой пере‑попытке** | 60‑80 % | ≥ 90 % (с backoff + jitter) |
| **Хит‑рейт кеша** | 10‑30 % | ≥ 25 % (агенты поддержки) |

- **Шаблоны и примеры** – *«Для простого запроса удерживаем стоимость <$0.03, используя кэш‑слой»*.  
- **Ошибки и предупреждения** – игнорировать кеширование → рост стоимости; низкая точность инструментов → плохие ответы.  
- **Где пригодится** – построение мониторинга KPI агентов, автоматическая проверка в CI, бюджетирование расходов.

## 5. Quick Reference — дерево выбора фреймворка (стр. 318‑318)  
- **Главная мысль** – последовательный набор вопросов помогает быстро решить, какой фреймворк нужен.  
- **Как делать**  
  1. **Нужна ли координация нескольких агентов?**  
     - Да → *CrewAI* (role‑based) или свой продакшн‑фреймворк.  
     - Нет → переходим к пункту 2.  
  2. **Нужна ли сложная ветвистость/машина состояний?**  
     - Да → *LangGraph*.  
     - Нет → пункт 3.  
  3. **Нужна ли простая цепочка или RAG‑pipeline?**  
     - Да → *LangChain*.  
     - Нет → пункт 4.  
  4. **Требуется максимум контроля и отладки?**  
     - Да → кастомный Python (50‑200 строк для прод‑агента).  
     - Нет → LangChain (самый низкий порог входа).  
- **Правила и числа** – нет дополнительных чисел, только булевые ответы.  
- **Шаблоны и примеры** – *«Если нужен мульти‑агентный советник → выбираем CrewAI»*.  
- **Ошибки и предупреждения** – пропустить первый вопрос и сразу взять LangChain → невозможна координация нескольких специалистов.  
- **Где пригодится** – при быстром подборе стека для нового проекта, в чек‑листах технического интервью.

## 6. Appendix G — Шаблоны типовых архитектур агентов (стр. 319‑331)

### 6.1 Template 1 — Customer Support Agent (стр. 319‑320)  
- **Главная мысль** – готовый «скелет» поддержки с KB, клиентской информацией и эскалацией.  
- **Как делать** (примерный цикл)  
  1. При запросе клиента вызывайте `search_knowledge_base`.  
  2. При необходимости получайте данные клиента через `get_customer_info`.  
  3. Если ответ insufficient → `create_ticket`.  
  4. Оцените уверенность; если < 0.7 → эскалация.  
- **Правила и числа** – `max_steps: 5`; `cost_budget: $0.05` / разговор; `escalation_threshold: 0.7`.  
- **Шаблоны и примеры** – *SYSTEM_PROMPT* и *TOOLS* списки из текста.  
- **Ошибки и предупреждения** – никогда не «выдумывайте» информацию о продуктах; всегда проверяйте KB.  
- **Где пригодится** – быстрый запуск чат‑поддержки, прототипирование Help‑Desk.

### 6.2 Template 2 — Data Analysis Agent (стр. 321‑322)  
- **Главная мысль** – агент, формирующий SQL‑запросы, объясняющий результаты и предлагающий визуализацию.  
- **Как делать**  
  1. При вопросе формируйте SQL, выводите его (`run_sql`).  
  2. Покажите схему при запросе (`get_schema`).  
  3. При необходимости генерируйте график (`create_chart`).  
- **Правила и числа** – `max_steps: 8`; `cost_budget: $0.30`; `query_timeout: 30 сек`; `max_rows: 100`.  
- **Шаблоны и примеры** – содержатся в `SYSTEM_PROMPT`, `TOOLS`, `CONFIG`.  
- **Ошибки и предупреждения** – допускается только `SELECT`; любые DML‑операции запрещены.  
- **Где пригодится** – быстрые BI‑запросы, автоматические дашборды для стартапа.

### 6.3 Template 3 — Content Generation Agent (стр. 322‑323)  
- **Главная мысль** – агент‑писатель, соблюдающий бренд‑голос, SEO и проверку на плагиат.  
- **Как делать**  
  1. Запрашивайте `search_web` для фактов.  
  2. Берите руководство бренда (`get_brand_guide`).  
  3. После генерации проверяйте `check_plagiarism`.  
  4. Оценивайте SEO через `seo_analyze`.  
- **Правила и числа** – `max_steps: 6`; `cost_budget: $0.20`; `quality_threshold: 0.85` (оценка самого агента).  
- **Шаблоны и примеры** – SYSTEM_PROMPT и список `TOOLS`.  
- **Ошибки и предупреждения** – не публикуйте контент без проверки plagiarism и SEO‑оценки.  
- **Где пригодится** – генерация блога, лендингов, email‑рассылок.

### 6.4 Template 4 — Code Review Agent (стр. 324‑325)  
- **Главная мысль** – автоматизировать ревью PR, проверяя корректность, безопасность, производительность и поддерживаемость.  
- **Как делать**  
  1. Получите дифф (`get_diff`).  
  2. При необходимости читайте файлы (`read_file`).  
  3. Ищите похожие куски в коде (`search_codebase`).  
  4. Оставляйте комментарий (`post_review_comment`) с указанием severity (CRITICAL/WARNING/STYLE).  
- **Правила и числа** – `max_steps: 10`; `cost_budget: $0.50`; `max_files_to_review: 20`.  
- **Шаблоны и примеры** – `SYSTEM_PROMPT`, `TOOLS`, `CONFIG`.  
- **Ошибки и предупреждения** – не забывайте классифицировать проблемы по severity; без этого трудно приоритизировать.  
- **Где пригодится** – в CI‑pipeline для автоматического PR‑review, быстрый фидбэк для небольших команд.

### 6.5 Template 5 — Scheduling Agent (стр. 325‑326)  
- **Главная мысль** – агент‑ассистент, умеющий планировать встречи с учётом предпочтений и тайм‑зон.  
- **Как делать**  
  1. Получите календарь (`get_calendar`).  
  2. Проверьте свободные окна (`check_availability`).  
  3. Предложите время, учитывая правила (после 12 ч, 15‑минутный буфер, не‑дублирование).  
  4. После подтверждения пользователя создайте событие (`create_event`).  
- **Правила и числа** – `max_steps: 6`; `cost_budget: $0.03`; `requires_confirmation: ["create_event"]`.  
- **Шаблоны и примеры** – `SYSTEM_PROMPT`, `TOOLS`, `CONFIG`.  
- **Ошибки и предупреждения** – никогда не создавайте событие без пользовательского подтверждения.  
- **Где пригодится** – автоматическое планирование встреч для фрилансера/консультанта.

### 6.6 Template 6 — Monitoring & Alerting Agent (стр. 326‑327)  
- **Главная мысль** – SRE‑агент, реагирующий на алерты, собирающий метрики и создающий инциденты.  
- **Как делать**  
  1. Получить детали алерта (`get_alert_details`).  
  2. Спросить метрики (`query_metrics`).  
  3. При необходимости поискать логи (`search_logs`).  
  4. Сравнить с последними деплоем (`get_recent_deployments`).  
  5. При P1/P2 сразу предлагайте смягчения; при P3‑P4 создавайте тикет (`create_incident`).  
- **Правила и числа** – `max_steps: 8`; `cost_budget: $0.40`; `requires_confirmation: ["create_incident"]`; `auto_escalate_after: 300 сек`.  
- **Шаблоны и примеры** – `SYSTEM_PROMPT`, список `TOOLS`, `CONFIG`.  
- **Ошибки и предупреждения** – **не** перезапускайте сервисы без согласования людей; если инцидент P1‑P2, действуйте мгновенно.  
- **Где пригодится** – on‑call rotation, автоматизация наблюдения за инфраструктурой.

### 6.7 Template 7 — Document Processing Agent (стр. 328‑329)  
- **Главная мысль** – извлекать, классифицировать и маршрутизировать документы (инвойсы, контракты, отчёты).  
- **Как делать**  
  1. Считать документ (`read_document`).  
  2. Классифицировать тип (`classify_document`).  
  3. Извлечь поля согласно схеме (`extract_fields`).  
  4. Валидировать извлечённые данные (`validate_extraction`).  
  5. Если уверенность < threshold → пометить `NEEDS_REVIEW`.  
  6. Проконсультировать в нужный workflow (`route_document`).  
- **Правила и числа** – `max_steps: 5`; `cost_budget: $0.08`; `confidence_threshold: 0.90`; `review_queue: "needs_review"`.  
- **Шаблоны и примеры** – `SYSTEM_PROMPT`, `TOOLS`, `CONFIG`.  
- **Ошибки и предупреждения** – никогда не «угадывайте» значение полей; ставьте `NEEDS_REVIEW`, если не уверены.  
- **Где пригодится** – автоматизация обработки счетов, договоров, заявок.

### 6.8 Template 8 — Multi‑Agent Supervisor (стр. 330‑331)  
- **Главная мысль** – «координатор», который делегирует подзадачи специалистам‑агентам и собирает их результаты.  
- **Как делать**  
  1. **Разбейте** задачу на подзадачи (правило 1).  
  2. **Запустите** их параллельно (`parallel_delegate`) (правило 2).  
  3. **Проверьте** каждый вывод (`review_output`) (правило 3).  
  4. Если специалист провалился → повторите один раз, потом решайте сами (правило 4).  
- **Правила и числа** – `max_steps: 12`; `total_budget: $2.00` (все суб‑агенты); распределение моделей (`specialist_models`).  
- **Шаблоны и примеры** – `SYSTEM_PROMPT`, `TOOLS` (`delegate_task`, `parallel_delegate`, `review_output`), `CONFIG`.  
- **Ошибки и предупреждения** – не забывайте задать **max_budget** для каждой подзадачи, иначе переплатите; не проверяйте вывод → риск «плохих» результатов.  
- **Где пригодится** – сложные проекты, требующие исследования, кодинга и аналитики одновременно (например, MVP‑консультация).
