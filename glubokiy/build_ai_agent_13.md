## 10 . Оценка агентов – Операции: CI/CD (стр. 323‑326)

### Главная мысль  
Оценка должна стать постоянной частью конвейера разработки (CI / CD), иначе небольшие изменения в подсказках, инструментах или моделях могут незаметно ухудшить качество ответов и вызвать новые сбои.

### Как делать  

**10.4 Operations: CI/CD**  
1. **Подготовьте автоматизированный оценочный набор** (см. часть 10.3, где описывался автоматический harness).  
2. **Встроите его в две стадии CI/CD:**  

   **Этап 1 – pre‑merge integration (CI).**  
   - Запускается автоматически при открытии Pull‑Request (PR).  
   - Выполняет быстрые, повторяемые проверки: юнит‑тесты, линтинг, сканирование зависимостей и уязвимостей.  
   - При изменении подсказок, политик или потоков запускает **небольшой тест‑сет** (≈ 20‑50 кейсов, включающих базовые сценарии) и сравнивает текущую версию с предыдущей → проверка **регрессии**.  

   **Этап 2 – staging validation (CD).**  
   - После слияния PR, Ops‑команда упаковывает агент и деплоит в **staging** (окружение‑реплика продакшена).  
   - Проводятся **тяжелые, более реалистичные проверки**:  
     * нагрузочное и длительное тестирование (утечки памяти, лимиты запросов, «шторм» повторных попыток);  
     * тесты интеграции с удалёнными сервисами (права, квоты, потери сети);  
     * оценка на **большом тест‑сете** (больше, чем в CI).  

3. **Настройте «gate» (врату) качества:**  
   - При автоматическом режиме, если **overall_pass** < заданного порога → **деплой блокируется**.  
   - При ручном режиме – генерируйте оценку локально и прикладывайте её к PR как артефакт, который проверяют ревьюеры.  

**10.4.1 Evaluation‑gated deployment**  
- **Принцип:** без подтверждения качества — нет продакшн‑деплоя.  
- **Реализация:** либо — ручная проверка перед PR, либо — авто‑gate в CI/CD, где программа автоматически отклоняет изменение, если оценка не прошла.

**10.4.2 Улучшение тест‑сета и оценщика: «flywheel» качества агента**  
1. **Определить критерии качества** (шаг 1).  
2. **Инструментировать систему** → собрать телеметрию реального поведения (шаг 2).  
3. **Оценить** собранные данные, выявить паттерны ошибок (шаг 3).  
4. **Архитектурировать обратную связь** → обновить наборы данных, рубрики, метрики (шаг 4).  
5. **Вернуться к шагу 1**, уточнив определение качества.  

### Правила и числа  

| Правило | Стр. |
|--------|------|
| `overall_pass` = PASS **только если** все **три** пункта рубрики PASS; иначе = FAIL. | 323 |
| Малый тест‑сет в CI ≈ 20‑50 кейсов. | 324 |
| Минимальная оплата за OpenAI API = \$5 (кредиты истекают через 1 год). | 327 |
| При автоматическом gate можно задать порог — например, **overall pass rate** < 70 % → блокировать деплой. (пример в тексте) | 323‑325 |

### Шаблоны и примеры  

- **PR‑артефакт:** файл с результатами автоматической оценки (PASS/FAIL, детали) прикрепляется к PR и проверяется ревьюером.  
- **Flywheel (рис. 10.4):** визуальный цикл из 4‑х шагов: *Define quality → Instrument → Evaluate → Feedback*.  

### Ошибки и предупреждения  

| Ошибка | Предупреждение |
|--------|----------------|
| Пускать оценку **только один раз** в процессе разработки → риск незаметных регрессий. | Оценка обязана быть **непрерывным** процессом, встроенным в CI/CD. |
| Полагаться **на один фиксированный набор тестов** → со временем не отражает новые типы ошибок. | Постоянно **расширяйте и обновляйте** тест‑сет через цикл flywheel. |
| Хард‑кодить OpenAI API‑key в коде. | Храните ключ в `.env`, загружайте через `python‑dotenv` (см. Приложение). |

### Где нам пригодится  

- **Запросы:** автоматический блок перехода в продакшн при ухудшении качества агента.  
- **Проверка:** CI‑проверка новых подсказок/инструментов.  
- **Память:** хранение истории ошибок в рубрике/метриках.  
- **Помощники:** создание собственного “gate‑скрипта” для Claude, который откажет в деплое, если падёт overall_pass.

## Приложение A – OpenAI API Key (стр. 326‑328)

### Главная мысль  
Получить и безопасно хранить API‑ключ OpenAI – необходимо для всех экспериментов с LLM‑агентами.

### Как делать (шаги)  

1. **Создать аккаунт** на https://platform.openai.com (регистрация через e‑mail, Google или Microsoft).  
2. **Добавить платёжный метод** в разделе *Billing* (кредит/дебет‑карта). OpenAI требует её даже при использовании бесплатных кредитов.  
3. **Проверить баланс**: в *Billing* смотрим текущие кредиты; если их нет – пополняем минимум **\$5** (кредиты истекают через год).  
4. **Создать API‑ключ:** в *API Keys* → *Create New Secret Key*, дать осмысленное имя (например, `agent-development`).  
5. **Сразу скопировать** ключ (после ухода со страницы увидеть его нельзя).  
6. **Хранить безопасно:** не хард‑кодить; положить в файл `.env` и загрузить через библиотеку `python‑dotenv`.  

### Правила и числа  

- Минимальный пополнение = **\$5**.  
- Кредиты **истекают через 1 год**.  
- Ключ **никогда** не должен быть закоммичен в репозиторий.  

### Шаблоны и примеры  

```dotenv
# .env
OPENAI_API_KEY=sk-xxxxxxxxxxxxxxxxxxxxxxxxxxxx
```
```python
# загрузка
from dotenv import load_dotenv
import os

load_dotenv()
api_key = os.getenv("OPENAI_API_KEY")
```

### Ошибки и предупреждения  

| Ошибка | Предупреждение |
|--------|----------------|
| Потеря ключа после его создания. | Сразу скопировать; если утерян – **создать новый**. |
| Хард‑кодить ключ в исходнике. | Хранить в `.env`, использовать переменные окружения. |
| Не пополнять баланс, полагаясь на старые бесплатные кредиты. | Проверять баланс каждый раз перед запуском скриптов. |

### Где нам пригодится  

- **Запросы:** все обращения к OpenAI (создание, тестирование, деплой агентов).  
- **Проверка:** автоматическая проверка наличия и валидности ключа перед CI‑запуском.  
- **Память:** хранение ключа в отдельном файле конфигурации, недоступном публично.
