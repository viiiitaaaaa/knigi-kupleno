## Глава 9. Кастомные и продвинутые методы оценки агентных систем (стр. — )

### 1. От production‑трассировок к пользовательским бенчмарк‑наборам  
**Главная мысль** – Чтобы получать надёжные показатели качества после выпуска, надо превратить реальные трассировочные данные в структурированные наборы тестов, которые можно запускать повторно и сравнивать с новыми моделями/промптами.  

**Как делать**  
1. С помощью платформ Langfuse / LangSmith собрать трассы реального использования (ошибки, повторные запросы, падения инструментов, эскалации).  
2. Выбрать «репрезентативные» трассы – отфильтровать по времени, тегам, workflow и типу агента (см. пример 9‑1).  
3. Привести разнообразные форматы payload‑ов к единой схеме (пример 9‑2).  
4. Отобрать трассы, соответствующие цели бенчмарка (пример 9‑3, 9‑4).  
5. Сохранить выбранные трассы как набор тестов (JSONL) – каждый элемент содержит `case_id`, `workflow`, `agent_type`, `payload`, `reference_answer` и др. (пример 9‑10).  

**Правила и числа**  
- `BATCH_SIZE = 10` – количество трасс в первой проверочной партии (пример 9‑1).  
- `TOTAL_TRACES = 100` – максимум запросов к платформе (пример 9‑1).  
- Тег оценки: `EVAL_TAG = "ext_eval_pipelines"` (пример 9‑1).  
- Фильтры workflow: `{"billing", "shipping", "returns", "account_access"}` (пример 9‑1).  
- Фильтры типа агента: `{"triage_agent", "billing_agent", "returns_agent"}` (пример 9‑1).  

**Шаблоны и примеры**  

| Шаг | Пример кода |
|-----|--------------|
| Нормализация payload | `def parse_trace_payload(run): …` (пример 9‑2) |
| Классификация поддержки | `def is_support_case_trace(run): …` (пример 9‑3) |
| Применение фильтров | `def matches_eval_filters(run): …` (пример 9‑4) |
| Получение метаданных | `def run_tags(run): …` (пример 9‑5) |
| Выбор трасс | `def fetch_support_traces(...): …` (пример 9‑6) |

**Ошибки и предупреждения**  
- Не копировать *все* недавние трассы – это создаст шум и перегрузит процесс (см. рекомендацию фильтрации).  
- При работе с PII, учетными данными и конфиденциальной информацией отключайте трассировку (раздел *Sensitive Operations and Data Retention*).  

**Где пригодится** – При построении собственного набора регрессионных тестов, который будет использоваться в CI/CD для проверки новых моделей и промптов.

### 2. Не полагайтесь только на пользовательскую обратную связь  
**Главная мысль** – Прямой фидбек от пользователей (рейты, комментарии) обычно редок и предвзят; вместо него следует извлекать косвенные сигналы (ретраи, исправления, эскалации) и превращать их в воспроизводимые тесты.  

**Как делать**  
1. Собирать автоматические сигналы: количество ретраев, коррекций, провалённых вызовов инструментов, паттерн эскалаций.  
2. Сопоставлять каждый сигнал с типичной проблемой (таблица 9‑3).  
3. Преобразовывать сигналы в формальные бенчмарк‑кейсы (см. код в предыдущем разделе).  

**Правила и числа** – Таблица 9‑3 перечисляет сигналы и их интерпретацию (например, “User retries → response unclear”).  

**Шаблоны и примеры** – Пример кода, формирующего набор кейсов из трасс (см. пример 9‑6‑9‑9).  

**Ошибки и предупреждения**  
- Не считать отсутствие фидбека гарантией корректности – пользователь может просто «покинуть» сессию.  
- Не использовать единственный LLM‑judge для всех оценок – это дорого, медленно и приводит к смещению (см. раздел *Don’t Depend on User Feedback*).  

**Где пригодится** – При построении метрик качества в системах, где пользователи редко оставляют явный рейтинг (например, внутренние инструменты автоматизации).

### 3. Дизайн и поддержка кастомных бенчмарков (таблица 9‑1, 9‑4)  
**Главная мысль** – Бенчмарк — это живой артефакт: сначала его проектируют и реализуют, а затем поддерживают, обновляя в ответ на новые типы ошибок и пользовательские группы.  

**Как делать** (по таблице 9‑1)  
1. **Что тестировать?** – Определить конкретную способность (например, «корректность маршрутизации инструментов»).  
2. **Какой кейс?** – Выбрать реалистичную задачу из вашего домена.  
3. **Как оценивать успех?** – Задать метрики, базовые линии (человек, случайный, потолок/пол).  
4. **Воспроизводимость?** – Описать источник данных, логику оценки, ограничения.  
5. **Долговечность?** – Определить владельца, частоту обновлений, набор регрессий, цикл обратной связи.  

**Правила и числа**  
- Жёсткие (детерминированные) проверки: `retry_budget_respected`, `correct_handoff`, `required_step_completed` (таблица 9‑4, тип *Deterministic*).  
- LLM‑based проверки: `final_answer_sufficient`, `final_answer_correct`, `task_completion`, `argument_correctness`, `step_efficiency` (таблица 9‑4, тип *LLM‑based*).  

**Шаблоны и примеры**  
- Детерминированный чек:  

```python
def correct_handoff(payload):
    payload = normalize_payload(payload)
    return payload["handoff_target"] == payload["expected_handoff"]
```  
(пример 9‑7)  

- LLM‑based чек (использует DeepEval/GEval):  

```python
metric = GEval(name="final_answer_correct", criteria=..., model=JUDGE_MODEL)
test_case = LLMTestCase(input=trajectory_summary(payload),
                        actual_output=payload["final_answer"],
                        expected_output=payload["reference_answer"])
metric.measure(test_case)
```  
(пример 9‑8)  

**Ошибки и предупреждения**  
- Не ограничиваться только одним LLM‑judge – комбинируйте с детерминированными проверками.  
- При оценке открытых ответов используйте ранжирование группы (RULER), а не одиночные скоры.  

**Где пригодится** – При построении автоматизированного пайплайна сравнения моделей/промптов перед переходом в продакшн.

### 4. Превращаем репозиторий в исполняемую среду бенчмарка (SWE‑smith)  
**Главная мысль** – Для кодирующих агентов удобно генерировать задачи напрямую из собственного кода, а не полагаться на внешние наборы (SWE‑bench и т.п.).  

**Как делать**  
1. Склонировать репозиторий и построить Docker‑образ (пример 9‑14).  
2. Сгенерировать *баг‑инстансы* – модифицировать функции с помощью LLM или детерминированных AST‑преобразований (пример 9‑15).  
3. Проверить, что каждый инстанс действительно ломает хотя бы один тест (пример 9‑16).  
4. Сохранить валидные инстансы в набор задач (пример 9‑17).  
5. При желании создать подмножество (по критериям, например‑кол-во падающих тестов) – фильтровать (пример 9‑18).  

**Правила и числа**  
- `--n_bugs 1` – количество генерируемых багов (пример 9‑15).  
- Методы генерации (таблица 9‑5):  
  * LLM‑generated – семантические, неопределённые ошибки.  
  * AST‑based – детерминированные, воспроизводимые изменения.  
  * PR‑mirroring – восстановление реальных багов из истории pull‑request.  

**Шаблоны и примеры**  
- Команда создания образа:  

```bash
python -m swesmith.build_repo.create_images -r <your_repo_name>
```  

- Генерация багов LLM:  

```bash
python -m swesmith.bug_gen.llm.modify $repo \
  --n_bugs 1 \
  --model openai/gpt-4o \
  --config_file configs/bug_gen/lm_modify.yml
```  

- Проверка валидных патчей:  

```bash
python -m swesmith.bug_gen.collect_patches logs/bug_gen/<repo>
python -m swesmith.harness.valid logs/bug_gen/<repo>_all_patches.json
```  

**Ошибки и предупреждения**  
- Не запускать генерацию багов в оригинальном репозитории – используйте копию/Docker, иначе можно сломать рабочий код.  
- AST‑модификации дают полную воспроизводимость, но могут не охватывать «реальные» логические ошибки LLM‑моделей.  

**Где пригодится** – При тестировании кодирующих агентов, которые должны генерировать патчи/рефакторинг в вашем собственном проекте.

### 5. Оценка длинных (мульти‑шаговых) цепочек в мульти‑модальных задачах  
**Главная мысль** – В визуально‑ориентированных системах (GUI, веб‑интерфейсы, дашборды) качество результата недостаточно; важна целостная траектория действий: что видеть, какие инструменты вызывать, как хранить состояние.  

**Как делать**  
1. Записывать каждое действие агента: просмотр экрана, вызов инструмента, полученный вывод, обновление контекста.  
2. Оценивать не только финальный ответ, а и **трейекторию**: правильность выбора инструментов, порядок, эффективность (меньше шагов), отсутствие «застреваний».  
3. При необходимости использовать визуальные метрики (скриншоты, mock‑up’ы, диаграммы) – сравнивать их с ожидаемыми результатами.  
4. Интегрировать оценку в существующий пайплайн (как в примерах 9‑11 – 9‑13) – агент возвращает JSON‑структуру с полями `retry_count`, `handoff_target`, `steps_completed`, `tool_calls`, `final_answer`.  

**Правила и числа**  
- Тестируемые модели (пример 9‑19): `openai/gpt-5.4`, `qwen/qwen3.5-35b-a3b`, `google/gemini-3.1-pro-preview`.  
- Инструменты, которые нужно включить: `web_search`, `image_search`, `visit`, `code_interpreter` (переменная `ENABLED_TOOLS`).  

**Шаблоны и примеры**  
- Промпт, требующий от модели вернуть строго JSON (пример 9‑11).  
- Конфигурация OpenRouter для мульти‑модального тестирования (пример 9‑19).  

**Ошибки и предупреждения**  
- Оценка только по `final_answer` не отражает ошибки в промежуточных шагах (см. объяснение про траекторию).  
- Не забывать о данных конфиденциальности: при работе с UI‑скриншотами могут появляться PII – требуется анонимизация.  

**Где пригодится** – При разработке агентов, которые работают с интерфейсами (веб‑боты, инструменты автотестов UI, системы визуального мониторинга).

## Общие рекомендации для Claude‑помощника (одиночный предприниматель)

| Задача | Как использовать материал |
|--------|----------------------------|
| **Создание собственного регрессионного набора** | Следовать секции 1: собрать трассы, отфильтровать, сохранить в JSONL. |
| **Автоматическая оценка новых моделей/промптов** | Реализовать функции из таблицы 9‑4 (детерминированные + LLM‑based), запускать их по примеру 9‑12. |
| **Оценка кода, генерируемого агентом** | Применить подход из секции 4 (SWE‑smith) – генерировать баг‑инстансы из своего репозитория, проверять их. |
| **Контроль стоимости и латентности** | При планировании новых запусков отслеживать сигналы «Token usage and cost», «Latency» из таблицы 8‑6 (см. предыдущее содержание). |
| **Обучение и отладка** | Использовать примеры кода (9‑1 – 9‑13) как шаблоны для быстрых скриптов в Jupyter/Colab, адаптировать под свои API‑ключи. |
| **Мультимодальная оценка** | При работе с UI‑агентами использовать схему из секции 5: собрать скриншоты, задавать агенту структурированный запрос, проверять траекторию. |

Эти конспекты позволяют быстро построить всё‑в‑одном пайплайн: от сбора production‑данных → формирование кастомного бенчмарка → автоматическое раннее тестирование новых моделей → непрерывную обратную связь и поддержание актуальности тестов.
