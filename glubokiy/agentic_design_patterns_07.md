## 1. AI‑код‑генератор (стр. 186‑190)

- **Главная мысль** – Автономный агент, используя LLM, генерирует код по use‑case, проверяет его соответствие заданным целям и в цикле (≤ 5 итераций) дорабатывает решение до тех пор, пока LLM не подтвердит, что все цели выполнены.  

### Как делать  
1. **Инициализация**: загрузить переменную `OPENAI_API_KEY` (в противном случае `EnvironmentError`).  
2. **Создать LLM**: `ChatOpenAI(model="gpt-4o", temperature=0.3, openai_api_key=…)`.  
3. **Сформировать запрос** `generate_prompt(use_case, goals, previous_code, feedback)`.  
   - Базовый шаблон включает Use Case и перечень целей (список `- …`).  
   - При наличии `previous_code` добавить блок «Previously generated code».  
   - При наличии `feedback` добавить «Feedback on previous version».  
   - В конце указать: *«return only the revised Python code; no comments outside the code»*.  
4. **Получить код**: `llm.invoke(prompt) → raw_code → clean_code_block(raw_code)`.  
5. **Оценить код**: `get_code_feedback(code, goals)` → LLM‑ответ с критикой.  
6. **Определить, выполнены ли цели**: `goals_met(feedback_text, goals)`  
   - В `review_prompt` запросить у LLM ответ **одним словом**: `True` или `False`.  
7. **Если True** – завершить цикл; иначе – передать текущий код как `previous_code` и повторить (заданное `max_iterations`, по‑умолчанию 5).  
8. **Финальная обработка**: добавить заголовок‑комментарий `add_comment_header`, затем сохранить файл `save_code_to_file`.  
   - Сократить `use_case` до ≤ 10 символов через LLM‑summarizer, очистить от недопустимых символов, добавить случайный суффикс `random.randint(1000, 9999)` → имя `<short>_<xxxx>.py`.  

### Правила и числа  
- `temperature = 0.3` – степень «креативности» модели (стр. 186).  
- `max_iterations = 5` – максимум попыток улучшения (стр. 188).  
- При формировании имени файла: **≤ 10 символов** короткое имя + случайный суффикс от 1000 до 9999 (стр. 188).  
- `goals_met` должен вернуть ровно **«True»** или **«False»** (стр. 187).  

### Шаблоны и примеры  
```text
You are an AI coding agent. Your job is to write Python code based 
on the following use case:

Use Case: {use_case}

Your goals are:
- {goal1}
- {goal2}
...
```
(функция `generate_prompt`).  

```text
You are a Python code reviewer. A code snippet is shown below.
Based on the following goals:
- {goal1}
- {goal2}
Please critique this code …
```
(функция `get_code_feedback`).  

```text
You are an AI reviewer.

Here are the goals:
- {goal1}
...
Here is the feedback on the code:
"""
{feedback_text}
"""
Based on the feedback above, have the goals been met?

Respond with only one word: True or False.
```
(функция `goals_met`).  

### Ошибки и предупреждения  
- Отсутствие `OPENAI_API_KEY` → `EnvironmentError`.  
- LLM может «галлюцинировать» и ошибочно оценить, что цели достигнуты → необходимо вручную проверять полученный код.  
- Возможна бесконечная итерация, если `max_iterations` не ограничить.  

### Где нам пригодится  
Для автоматической генерации и отладки небольших скриптов/утилит, быстрой проверки идей и обучения «prompt‑инжинирингу», где нужен чек‑лист целей (см. раздел Goal Setting).  



## 2. Паттерн «Goal Setting and Monitoring» (стр. 191‑195)

- **Главная мысль** – Чтобы автономный агент мог выполнять многократно‑шаговые задачи, нужно явно задать измеримые цели и постоянно проверять их выполнение, создавая замкнутый цикл обратной связи.  

### Как делать  
1. **Определить цели** – конкретные, измеримые, достижимые, релевантные, ограниченные во времени (SMART).  
2. **Сформировать чек‑лист** (quality checklist) – например, «решение простое», «функционально корректно», «обрабатывает краевые случаи».  
3. **Сгенерировать первый вариант** кода/действия.  
4. **Само‑рецензия**: сравнить результат со всеми пунктами чек‑листа (как в функции `get_code_feedback`).  
5. **Вердикт**: LLM отвечает *True* / *False*.  
6. **Если False** – использовать полученные замечания для исправления и повторить шаг 3‑5, пока не будет получен *True* или не исчерпаем лимит попыток (см. `max_iterations`).  

### Правила и числа  
- Цели должны быть **SMART** (стр. 193).  
- Цикл повторяется до **«True»**‑вердикта **или** до предельного количества итераций (в примере 5 шагов, стр. 188).  

### Шаблоны и примеры  
- **Fig. 1** – схематичный пример «Goal Setting and Monitor».  
- **Текстовое описание**: «draft → self‑review → verdict → revision → repeat».  

### Ошибки и предупреждения  
- LLM может «не понять» цель → неверный вердикт.  
- При «False» агент может «застрять» в бесконечном цикле без ограничителя.  
- Паттерн в примерах **не готов к продакшну** (стр. 192).  

### Где нам пригодится  
Для построения агентов, которые должны самостоятельно достигать целей без постоянного контроля человека (например, планировщики, автогенераторы отчётов).  



## 3. Паттерн «Exception Handling and Recovery» (стр. 196‑203)

- **Главная мысль** – Надёжные агенты должны предвидеть и обрабатывать непредвиденные ошибки, используя логирование, повторные попытки, откаты и эскалацию, чтобы сохранять работоспособность в реальном мире.  

### Как делать  
1. **Обнаружение ошибок**: проверять ответы инструментов, коды HTTP (404, 500, 503), тайм‑ауты, несоответствия формату.  
2. **Обработка**:  
   - **Логировать** детали.  
   - **Retry** – повторить запрос (при временных сбоях).  
   - **Fallback** – использовать альтернативный инструмент/метод.  
   - **Graceful degradation** – предоставить ограниченную функциональность вместо полной отказа.  
   - **Notification** – оповестить человека или другой агент.  
3. **Восстановление**:  
   - **State rollback** – откатить изменения.  
   - **Self‑correction** – скорректировать план/параметры.  
   - **Escalation** – передать задачу человеку.  
4. **Организовать цепочку агентов** (пример SequentialAgent) с primary, fallback и response‑агентами (стр. 199‑200).  

### Правила и числа  
- Примеры кодов ошибок: **404**, **500**, **503** (стр. 197).  
- При генерации имени файла в предыдущем разделе использовался случайный суффикс **1000‑9999** (стр. 188) – здесь же нет новых чисел.  

### Шаблоны и примеры  
```python
primary_handler = Agent(
    name="primary_handler",
    model="gemini-2.0-flash-exp",
    instruction="""Your job is to get precise location information…
    Use get_precise_location_info tool.""",
    tools=[get_precise_location_info]
)

fallback_handler = Agent(
    name="fallback_handler",
    instruction="""Check state["primary_location_failed"]…
    If True → use get_general_area_info.""",
    tools=[get_general_area_info]
)

robust_location_agent = SequentialAgent(
    name="robust_location_agent",
    sub_agents=[primary_handler, fallback_handler, response_agent]
)
```
(стр. 199‑200).  

### Ошибки и предупреждения  
- Если агент отвечает за и написание, и оценку кода, он может не увидеть собственные ошибки (стр. 192).  
- Необходимо обеспечить **тайм‑ауты** и **предел попыток**, иначе процесс может «зависнуть».  

### Где нам пригодится  
Во всех скриптах, где нужен надёжный доступ к внешним сервисам (API, базы данных, устройства IoT), особенно в продакшн‑проектах с минимальными простоями.  



## 4. Паттерн «Human‑in‑the‑Loop (HITL)» (стр. 204‑212)

- **Главная мысль** – Идеальная система объединяет вычислительные возможности ИИ с человеческим суждением, чтобы обеспечить безопасность, этичность и высокое качество в сложных или рискованных задачах.  

### Как делать  
1. **Определить роли**:  
   - **Human Oversight** – мониторинг вывода агента.  
   - **Intervention & Correction** – человек исправляет ошибки, добавляет недостающие данные.  
   - **Human Feedback for Learning** – собирается обратная связь для дообучения модели.  
   - **Decision Augmentation** – ИИ предлагает рекомендации, человек принимает окончательное решение.  
   - **Escalation Policies** – чётко прописанные условия передачи задачи человеку.  
2. **Встроить проверку**: агент перед отправкой результата проверяет, не превышен ли порог «неопределённости»; если да – запрашивает вмешательство.  
3. **Эскалация**: использовать инструменты `escalate_to_human` (стр. 208‑210).  
4. **Персонализация** через callback‑функцию, добавляющую данные клиента в системный контекст (стр. 209).  

### Правила и числа  
- **Отсутствие масштабируемости** – главная ограничивающая характеристика (стр. 206).  
- **Необходимо** наличие **экспертных операторов** (стр. 206).  
- **Приватность** – данные должны быть анонимизированы перед передачей человеку (стр. 206).  

### Шаблоны и примеры  
```python
def personalize_callback(callback_context, llm_request):
    customer_info = callback_context.state.get("customer_info")
    if customer_info:
        note = f"\nIMPORTANT PERSONALIZATION:\nCustomer Name: {customer_info.get('name')}"
        llm_request.contents.insert(0, system_content)   # вставляем системное сообщение
```
(стр. 209‑210).  

```python
technical_support_agent = Agent(
    name="technical_support_specialist",
    instruction="""You are a technical support specialist…
    1. Use troubleshoot_issue …
    2. If persists → create_ticket …
    3. For complex → escalate_to_human …""",
    tools=[troubleshoot_issue, create_ticket, escalate_to_human]
)
```
(стр. 208‑210).  

### Ошибки и предупреждения  
- **Скалируемость** – человек не способен обработать миллионы запросов (стр. 206).  
- **Требуется высокая квалификация** операторов (стр. 206).  
- **Конфиденциальность** – необходимо анонимизировать личные данные (стр. 206).  

### Где нам пригодится  
Для задач, где стоимость ошибочного решения высока (финансы, медицина, автономное вождение) и где требуется периодическое улучшение моделей через человеческую обратную связь.  



## 5. Паттерн «Knowledge Retrieval (RAG)» (стр. 213‑216)

- **Главная мысль** – Чтобы LLM‑агент отвечал точно и актуально, к его запросу добавляют внешние данные (из векторных баз, документов, веб), тем самым «расширяя» генерацию фактами и уменьшая галлюцинации.  

### Как делать  
1. **Разбить (chunk) документы** на небольшие части, сохраняющие смысл (стр. 215).  
2. **Создать эмбеддинги** (векторные представления) для каждого чанка (стр. 214‑215).  
3. **Поместить эмбеддинги** в **vector‑database** (FAISS, ScaNN, Pinecone, Chroma и т.п.) (стр. 215‑216).  
4. **При пользовательском запросе**:  
   - Преобразовать запрос в эмбеддинг.  
   - Выполнить **vector search** (или гибридный поиск BM25 + semantic) → собрать релевантные чанки.  
   - **Augment** – добавить найденные фрагменты к исходному промпту.  
5. **Отправить** обогащённый запрос LLM, получить ответ, при необходимости указать **цитаты** (стр. 214).  

### Правила и числа  
- Не указаны конкретные параметры, но упоминаются **векторные алгоритмы** HNSW, **FAISS**, **ScaNN** (стр. 216).  
- При генерации имени файла в предыдущем примере ≤ 10 символов (стр. 188) – здесь нет новых чисел.  

### Шаблоны и примеры  
```text
User query → semantic search → retrieve chunks → augment prompt → LLM → answer (с указанием источника)
```  
(общее описание RAG, стр. 213‑214).  

### Ошибки и предупреждения  
- Если нужная информация разбросана по нескольким чанкам, система может вернуть неполный ответ (стр. 215).  
- Необходимо поддерживать актуальность векторных индексов, иначе будет «засорённый» поиск.  

### Где нам пригодится  
Для построения агента‑консультанта, который отвечает на вопросы из корпоративных баз, справочников, технической документации, а также для снижения «галлюцинаций» при генерации кода или рекомендаций.
