## 1. Retrieval‑Augmented Generation (RAG) — обзор и реализации (стр. 217‑225)

### 1.1 Что такое RAG? (стр. 217‑218)  
- **Главная мысль:** RAG — шаблон, который добавляет к запросу LLM (Large Language Model) внешний поиск релевантных фрагментов (chunks) из специального хранилища (векторной или графовой БД). Это делает ответы более достоверными и актуальными.  
- **Как работает:**  
  1. **Chunking** — разбить документы на небольшие куски.  
  2. **Embedding** — преобразовать каждый кусок в вектор (семантическое представление).  
  3. **Хранение** — сохранить векторную БД (или графовую БД).  
  4. **Retrieval** — по запросу находить топ‑K схожих векторов (по семантике).  
  5. **Augmentation** — добавить найденные куски к prompt LLM.  
  6. **Generation** — LLM генерирует ответ, опираясь на контекст.  

- **Проблемы RAG (стр. 217):**  
  - Низкое качество chunk‑инга → много шума.  
  - Противоречивые источники → трудно синтезировать.  
  - Требуется предварительная обработка и поддержка векторных/графовых БД → дополнительные затраты и латентность.  

### 1.2 GraphRAG (стр. 217‑218)  
- **Главная мысль:** вместо простой векторной БД используется *knowledge graph* — структурированный набор узлов (сущностей) и рёбер (отношений).  
- **Плюсы:** может «склеить» информацию, разбросанную по разным документам; лучше подходит для сложных вопросов (финансовый анализ, генетика).  
- **Минусы:** сложность построения и поддержания графа, высокая стоимость, большая задержка.  

### 1.3 Agentic RAG (стр. 218‑220)  
- **Главная мысль:** в RAG добавляется «агент‑слой», который **активно** оценивает, проверяет и дорабатывает полученные фрагменты до передачи их LLM.  
- **Сценарии использования (стр. 219‑220):**  
  1. **Валидация источников** — агент сравнивает метаданные (дата, авторитет) и отбрасывает устаревшие данные.  
  2. **Урегулирование конфликтов** — при противоречиях выбирает более надёжный документ (например, финансовый отчёт вместо предложения).  
  3. **Многошаговое рассуждение** — разбивает сложный запрос на под‑запросы, собирает отдельные ответы и синтезирует их.  
  4. **Заполнение пробелов** — если в базе нет нужной информации, агент активирует внешние инструменты (web‑search API) и добавляет свежие данные.  

- **Недостатки (стр. 219‑220):** рост сложности, стоимости и латентности; возможные новые ошибки агента (застревания в циклах, неверные отсеивание данных).  

### 1.4 Практические применения RAG (стр. 220‑221)  
| Область | Пример использования |
|---|---|
| Enterprise search & Q&A | Внутренний чат‑бот, отвечающий по HR‑полисам, тех. докам, спецификациям. |
| Customer support | Автоматические ответы из мануалов, FAQ, тикетов. |
| Персонализированные рекомендации | Поиск семантически схожих статей/товаров. |
| Сводки новостей | Интеграция с потоками новостей, актуальная генерация резюме. |  

### 1.5 Hands‑On Code Example – Google ADK (стр. 221‑222)  
- **Google Search tool** как простейший RAG‑источник.  
- **VertexAiRagMemoryService** — подключение к Vertex AI RAG‑корпусу.  
- **Ключевые параметры (стр. 222):**  
  - `SIMILARITY_TOP_K = 5` — сколько топ‑к схожих фрагментов возвращать.  
  - `VECTOR_DISTANCE_THRESHOLD = 0.7` — максимальный семантический «расстояние», выше которого результаты отбрасываются.  

```python
memory_service = VertexAiRagMemoryService(
    rag_corpus=RAG_CORPUS_RESOURCE_NAME,
    similarity_top_k=SIMILARITY_TOP_K,
    vector_distance_threshold=VECTOR_DISTANCE_THRESHOLD
)
```  

### 1.6 Hands‑On Code Example – LangChain + LangGraph (стр. 223‑225)  
1. **Подготовка данных:** загрузка текста, разбиение (`CharacterTextSplitter(chunk_size=500, chunk_overlap=50)`).  
2. **Эмбеддинг + хранение:** `OpenAIEmbeddings` → `Weaviate` (векторное хранилище).  
3. **Retriever:** `vectorstore.as_retriever()`.  
4. **Определение состояния графа** (`RAGGraphState`).  
5. **Ноды:**  
   - `retrieve_documents_node` — запрашивает документы.  
   - `generate_response_node` — формирует prompt и генерирует ответ через `ChatOpenAI`.  
6. **Граф:** `workflow = StateGraph(RAGGraphState)` → add nodes, edges, compile.  
7. **Запуск:** `app.stream(inputs)` выводит ответы для вопросов.  

- **Главный вывод (стр. 225):** Этот код иллюстрирует полный конвейер: загрузка, chunk‑инг, эмбеддинг, поиск, генерация.  

### 1.7 Ошибки и предупреждения (всё, что упомянуто)  
- **Плохой chunk‑инг** → шум, неправильные ответы.  
- **Противоречивые источники** → необходима логика согласования (Agentic RAG).  
- **Сложный граф** → высокие затраты и латентность (GraphRAG).  
- **Agentic слой** → может добавить новые баги (застревание, неверный отбор).  

### 1.8 Где пригодится ?  
- **Запросы** к корпоративному вики, справочным базам, актуальным новостям.  
- **Проверка фактов** и **добавление источников** в ответы (для доверия).  
- **Сложные аналитические задачи**, требующие комбинирования разрозненных данных.

## 3. Глава 15 — Inter‑Agent Communication (A2A) (стр. 231‑244)

### 3.1 Что такое A2A? (стр. 231‑232)  
- **Главная мысль:** разные AI‑агенты (может быть разный стек — LangGraph, CrewAI, Google ADK) нуждаются в **универсальном протоколе** для совместной работы; A2A (Agent‑to‑Agent) обеспечивает это через HTTP‑JSON‑RPC 2.0.  

### 3.2 Core Concepts — основные элементы (стр. 232‑235)  

1. **Core Actors** (стр. 232):  
   - **User** — запускает запрос.  
   - **A2A Client (Client Agent)** — агент, который от имени пользователя отправляет задачи.  
   - **A2A Server (Remote Agent)** — агент, принимающий HTTP‑запросы, работает «непрозрачно».  

2. **Agent Card** (стр. 232‑233): JSON‑файл, описывающий:  
   - `name`, `description`, `url`, `version`.  
   - `capabilities` (streaming, push‑notifications, stateTransitionHistory).  
   - `authentication` (e.g., `apiKey`).  
   - `defaultInputModes`/`defaultOutputModes`.  
   - `skills` — массив объектов с `id`, `name`, `description`, `inputModes`, `outputModes`, `examples`, `tags`.  

   *Пример* (стр. 232‑233) – WeatherBot.  

3. **Agent Discovery** (стр. 233‑234):  
   - **Well‑Known URI** — `/.well-known/agent.json`.  
   - **Curated Registries** — централизованный каталог.  
   - **Direct Configuration** — ручная передача JSON.  

4. **Communications & Tasks** (стр. 235‑236):  
   - **Task** — асинхронный блок работы (статусы: submitted, working, completed, failed).  
   - **Message** — содержит *attributes* (метаданные) + *parts* (действительный контент).  
   - **Artifact** — результат задачи, тоже состоит из parts, может стримиться.  
   - **contextId** — группирует связанные задачи.  

5. **Interaction Mechanisms** (стр. 236‑238):  
   - **Синхронный запрос/ответ** (`sendTask`).  
   - **Асинхронный polling** (`sendTask` → получаем `taskId`, периодически проверяем статус).  
   - **Streaming (SSE)** (`sendTaskSubscribe`) – потоковые обновления.  
   - **Push‑notifications (Webhooks)** – сервер отправляет POST к клиенту по завершении.  

   *Пример синхронного JSON‑запроса* (стр. 235).  
   *Пример streaming‑запроса* (стр. 236).  

6. **Security** (стр. 236‑237):  
   - **mTLS** — взаимная TLS‑аутентификация.  
   - **Audit logs** — полный журнал всех обменов.  
   - **Agent Card** — явно указывает требуемые схемы аутентификации (OAuth 2.0, API‑key).  

7. **A2A vs MCP** (стр. 237‑238):  
   - **MCP (Model Context Protocol)** — структурирует контекст для LLM и инструменты.  
   - **A2A** — координирует взаимодействие между несколькими агентами (делегирование, оркестрация).  

### 3.3 Практические применения (стр. 239‑242)  
- **Мульти‑фреймворк коллаборация** — агенты разных стеков могут совместно решать задачи.  
- **Автоматизированная оркестрация** — цепочки: сбор данных → анализ → генерация отчёта.  
- **Динамический поиск** — один агент запрашивает актуальные данные у специализированного «data‑fetcher».  

### 3.4 Hands‑On Code Example – Calendar Agent (стр. 239‑242)  
1. **Создание инструментария:** `CalendarToolset(client_id, client_secret)`.  
2. **Определение агента:** `LlmAgent` с моделью `gemini-2.0-flash-001`, описанием, инструкциями и календарными инструментами.  
3. **Agent Card** — включает навык `check_availability`.  
4. **Запуск A2A‑сервера:**  
   - Проверка переменных окружения (`GOOGLE_API_KEY` и т.п.).  
   - `Runner`, `InMemoryArtifactService`, `InMemorySessionService`, `InMemoryMemoryService`.  
   - `A2AStarletteApplication` + роут `handle_auth`.  
5. **Запуск** через `uvicorn.run`.  

**Где пригодится:** быстрый старт создания собственного A2A‑совместимого агента (календарь, задачи, CRM).  

### 3.5 At a Glance / Rule of Thumb (стр. 242‑244)  
- **What:** без общего протокола агенты работают в изоляции → сложные системы невозможны.  
- **Why:** A2A — HTTP‑протокол, Agent Card обеспечивает автоматическое обнаружение и описание возможностей.  
- **Rule of thumb:** использовать A2A, когда требуется **оркестрация нескольких специализированных агентов** (разные фреймворки, разные задачи).  

### 3.6 Ключевые выводы (стр. 243‑244)  
- Открытый протокол, поддержка **streaming**, **push‑notifications**, **мульти‑модальность** (текст, аудио, видео).  
- Позволяет **модульную архитектуру**, масштабируемую по портам и сервисам.  
- **Безопасность** встроена (mTLS, audit‑лог).  

### 3.7 Заключение (стр. 244‑245)  
- A2A устраняет изоляцию агентов, создавая **интероперабельную экосистему** (Google ADK, LangGraph, CrewAI и др.).  
- Платформенно‑нейтральный, поддерживаемый крупными tech‑компаниями.  
- Протокол дополняет, а не заменяет MCP.  

**Где пригодится:** построение **многоагентных систем**: менеджер‑координатор + специалисты (анализ данных, генерация текста, планирование, интеграция внешних API).

## 4. Глава 16 — Resource‑Aware Optimization (стр. 246‑253)

### 4.1 Суть (стр. 246‑247)  
- **Главная мысль:** агенту нужно **само‑регулировать** свой расход вычислительных, временных и финансовых ресурсов, выбирая между несколькими моделями/алгоритмами в зависимости от *ограничений* и *целей*.  
- **Ключевые стратегии:**  
  1. **Выбор модели** — мощный (дорогой) vs быстрый (дешёвый).  
  2. **Fallback‑механизм** — при перегрузке/таймауте переключаться на более надёжный (обычно дешевый) вариант.  

### 4.2 Практические сценарии (стр. 246‑247)  
| Сценарий | Как оптимизировать |
|---|---|
| **Cost‑Optimized LLM usage** | При простом запросе использовать **Gemini Flash**, при сложном — **Gemini Pro**. |
| **Latency‑sensitive** | При требовании мгновенного ответа (чат‑бот) отдавать быстрый, но менее глубинный путь. |
| **Energy‑efficiency (edge)** | Выбирать модели с меньшим энергопотреблением, ускоряя inference. |
| **Fallback for reliability** | При недоступности выбранного сервиса переключаться на запасной. |
| **Data‑usage management** | Скачивать только части датасета, а не весь массив. |
| **Adaptive task allocation** | Агент в мульти‑агентной системе принимает задачи в зависимости от текущей нагрузки. |

### 4.3 Hands‑On Code Example – Router Agent (стр. 248‑250)  
1. **Два LLM‑агента:**  
   - `GeminiProAgent` (дорогой, мощный).  
   - `GeminiFlashAgent` (быстрый, дешёвый).  
2. **Router‑Agent** (на основе `BaseAgent`) оценивает **длину** запроса (`query_length = len(user_query.split())`).  
3. **Пример логики:**  

```python
if query_length < 20:
    # короткий запрос → Flash
    response = await gemini_flash_agent.run_async(context.current_message)
else:
    # длинный запрос → Pro
    response = await gemini_pro_agent.run_async(context.current_message)
```

4. **Оптимизация роутера:**  
   - **Prompt tuning** — формулировать инструкцию так, чтобы роутер лучше определял тип запросов.  
   - **Fine‑tuning** — обучить роутер на датасете (запрос ↔ оптимальная модель).  

### 4.4 Critic Agent (стр. 250‑251)  
- **Назначение:** проверять ответы от LLM‑агентов, давать обратную связь (ошибки, пропуски, предвзятость).  
- **Триггер для экономии:** если Critic отмечает, что простой запрос был обработан дорогой моделью, роутер перестраивается, чтобы в будущем отправлять такие запросы в более дешёвый агент.  
- **Системный промпт (CRITIC_SYSTEM_PROMPT):** чётко описывает роль, задачи и стиль обратной связи.  

### 4.5 Классификация запросов (стр. 252‑253)  
- **Функция `classify_prompt`** отправляет запрос в LLM (`gpt‑4o`) с системой‑подсказкой, которая **обязанно** вернуть **только** один из трёх вариантов в JSON:  

```json
{ "classification": "simple" }
```

- **Правила (стр. 252):**  
  - `simple` — прямой факт без рассуждений и без текущих событий.  
  - `reasoning` — логика, математика, многошаговое вывода.  
  - `internet_search` — вопрос о текущих событиях/данных, которых нет в обучении.  

### 4.6 Google Search интеграция (стр. 252‑253)  
```python
def google_search(query, num_results=1):
    # делаем запрос к Custom Search API
    # возвращаем список dict: title, snippet, link
```

- Обрабатываем `requests.exceptions` и возвращаем `{"error": str(e)}` в случае сбоя.  

### 4.7 Генерация ответа в зависимости от классификации (стр. 253‑254)  
| Классификация | Выбор модели | Промпт | Как включается внешний контекст |
|---|---|---|---|
| `simple` | `gpt‑4o-mini` | `full_prompt = prompt` | без внешних данных |
| `reasoning` | `o4-mini` | `full_prompt = prompt` | без внешних данных |
| `internet_search` | `gpt‑4o` | `full_prompt = "Use the following web results to answer the user query: …"` | включаем строки из `search_results` (title, snippet, link) |

**Где пригодится:** система, которая **экономит ресурсы**, отправляя простые вопросы в дешёвый LLM, а сложные / текущие – в более мощный, при этом **автоматически** добавляет свежие данные из Интернета.

### Сводка по всему материалу (страницы 217‑253)

| Тема | Ключевые идеи | Краткие рекомендации для одиночного предпринимателя |
|---|---|---|
| **RAG** | Внешний поиск → более достоверные ответы; нужны chunk‑инг, embeddings, векторный/графовый store. | Создай локальное векторное хранилище (Weaviate, FAISS) из своих скриптов/документов; подключи к LLM через RAG‑pipeline. |
| **GraphRAG** | Knowledge‑graph для сложных взаимосвязей; дороже и медленнее. | Используй только если нужен глубокий анализ взаимосвязей (например, связь продуктов с рыночными событиями). |
| **Agentic RAG** | Агент проверяет актуальность, разрешает конфликты, разбивает запросы, заполняет пробелы внешними инструментами. | Добавь простой «фильтр‑агент» (Python‑функция), который проверяет дату/источник перед подачей в LLM. |
| **A2A (Inter‑Agent Communication)** | Стандартный HTTP‑протокол, Agent Card, задачи, streaming, безопасность. | Если разрабатываешь несколько микросервисов‑агентов (например, один для данных, другой для генерации), описывай каждый через Agent Card и связывай их через A2A. |
| **Resource‑Aware Optimization** | Выбор модели по стоимости/времени, fallback, роутинг запросов, критерий классификации. | Реализуй роутер, который отправляет короткие запросы в бесплатный LLM (Gemini Flash) и сложные — в платный (Gemini Pro). Добавь классификатор, как в примерах, чтобы автоматически определять тип запроса. |

Эти конспекты можно сразу использовать в подсказках (prompt) для Claude:  
- При построении **RAG‑системы** – вызывай шаблон «RAG‑pipeline», указав `SIMILARITY_TOP_K=5`, `VECTOR_DISTANCE_THRESHOLD=0.7`.  
- При необходимости **мульти‑агентной оркестрации** – сформируй запрос «создай Agent Card для <название>», а затем «вызови A2A‑method sendTask…».  
- При ограничениях по бюджету – используй «classification‑prompt» и «router‑logic» из главы 16.
