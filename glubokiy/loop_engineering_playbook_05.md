## CASE STUDY: HOW DEVIN DEPLOYS APPLICATIONS END‑TO‑END (стр. 191)

- **Главная мысль** – полностью автономный инженер Devin выполняет развёртывание приложений в 4 фазах за 10‑60 минут, при этом умеет восстанавливать работу после ошибок и эскалировать их человеку.  
- **Как делать**  
  1. **Phase 1 – Environment discovery** (2‑5 мин). Читать README, искать Dockerfile/terraform/CI‑CD, понять стек.  
  2. **Phase 2 – Planning** (1‑3 мин). Составить план: Dockerfile → ECR → ECS → LB → переменные окружения → деплой → проверка.  
  3. **Phase 3 – Execution** (5‑30 мин). Выполнять шаги последовательно в полном Linux‑окружении (браузер, терминал, редактор). При ошибке читать вывод, искать решение, повторять.  
  4. **Phase 4 – Verification** (2‑5 мин). Открыть URL, выполнить smoke‑тесты, отчитаться о результате.  
- **Правила и числа**  
  - Бюджет цикла = 30 мин + (для автономных агентов) вместо 30 сек для копилотов.  
  - Ожидать 5‑10 ошибок в обычном деплое.  
  - Эскалация, если блокируется > 5 мин на одном шаге.  
- **Шаблоны / примеры** – нет (описан процесс).  
- **Ошибки / предупреждения** – отсутствие надёжного восстановления делает агента лишь скриптом.  
- **Где пригодится** – запросы *«разверни Flask‑приложение в AWS»*; проверка статуса развертывания; автоматическое восстановление после ошибок.

- **Главная мысль** – агенты различаются по латентности, контексту, уровню автономии, стоимости и требуемой среде; выбирайте в зависимости от задачи.

- **Правила и числа**

- **Шаблоны / примеры** – таблица сравнения (см. оригинал).  
- **Ошибки / предупреждения** – нельзя требовать от Copilot‑уровня долгих, сложных сценариев – он будет «отбрасывать плохие предложения».  
- **Где пригодится** – при выборе инструмента для *«пишу код, тестирую, фиксирую»*; планирование бюджета LLM‑операций.

## Chapter 14 Summary (стр. 193)

- **Главная мысль** – цикл **write‑test‑fix** – ядро программных агентов; ключевые практики: ограниченный контекст, поиск‑замена, тест‑первый подход, задачи‑специфичные подсказки, выбор позиции на спектре автономии.  
- **Как делать** (кратко)  
  1. Писать тест **до** кода (уменьшает «сломанные» фиксы ≈ 40 %).  
  2. При большом коде использовать **targeted search** с токен‑бюджетом, а не полное чтение.  
  3. По‑умолчанию использовать **search‑and‑replace** как редактирование.  
  4. Выбрать уровень автономии в зависимости от стоимости и требуемого человеческого времени.  
- **Правила и числа** – максимум 3 итерации в write‑test‑fix; тест‑первый снижает сломанные фиксы ≈ 40 %; автономность ↑ → стоимость ↑, человек‑время ↓.  
- **Шаблоны / примеры** – не приводятся.  
- **Ошибки / предупреждения** – «скрывать» сложный код в полном контексте приводит к переполнению токенов.  
- **Где пригодится** – при построении **coding‑assistant** для авто‑рефакторинга, генерации функций, отладки.

## Research Agents (стр. 194‑200)

### 1️⃣ The Research Loop (стр. 194‑195)

- **Главная мысль** – исследовательский агент проходит **6‑шаговый** цикл: разбить вопрос, искать источники, читать/извлекать, синтезировать, верифицировать, оформить с цитатами.  
- **Как делать** (шаги)  
  1. **Decompose** – разбить вопрос на подпункты.  
  2. **Search** – найти релевантные источники (по 5 результатам).  
  3. **Read & extract** – прочитать страницу, извлечь ключевые выводы.  
  4. **Synthesize** – собрать ответы в связный отчёт, добавить цитаты.  
  5. **Verify** – сравнить утверждения с источниками.  
  6. **Produce** – итоговый отчёт с цитатами.  
- **Правила и числа** – обычно 5‑10 источников на под‑вопрос; в примерах ≤ 5 результатов per sub‑question.  
- **Шаблоны / примеры** – классы `ResearchAgent` и `ClaimVerifier` (см. код).

### 5️⃣ Scored Walkthrough 15.2 – Handling Contradictory Sources (стр. 197‑198)

- **Главная мысль** – при конфликтных данных агент:  
  1. Отчитывается о **обоих** цифрах с полными цитатами.  
  2. Анализирует причинные различия (методология, период, гео).  
  3. Оценивает достоверность (peer‑reviewed > industry > news > blog).  
  4. Триангулирует с третьим источником, если возможно.  
  5. Выводит диапазон `$X‑$Y billion` вместо единственного числа.  
- **Правила и числа** – 5 шагов, конфиденциальность > 0.8 → "verified".

### 7️⃣ ANTI‑PATTERN: TRUSTING MODEL MEMORY FOR RECENT FACTS (стр. 199)

- **Главная мысль** – если агент отвечает из своей обученной модели без ссылки, это считается **unverified**. Добавляйте оговорку *«based on training data as of [cut‑off]»*.  

### 8️⃣ Scored Walkthrough 15.3 – Citation Verification System (стр. 200‑201)

- **Шаги**  
  1. Выделить пары *claim‑citation* из отчёта.  
  2. Запросить каждый URL, прочитать контент.  
  3. LLM‑опрос: *«SUPPORTED, CONTRADICTED, NOT_FOUND»*.  
  4. Если НЕ SUPPORTED → найти лучший источник **или** удалить/пометить.  
  5. Пересинтезировать отчёт.  
- **Стоимость** – ≈ $0.30 добавочно → точность ≈ 97 % (vs 80 %).  

### 9️⃣ Research Synthesizer Implementation (стр. 202‑205)

  1. `_rank_findings` (дедупликация/ранжирование).

### 10️⃣ PRODUCTION TIP (стр. 206‑207)

- **Главная мысль** – использовать **Haiku** для извлечения, **Sonnet** для разрешения противоречий, **Opus** для финального редактирования.

## Business Process Agents (стр. 210‑222)

### 1️⃣ What are Business Process Agents? (стр. 210‑211)

- **Главная мысль** – автоматизируют повторяющиеся, судорожные задачи (инвойсы, онбординг, комплаенс), заменяя часы ручного труда на минуты и уменьшая ошибки. ROI ≈ $200K‑$500K в год.  

### 2️⃣ The Business Process Loop (стр. 211‑212)

1. **Trigger** (новый документ, форма, расписание).  
2. **Extract & Validate** (получить требуемые данные).  
3. **Apply Rules & Decide** (бизнес‑логика).  
4. **Execute Actions** (взаимодействие с несколькими системами).  
5. **Exception Handling & Escalate** (при ошибках).  
6. **Record Outcome** (обновление статуса).  

### 3️⃣ Scoring Framework for Automation (стр. 210‑212)

| Data availability | разн.‑неструктур.; verbal | цифровые, централизованные |

## Creative Agents (стр. 224‑233)

### 1️⃣ What are Creative Agents? (стр. 224‑225)

- **Главная мысль** – генерация‑оценка‑улучшение (generate‑evaluate‑refine) цикл позволяет создавать контент с контролируемым качеством; важно формализовать **quality dimensions** (ясность, вовлечённость, точность, тон, SEO).  
- **Ключевой инсайт** – без правильных измерений (например, только Flesch‑Kincaid) получаем **бледный** текст; надо собрать человеческие рейтинги ≥ 30 примеров, откалибровать рубрику.  

### 2️⃣ Generate‑Evaluate‑Refine Loop (стр. 224‑227)

- **Алгоритм**  
  1. **Generate** – создать черновик из brief.  
  2. **Evaluate** – измерить все quality‑dimensions (LLM‑judge + метрики).  
  3. **Identify weakest** – найти минимальный score.  
  4. **Refine** – доработать в точке слабости.  
  5. **Repeat** – до всех scores > threshold или max‑revisions (3‑4).  

### 3️⃣ Примеры кода  

| Пример | Стр. | Описание |
|--------|------|----------|
| `ContentAgent` | 224‑226 | генерирует черновик, оценивает (scores > 0.8), уточняет weakest‑dimension, максимум `max_revisions`. |
| `VariantGenerator` | 227‑228 | создаёт n вариантов по стратегиям (emotional, data‑driven, …), оценивает `predicted_score`. |
| `VoiceMatchingAgent` | 227‑229 | анализирует 5‑10 образцов, извлекает количественные метрики + качественное описание, генерирует текст в том же тоне, проверка `match_score` < 0.7 → refine. |

### 4️⃣ Quality Gain & Cost Table (стр. 225)

### 5️⃣ Scored Walkthrough 17.1 – Blog Writing Agent (стр. 226‑227)

- **Фазы**: Research (3‑5 источника), Outline (human‑approved), Draft (по‑секциям), Refine (evaluate 4‑dim, improve weakest), Polish (grammar, meta‑data).  
- **Вывод** – готовый Markdown‑файл.  

### 6️⃣ Scored Walkthrough 17.2 – Evaluating Creative Quality (стр. 227‑228)

- **Разложить** «качество» на:  
  1. **Objective metrics** – reading level, sentence‑length variance, vocab‑diversity, grammar.  
  2. **LLM‑judged** – engagement, clarity, tone match.  
- **Калибровать** модель против человеческих оценок ≥ 50 примеров; если > 20 % разногласий → перепрограммировать рубрику.  

### 7️⃣ Diminishing Returns of Revision (стр. 228‑229)

- **Статистика** – улучшение от 1‑й к 2‑й ревизии ≈ +30 %; 2 → 3 ≈ +10 %; 3 → 4 ≈ +3 %.  
- **Рекомендация** – max 3‑4 ревизии, а оставшиеся токены инвестировать в лучшее первое поколение (лучшие промпты).  

### 8️⃣ ANTI‑PATTERN – Revision Loop without Stopping Condition (стр. 229‑230)

- **Ошибка** – бесконечный цикл или «обратный» эффект. Нужно:  
  - **max revisions = 3‑4**;  
  - **termination condition** – улучшение < 0.05 по min score → вернуть лучший вариант.  

### 9️⃣ Scored Walkthrough 17.3 – Handling “Creative Direction” (стр. 230‑231)

- **Проблема** – высокий объективный score, но редактор считает контент «скучным».  
- **Решение** – собрать примеры «boring» vs «great», количественно измерить:  
  - **Analogy count** (≥ 2 / 1000 слов)  
  - **Specificity score** (отношение конкретных к общим утверждениям)  
  - **Hook quality** (LLM‑judge 1‑10)  
  - **Example density** (≥ 1 пример / секция)  
- Добавить эти измерения в цикл оценки, калибровать.  

### 1️⃣0️⃣ Case Study: Marketing Team Content Pipeline (стр. 231‑232)

- **Пайплайн**: `ResearchAgent` (Haiku) → `WriterAgent` (Sonnet) → `EditorAgent` (Opus).  
- **Результаты** (3 мес): 4× выход (8 → 32 pieces/мес), **стоимость ≈ $1.20/штука** vs $250 у фрилансера; **качество ≈ 82 %** vs 78 % у людей; **время до публикации** 15 мин vs 3 дня; **человек‑время** 10 мин vs 2 ч.  

### 1️⃣1️⃣ PRODUCTION TIP – Model Tiering (стр. 232)

- **Сначала** – Sonnet для черновика, **затем** Opus для финального редактирования → 7‑9 % прирост качества при 40 % экономии токенов.  

### 1️⃣2️⃣ When Not to Use Creative Agents (стр. 233)

- **Неэффективно** для: полностью новых креативных идей (фантастика, прорывные кампании), глубоких предметных экспертиз, эмоционально‑чувствительного контента, сильно уникального бренда. Лучше использовать агент как **first‑draft + research** и оставить финальную креативную работу человеку.

### 1️⃣4️⃣ Chapter 17 Summary (стр. 234‑235)

- **Главная мысль** – креативные агенты работают по **generate‑evaluate‑refine**, где качество раскладывается на измеримые подпараметры; после 3‑4 ревизий отдавать токены в лучший первый черновик; модели tier = Haiku → Research, Sonnet → Writing, Opus → Editing; голос‑соответствие → количественная+качественная аналитика; использовать людей для эмоционально‑чувствительного или действительно новаторского контента.

## Building Agent Products (стр. 236‑239)

### 1️⃣ Product Stack Overview (стр. 236‑237)

- **Пять слоёв** над агентом:  
  1. **User Interface** (чат, дашборд, API).  
  2. **Auth & Authorization**.  
  3. **Rate Limiting & Billing** (трекинг, квоты, платежи).  
  4. **Monitoring & Ops** (health‑checks, alerts, incident response).  
  5. **Feedback Loop** (пользовательский фидбек → пере‑обучение).  

### 2️⃣ Пример архитектуры (стр. 237)

```python
class AgentProduct:
    def __init__(self):
        self.auth = AuthService()
        self.rate_limiter = RateLimiter()
        self.billing = BillingService()
        self.agent = CoreAgent()
        self.monitor = MonitoringService()

    async def handle_request(self, request):
        user = self.auth.verify(request.token)               # Auth
        if not self.rate_limiter.allow(user.id):            # Rate limit
            return Error(429, "Rate limit exceeded")
        trace = self.monitor.start_trace(user.id)            # Monitoring
        result = await self.agent.run(request.input)         # Execute
        trace.complete(result)
        self.billing.record_usage(user.id,
                                 tokens=trace.total_tokens,
                                 cost=trace.total_cost)  # Billing
        return result
```

### 4️⃣ Key Insight по ценообразованию (стр. 238‑239)

- **Цените по ценности**, а не по токенам.  
- Пример: юрист экономит $150 ч/документ; если пользователь платит $0.49 за документ → **ROI ≈ 300×**.  
- **Анкеровка цены** → 5‑15 % от стоимости заменённого ручного труда.  

### 5️⃣ Scored Walkthrough 18.1 – MVP для Legal Document Review (стр. 239‑240)

- **Объём MVP** – один агент: PDF → рисковый отчёт с флагами, тяжестью, объяснением.  
- **Пользовательский поток**:  
  1. **Upload PDF**.  
  2. **Wait 2‑5 мин**.  
  3. **View report**.  
- **Технологии** – Python backend, простая веб‑UI, Stripe, S3.  
- **Тариф** – free 5 docs/мес, $49 / мес за 50 docs.  
- **Метрики** – число обработанных документов, количество флагов, ретеншн через 1 мес.  

### 6️⃣ Scored Walkthrough 18.2 – Handling Agent Failures (стр. 240‑241)

- **Стратегия** (5 шагов)  
  1. **Classify** ошибки (по входу, пользователю, времени).  
  2. **Graceful degradation** – частичный результат + объяснение.  
  3. **Fallback to human** (для premium‑пользователей).  
  4. **Collect failures** → automatic training data.  
  5. **Target** – снизить ошибку с 5 % → 2 % за 30 дней; мониторинг – дашборд.  

### 7️⃣ Chapter 18 Summary (стр. 241‑242)

- **Главная мысль** – построить **продукт‑агент** нужно с учётом **надёжности, ценообразования, UX и операционки**; 60 % времени → интеграции, 20 % → логика агента, 20 % → тесты; важен **feedback‑loop** и **система биллинга**, привязанная к реальной ценности заменённого труда.
