## 1. Prompt Engineering — как разговаривать с ИИ (стр. 490‑493)  
- **Главная мысль** – Чтобы модель выполнила нужное действие, нужно чётко сформулировать инструкцию — это и есть *prompt engineering*. Чем чувствительнее модель к формулировкам, тем больше требуется «шлифовки» подсказки.  
- **Как делать**  
  1. Сформулировать задачу ясными инструкциями.  
  2. Добавить примеры желаемого поведения (few‑shot).  
  3. При необходимости указать модели «думать шаг за шагом».  
  4. Проверять, как небольшие изменения подсказки влияют на ответ; при сильной чувствительности – уточнять дальше.  
- **Правила и числа**  
  - Если модель меняет ответ при небольшом изменении подсказки → требуется более тщательная проработка (стр. 490).  
  - Примерное ограничение для Claude внутри 200 000 токенов ≈ 500 страниц — можно включить полностью, без RAG (стр. 498).  
- **Шаблоны и примеры**  
  - “Ask the model to **slow down and think step by step**” — простой трюк, дающий заметный прирост качества (стр. 490).  
  - Пример «NIAH test for doctor visits» (Шрёя Шанкар) показывает практическое применение (стр. 492).  
- **Ошибки и предупреждения**  
  - «Prompt engineering — легко начать, но тяжело делать правильно» — не стоит полагаться на быструю настройку (стр. 490).  
  - Модели могут не отличать ваш ввод от собственного вывода → возможны повторные‑токен‑атаки (стр. 493).  
- **Где пригодится** – для построения запросов к LLM, проверки их надёжности и предотвращения атак.

## 2. Атаки на подсказки — риски безопасности (стр. 491‑493)  
- **Главная мысль** – Возможность заставить модель выполнять злонамеренные команды (prompt attacks) делает безопасность ключевой проблемой; полностью надёжных мер нет, игра «кот‑мышь» продолжается.  
- **Как делать** – (описано в тексте как исследовательская процедура)  
  1. Собирать «корпус» запросов (например, 100 МБ из Википедии).  
  2. Случайным образом генерировать подсказки, ищущие фрагменты обучающего набора ≥ 50 токенов (стр. 493).  
  3. Оценивать, какие модели успешно «выводят» эти куски.  
- **Правила и числа**  
  - Успешной считается генерация текста, содержащего подстроку ≥ 50 токенов из обучающего набора (стр. 493).  
  - Пример «repeat‑token attack»: повторять фразу несколько раз (стр. 493).  
- **Шаблоны и примеры**  
  - «Bye Bye Bye…» — статья Dropbox о повторяющихся токен‑атаках (стр. 493).  
- **Ошибки и предупреждения**  
  - Любые защитные меры могут быть обойдены; полностью надёжных решений нет (стр. 491‑492).  
- **Где пригодится** – при оценке рисков внедрения ИИ в бизнес‑процессы, особенно в высоко‑рисковых сферах.

## 3. RAG и агенты: вводный обзор (стр. 494‑495)  
- **Главная мысль** – Для решения задачи модели нужны **инструкции** (одинаковые для всех запросов) и **контекст** (индивидуальный). RAG (retrieval‑augmented generation) и агенты – два основных способа построения контекста.  
- **Как делать** – (общий процесс)  
  1. Сформулировать глобальные инструкции (см. главу 4).  
  2. Для каждого запроса собрать релевантный контекст:  
     - через RAG — поиск в внешних источниках;  
     - через агенты — вызов инструментов (поиск в интернете, API и т.п.).  
- **Правила и числа** – нет новых чисел.  
- **Шаблоны и примеры** – «RAG позволяет включать только нужные куски данных, а не весь массив» (стр. 495).  
- **Ошибки и предупреждения** – не использовать один и тот же контекст для всех запросов → повышается риск «галлюцинаций».  
- **Где пригодится** – при построении системы вопросов‑ответов, чат‑ботов, вспомогательных агентов.

## 4. RAG — что это и зачем (стр. 495‑497)  
- **Главная мысль** – RAG — первый этап *retrieve‑then‑generate*: система извлекает самые релевантные документы, затем модель генерирует ответ на их основе. Это снижает галлюцинации и экономит токены.  
- **Как делать** – (пример из статьи 2017)  
  1. По запросу подобрать N документов (обычно 5) из внешнего источника (например, Википедии).  
  2. Передать их модель‑генератору вместе с запросом.  
- **Правила и числа**  
  - В оригинальном примере использованы 5 документов (стр. 495).  
  - Даже если контекст модели станет 200 000 токенов, RAG всё равно может быть полезен, потому что объём данных растёт быстрее (стр. 497).  
- **Шаблоны и примеры** – «Can Acme’s fancy‑printer‑A300 print 100 pps?» → спросить спецификации принтера (стр. 496).  
- **Ошибки и предупреждения** – «Большой контекст ≠ хорошее использование»: модель может сосредоточиться не на той части (стр. 497).  
- **Где пригодится** – для построения запросов к базе знаний, снижения стоимости токенов.

## 5. Архитектура RAG (стр. 498‑500)  
- **Главная мысль** – RAG состоит из **ретривера** (поиск) и **генератора** (LLM). Они могут быть обучены совместно, но зачастую используют готовые компоненты.  
- **Как делать** – базовый пайплайн  
  1. **Индексация**: обработать внешние документы → векторные/текстовые представления.  
  2. **Запрос**: при получении пользовательского запроса ретривер ищет релевантные куски.  
  3. **Пост‑обработка**: объединить найденные куски с пользовательским запросом → финальная подсказка.  
  4. **Генерация**: передать в LLM и получить ответ.  
- **Правила и числа** –  
  - Если база < 200 000 токенов → можно просто включить её в подсказку без RAG (стр. 498).  
- **Шаблоны и примеры** – Схема Figure 6‑2 (стр. 498).  
- **Ошибки и предупреждения** – незнание качества ретривера сильно ограничивает итоговый результат (стр. 499).  
- **Где пригодится** – при проектировании собственного RAG‑сервиса.

## 6. Алгоритмы поиска (Retrieval) (стр. 501‑507)  

### 6.1. Общее о поиске (стр. 501‑502)  
- **Главная мысль** – Поиск = ранжирование документов по релевантности запросу. Основные подходы: **термин‑базированный (sparse)** и **векторный/эмбеддинг‑базированный (dense)**.  
- **Правила и числа** – Много‑вековая традиция, детали не приведены (стр. 501).  

### 6.2. Sparse vs Dense (стр. 502‑504)  
- **Главная мысль** – *Sparse* использует разреженные векторы (one‑hot), *Dense* — полные векторы‑эмбеддинги. SPLADE – гибрид (sparse‑embedding) (стр. 502).  
- **Как делать** –  
  1. Для term‑based: построить one‑hot вектор по словарю.  
  2. Для embedding‑based: получить эмбеддинг через BERT‑подобную модель, затем приоритизировать ненулевые элементы (если используют SPLADE).  
- **Правила и числа** – Пример one‑hot: {“food”:0,“banana”:1,“slug”:2} → векторы [1,0,0] и т.д. (стр. 502).  

### 6.3. Term‑based retrieval (стр. 503‑506)  
- **Главная мысль** – Наиболее простой способ: искать документы, содержащие ключевые слова. Два ключевых показателя: **TF** (частота термина в документе) и **IDF** (обратная частота документа).  
- **Как делать** – TF‑IDF расчёт:  
  1. Считайте TF = f(t, D).  
  2. Вычислите IDF(t) = log(N / C(t)), где N — общее число документов, C(t) — число документов с термином t. (стр. 504).  
  3. Суммируйте IDF·TF по всем терминам запроса → Score(D, Q).  
- **Правила и числа** – Пример: N = 10, C(t)=5 → IDF = 10/5 = 2 (стр. 504).  
- **Шаблоны и примеры** – Elasticsearch использует **инвертированный индекс** (таблица 6‑1) (стр. 505).  
- **Ошибки и предупреждения** –  
  - Токенизация может разбить многословные термины («hot dog») → потеря смысла (стр. 506).  
  - Длинные документы получают более высокий TF, поэтому BM25 нормализует по длине (стр. 506).  

### 6.4. Embedding‑based retrieval (стр. 507‑512)  
- **Главная мысль** – Ранжировать документы по семантическому сходству запрос‑документ, используя векторы‑эмбеддинги.  
- **Как делать** – Пайплайн (Figure 6‑3)  
  1. Преобразовать запрос в эмбеддинг тем же моделем, что использовался при индексации.  
  2. Найти *k* ближайших векторов в **векторной базе** (ANN‑поиск).  
  3. При необходимости – до‑ранжировать (rerank) полученные кандидаты.  
- **Правила и числа** –  
  - *k* выбирается в зависимости от задачи, модели и запроса (стр. 508).  
  - Для больших наборов применяется **approximate nearest neighbor (ANN)**, а не полный k‑NN (стр. 510).  
- **Шаблоны и примеры** – Библиотеки: FAISS, ScaNN, Annoy, Hnswlib (стр. 510‑511).  
- **Ошибки и предупреждения** – Плохой эмбеддинг → плохой поиск; генерация эмбеддингов дорого стоит (стр. 515).

## 7. Сравнение term‑based и embedding‑based retrieval (стр. 513‑517)  

- **Главная мысль** – У каждого подхода есть плюсы/минусы: term‑based быстрее и дешевле, embedding‑based семантически точнее и улучшаемый, но дороже и медленнее.  
- **Таблица 6‑2 (стр. 516)** – Сводка:  

| Показатель | Term‑based | Embedding‑based |
|------------|------------|-----------------|
| Скорость запросов | **Много быстрее** | Медленнее (вкл. генерацию эмбеддингов) |
| Производительность | Хороша «из коробки», трудно донастройить | Может превзойти после донастройки |
| Стоимость | **Дешевле** | Дороже (эмбеддинги, векторное хранение, поиск) |

- **Как измерять** – Метрики: **Context Precision**, **Context Recall**, **NDCG**, **MAP**, **MRR** (стр. 514‑515).  
- **Правила и числа** –  
  - При оценке recall нужно аннотировать релевантность *всех* документов в базе (стр. 514).  
  - При оценке precision достаточно сравнить полученные документы с запросом (стр. 514).  
  - Константа *k* = 60 в формуле RRF (стр. 520).  
- **Ошибки и предупреждения** – Не стоит полагаться только на точность без учёта ранжирования (стр. 514).  
- **Где пригодится** – При выборе стратегии поиска для вашего продукта (экономия vs качество).

## 8. Оптимизация Retrieval (стр. 518‑525)  

### 8.1. Chunking (разбиение) (стр. 520‑523)  
- **Главная мысль** – Как разбить документы на куски сильно влияет на эффективность поиска и генерации.  
- **Как делать** – Рекомендации:  
  1. Выберите единицу разбиения: символы, слова, предложения, абзацы, токены.  
  2. При желании задайте **overlap** (перекрытие) — чтобы важные границы не терялись (пример ≈ 20 символов; стр. 522).  
  3. Не превышайте **максимальный контекст модели** (стр. 521‑522).  
  4. При смене модели‑генератора, может потребоваться пере‑индексация (стр. 522).  
- **Правила и числа** –  
  - Примеры размеров: 2 048 символов, 512 слов, 20 предложений (стр. 520).  
  - Перекрытие 20 символов при размере 2 048 символов (стр. 522).  
- **Ошибки и предупреждения** – Слишком мелкие куски → рост вычислительных расходов и размер векторного индекса (стр. 523).  

### 8.2. Reranking (перестановка) (стр. 524‑525)  
- **Главная мысль** – После первичной выборки можно улучшить порядок документов, особенно если нужно ограничить количество токенов.  
- **Как делать** –  
  1. Сначала используем быстрый, менее точный ретривер (term‑based).  
  2. Затем более дорогой, точный модуль (k‑NN, vector search) – **rerank**.  
  3. При необходимости учитываем свежесть (время) документов.  
- **Ошибки и предупреждения** – В RAG порядок менее критичен, чем в обычном поиске, но всё же влияет на восприятие модели (стр. 525).  

### 8.3. Query Rewriting (переформулировка) (стр. 525‑526)  
- **Главная мысль** – Запрос часто бывает неоднозначным; нужно превратить его в самодостаточную формулировку.  
- **Как делать** –  
  1. По контексту диалога определить смысл последнего сообщения.  
  2. Сгенерировать полную формулировку (можно промпт «Rewrite the last user input …»).  
  3. При невозможности понять – вернуть сообщение о невозможности (стр. 526).  
- **Пример** – «How about Emily Doe?» → «When was the last time Emily Doe bought something from us?» (стр. 525).  

### 8.4. Contextual Retrieval (контекстуальный поиск) (стр. 527‑529)  
- **Главная мысль** – Укрепить каждый кусок метаданными (теги, ключевые слова, вопросы), чтобы упрощать поиск.  
- **Как делать** –  
  1. Добавить к куску **metadata**: описание, теги, извлечённые сущности (пример — error code EADDRNOTAVAIL).  
  2. Сгенерировать короткую «ситуационную» подсказку (50‑100 токенов) при помощи LLM (пример prompt в стр. 528).  
  3. При индексации хранить это дополнение вместе с оригинальным куском.  
- **Ошибки и предупреждения** – При отсутствии контекста у куска векторный поиск может «потерять» его (стр. 527).

## 9. Оценка и выбор решения для Retrieval (стр. 530‑531)  

- **Главная мысль** – При выборе библиотеки/сервиса проверяйте поддерживаемые механизмы (гибридный поиск, типы эмбеддингов), масштабируемость, скорость индексации, latency запросов и модель ценообразования.  
- **Критерии оценки** (стр. 530):  
  1. Поддержка **гибридного поиска** (term + embedding).  
  2. Какие **embedding‑модели** и **ANN‑алгоритмы** реализованы.  
  3. **Масштабируемость** по объёму данных и запросов.  
  4. **Время индексации** и объём данных, которые можно загрузить за раз.  
  5. **Задержка запросов** для разных алгоритмов.  
  6. **Ценовая модель** (по объёму документов, векторов или запросов).  
- **Multimodal RAG** (стр. 531) – При генеративных моделях, поддерживающих мультимодальный ввод, к контексту можно добавить **изображения, видео, аудио**. Пример: запрос «What’s the color of the house in the Pixar movie Up?», ретривер возвращает картинку (Figure 6‑6).  

- **Где пригодится** – При построении собственного поискового/вопросно‑ответного сервиса, требующего оценки стоимости и производительности.
