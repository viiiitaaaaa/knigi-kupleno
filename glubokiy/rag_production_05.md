## Работа с PDF и обновление данных (стр. 98–100)
- **Главная мысль**: Для работы с большими PDF их нужно разбивать на части (чанки), а для актуальности RAG-системы — внедрить механизм обновления данных, чтобы ответы не устаревали.
- **Как делать (разбиение PDF)**:
    1. Получить PDF из URL и определить общее количество страниц.
    2. Рассчитать количество чанков (всего страниц / страниц на один чанк).
    3. В цикле создать новые PDF-файлы, добавляя в каждый заданное количество страниц.
    4. Сохранить каждый чанк в отдельную папку.
- **Как делать (обновление данных)**:
    1. **Инкрементальное обновление**: вместо переиндексации всего массива данных искать только измененные, новые или удаленные документы.
    2. **CDC (Change Data Capture)**: использовать триггеры базы данных или логи транзакций для отслеживания изменений в источнике.
    3. **Оптимизация для Real-time**: параллелить пайплайн, использовать GPU/TPU, быстрые модели эмбеддингов и асинхронную обработку.
- **Правила и числа**:
    - В примере используется разбиение по 50 страниц (стр. 99).
- **Ошибки и предупреждения**: Игнорирование цикла обновления данных ведет к деградации системы и неточным ответам (стр. 99).
- **Где нам пригодится**: Для данных (автоматизация обновления базы знаний).

## Продвинутый поиск: Двухэтапный конвейер (стр. 101–104)
- **Главная мысль**: Простой векторный поиск неэффективен на больших масштабах. Нужно использовать двухэтапную схему: сначала быстрый отбор кандидатов, затем точная переранжировка.
- **Как делать (процесс)**:
    1. **Этап 1: Генерация кандидатов**. Быстрое сужение пространства поиска. Используются метаданные (фильтры по дате/отделу), векторный поиск или лексический поиск. Цель — высокий *recall* (найти максимум всего подходящего, даже с лишним).
    2. **Этап 2: Переранжирование (Reranking)**. Точная оценка небольшой группы кандидатов с помощью сложных моделей (например, cross-encoders).
- **Гибридный поиск (Hybrid Search)**:
    - Сочетает **векторный поиск** (смысл, контекст) и **лексический поиск** (точные слова, термины, артикулы).
    - Лексический поиск работает через *инвертированный индекс* (таблица, где каждое слово ссылается на документы с этим словом), чаще всего по алгоритму **BM25** (стр. 103).
- **Как объединить результаты гибридного поиска**:
    1. **RRF (Reciprocal Rank Fusion)**: сумма обратных рангов ($1/\text{позиция}$). Не требует нормализации оценок.
    2. **Взвешенное среднее**: нормализация оценок обеих систем (от 0 до 1) и их сложение с весами (например, 60% вектор + 40% лексика).
- **Где нам пригодится**: Для запросов (повышение точности поиска в больших базах).

## Переранжирование / Reranking (стр. 105–109)
- **Главная мысль**: Реренкер переупорядочивает найденные чанки, чтобы самые релевантные оказались в топе, что критично для качества ответа LLM.
- **Виды переранжирования**:
    1. **По релевантности**: использование cross-encoder моделей (например, `bge-reranker-v2`), которые анализируют пару «запрос + чанк» целиком.
    2. **MMR (Maximum Marginal Relevance)**: поиск баланса между релевантностью и разнообразием. Убирает дублирующиеся по смыслу чанки, чтобы LLM получила разные аспекты информации (стр. 108).
    3. **Кастомное**: сортировка по бизнес-логике (например, по дате обновления — самые свежие выше).
- **Примеры моделей (стр. 106)**:
    - *Open Source*: Sentence Transformers, BGE Reranker, Mixedbread.
    - *Commercial*: Cohere Rerank, Voyage AI, Jina Reranker.
- **Ошибки и предупреждения**: Использование общей LLM (типа GPT-4o) в качестве реранкера проще в реализации, но ведет к галлюцинациям, высокой задержке и стоимости (стр. 106).
- **Где нам пригодится**: Для помощников (чтобы ИИ не путался в похожих документах).

## Guardrails: Безопасность и защита (стр. 109–114)
- **Главная мысль**: «Гардрейлы» (ограничители) нужны для фильтрации токсичного контента, предотвращения галлюцинаций и защиты от атак.
- **Методы обеспечения безопасности**:
    1. **Курирование данных**: включение разных точек зрения в базу.
    2. **Промпт-инструкции**: добавить в системный промпт запреты (например, «никогда не используй дискриминационный язык»).
    3. **Специализированные модели-аудиторы**: использование моделей типа **ShieldGemma** или **Llama Guard** для проверки сгенерированного текста перед показом пользователю (стр. 110).
- **Защита от Prompt Injection (инъекций промптов)**:
    - *Прямые атаки*: пользователь просит «забудь все инструкции и сделай X».
    - *Косвенные атаки*: вредоносный текст спрятан в документе, который RAG скачивает из сети.
- **Как защищаться (стр. 113)**:
    1. **Санитизация (очистка)**: поиск подозрительных фраз («игнорируй инструкции») в запросах и документах.
    2. **Защита инструкций**: использование четких разделителей в промпте (например, XML-теги `<query>{query}</query>` и `<context>{context}</context>`), чтобы LLM понимала, где данные, а где команды.
- **Где нам пригодится**: Для данных и помощников (безопасность и фильтрация).

## Борьба с галлюцинациями (стр. 114–120)
- **Главная мысль**: RAG снижает риск галлюцинаций, но не убирает их. Важно уметь их определять и классифицировать.
- **Причины галлюцинаций в RAG (стр. 116)**:
    - Ошибка поиска (ретривера): не найден нужный кусок или найдены противоречивые.
    - Плохое качество данных: в базе старая или неверная информация.
    - Ошибка LLM: проигнорировала контекст, доверилась своим старым знаниям или неправильно объединила факты.
- **Классификация галлюцинаций (стр. 117)**:
    - *Сомнительные*: неоднозначная интерпретация (например, смещение временных рамок).
    - *Безобидные*: вывод, которого нет в тексте, но он соответствует здравому смыслу.
    - *Нежелательные*: явное искажение фактов из источника.
- **Как обнаруживать (стр. 118)**:
    1. **LLM-as-a-judge**: отдельная мощная LLM оценивает ответ по шкале от 1 до 5 на основе предоставленного источника.
    2. **Специализированные модели (HHEM)**: классификаторы (например, `vectara/hallucination_evaluation_model`), которые выдают вероятность соответствия от 0 до 1.
- **Где нам пригодится**: Для учёбы и проверки (верификация ответов ИИ).
