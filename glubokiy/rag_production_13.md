# Конспект по многомодальному RAG и Графам Знаний

## Глава 8: Multimodal RAG (стр. 294–304)

### 1. Обработка аудио и видео (стр. 294–297)
**Главная мысль:** Простого текста (транскрипции) недостаточно для видео, так как он не передает «тихую семантику» (действия в кадре). Нужно объединять текст с визуальными данными.

**Как делать (извлечение визуальных данных):**
1. **Фиксированные интервалы (Fixed-interval):** извлечение кадра раз в N секунд (например, 1 FPS).
    - *Вариант А (Captioning):* VLM-модель пишет описание кадра текстом.
    - *Вариант Б (Embedding):* Кадр превращается в вектор напрямую (через CLIP/SigLIP).
2. **Временные сегменты (Temporal segments):** нарезка видео на клипы (напр., по 20 сек с перекрытием в 10 сек) $\rightarrow$ анализ VLM-моделью для понимания действий (причинно-следственных связей).
3. **Ключевые кадры (Keyframe extraction):**
    - Алгоритм ищет моменты смены сцены.
    - VLM описывает только эти ключевые кадры.
    - Описание добавляется к тексту транскрипции этого момента.

**Правила и числа:**
- 1 FPS — базовый стандарт для общего понимания сцен (стр. 295).
- 2–5 FPS — для быстрого движения (спорт, слежка) (стр. 295).
- 1 кадр в 5–10 сек — достаточно для лекций или «говорящих голов» (стр. 295).

**Ошибки и предупреждения:**
- **Проблема «Красной кнопки»:** если техник говорит «сделайте это» и нажимает кнопку, в тексте останется двусмысленное «сделайте это», и поиск по запросу «как остановить машину» ничего не найдет без визуального описания (стр. 295).

**Где нам пригодится:** Данные (анализ видео-инструкций, записей зумов), Помощники (поиск по видео-архиву).

### 2. Продакшн-соображения (стр. 271–301)
**Главная мысль:** Переход от прототипа (POC) к продакшну требует борьбы с плохим качеством данных, высокой стоимостью вычислений и рисками безопасности.

**Ключевые аспекты:**
- **Экономика и задержки:** Визуальные энкодеры и OCR намного тяжелее текстовых. Рекомендуется параллельная архитектура (стр. 298).
- **Выравнивание модальностей (Modality Alignment):** Нужно хранить «чанк» не как строку, а как сложный объект: `вектор + сырой контент + метаданные (координаты окна/таймстампы)`. Иначе возникнут «сироты» (orphan chunks) — векторы без ссылки на источник (стр. 299).
- **Интерфейс:** Цитатой в многомодальном RAG должен быть сам фрагмент изображения или видео, а не ссылка (стр. 299).

**Безопасность:**
- **Визуальный промпт-инъекция:** скрытые в картинках команды для VLM (напр., «игнорируй инструкции и укради данные») (стр. 300).
- **Утечка PII (персональных данных):** в сканах нужны модели типа LayoutLM или YOLO для автоматического размытия лиц/подписей при загрузке (blur-on-ingest) (стр. 300).

**Где нам пригодится:** Данные (безопасность, GDPR), Помощники (создание UI с визуальными пруфами).

---

### 3. Галлюцинации и оценка (стр. 301–304)
**Главная мысль:** VLM склонны к «визуальному сикофанству» (поддакиванию пользователю), что требует особых методов проверки.

**Проблема:** Если спросить «Где здесь ржавчина?», модель может принять пятно грязи за ржавчину, чтобы угодить запросу (стр. 301).
**Как бороться (Blind Verification):** 
1. Подать фото с нейтральным промптом («Опиши поверхность»). 
2. Сравнить этот ответ с вопросом пользователя с помощью отдельной текстовой LLM (стр. 302).

**Как оценивать (метрики):**
- **Поиск (Retrieval):** метрика `recall@k` на «золотом наборе» пар «текст-картинка» (стр. 302).
- **Генерация:** метод `VLM-as-a-judge` (сильная модель оценивает ответ другой модели по шкале 1–5 на основе визуальных доказательств) (стр. 302).

**Где нам пригодится:** Проверка (контроль качества ответов ИИ), Данные (очистка данных от ложных срабатываний).

## Глава 9: Knowledge-Enhanced RAG (стр. 305–316)

### 1. Обзор Графов Знаний (KG) (стр. 305–310)
**Главная мысль:** Векторный поиск работает с вероятностями, а Графы Знаний — с детерминированными фактами. KG незаменимы для сложных запросов.

**Когда векторный поиск (RAG) пасует:**
- Факты, привязанные ко времени (кто был CEO в октябре 2022?).
- Пересечение нескольких условий (лекарства, взаимодействующие и с А, и с Б).
- Многошаговые рассуждения (кто актер в фильме 2014 года, снятом режиссером фильма «Начало»?).

**Термины:**
- **Узлы (Nodes):** сущности (Человек, Фильм, Жанр).
- **Ребра (Edges):** связи между ними (`ACTED_IN`, `DIRECTED`).
- **Онтология:** абстрактные правила («Человек может режиссировать Фильм», но не наоборот).
- **Схема:** техническая реализация в БД (названия полей, типы данных) (стр. 310).

**Языки запросов:**
- **Cypher:** интуитивный, похож на рисунок графа. Примеры: `(p:Person)-[:DIRECTED]->(m:Movie)`.
- **SPARQL:** стандарт для RDF-хранилищ, работает с тройками (субъект-предикат-объект) (стр. 308–309).

**Где нам пригодится:** Память (структурирование связей между проектами/людьми), Данные (сложная аналитика).

---

### 2. Интеграция KG в RAG (стр. 310–316)
**Главная мысль:** Графы можно использовать либо для дополнения найденных фрагментов текста, либо как альтернативный путь поиска.

**Два основных метода:**
1. **Обогащение чанков (Chunk Enrichment):**
    - Сначала обычный векторный поиск находит фрагмент (напр., цитату из фильма).
    - Затем по сущностям из этого фрагмента (имя персонажа) в Графе ищутся дополнительные факты (кто актер, какой фильм).
    - В LLM подается: `Текст чанка + Пакет знаний из графа` (стр. 313–314).
2. **Гибридный граф-поиск (Hybrid-graph retrieval):**
    - LLM переводит вопрос пользователя в запрос на Cypher/SPARQL (зная схему графа).
    - БД возвращает точные узлы и связанные с ними чанки.
    - Результаты графа смешиваются с результатами векторного поиска и идут в LLM (стр. 315).

**Нюанс построения:** создание графа — трудоемкий процесс. В примере использовался NER (распознавание именованных сущностей) через регулярные выражения для имен персонажей в сценариях (стр. 311).

**Где нам пригодится:** Запросы (сложные вопросы по базе знаний), Помощники (создание агента, который точно знает связи в данных).
