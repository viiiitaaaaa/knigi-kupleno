## 1. Reranking (стр. 220‑220)  
- **Главная мысль** – Ререйтенг (перестановка) используется как второй проход над результатами поиска, оставляя только K самых релевантных элементов.  
- **Как делать**  
  1. Выполнить «быстрый» первоначальный поиск (BM25, косинус и т.п.).  
  2. Объединить кандидаты из всех источников (20 + штук, если их несколько).  
  3. Применить ререйтенг‑модель (LLM‑based или cross‑encoder).  
  4. Отфильтровать топ‑K (обычно 5‑10) результатов и передать дальше в генерацию.  
- **Правила и числа**  
  - Применять, если ≥ 20 кандидатов, если начальный поиск «шумный» (стр. 220).  
  - Пропускать, если один источник с хорошим ранжированием, либо стоимость LLM‑вызова не оправдывается (стр. 220).  
  - Стоимость – один LLM‑запрос + возможный cross‑encoder; latency – добавочный шаг (стр. 220).  
- **Шаблоны и примеры** – Интеграция через LangChain → `RankLLM Reranker`, LlamaIndex → `ColbertRerank`, Haystack → `SentenceTransformersSimilarityRanker` (стр. 220).  
- **Ошибки и предупреждения** – Не заменяйте быстрый первичный поиск ререйтенгом; это лишь второй шаг, иначе потеряется эффективность.  
- **Где нам пригодится** – При построении RAG‑систем с несколькими источниками (поиск, фильтрация, генерация).  

## 2. Разбиение сложных запросов на подзапросы (стр. 221‑224)  
### 7.8 Decomposing Complex Queries into Multiple Subqueries (стр. 221‑224)  
- **Главная мысль** – Сложный вопрос разбивается на серию более простых подзапросов, каждый из которых отдельно ищет контекст, а потом собирает ответы в один итоговый вывод.  
- **Как делать**  
  1. С помощью LLM сформулировать запрос‑промпт, который будет делить вопрос (см. `splitter_prompt`).  
  2. Передать оригинальный запрос и промпт в OpenAI SDK с `response_format=Questions` (стр. 221).  
  3. Получить список `Question`‑объектов (разложенные вопросы).  
  4. Для каждого подзапроса выполнить семантический поиск, сгенерировать ответ.  
  5. С помощью финального «reasoning‑prompt» собрать все под‑ответы в один обобщённый ответ.  
- **Правила и числа**  
  - Использовать, когда вопрос требует агрегировать данные из нескольких источников (стр. 223).  
  - Стараться избегать, если вопрос прост (стр. 223).  
  - Требует 2 вызова LLM (разбор + синтез) + N поисков (стр. 223).  
- **Шаблоны и примеры**  
  - Промпт `splitter_prompt` (стр. 222)  
  - Пример кода: `client.beta.chat.completions.parse(..., response_format=Questions)` (стр. 222).  
  - Пример разбивки: «What are the benefits of renewable energy compared to fossil fuels?» → 5 подзапросов (стр. 223).  
- **Ошибки и предупреждения** – Не использовать, если добавленная латентность из‑за двух LLM‑вызовов недопустима; проверяйте, что отдельные подзапросы действительно нужны.  
- **Где нам пригодится** – При запросах типа «Сравните X и Y», «Какая компания прибыльнее?», где нужен сбор разных данных.  

## 3. Введение в агентный RAG (стр. 225‑229)  
### 8.1 Designing a Custom Tool in Python (стр. 229‑230)  
- **Главная мысль** – Инструменты для агентных систем реализуются как обычные Python‑функции, а их описание (docstring) служит «контрактом» для LLM, который решает, когда их вызывать.  
- **Как делать**  
  1. Написать функцию, реализующую нужную задачу (пример — `get_weather`).  
  2. Оформить подробный docstring: цель, параметры, типы, возвращаемое значение.  
  3. Добавить функцию в набор «tools», который передаётся LLM.  
- **Правила и числа**  
  - Каждый инструмент должен решать одну задачу (стр. 230).  
  - Не писать инструменты, если есть готовые решения (веб‑поиск, исполнение кода) (стр. 230).  
- **Шаблоны и примеры** – Функция `get_weather(latitude, longitude)` с полной docstring (стр. 229).  
- **Ошибки и предупреждения** – Пропустить обработку ошибок: таймауты, ограничения API (стр. 230).  
- **Где нам пригодится** – При построении собственных бизнес‑инструментов (внутренние БД, расчёты).  

### 8.2 Using Workflow Patterns in Multi‑agent Systems (стр. 230‑235)  
- **Главная мысль** – Существует пять типовых паттернов организации работы агентов: последовательное цепочечное (Prompt chaining), маршрутизация (Routing), параллельные задачи (Parallel tasks), оркестратор‑рабочие (Orchestrator‑workers) и оценка‑оптимизация (Evaluator‑optimizer). Выбор зависит от взаимозависимости шагов и требований к скорости.  
- **Как делать** (общий алгоритм)  
  1. Определить характер задачи (зависит ли шаг от результата предыдущего?).  
  2. Выбрать подходящий паттерн:  
     - **Prompt chaining** – каждый LLM‑вызов получает вывод предыдущего (стр. 231).  
     - **Routing** – первый LLM решает, какой инструмент/под‑workflow задействовать (стр. 231‑232).  
     - **Parallel tasks** – независимые подзадачи исполняются одновременно, потом агрегируются (стр. 232‑233).  
     - **Orchestrator‑workers** – главный агент распределяет работу между специализированными суб‑агентами (стр. 233‑234).  
     - **Evaluator‑optimizer** – один LLM генерирует черновик, другой проверяет, цикл повторяется (стр. 234‑235).  
  3. Реализовать выбранный паттерн (см. рецепты 8.5, 8.8 для кода).  
- **Правила и числа**  
  - Параллельность ограничена токен‑лимитом API (стр. 232).  
  - Маршрутизация удобна при 5‑10 типах сценариев (стр. 232).  
  - Оценка‑оптимизация ограничивается максимумом итераций (стр. 234).  
- **Шаблоны и примеры** –  
  - Prompt chaining: извлечение текста из PDF → перевод → переформулировка (стр. 231).  
  - Routing: обработка письма с вложениями vs. простое письмо (стр. 232).  
  - Parallel tasks: обработка страниц контракта параллельно (стр. 232‑233).  
  - Orchestrator‑workers: запрос SQL, поиск Wiki, прямой LLM‑вызов (стр. 233‑234).  
  - Evaluator‑optimizer: написание технического блога, оценка и исправление (стр. 234‑235).  
- **Ошибки и предупреждения** – Параллельные паттерны добавляют оверхед, полезны лишь для долгих подзадач; маршрутизация требует чёткой классификации; оркестратор повышает латентность из‑за множества LLM‑вызовов (стр. 235).  
- **Где нам пригодится** – При построении агентов, где подзадачи могут быть независимы (параллельные), или где нужно динамически выбирать инструмент (routing).  

### 8.3 Choosing an Agentic Framework (стр. 235‑239)  
- **Главная мысль** – Фреймворки различаются уровнем абстракции: без кода (но‑код), агентные библиотеки (code‑first) и «с нуля». Выбор зависит от требуемого контроля, скорости разработки и ресурсов команды.  
- **Как делать** (по таблицам)  
  1. Оценить требуемый срок разработки, размер команды, уровень опыта.  
  2. Сопоставить требования с уровнем абстракции:  
     - **No‑code** (Copilot Studio, Zapier) – быстрый старт, без кода, но ограниченный контроль (стр. 236).  
     - **Agentic frameworks** (OpenAI Agents SDK, LangGraph) – код‑first, стандартные примитивы (инструменты, память, трассировка) (стр. 236‑237).  
     - **From scratch** – прямой вызов моделей, полное управление (стр. 237‑238).  
  3. Выбрать вариант, учитывая: масштаб, гибкость, необходимость аудита/трассировки, зависимостей (стр. 237‑238).  
- **Правила и числа**  
  - No‑code подходит для 2‑5‑шаговых внутренних процессов (стр. 236).  
  - Light‑weight frameworks дают лёгкую миграцию и минимум блокировки (стр. 236).  
  - From‑scratch требует высоко квалифицированных разработчиков (стр. 237).  
- **Шаблоны и примеры** – Таблица 8‑1 (уровни), Таблица 8‑2 (сценарии) (стр. 236‑238).  
- **Ошибки и предупреждения** – Не начинать с тяжёлых фреймворков, если простой прототип нужен быстро; каждое дополнительное зависимое ПО увеличивает поверхность атак и сложность отладки (стр. 239).  
- **Где нам пригодится** – При планировании собственного агентного решения: выбираем SDK‑/LangGraph‑подход, если нужен баланс между контролем и скоростью.  

### 8.4 Building an Agentic System via Function Calling (стр. 239‑244)  
- **Главная мысль** – Без использования фреймворков агентную логику можно реализовать через «function calling»: LLM получает словарь с описаниями функций, решает, какие из них вызывать, а Python исполняет их.  
- **Как делать**  
  1. **Определить функции‑инструменты** (например, `add_numbers`, `subtract_numbers`, `get_weather`). Каждый функции нужен подробный docstring (стр. 240‑241).  
  2. **Собрать словарь `tools`**:  
     - `type: "function"`  
     - `function: { name, description (из `__doc__`), parameters (JSON‑схема) }` (стр. 241‑242).  
  3. **Отправить запрос LLM** с параметром `tools=tools` и пользовательским запросом (стр. 242‑243).  
  4. **Получить `tool_calls`** из ответа, распарсить аргументы, вызвать соответствующую функцию (`globals().get(tool_name)`) (стр. 242‑243).  
  5. **Повторять в цикле**, пока модель не вернёт финальный ответ (`finish_reason != "tool_calls"`). Цикл реализован в `while finish_reason == "tool_calls": …` (стр. 242‑244).  
- **Правила и числа**  
  - Каждый вызов функции → один дополнительный LLM‑раунд‑трип (стр. 244).  
  - Для ускорения использовать батчинг или асинхронность (см. рецепт 8.5).  
- **Шаблоны и примеры**  
  - Функция `add_numbers` с docstring (стр. 240‑241).  
  - Пример создания `tools`‑словаря, где `description` берётся из `add_numbers.__doc__` (стр. 241‑242).  
  - Цикл выполнения `process_function_invocations` и `while finish_reason == "tool_calls"` (стр. 242‑244).  
  - Пример математической задачи: `"What is the result of (5.0 + 3.0) * 2.0?"` (стр. 242‑244).  
- **Ошибки и предупреждения** – Не полагаться только на LLM для арифметики (стр. 244); каждый вызов увеличивает латентность, поэтому для простых запросов лучше один LLM‑вызов.  
- **Где нам пригодится** – Когда нужен доступ к внешним данным (погода, БД) или точные вычисления, которые LLM выполнить не может.  

### 8.5 Accelerating Agents with asyncio (стр. 245‑250)  
- **Главная мысль** – `asyncio` позволяет запускать независимые I/O‑объективные задачи (вызовы API, обработку файлов) параллельно, тем самым сокращая общее время ответа агента.  
- **Как делать**  
  1. Объявить функции‑корутины `async def …` (например, `fetch_data`, `process_data`).  
  2. Внутри использовать `await asyncio.sleep(...)` или реальный async‑API (стр. 245).  
  3. В главной функции `async def main():` вызвать `await asyncio.gather(coro1, coro2, …)` (стр. 245).  
  4. Запустить цикл `asyncio.run(main())`.  
  5. При работе с реальными LLM‑вызовами использовать `openai.AsyncOpenAI()` и `await client.chat.completions.create(...)` (стр. 247‑248).  
- **Правила и числа**  
  - Общая длительность задачи ≈ самому долгому отдельному вызову (стр. 245).  
  - При обработке PDF‑страниц ограничение – токен‑лимит API (стр. 248).  
  - Пример ускорения: 3 сек → 2 сек при двух задачах (стр. 245).  
- **Шаблоны и примеры**  
  - Мини‑пример с `fetch_data` и `process_data` (стр. 245).  
  - Параллельный извлекатель сущностей из изображений (`extract_entities_from_image`) и агрегатор (стр. 247‑249).  
- **Ошибки и предупреждения** – Не использовать для последовательных зависимых шагов; асинхронность усложняет отладку и требует обработки частичных ошибок (стр. 235).  
- **Где нам пригодится** – При одновременном запросе к нескольким API (поиск, эмбеддинги, визуальная модель) в пользовательском чат‑боте.  

### 8.6 Building a Sales Negotiation Agent with OpenAI’s Agents SDK and Chroma (стр. 250‑256)  
- **Главная мысль** – С помощью лёгкого фреймворка OpenAI Agents SDK и векторного хранилища Chroma можно собрать многоагентную систему (модератор + продавец + клиент) для автоматизированных переговоров.  
- **Как делать**  
  1. **Установить зависимости**: `pip install openai-agents chromadb` и, при работе с PDF, `poppler-utils` (стр. 251).  
  2. **Создать векторный магазин** `chroma_email_history_db`, загрузить в него документы‑письма и добавить в коллекцию `email_history` (стр. 252).  
  3. **Определить инструмент‑поиск** `query_database` (декоратор `@function_tool`) – делает семантический запрос к Chroma (стр. 253).  
  4. **Создать агента‑продавца** (`salesman_agent`) с инструкциями, инструментом `query_database` и моделью `gpt‑5.2` (стр. 254).  
  5. **Определить вспомогательную функцию** `negotiate_with_customer` для вызова агента (стр. 254).  
  6. **Создать клиентского агента** (`customer_agent`) без специальных инструментов (стр. 255).  
  7. **Обернуть оба агента в инструменты** с помощью `as_tool` (стр. 255).  
  8. **Сконструировать модератора** (`moderator_agent`) с инструкциями, где он чередует вызовы `salesman_agent_tool` и `customer_agent_tool` до согласования (стр. 256).  
  9. **Запустить процесс** через `Runner.run(moderator_agent, ...)` и наблюдать трассировку в OpenAI‑консоли (стр. 256).  
- **Правила и числа**  
  - Для демонстрации используют 3 страницы PDF, но реальная система может работать с произвольным объёмом (стр. 247‑249).  
  - При работе с Chroma удалять предыдущую директорию, чтобы перезаписать данные (стр. 252).  
- **Шаблоны и примеры**  
  - Пример кода создания Chroma DB (стр. 252).  
  - Декоратор `@function_tool` над `query_database` (стр. 253).  
  - Инструкция продавца (стр. 254).  
  - Пример модератора, чередующего два агента (стр. 256).  
- **Ошибки и предупреждения** – Не забывать о трассировке и логировании (стр. 256); при масштабировании может возникнуть блокировка из‑за частых запросов к Chroma, планировать кэширование.  
- **Где нам пригодится** – Автоматизация переговоров, поддержка продаж, обработка цепочек писем с рекомендациями и ценами.
