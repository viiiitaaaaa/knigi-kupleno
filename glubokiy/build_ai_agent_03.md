## 1. Установка «дефолтного» отношения к инструментам (стр. 53‑53)  
- **Главная мысль** – Чётко задайте агенту правило, когда он обязан использовать инструменты, а когда может обойтись без них.  
- **Как делать**  
  1. Сформулируйте положительное правило: «использовать проактивно, без разрешения».  
  2. Укажите конкретные случаи: для быстро меняющейся информации (цены акций, новости) – поиск сразу; для медленно меняющихся тем (позиции правительств, CEO) – поиск всегда, когда вопрос о текущем статусе.  
- **Правила и числа** – Нет числовых ограничений, только формулировка «use proactively, without asking permission».  
- **Шаблоны и примеры** – *«For rapidly changing information (stock prices, breaking news), search immediately. For slower‑changing topics … always search if the question asks about the current status.»*  
- **Ошибки и предупреждения** – Слишком общие формулировки («use when necessary») приводят к неопределённому поведению.  
- **Где нам пригодится** – При проектировании систем‑подсказок (system prompt) для любого агент‑бота, который будет использовать поиск, калькуляторы и пр.

## 2. Определение триггер‑шаблонов (стр. 53‑54)  
- **Главная мысль** – Дайте LLM чёткие лингвистические сигналы, по которым он будет вызывать нужный инструмент.  
- **Как делать**  
  1. Составьте список типовых выражений, указывающих на необходимость инструмента.  
  2. Привяжите каждый шаблон к конкретному инструменту (например, поиск по разговору).  
- **Шаблоны и примеры**  

| тип | примеры |
|-----|----------|
| Явные ссылки | «What we discussed…», «As I mentioned before…» |
| Временные ссылки | «What did we talk about yesterday?», «Show me last week’s chat.» |
| Неявные сигналы | «You suggested», «We decided», «My project», «That bug» |

- **Ошибки** – Пропуск типовых формулировок из реального общения ухудшает точность вызова.  
- **Где пригодится** – При построении инструкций для инструментов «поиск по истории диалога», «поиск файлов».

---

## 3. Негативные направления (стр. 53‑54)  
- **Главная мысль** – Нужно явно указать, когда инструменты **не** использовать, иначе будет рост расходов и задержек.  
- **Как делать**  
  1. Перечислите типы запросов, где поиск не нужен (вневременная информация, определения, фундаментальные факты).  
  2. Добавьте в системный промпт фразу‑запрет: «Don’t search for…».  
- **Шаблоны** – *«Don’t search for timeless information, fundamental concepts, definitions, or well‑established technical facts.»*  
- **Ошибки** – Позволять агенту искать всё приводит к лишним расходам и плохому UX (запросы «How do I write a for loop in Python?»).  
- **Где пригодится** – При работе с платными API‑инструментами (web‑search, база данных), где важно контролировать количество запросов.

## 4. Якорение примером (стр. 53‑54)  
- **Главная мысль** – Примеры ввод‑вывод (инпут‑аутпут) делают правила более понятными LLM, чем абстрактные указания.  
- **Как делать**  
  1. Приведите пару типовых диалогов: запрос → действие → ответ.  
  2. Покажите как **не** вызывать инструмент (пример с теоремой Пифагора).  
- **Примеры**  

1. *User*: «What’s Samsung Electronics’ current stock price?» → *Action*: `[web_search: Samsung Electronics stock price]` → *Response*: «Samsung Electronics’ current stock price is XX won».  
2. *User*: «What is the Pythagorean theorem?» → *Action*: *none* → *Response*: «The Pythagorean theorem states that …».  

- **Ошибки** – Отсутствие конкретных пар приводит к неоднозначности.  
- **Где пригодится** – При обучении собственного агента‑помощника в Claude.

## 5. Описание инструментов в промпте (стр. 54‑55)  
- **Главная мысль** – Чтобы LLM правильно выбирал и вызывал инструменты, нужно дать ему чёткое, полное описание каждого инструмента (что делает, какие параметры принимает, что возвращает).  
- **Как делать**  
  1. Для каждого инструмента составьте схему (JSON‑schema) с полями `name`, `description`, `parameters`.  
  2. Включите типы параметров, ограничения (`enum`, `minimum`, `format`).  
- **Ошибки** – Вагонные или неполные описания приводят к неверному выбору инструмента или к его не вызову.  
- **Где пригодится** – При реализации собственного калькулятора, веб‑поиска, чтения файлов.

## 6. Эксперимент GAIA (стр. 55‑61)  

### 6.1 Зачем GAIA (стр. 55‑55)  
- **Главная мысль** – GAIA — публичный набор проверяемых задач, позволяющий измерять прогресс агента.  
- **Требования к тест‑кейсам**  
  1. Иметь проверяемый ответ.  
  2. Быть реалистичными запросами пользователей.  
  3. Охватывать разные уровни сложности.  

### 6.2 Загрузка датасета (стр. 55‑55)  
```python
from datasets import load_dataset
level1_problems = load_dataset("gaia-benchmark/GAIA", "2023_level1", split="validation")
print(f"Number of Level 1 problems: {len(level1_problems)}")
```  
- **Важно** – Нужно иметь аккаунт HF и переменную окружения `HF_TOKEN`.  

### 6.3 Структура проблемы (стр. 55‑56)  
```json
{
  "task_id": "...",
  "Question": "...",
  "Level": 1,
  "Final answer": "17",
  "file_name": "",
  "Annotator Metadata": {
    "Steps": "...",
    "Tools": "1. A web browser.\n2. A search engine.\n3. A calculator.",
    "Number of tools": "3"
  }
}
```  
- **Вывод** – Уже уровень 1 может требовать 3 инструмента.  

### 6.4 Определение формата ответа (стр. 56‑57)  
```python
class GaiaOutput(BaseModel):
    is_solvable: bool
    unsolvable_reason: str = ""
    final_answer: str = ""
```  
- **Поле `is_solvable`** – сообщает, может ли модель решить задачу без инструментов.  

### 6.5 Пайплайн оценки  

| Шаг | Описание |
|-----|----------|
| **1** | Формулируем системный запрос GAIA (см. текст). |
| **2** | Реализуем асинхронный вызов `solve_problem` с семафорами‑лимитерами. |
| **3** | Проверяем `finish_reason` = `refusal` → считаем задачу **unsolvable**. |
| **4** | Сравниваем `final_answer` с `Final answer` при помощи `is_correct`. |
| **5** | Сохраняем метаданные (правильность, причина отказа, ошибки). |
| **6** | Параллельно обрабатываем все комбинации `модель‑задача` через `asyncio.gather`. |

#### 6.5.1 Управление лимитами API (стр. 57‑58)  
```python
PROVIDER_SEMAPHORES = {"openai": asyncio.Semaphore(30),
                       "anthropic": asyncio.Semaphore(10)}
```  
- **Совет** – Настраивайте значения под ваш тариф.  

#### 6.5.2 Функция `solve_problem` (стр. 58‑59)  
- Делает запрос к модели, возвращает `GaiaOutput`.  
- Обрабатывает отказ модели (`finish_reason == "refusal"`).  

#### 6.5.3 Функция `is_correct` (стр. 59‑60)  
```python
def is_correct(prediction, answer):
    return prediction.strip().lower() == answer.strip().lower()
```  
- Игнорирует регистр и пробелы.  

#### 6.5.4 Оценка одной задачи `evaluate_gaia_single` (стр. 60‑61)  
- Возвращает словарь с `task_id`, `model`, `correct`, `is_solvable`, `prediction`, `unsolvable_reason`, `error` (при исключении).  

#### 6.5.5 Запуск полного эксперимента (стр. 61‑62)  
- Пример выбора моделей: `gpt-5`, `gpt-5-mini`, `anthropic/claude-sonnet-4-5`, `anthropic/claude-haiku-4-5`.  
- Тестируем сначала 20 вопросов, потом расширяем.  

### 6.6 Результаты и анализ (стр. 62‑63)  

| Model | Accuracy (correct/20) | Judged solvable |
|-------|----------------------|-----------------|
| GPT‑5 | 10 / 20 (50 %) | 11 / 20 (55 %) |
| GPT‑5‑mini | 4 / 20 (20 %) | 8 / 20 (40 %) |
| Claude Sonnet 4.5 | 3 / 20 (15 %) | 4 / 20 (20 %) |
| Claude Haiku 4.5 | 3 / 20 (15 %) | 4 / 20 (20 %) |

- **Вывод** – Без инструментов максимум ≈ 25 % (5 из 20) решаемых.  
- **Самооценка моделей** – Некоторые «консервативно» определяют решаемость (близко к 5), другие «амбитно» (8‑11) и иногда «угадывают» ответы из тренировочных данных.  
- **Отказ модели** – При нелинейном/зашифрованном запросе («.rewsna…») некоторые модели отказываются из‑за политики безопасности.  

### 6.7 Ключевые выводы (стр. 63‑64)  
- LLM‑модели умеют **отмечать свои ограничения** → полезно для решения через инструменты.  
- Память‑тренировочные данные **не заменяют** актуальные источники.  
- **> 75 %** даже самых простых GAIA‑задач нуждаются в веб‑поиске, чтении файлов, калькуляции.  

### 6.8 Краткое итоги (стр. 64‑64)  
- Закрытые LLM (OpenAI, Anthropic) удобны для прототипов (утилита tool‑calling, structured output).  
- LiteLLM — унифицированный клиент с async‑вызовами и rate‑лимитами.  
- System prompt должен подчёркивать **автономные действия** и **стратегическое использование инструментов**.

## 7. Введение в инструменты (страница 64‑66)  

### 7.1 Зачем инструменты (стр. 64‑65)  
- **Главная мысль** – LLM не могут напрямую получать актуальные данные, влиять на мир или выполнять специализированные вычисления; инструменты решают временные, интерактивные и функциональные ограничения.  

### 7.2 Типы инструментов (стр. 66‑67)  
| Категория | Примеры |
|-----------|--------|
| **Временные** | веб‑поиск, API новостей, цены акций |
| **Интерактивные** | бронирование билетов, отправка email, управление IoT |
| **Функциональные** | калькуляторы, исполнители кода, генераторы изображений, синтез речи |

### 7.3 Кастомные vs нестандартные инструменты (стр. 67‑68)  
- **Кастомные** – пишутся разработчиком (внутренние API, скрипты). Плюс — полный контроль, минус — ответственность за поддержку и безопасность.  
- **Нестандартные (provider‑tools)** – готовые (OpenAI web‑search, Anthropic web‑search, Gemini code‑execution). Плюс — мгновенная готовность, минус — ограниченная кастомизация и потенциальные изменения со стороны провайдера.  

### 7.4 Почему строить свои инструменты (стр. 68‑69)  
- Позволяет отлаживать процесс (какой из этапов сломался).  
- Необходимость уникальных бизнес‑функций (внутренние базы, проприетарные API).

## 8. Механизм вызова инструментов (стр. 69‑73)  

### 8.1 Общий процесс (стр. 69‑70)  
1. **Отправка** сообщения + **определений** инструментов LLM.  
2. LLM **решает**, нужен ли инструмент, и **генерирует** структуру вызова (`tool_calls`).  
3. **Внешняя** система **выполняет** инструмент, получает результат.  
4. Результат возвращается в LLM как сообщение роли `tool`.  
5. LLM **формирует** окончательный пользовательский ответ.  

### 8.2 Схема определения инструмента (пример калькулятора) (стр. 70‑71)  

```json
{
  "type": "function",
  "function": {
    "name": "calculator",
    "description": "Perform basic arithmetic operations.",
    "parameters": {
      "type": "object",
      "properties": {
        "operator": {"type": "string", "enum": ["add","subtract","multiply","divide"]},
        "first_number": {"type": "number"},
        "second_number": {"type": "number"}
      },
      "required": ["operator","first_number","second_number"]
    }
  }
}
```  

### 8.3 Реализация функции (стр. 71‑72)  
```python
def calculator(operator, first_number, second_number):
    if operator == 'add': return first_number + second_number
    elif operator == 'subtract': return first_number - second_number
    elif operator == 'multiply': return first_number * second_number
    elif operator == 'divide':
        if second_number == 0: raise ValueError("Cannot divide by zero")
        return first_number / second_number
    else: raise ValueError(f"Unsupported operator: {operator}")
```  

### 8.4 Пример вызова (стр. 72‑73)  

| Запрос | Что делает LLM |
|--------|----------------|
| «What is the capital of South Korea?» | Отдаёт прямой текст, `tool_calls = None`. |
| «What is 1234 × 5678?» | Генерирует `tool_calls` → `calculator` с аргументами `{"operator":"multiply","first_number":1234,"second_number":5678}`. |

### 8.5 Выполнение и возврат результата (стр. 73‑74)  
- Извлекаем `function_name` и `function_args` из `tool_calls`.  
- Вызываем соответствующую функцию (`calculator`).  
- Добавляем сообщение роли `tool` с полем `content` = результат.  
- Повторный запрос к LLM → окончательный человекочитаемый ответ.  

### 8.6 Обратный цик (стр. 74‑74)  
1. **Call** → **Execute** → **Return** → **Reason**.  
- Для простых инструментов (калькулятор) окончательный ответ может совпадать с результатом, но для сложных (веб‑поиск) требуется дополнительный шаг синтеза.

## 9. Как LLM выбирает инструмент (стр. 74‑75)  
- Обучение на датасетах «tool definition ↔ tool call» (пример – `hermes-function-calling-v1`).  
- После обучения модель умеет:  
  1. Понять, нужен ли инструмент.  
  2. Выбрать нужный из списка.  
  3. Выделить параметры из естественного языка.  
  4. Сформировать структурированный `function call`.

## 10. Рекомендации по корректному описанию инструментов (стр. 75‑77)  

### 10.1 Чёткие и явные определения (стр. 75‑75)  
- **Антипаттерн**: `{ "name":"book", "description":"Book something", "parameters":{ "when": {"type":"string"} } }` – неясно, что бронировать.  
- **Улучшенный**:  

```json
{
  "name": "reserve_table",
  "description": "Create a restaurant table reservation.",
  "parameters": {
    "type": "object",
    "properties": {
      "restaurant_id": {"type":"string","description":"Internal ID, e.g., rst_123"},
      "datetime": {"type":"string","format":"date-time","description":"ISO‑8601"},
      "party_size": {"type":"integer","minimum":1,"maximum":20},
      "notes": {"type":"string","description":"Optional (allergies, occasion)"}
    },
    "required": ["restaurant_id","datetime","party_size"]
  }
}
```  

### 10.2 Избегать конфликтных параметров (стр. 76‑76)  
- **Антипаттерн**: `toggle_light(on: bool, off: bool)` → может быть `on=True, off=True`.  
- **Правильный**: один параметр‑enum:  

```json
{
  "name": "toggle_light",
  "description": "Control the light state",
  "parameters": {
    "type":"object",
    "properties": {"state":{"type":"string","enum":["on","off"]}},
    "required":["state"]
  }
}
```  

### 10.3 Сокращение нагрузки модели (стр. 77‑77)  
- Не заставляйте модель постоянно передавать уже известные ID.  
- **Плохой пример**: `submit_refund(order_id, reason)`.  
- **Хороший пример**: `submit_refund(reason)` → код передаёт актуальный `order_id` из контекста.  

### 10.4 Ограничение числа инструментов (стр. 77‑77)  
- Рекомендовано ≤ 20 инструментов; больше – повышает риск неверного выбора. При необходимости – **файн‑тюн** модель.

## 11. Создание собственного веб‑поиска (стр. 77‑78)  

### 11.1 Выбор провайдера (Tavily) (стр. 77‑77)  
- Tavily — оптимизированный под LLM API, до 1 000 запросов / мес бесплатно.  
- Регистрация → API‑ключ → `.env` (`TAVILY_API_KEY`).  

### 11.2 Установка пакета (стр. 77‑77)  
```bash
uv add tavily-python
```  

### 11.3 Базовая реализация (стр. 78‑78)  
```python
import os
from tavily import TavilyClient
from dotenv import load_dotenv

load_dotenv()
client = TavilyClient(os.getenv("TAVILY_API_KEY"))

def search_web(query: str, max_results: int = 2):
    return client.search(query, max_results=max_results)
```  

- **Цель** – простая проверка соединения и возврата результатов.
