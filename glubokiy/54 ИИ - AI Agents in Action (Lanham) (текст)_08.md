## 8.1 Understanding retrieval in AI applications (стр. 205–206)
- Главная мысли: Извлечение (Retrieval) в агентах и чатах — это механизм получения знаний из внешнего долгосрочного хранилища для добавления контекста в промпт. Оно бывает двух типов: неструктурированные знания (история диалогов, факты, предпочтения) и структурированные знания (базы данных, файлы).
- Правила и числа: Нет числовых значений в этом разделе.
- Шаблоны и примеры: Стратегии промпт-инжиниринга: «Предоставить опорный текст» (Provide Reference Text — снижает галлюцинации) и «Использовать внешние инструменты» (Use External Tools — поиск на основе эмбеддингов, выполнение кода).
- Ошибки и предупреждения: Знания не считаются памятью, это дополнение промпта из существующих документов.
- Где нам пригодится: Для запросов, проверки и памяти при работе со своими скриптами.

## 8.2 The basics of retrieval augmented generation (RAG) (стр. 206–207)
- Главная мысль: RAG (генерация, дополненная извлечением) — стандарт для запросов по документам, состоящий из двух фаз: предварительное индексирование (загрузка, разбивка на чанки, создание эмбеддингов и сохранение в векторную БД) и сам запрос через семантический поиск. Память работает по тому же принципу, но сохраняет части разговоров.
- Как делать (фазы RAG):
  1. Загрузить документ, трансформировать и разбить на чанки (фрагменты текста).
  2. Превратить чанки в векторы (эмбеддинги) и сохранить в векторную БД.
  3. Сделать запрос пользователя, превратить его в вектор.
  4. Найти семантически похожие чанки в БД (поиск по векторному сходству).
  5. Передать найденный контекст и запрос в LLM для генерации ответа.
- Правила и числа: Нет числовых значений в этом разделе.
- Шаблоны и примеры: Паттерны RAG и Memory Retrieval (показаны на схемах рис. 8.2 и 8.3): Шаг 1: Retrieve (Поиск), Шаг 2: Augment (Дополнение промпта), Шаг 3: Generate (Генерация ответа), Шаг 4: Remember (Сохранение ответа в память).
- Ошибки и предупреждения: Паттерн извлечения и индексация документов имеют множество нюансов и требуют тщательного проектирования.
- Где нам пригодится: Для понимания логики работы RAG-пайплайнов и памяти агентов.

## 8.3 Delving into semantic search and document indexing (стр. 208–215)
- Главная мысль: Индексирование преобразует информацию для легкого поиска по смыслу (семантический поиск), используя векторные представления, расчеты расстояний и векторные базы данных.
- Как делать (векторизация и поиск через TF-IDF и Chroma):
  1. Установить зависимости из `requirements.txt` в окружении VS Code.
  2. Рассчитать Term Frequency (TF): частота слова в документе делим на общее число слов.
  3. Рассчитать Inverse Document Frequency (IDF): логарифм (всего документов ÷ документов со словом).
  4. Вычислить TF-IDF = TF × IDF.
  5. Вычислить косинусное сходство (cosine similarity) между векторами документов.
  6. Сохранить векторы в векторную БД (например, локальную Chroma DB) и выполнять запросы через `collection.query`.
- Правила и числа:
  - Формула TF: `TF = (Количество вхождений слова) ÷ (Общее число слов в документе)` (стр. 209).
  - Пример для слова «blue» (документ из 6 слов, встречается в 4 из 8 документов): TF = 0.1670, IDF = 0.301, TF-IDF = 0.050 (стр. 209–210).
  - Косинусное сходство: диапазон от –1 (не похожи) до 1 (идентичны) (стр. 210).
  - Косинусное расстояние: `1 – Косинусное сходство`, диапазон от 0 (идентичны) до 2 (противоположны) (стр. 211, 215).
  - Размерность эмбеддингов OpenAI (`text-embedding-ada-002`): 1536 измерений, которые с помощью PCA можно уменьшить до 3 для визуализации (стр. 213–214).
- Шаблоны и примеры: Примеры кода `document_vector_similarity.py` (с использованием `scikit-learn`), `document_vector_database.py`, `document_visualizing_embeddings.py` (OpenAI + PCA) и `document_query_chromadb.py` (Chroma DB).
- Ошибки и предупреждения: TF-IDF прост, но ненадежен, так как только считает частоту слов и не понимает контекст и связи между ними.
- Где нам пригодится: Для написания скриптов индексации данных и настройки локальной векторной БД (Chroma).

## 8.4 Constructing RAG with LangChain (стр. 216–220)
- Главная мысль: Библиотека LangChain предоставляет готовые инструменты для упрощения загрузки, разбивки (chunking), эмбеддинга и сохранения документов в векторные хранилища.
- Как делать (загрузка и разбивка через LangChain):
  1. Загрузить документ (например, HTML-файл через `UnstructuredHTMLLoader`).
  2. Разбить текст на чанки с помощью `RecursiveCharacterTextSplitter` или `CharacterTextSplitter.from_tiktoken_encoder`.
  3. Сгенерировать эмбеддинги и сохранить их в векторное хранилище (например, Chroma).
  4. Выполнить поиск по схожести (`db.similarity_search`).
- Правила и числа:
  - Размер чанка в примере: 100 символов с нахлестом (overlap) 25 символов (стр. 218).
  - Токенизация: чанки по 50 токенов с нахлестом 10 токенов (стр. 219).
- Шаблоны и примеры: Файлы кода `langchain_load_splitting.py` и `langchain_token_splitting.py` для загрузки сказок Mother Goose («Матушка Гусыня») и поиска по ним.
- Ошибки и предупреждения: Слишком большие документы нельзя было подавать целиком в старые модели из-за лимита токенов; сегодня подавать целиком можно (например, в GPT-4 Turbo), но это дороже и часто дает худший результат, поэтому разбивка на чанки остается лучшей практикой.
- Где нам пригодится: Для написания скриптов предобработки и загрузки больших объемов текстовых данных.

## 8.5 Applying RAG to building agent knowledge (стр. 220–224)
- Главная мысль: Знания (Knowledge) в агентных системах реализуются через применение RAG для семантического поиска по неструктурированным документам (PDF, Word, скрипты, код). Платформа Nexus объединяет эти функции в интерфейсе Knowledge Store Manager.
- Как делать (работа со знаниями в Nexus):
- 1. Установить Nexus командой `pip install git+https://github.com/cxbxmxcx/Nexus.git` или клонировать репозиторий для разработки (`pip install -e Nexus`) (стр. 220).
  2. Запустить приложение командой `nexus run` (стр. 220).
  3. Перейти на страницу Knowledge Store Manager, создать хранилище и загрузить документ (например, сценарий `back_to_the_future.txt`) (стр. 221).
  4. Подключить хранилище знаний к агенту на странице чата и задавать вопросы (стр. 221).
- Правила и числа: На момент написания главы Nexus поддерживает работу только с одним хранилищем знаний одновременно (стр. 221).
- Шаблоны и примеры: Загрузка текстового файла сценария фильма, настройка параметров сплиттера (Chunking Option, Chunk Size, Overlap) во вкладке Configuration (стр. 221–223).
- Ошибки и предупреждения: Загрузка больших документов (как сценарий фильма) может занять некоторое время на индексацию, чанкинг и создание эмбеддингов.
- Где нам пригодится: Для проверки работы агентов со своими документами и базами знаний через готовый интерфейс.

## 8.6 Implementing memory in agentic systems (стр. 224–230)
- Главная мысль: Память агентов строится по аналогии с когнитивной памятью человека (сенсорная, кратковременная/рабочая, долговременная: эпизодическая, семантическая, процедурная). В отличие от статических знаний, память обновляется и дополняется в процессе диалогов.
- Как делать (настройка памяти в Nexus):
  1. Перейти на страницу Memory в Nexus и создать новое хранилище памяти (например, `my_memory`) (стр. 226).
  2. Выбрать движок агента и добавить личные факты/предпочтения (стр. 226).
  3. Использовать языковую модель с функцией памяти для извлечения фактов из разговора в формате JSON (стр. 227).
  4. Переключить тип памяти на **SEMANTIC** во вкладке Configuration для более глубокой семантической категоризации (стр. 228–229).
- Правила и числа: Нет новых жестких чисел, используются те же принципы векторизации.
- Шаблоны и примеры:
  - Промпт для извлечения фактов из разговора (Listing 8.10): «Summarize the conversation and create a set of statements... Return a JSON object with the following keys: 'summary'» (стр. 227).
  - Схемы разделения памяти на сенсорную (иконическая, эхоическая, тактильная), кратковременную (контекст диалога) и долговременную (декларативная, процедурная, эпизодическая, семантическая) (стр. 224).
- Ошибки и предупреждения: Память использует те же механизмы извлечения, что и знания, но кардинально отличается процессом обновления и добавления записей (информация извлекается из диалогов через LLM).
- Где нам пригодится: Для проектирования долговременной памяти персонального ИИ-помощника, помнящего предпочтения владельца.

## 8.7 Understanding memory and knowledge compression (стр. 231–233)
- Главная мысль: Со временем хранилища памяти и знаний засоряются дубликатами и нерелевантной информацией. Применение алгоритмов кластеризации (k-means) и последующего сжатия (суммаризации) через LLM очищает и оптимизирует базы данных.
- Как делать (сжатие памяти/знаний):
  1. Выбрать хранилище в Nexus и открыть интерфейс сжатия (Compression).
  2. Запустить алгоритм оптимальной кластеризации k-means для группировки похожих эмбеддингов в 3D-пространстве (стр. 231).
  3. Нажать кнопку Compress для запуска суммаризации каждой группы через LLM (стр. 232).
- Правила и числа: Для сжатия требуется движок агента, предпочтительно модели уровня GPT-4 и выше (стр. 232).
- Шаблоны и примеры: Схема процесса: сырые данные → кластеризация k-means → функция сжатия (compression function) → новые компактные эмбеддинги в векторной БД (стр. 231).
- Ошибки и предупреждения: Процесс сжатия может занять несколько минут в зависимости от размера хранилища. Память выигрывает от *периодического* сжатия, в то время как знания обычно сжимают один раз при загрузке. Множественные проходы сжатия (несколько уровней) улучшают качество поиска.
- Где нам пригодится: Для написания скриптов оптимизации локальных баз данных агента и предотвращения раздувания контекста.
