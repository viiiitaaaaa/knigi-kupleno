## 9.1 Добавление Transfer‑tool в запрос LLM (стр. 299‑300)

- **Главная мысль** – Чтобы LLM мог вызвать перенос управления между агентами, Transfer‑tool должен быть зарегистрирован в контексте и включён в список инструментов, передаваемых в запрос модели.  
- **Как делать**  
  1. При первом вызове агента проверить, есть ли уже Transfer‑tool в `context.transfer_tools`. Если нет – вызвать `_get_transfer_targets()` и, если есть цели, создать инструмент через `create_transfer_tool` и сохранить в `context.transfer_tools[self.name]`.  
  2. В `_prepare_llm_request()` собрать список текущих инструментов (`self.tools`) и добавить Transfer‑tool, если он присутствует в `context.transfer_tools`.  
  3. В `act()` построить словарь `tools_dict` из `self.tools`; если в контексте есть Transfer‑tool, добавить его в `tools_dict`.  
  4. После каждой итерации `step()` проверять `context.transfer_to`. Если флаг установлен, найти агент‑получатель (`_find_agent`) и вызвать его `run()` с тем же `context`, затем выйти из текущего цикла.  

- **Правила и числа**  
  - `max_steps` – максимальное число шагов выполнения агента (стр. 300).  
  - При обнаружении `context.transfer_to` необходимо **сбросить** флаг (`context.transfer_to = None`) перед передачей управления (стр. 300).  

- **Шаблоны и примеры**  
  ```python
  # Добавляем Transfer‑tool в запрос LLM
  if self.name in context.transfer_tools:
      llm_tools.append(context.transfer_tools[self.name])
  ```  
  ```python
  # Обнаруживаем и исполняем перенос
  if context.transfer_to:
      next_agent = self._find_agent(context.transfer_to)
      context.transfer_to = None
      await next_agent.run(None, context, verbose)
      break
  ```  

- **Ошибки и предупреждения**  
  - Не включать Transfer‑tool в список инструментов – LLM не сможет его вызвать.  
  - Оставлять `context.transfer_to` в состоянии «установлен», не сбрасывая его, может привести к бесконечному переносу.  

- **Где нам пригодится** – При построении запросов к агенту‑оркестратору и в логике `run()`/`step()` для поддержки Transfer‑pattern.

## 9.2 A2A‑протокол: Основы (стр. 301‑302)

- **Главная мысль** – A2A (Agent‑to‑Agent) – открытый HTTP‑протокол, позволяющий агентам разных команд, серверов и языков взаимодействовать, обменявшись «визитной карточкой» (agent‑card) и запросами / ответами.  

- **Как делать**  
  1. **Agent card** — JSON‑документ, размещаемый по пути `/.well-known/agent.json`. Содержит поля `name`, `description`, `url`, `version`, `capabilities`.  
  2. **Task request** — клиент отправляет POST‑запрос на `url` из карточки с полем `input`.  
  3. **Task response** — сервер возвращает JSON с полем `output`.  

- **Правила и числа** – Нет специфических чисел, только структура JSON‑карточки (стр. 302).  

- **Шаблоны и примеры**  
  ```python
  agent_card = AgentCard(
      name="math_expert",
      description="Specializes in mathematical calculations and equation solving",
      url="http://localhost:9999/",
      version="1.0.0",
      capabilities=AgentCapabilities(streaming=True),
  )
  ```  

- **Ошибки и предупреждения**  
  - Неправильный `url` — клиент будет отправлять запросы не туда.  
  - Отсутствие `/.well-known/agent.json` — клиент не сможет узнать, как обращаться к агенту.  

- **Где нам пригодится** – При интеграции внешних (локальных или облачных) агентов в пайплайн и при построении «чувствительных» к сети систем.

## 9.3 Сервер‑A2A: Экспонирование агента (стр. 303‑304)

- **Главная мысль** – Чтобы агент стал доступен по сети, нужно реализовать сервер‑A2A, который отдаёт **agent‑card** и обрабатывает **task‑request** через адаптер `AgentExecutor`.  

- **Как делать**  
  1. Создать класс‑адаптер, наследующий `AgentExecutor`. В `execute()`:  
     - получить пользовательский ввод из `RequestContext` (`context.get_user_input()`);  
     - вызвать локальный `agent.run(user_input)`;  
     - упаковать результат в A2A‑сообщение (`new_agent_text_message(result.output)`) и добавить в `event_queue`.  
  2. Сформировать `AgentCard` (см. §9.2).  
  3. Сконфигурировать `DefaultRequestHandler` с `agent_executor` и `InMemoryTaskStore`.  
  4. Создать `A2AStarletteApplication` с картой и обработчиком, запустить через `uvicorn`.  

- **Правила и числа** – Порт `9999` в примере (стр. 304).  

- **Шаблоны и примеры**  
  ```python
  class MathAgentExecutor(AgentExecutor):
      async def execute(self, context, event_queue):
          user_input = context.get_user_input()
          result = await self.agent.run(user_input)
          await event_queue.enqueue_event(
              new_agent_text_message(result.output)
          )
  ```
  ```python
  uvicorn.run(server.build(), host="0.0.0.0", port=9999)
  ```  

- **Ошибки и предупреждения**  
  - Не реализовать `execute()` — сервер не сможет запустить агент.  
  - Не подключить `agent_card` к приложению — клиент не узнает о сервере.  

- **Где нам пригодится** – При публикации собственного агента как микросервиса, которым могут пользоваться коллеги или партнёры.

## 9.4 Клиент‑A2A: RemoteAgent (стр. 305‑306)

- **Главная мысль** – `RemoteAgent`‑класс скрывает HTTP‑взаимодействие, делая удалённый агент полностью совместимым с локальными агентами (можно использовать в `sub_agents` или как `AgentTool`).  

- **Как делать**  
  1. При инициализации сохранять `base_url` и сразу запросить `/.well-known/agent.json` (метод `_load_agent_info`).  
  2. Записать `self.name` и `self.description` из полученной карточки.  
  3. Переопределить `run()`: отправить POST‑запрос на `self._agent_card["url"]` с JSON `{"input": user_input}`; получить `output` из ответа и вернуть `AgentResult`.  

- **Правила и числа** – Нет дополнительных чисел.  

- **Шаблоны и примеры**  
  ```python
  class RemoteAgent(Agent):
      def __init__(self, base_url: str):
          self.base_url = base_url
          self._load_agent_info()
      def _load_agent_info(self):
          response = httpx.get(f"{self.base_url}/.well-known/agent.json")
          self._agent_card = response.json()
          self.name = self._agent_card["name"]
          self.description = self._agent_card["description"]
      async def run(self, user_input, context=None, verbose=False):
          async with httpx.AsyncClient() as client:
              resp = await client.post(self._agent_card["url"], json={"input": user_input})
          output = resp.json().get("output", "")
          return AgentResult(output=output, context=context)
  ```
  ```python
  router = Agent(
      name="router",
      sub_agents=[local_search_agent,
                  RemoteAgent(base_url="http://partner.com")],
  )
  ```  

- **Ошибки и предупреждения**  
  - Не вызвать `_load_agent_info()` — `name/description` останутся `None`, LLM‑ориентированные решения не смогут выбрать агент.  
  - Не обрабатывать ошибки HTTP‑запроса — падение клиента при недоступном сервере.  

- **Где нам пригодится** – При построении гибридных систем, где часть агентов развернуты в разных дата‑центрах, облаках или на сторонних сервисах.

## 10.1 Почему и как автоматизировать оценку агентов (стр. 308‑309)

- **Главная мысль** – Оценка критична, так как ошибки агента могут привести к реальным потерям; автоматизация необходима из‑за огромного пространства возможных действий и необходимости проверять не только финальный вывод, но и весь процесс рассуждения.  

- **Как делать**  
  1. Встроить **наблюдаемость** (метрики, трассы, логи) в каждый уровень агента (ввод, рассуждение, вызовы инструментов, вывод).  
  2. Собрать **телеметрию** (latency, token‑usage, ошибки).  
  3. На основе телеметрии формировать **тестовые наборы** и **рубрики**.  

- **Правила и числа** – Примерные метрики (стр. 310): latency per ToolCall, total task‑completion time, API call frequency, token use, cost per task, context‑window use, LLM call error rate.  

- **Шаблоны и примеры** – Нет конкретных код‑примеров, только перечисление метрик.  

- **Ошибки и предупреждения**  
  - Собирать только логи — может привести к “data‑explosion” и сложностям анализа.  
  - Игнорировать LLM‑специфику (галлюцинации, непредсказуемость) — недостаточная оценка.  

- **Где нам пригодится** – При построении CI/CD‑потоков для агентных сервисов, когда нужно быстро проверять регрессии и стоимость.

## 10.2 Пилары наблюдаемости: Метрики, трассы, логи (стр. 310‑311)

- **Главная мысль** – Наблюдаемость состоит из трёх взаимодополняющих компонентов: **метрики** (что происходит), **трассы** (как происходит) и **логи** (подробности).  

- **Как делать**  
  1. **Метрики**: собрать численные показатели (latency, токены, стоимость, ошибки).  
  2. **Трассы**: для каждой пользовательской сессии формировать объект‑трассу, разбивая её на **spans** (LLM‑запрос, вызов инструмента, планирование) и **events** (исключения, повторные попытки).  
  3. **Логи**: записывать важные сообщения (ошибки аутентификации, ввод‑вывод инструментов).  

- **Правила и числа** – Нет новых цифр, только списки примеров (стр. 310).  

- **Шаблоны и примеры** – Пояснение: *span* — «единица работы», *event* — «мгновенное событие».  

- **Ошибки и предупреждения** – Записывать **все** логи приводит к огромному объёму; лучше использовать **селективный** подход.  

- **Где нам пригодится** – При построении дашбордов мониторинга агентов, отладке цепочек вызовов, анализе стоимости.

## 10.3 Генерация и экспорт телеметрии через OpenTelemetry (стр. 311‑312)

- **Главная мысль** – OpenTelemetry (OTel) — стандартный, вендорно‑нейтральный фреймворк для генерации, сбора и экспорта метрик, трасс и логов; использует протокол OTLP для передачи данных в любые наблюдательные платформы.  

- **Как делать**  
  1. Включить **instrumentation** в своем коде: добавить дамперы (`tracer`, `meter`) в места LLM‑вызовов, инструментов, планирования.  
  2. Сконфигурировать **экспортер** (OTLP) к выбранной системе (Langfuse, LangSmith, etc.).  
  3. Запускать сбор в продакшене; визуализировать в консоли/дашборде.  

- **Правила и числа** – Нет новых цифр.  

- **Шаблоны и примеры** – Упомянуты платформы: Langfuse, LangSmith, Arize AI, Weights & Biases.  

- **Ошибки и предупреждения** – Не использовать проприетарный код без OTel — будет трудно менять поставщика.  

- **Где нам пригодится** – При построении кросс‑командного мониторинга агентов, когда требуется портировать данные в разные аналитические бекенды.

## 10.4 Что именно оцениваем: финальный вывод, компоненты, траектория (стр. 313‑314)

- **Главная мысль** – Оценка должна охватывать **три измерения**:  
  1. **Final output** – удовлетворяет ли конечный ответ требованиям?  
  2. **Component** – корректно ли работают отдельные модули (поиск, код‑исполнитель, LLM)?  
  3. **Trajectory** – рационален ли путь (количество и порядок вызовов инструментов).  

- **Как делать**  
  1. Сформировать **evaluation dataset** (см. дальше).  
  2. Запустить агента по каждому запросу, собрать **полные трассы**.  
  3. Проанализировать каждое из трёх измерений с помощью соответствующих метрик/рубрик.  

- **Правила и числа** – Нет новых цифр.  

- **Шаблоны и примеры** – Пример оценки траектории в виде списка шагов (стр. 313).  

- **Ошибки и предупреждения** – Оценка только финального вывода может скрывать систематические ошибки.  

- **Где нам пригодится** – При построении комплексных тест‑сьютов, где нужно видеть не только «что получено», но и «как получено».

## 10.5 Типы наборов данных для оценки (стр. 315‑317)

- **Главная мысль** – Существует три основных источника данных: **Benchmark**, **Custom**, **Production**; каждый имеет свои плюсы/минусы, и лучший набор обычно комбинирует их.  

- **Как делать**  
  1. **Benchmark** – загрузить публичные наборы (HotpotQA, GAIA, SWE‑bench).  
  2. **Custom** – собрать сценарии, отражающие реальные бизнес‑задачи (корзина из 10‑30 примеров, расширять со временем).  
  3. **Production** – собрать реальные запросы и обратную связь из продакшена; при необходимости аннотировать вручную.  

- **Правила и числа** –  
  - При **error‑analysis** рекомендуется просматривать **50‑100** примеров за проход (стр. 317).  

- **Шаблоны и примеры** – Таблица 10.2 (стр. 315) с полями: `Type`, `Description`, `Pros`, `Cons`.  

- **Ошибки и предупреждения**  
  - Переоценка **benchmark** может привести к «over‑fitting» на искусственные задачи.  
  - Неполные **production**‑данные без ground‑truth затрудняют автоматическую оценку.  

- **Где нам пригодится** – При планировании тест‑плана: от базовой проверки к реальному пользовательскому опыту.

## 10.6 Анализ ошибок: открытое кодирование, таксономия, повторение (стр. 318‑319)

- **Главная мысль** – Ошибочный анализ начинается с **open coding** (ручное описание проблем), затем формируется **failure taxonomy**, после чего процесс повторяется до стабилизации.  

- **Как делать**  
  1. **Open coding** – читаем трассы, пишем короткие заметки о том, что пошло не так (пример в таблице 10.3).  
  2. **Создаем таксономию** – группируем схожие замечания в категории (например, *citation mismatch*, *reasoning failure*).  
  3. **Повторяем** – после того как новые типы перестали появляться, фиксируем первую версию таксономии; при значимых изменениях повторяем процесс (рекомендация 50‑100 образцов за проход).  

- **Правила и числа** – `50–100` примеров для одного цикла (стр. 319).  

- **Шаблоны и примеры** – Таблица 10.3 с полями: `Input`, `Agent output`, `Tool trace`, `Evaluation note`.  

- **Ошибки и предупреждения**  
  - Слишком поверхностный open coding → пропуск редких, но критичных ошибок.  
  - Не обновлять таксономию после существенных изменений в системе.  

- **Где нам пригодится** – При построении автоматических тестов, когда нужно формализовать типичные сбои.

## 10.7 Рубрики и метрики оценки (стр. 320‑321)

- **Главная мысль** – Рубрика (набор критериев) переводит качественную оценку в **метрики**, которые можно считать и отслеживать.  

- **Как делать**  
  1. Определить **rubric items** (PASS/FAIL):  
     - *Answer relevancy* – отвечает ли агент на вопрос.  
     - *Citation reliability* – поддерживают ли утверждения представленные источники.  
     - *Requirement compliance* – соблюдены ли форматы/ограничения.  
  2. Для каждой позиции задать **метрику**:  
     - *Overall pass rate* = `#all‑pass / total evaluations`.  
     - *Answer relevancy rate*, *Citation reliability rate*, *Requirement compliance rate* – отдельные PASS‑процентные показатели.  

- **Правила и числа** – Формула OPR (Overall Pass Rate) указана явно (стр. 321).  

- **Шаблоны и примеры** – Пример рубрики в виде булевых PASS/FAIL (стр. 321).  

- **Ошибки и предупреждения**  
  - Слишком мелкая градация (например, 1‑5 шкала) усложняет автоматизацию; рекомендуется **binary** (PASS/FAIL).  

- **Где нам пригодится** – При построении CI‑проверки качества агентных пайплайнов, когда нужна однозначная метрика отката.

## 10.8 LLM‑as‑a‑Judge: масштабируемая оценка (стр. 322‑324)

- **Главная мысль** – Использование другого LLM‑модели как судьи позволяет быстро и дешево оценивать тысячи ответов по рубрике, заменяя или дополняя человеческую оценку.  

- **Как делать**  
  1. **Single‑output grading** – судья получает `query`, `final_answer`, `evidence_pack` (при наличии) и `rubric`; возвращает PASS/FAIL для каждого пункта.  
  2. **Pairwise comparison** – судья сравнивает два ответа (A/B) и выбирает лучший или «Tie».  
  3. Формировать **json‑запрос** к судье согласно шаблону (стр. 323‑324).  
  4. Выбирать **более сильную** модель в роли судьи (пример: Claude Opus против Claude Haiku).  

- **Правила и числа** – Не указано конкретных чисел, но рекомендуется использовать более крупный/мощный LLM в роли судьи.  

- **Шаблоны и примеры**  
  - *Single‑output* запрос:  
    ```
    User request: Summarize key findings …
    Agent answer: “The study finds …”
    Rubric: 1–2 …
    Respond PASS or FAIL and explain.
    ```  
  - *Pairwise* запрос:  
    ```
    Question: What are the benefits of renewable energy?
    Answer A: …
    Answer B: …
    Respond with: A / B / Tie + brief reasoning.
    ```  
  - **Prompt‑шаблон** судьи (стр. 324) с обязательным выводом единого JSON‑объекта, включающим `overall_pass`, `rubric`‑поля и массив `failure_reasons`.  

- **Ошибки и предупреждения**  
  - Не включать **reference** в случае, когда она отсутствует – судья может «догадываться» и выдавать неверные оценки.  
  - Превышать **лимит токенов** в запросе судье (особенно при большом `evidence_pack`).  

- **Где нам пригодится** – При регулярном регрессионном тестировании новых версий агентов, когда нужно быстро оценить сотни‑тысячи сценариев без привлечения человеческих оценщиков.

---

## 10.9 Структурированный ввод для LLM‑judge (стр. 321‑324)

- **Главная мысль** – Чтобы судья мог работать автоматически, необходимо стандартизировать входные данные: запрос пользователя, финальный ответ, набор доказательств (`evidence_pack`) и рубрику.  

- **Как делать**  
  1. Формировать JSON‑объект:  
     ```json
     {
       "query": "...",
       "final_answer": "...",
       "evidence_pack": [
         {"source_id":"S1","title":"...","url":"...","excerpt":"..."},
         …
       ]
     }
     ```  
  2. Добавить рубрику в запрос (стр. 324) и указать строгие правила (использовать только `evidence_pack`, не добавлять внешний контекст).  
  3. Убедиться, что **output** судьи – единственный JSON‑объект, без лишнего текста.  

- **Правила и числа** – Описание схемы вывода (стр. 324) с обязательными полями `overall_pass`, `rubric`, `failure_reasons`.  

- **Шаблоны и примеры** – Пример полного промпта: блок `[System]`, `[User]`, `[INPUT]`, `[RUBRIC]`, `[OUTPUT JSON SCHEMA]`.  

- **Ошибки и предупреждения**  
  - Нарушить **CRITICAL RULES** (например, использовать внешние знания) — судья может дать неконсистентные оценки.  
  - Не вернуть **валидный JSON** — парсер упадёт и оценка будет потеряна.  

- **Где нам пригодится** – При автоматическом построении пайплайна оценки, где результаты тестов сразу собираются в метрики CI.

--- 

### Кратко о том, где каждый блок может быть применён в вашей работе (одиночный предприниматель)

- **Transfer‑tool** – при построении цепочки специализированных агентов (поиск → расчёт → генерация) в локальном скрипте.  
- **A2A server / RemoteAgent** – если часть функций (например, финансовый расчёт) вынесена на внешний сервис или в облако.  
- **Observability + OpenTelemetry** – для мониторинга расходов токенов и времени отклика ваших агентов в продакшене.  
- **Dataset + Error analysis** – для создания собственного тест‑набора из реальных запросов клиентов.  
- **Rubrics + Metrics** – для автоматической проверки, что каждый запуск агента удовлетворяет бизнес‑требованиям (точность, формат, отсутствие опасных действий).  
- **LLM‑as‑judge** – быстрая регрессионная проверка новых промптов или моделей без привлечения внешних оценщиков.  

Эти конспекты позволят вам быстро ориентироваться в каждом разделе книги, внедрять описанные паттерны и практики в свои скрипты, а также построить надёжную систему оценки и наблюдаемости для ваших AI‑агентов.
