## 5 – Building knowledge bases with RAG (стр. 135‑160)

### 5.1 The problem of using internal data (стр. 135‑137)

- **Главная мысль** – Для большинства реальных задач нужен доступ к закрытым (внутренним) данным: документы компании, код, личные файлы. По‑как‑и веб‑поиск, из огромного массива надо выбрать только релевантные фрагменты и добавить их в контекст LLM.  
- **Как делать**  
  1. Определить тип источника (один файл, несколько файлов, огромный файл/много документов).  
  2. Выбрать подходящий способ поиска (чтение полностью, структура‑ориентированный, векторный).  
- **Правила и числа** – Нет конкретных чисел, лишь указание, что «несколько сотен строк» помещаются в окна современных LLM.  
- **Шаблоны/примеры** – Пример вопроса к CSV‑файлу: *«What month had the highest sales in this data?»* → читаем весь файл и кладём в контекст.  
- **Ошибки/предупреждения** – Чтение **всех** файлов в архиве быстро становится неэффективным и выходит за пределы контекстного окна.  
- **Где пригодится** – При построении запросов к личным/корпоративным данным, при подготовке входных данных для агента‑помощника.

---

### 5.1.1 A simple case: Single file (стр. 136)

- **Главная мысль** – Если размер файла небольшой (пару‑три сотни строк) – просто читаем его полностью и передаём в контекст.  
- **Шаблон** – Добавить **file‑reading tool** из главы 4 к агенту, вызвать его для CSV‑файла.  

---

### 5.1.2 Multiple files (стр. 136‑137)

- **Главная мысль** – При наборе файлов (zip‑архив) заранее неизвестно, где находится ответ. Нужно **исследовать структуру**: папки, имена файлов → подсказки → чтение нужных файлов.  
- **Как делать** (пошагово)  
  1. Распаковать архив.  
  2. Вывести дерево каталогов (`tree`, `list_files`).  
  3. Поиск по названиям (README.md, requirements.txt, *.py, *.json).  
  4. Чтение выбранных файлов, при необходимости – дальнейшее исследование.  
- **Ошибки/предупреждения** – Чтение **всех** файлов в больших проектах непрактично, приводит к переполнению контекста.  

---

### 5.1.3 Large or extensive data (стр. 137)

- **Главная мысль** – Если отдельный файл слишком велик (лог‑файлы, большие документы) или количество документов огромно (тысячелетний вики), нужен механизм **селективного извлечения** (векторный или keyword‑поиск).

## 5.2 Types of search methods (стр. 137‑142)

### 5.2.1 Keyword search (стр. 138‑139)

- **Главная мысль** – Традиционный поиск по точному совпадению слов, использует частотные метрики TF‑IDF и BM25.  
- **Когда использовать** – Поиск **точных** функций/имен, кодовых символов, ошибок (например, `get_user_by_id`, `404`).  
- **Ограничения** – Не понимает синонимы, «sofa vs couch» считается нерелевантным без отдельного словаря.  
- **Пример** – Поиск фразы *sofa* не найдет документы, где только *couch*.  

### 5.2.2 Vector search (стр. 139‑140)

- **Главная мысль** – Текст преобразуется в **эмбеддинги** (векторы сотен‑тысяч измерений); близкие по смыслу тексты находятся ближе в пространстве.  
- **Как работает** –  
  1. **Embedding** модели (напр., `text‑embedding‑3‑small`) превращают строку в вектор.  
  2. Сохраняем вектор каждого фрагмента (документ/чанк).  
  3. При запросе также создаём вектор и вычисляем **cosine similarity** (‑1…1) или **Euclidean distance** (меньше → более похож).  
- **Плюсы** – Позволяет искать по **естественному языку**, обрабатывает синонимы, учитывает контекст (одно и то же слово → разные векторы).  
- **Минусы** – При необходимости точного совпадения (имя функции) лучше keyword; поэтому обычно используют **Hybrid search** (keyword + vector).  

### 5.2.3 Graph search (стр. 140‑141)

- **Главная мысль** – Данные представляются как граф – узлы = сущности, ребра = отношения. Позволяет отвечать на **многошаговые** вопросы, например «какой код вызывает эту функцию».  
- **Плюсы** – Хорошо работает с отношениями, зависимостями кода, организационной структурой.  
- **Недостатки** – Высокие затраты на **построение** графа, требуется спецификация схемы, экспертиза в моделировании графов.  
- **Заметка** – В этой книге граф не реализуется; см. *Essential GraphRAG* (стр. 141).  

### 5.2.4 Structure‑based search (стр. 141‑142)

- **Главная мысль** – При наличии **структурированных** данных (код‑репозитории, zip‑архивы) достаточно использовать **метаданные файлов** (имена, пути) и простые команды (`tree`, `grep`, `cat`).  
- **Плюсы** – Не требует сложных алгоритмов, быстрый доступ к нужному коду/документам.  
- **Где применимо** – GAIA‑benchmark с zip‑файлами, любые проекты с чёткой файловой иерархией.  

### Таблица 5.1 – Рекомендованные методы поиска (стр. 142)

| Ситуация | Метод | Почему |
|----------|-------|--------|
| Точный поиск кода/имени | Keyword | Точное совпадение |
| Вопросы на естественном языке | Vector | Семантическое сходство |
| Вопросы о связях/зависимостях | Graph | Трассировка отношений |
| Исследование структуры папок/файлов | Structure‑based | Метаданные файлов |
| Производственная среда | Hybrid | Комбинация преимуществ |

## 5.3 Practicing vector search (стр. 142‑150)

### 5.3.1 Embedding: Converting text to vectors (стр. 143‑144)

- **Главная мысль** – Эмбеддинг преобразует текст в массив чисел; близкие по смыслу тексты → близкие векторы.  
- **Шаги реализации** (см. листинг 5.1)  
  1. Приём `texts` (строка → список).  
  2. Вызов `client.embeddings.create` OpenAI.  
  3. Выборка `item.embedding` → `np.array`.  
- **Пример** – Получаем эмбеддинги трёх предложений, считаем `cosine_similarity`. Результат: `Cat vs Kitten = 0.385`, `Cat vs Dog = 0.200`.  

### 5.3.2 Chunking: Dividing long text into search units (стр. 144‑145)

- **Главная мысль** – Эмбеддинг **одного** большого документа приводит к потере тем и превышает токен‑лимит. Нужно **разбивать** документ на чанки.  
- **Правила**  
  - Размер чанка ≈ 200‑1000 токенов (≈ 150‑750 слов).  
  - **Overlap** = 10‑20 % от размера чанка (чтобы не потерять контекст на границе).  
- **Алгоритм (листинг 5.3)**  
  1. `start = 0`.  
  2. `end = start + chunk_size`.  
  3. Срез `text[start:end] → chunk`.  
  4. `start = end - overlap` (если не конец).  
  5. Повторять, пока `start < len(text)`.  
- **Пример** – Текст 283 симв., `chunk_size=100`, `overlap=20` → 4 чанка вместо 3.  

### 5.3.3 Implementing vector search (стр. 146)

- **Главная мысль** – Поиск – это сравнение вектора запроса со всеми векторами чанков и выбор топ‑k самых похожих.  
- **Алгоритм (листинг 5.5)**  
  1. `query_embedding = get_embeddings(query)`.  
  2. `similarities = cosine_similarity(query_embedding, chunk_embeddings)[0]`.  
  3. `top_indices = similarities.argsort()[::-1][:top_k]`.  
  4. Вернуть `{'chunk':…, 'similarity':…}` для каждого индекса.  
- **Параметры** – `top_k` по‑умолчанию = 3.  

### 5.3.4 Why vector databases are necessary (стр. 146‑147)

- **Главная мысль** – Прямой расчёт **O(n)** становится непрактичным при миллионах векторов.  
- **Решение** – **ANN‑поиск** в специализированных **vector DB** (Chroma, Pinecone, Weaviate, Qdrant, Milvus).  
- **Кратко о каждой** (стр. 147)  
  - *Chroma* – лёгкая, локальная, без сервера.  
  - *Pinecone* – облачная, управляемая, платная.  
  - *Weaviate* – open‑source, GraphQL, гибридный поиск.  
  - *Qdrant* – Rust‑реализация, быстрый фильтр.  
  - *Milvus* – GPU‑ускорение, масштаб до миллиардов векторов.  

### 5.3.5 Exercise: Finding relevant information from web search results (стр. 147‑150)

- **Задача** – Из 10‑ти веб‑результатов о «2025 Nobel Prize» вытянуть только релевантные куски про *quantum computing*.  
- **Пошаговый процесс**  

  1. **Получить результаты** (`tavily.search(..., include_raw_content=True)`).  
  2. **Подсчитать токены** (`tiktoken.encoding_for_model("gpt-5")`).  
  3. **Chunking** (`fixed_length_chunking(text, chunk_size=500, overlap=50)`).  
  4. **Эмбеддинг** всех чанков (`get_embeddings(chunk_texts)`).  
  5. **Vector search** (`vector_search("quantum computing", …, top_k=3)`).  
  6. **Подсчитать экономию токенов** – из 37 312 токенов осталось 304 токена (экономия ≈ 99.2 %).  

- **Ключевые вывода** (стр. 150)  
  - Векторный поиск обнаруживает семантические связи без точных слов.  
  - Выбор только топ‑чанков резко сокращает расход токенов и стоимость.

## 5.4 Structure‑based search (стр. 150‑160)

### 5.4.1 Preparing the GAIA dataset (стр. 152‑153)

- **Главная мысль** – Для работы с файлами‑приложениями GAIA нужно **скачать их** (не только метаданные).  
- **Команды** (листинг 5.12)  
  - `load_dataset("gaia-benchmark/GAIA", ...)` → метаданные.  
  - `snapshot_download(..., local_dir=CACHE_DIR)` → все вложения (zip, pdf, csv и пр.).  
- **Сброс рабочей области** (листинг 5.13) – `shutil.rmtree` + `shutil.copytree` → всегда чистый старт.  

### 5.4.2 Implementing filesystem tools (стр. 154‑158)

| Инструмент | Назначение | Краткое содержание реализации |
|------------|------------|--------------------------------|
| **unzip_file** | Распаковать zip‑архив | `zipfile.ZipFile` → `extractall`; возвращает список файлов и сообщение. |
| **list_files** | Показать структуру каталога | `Path.iterdir()`, сортировка, вывод папок с «/», исключение скрытых файлов. |
| **read_file** | Чтение текстовых, CSV, Excel‑файлов | Делит по расширениям (`TEXT_EXTENSIONS`, `SPREADSHEET_EXTENSIONS`), использует `_read_text_file`, `_read_csv`, `_read_excel`. |
| **read_media_file** | Анализ изображений, аудио, PDF через LLM | Определяет тип, отправляет в OpenAI (GPT‑4o for images/PDF, gpt‑4o‑audio‑preview for audio). |
| **_read_text_file** – вывод с номерами строк (листинг 5.18). |
| **_read_csv / _read_excel** – `pandas -> to_markdown`. |
| **_analyze_pdf** – извлечение текста + первые 5 страниц в PNG, отправка в LLM (листинг 5.20‑5.21). |

- **Ограничения** – В PDF‑обработке берём только первые 5 страниц и первые 3000 символов текста, иначе будет слишком дорого (токены & визуальные токены).  

### 5.4.3 Connecting tools to the agent (стр. 158‑159)

- **Главная мысль** – Инструменты «оборачиваем» декоратором `@tool` и передаём в конструктор `Agent`.  
- **Код (листинг 5.21)**  
  ```python
  @tool
  def unzip_file(...): ...
  tools = [search_web, unzip_file, list_files, read_file, read_media_file]
  agent = Agent(
      model=LlmClient(model="gpt-5"),
      tools=tools,
      instructions="You are a helpful assistant that can search the web and explore files...",
      max_steps=20
  )
  ```
- **Почему max_steps=20** – Поиск по файлам обычно требует нескольких последовательных действий.  

### 5.4.4 Solving GAIA zip file problems (стр. 159‑160)

- **Процесс решения** (листинг 5.22‑5.23)  
  1. `reset_workspace()`.  
  2. Выбрать задачу с zip‑файлом (`problem = zip_problems[1]`).  
  3. Сформировать подсказку, включающую путь к файлу.  
  4. Запустить `await agent.run(prompt)`.  
- **Поведение агента** –  
  - `unzip_file` → распаковать.  
  - `list_files` → увидеть `Job Listing.pdf` и `Applicants.xlsx`.  
  - `read_media_file` → проанализировать PDF (требования).  
  - `read_file` → прочитать Excel (кандидаты).  
  - Сопоставить требования и кандидатов → получить ответ.  

- **Где пригодится** – Автоматическое обследование архивов, кодовых репозиториев, наборов данных с вложенными файлами.

## 5.5 Extending agents with callbacks (стр. 160‑161)

### 5.5.1 The need for agent extension (стр. 160‑161)

- **Главная мысль** – Иногда требуется **вмешиваться** в работу агента (перед вызовом LLM, после, перед/после исполнения инструмента, после полного завершения) без изменения ядра. Делается через **callback‑функции**.  
- **Точки вставки** (рис. 5.7)  
  - `before_llm_callback` / `after_llm_callback` – модификация контекста, проверка кэша, пост‑обработка ответов.  
  - `before_tool_callback` / `after_tool_callback` – запрос подтверждения у пользователя, сжатие результатов, маскирование чувствительной информации.  
  - `after_run_callback` – сохранение диалога, построение summary (будет в главе 6).  

### 5.5.2 Implementing tool callbacks (стр. 161)

- **Главная мысль** – Добавление **поддержки** callback‑ов в класс `Agent` реализуется через объявление функций‑обработчиков и их вызов в нужных местах цикла `act()`.  
- **Что делаем** – Определяем сигнатуру callback‑ов, передаём их при инициализации `Agent`, затем в коде агента вызываем:  
  ```python
  if self.before_tool_callback:
      self.before_tool_callback(tool_name, args)
  result = tool(*args, **kwargs)
  if self.after_tool_callback:
      self.after_tool_callback(tool_name, result)
  ```  
- **Без изменения ядра** – Сам `Agent` остаётся неизменным; лишь расширяется возможность «подключать» внешние функции.  

- **Возможные применения** (не из текста, но в рамках примера) – запрос подтверждения перед удалением файлов, динамическое сжатие большого результата `read_file`, кэширование часто вызываемых запросов.  

- **Где пригодится** – Любые долгосрочные проекты, где нужны **пользовательские политики безопасности**, контроль расходов токенов, логирование/аудит.
