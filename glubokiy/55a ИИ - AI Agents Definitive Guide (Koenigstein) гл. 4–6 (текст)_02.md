## 5. Контракты, валидация данных и устойчивость продакшн‑систем (стр. не указаны)

### Главная мысль  
Слишком часто ошибки в агентах (неправильный тип, отсутствие поля, изменённый формат провайдера) «прокатываются» сквозь систему, превращаясь в дорогостоящие отладочные часы. Нужно ставить **жёсткую границу** (контракт) между агентами, инструментами и внешними системами и проверять её сразу при передаче данных.

### Как делать  

1. **Определите схему входных/выходных данных с помощью Pydantic.**  
   ```python
   class UserData(BaseModel):
       user_id: int
       age: int = Field(ge=0, le=150)
   ```
2. **В точке входа (границе) сразу создавайте объект модели.**  
   - Если типы несовпадают → `ValidationError` → отказ (fail‑fast) или автоматическое приведение.  
3. **Сделайте политики‑контракты под‑ключом в конфигурации (OmegaConf).**  
   - Пример YAML‑конфига — режим «strict», ограничения по длине промпта, разрешённые MIME‑типы, лимиты повторов, и т.д.  
4. **Создайте фабричную функцию, генерирующую Pydantic‑модели «на лету» на основе текущей политики.**  
   - Внутри функции собирайте параметры из `policy_dict` и объявляйте класс‑модель.  
5. **При старте задачи (run) «закрепите» (pin) политику:**  
   - посчитайте хеш политики (`policy_hash`) и хеш схемы (`schema_hash`).  
   - Сохраните их в состоянии графа (для аудита и кэширования).  
6. **В узле‑гейте валидации:**  
   - Попробуйте построить модель из текущих данных.  
   - При успехе — верните `prompt_ok=True` и `retry_count=0`.  
   - При ошибке — запишите `last_error`, увеличьте `retry_count`, при необходимости инициируйте повтор.  
7. **Включите checkpoint‑механизм (LangGraph + InMemorySaver / PostgresSaver).**  
   - Сохраняйте всё состояние (сообщения, результаты инструментов, текущий узел, политику, хеши, run‑id).  
   - При сбое восстановите граф до последнего стабильного узла, не пере‑исполняя уже отработанные шаги.  

### Правила и числа (из текста)

| Показатель | Без валидации | С валидацией |
|------------|----------------|--------------|
| Точность модели (system accuracy) — после валидации | 98 % → 99.8 % (при 1 вызове) | 94.1 % → 99.4 % (при 3 вызовах) |
| Точность модели (system accuracy) — при 10 вызовах | 81.7 % → 98.0 % | – |
| Максимальное количество повторов (retry) в `GOVERNANCE_CONFIG` | 3 | – |
| Длина промпта (min) | 50 симв. | – |
| Разрешённые MIME‑типы изображений | `["image/png"]` | – |
| Ограничения размера изображения | `size_px` от 512 до 1536 | – |
| Ограничения для `age` | `ge=0, le=150` | – |

### Шаблоны и примеры  

* **Пример плохого кода (без валидации)**  
  ```python
  def process_user_data_brittle(data):
      user_id = data.get("user_id")      # может быть str
      age = data.get("age")              # может быть None
      result = user_id * 2                # ошибка, если str
  ```
* **Пример безопасного кода (Pydantic)**  
  ```python
  class UserData(BaseModel):
      user_id: int
      age: int = Field(ge=0, le=150)

  def process_user_data_safe(data):
      user = UserData(**data)            # ValidationError → быстрый отказ
      return {"processed_id": user.user_id * 2}
  ```
* **YAML‑политика (OmegaConf)** – см. `GOVERNANCE_CONFIG` в тексте.  
* **Фабрика модели** – `build_image_prompt_model(...)` (пример 5‑4).  
* **Гейт‑валидации** – `node_prompt_validation_gate` (пример 5‑6).  

### Ошибки и предупреждения  

| Ошибка | Почему опасно | Как исправить |
|--------|---------------|---------------|
| Не проверять типы/поле данных | Сломается downstream‑узел, трудно отследить | Обязательно валидировать на границе (Pydantic) |
| Жёстко захардкоженные правила в коде | Невозможна гибкая смена политики, требует redeploy | Хранить правила в `OmegaConf`, менять «на лету» |
| Отсутствие checkpoint‑сохранения | При падении теряется прогресс, приходится пересчитывать всё | `InMemorySaver`/`PostgresSaver` + `thread_id` |
| Пропуск ограничения количества повторов | Возможен бесконечный цикл, растёт стоимость | Установить `max_retries` в политике, учитывать `retry_count` |
| Не фиксировать хеши политики/схемы | Невозможно точно воспроизвести, что использовалось в проде | Сохранять `policy_hash` и `schema_hash` в состоянии задачи |  

### Где нам пригодится  

- **Запросы/валидация** — при получении данных от LLM‑агентов (модель → код).  
- **Проверка** — при интеграции новых провайдеров/инструментов, чтобы не «сломать» форму данных.  
- **Память** — чекпоинты позволяют возобновлять работу без повторных запросов к дорогостоящим сервисам.  
- **Помощники** — встроенный «гейт» позволяет агенту быстро понять, что данные некорректны, и попросить исправить их.  
- **Учёба** — примерные контракты и политики можно использовать в учебных проектах, показывая, как построить надёжный пайплайн.

## 5. Инструктор (Instructor) — валидация **во время генерации** (стр. не указаны)

### Главная мысль  
`Instructor` соединяет генерацию LLM и валидацию Pydantic в один цикл: LLM генерирует JSON‑подобный ответ, тот сразу проверяется моделью, а при ошибке LLM получает **семантическую обратную связь** и пытается снова. Это избавляет от отдельного «фиксерного» узла и уменьшает количество повторных запросов к модели.

### Как делать  

1. **Создайте клиент Instructor, подсоединив его к OpenAI‑совместимому провайдеру (OpenRouter, Anthropic и т.д.).**  
   ```python
   client = instructor.from_provider(
       f"openrouter/{model_slug}",
       base_url="https://openrouter.ai/api/v1",
       mode=instructor.Mode.TOOLS,
   )
   ```
2. **Определите Pydantic‑модель контракта (например, `ImagePrompt`).**  
3. **Вызовите `client.create(.., response_model=ImagePrompt, max_retries=policy.max_retries, ...)`.**  
   - `Instructor` автоматически сравнивает выдачу с моделью.  
   - При несовпадении добавляет в запрос `handle_reask_kwargs()` и посылает ошибку LLM — та же модель получает обратную связь и генерирует новый вариант.  
4. **Настройте политику retry‑ов в `GOVERNANCE_CONFIG` (см. таблицу 5‑3).**  

### Правила и числа  

| Уровень | Где происходит retry | Что триггерит | Что повторяется |
|---------|--------------------|----------------|-----------------|
| **Pydantic‑validation gate** (внешний) | После генерации, при передаче в систему | Нарушение контракта (пропуск полей, тип) | Перезапуск **узла** (весь граф) |
| **Instructor enforcement** (внутренний) | Внутри одного вызова `client.create` | Нарушение контракта **во время генерации** | Повтор генерации **одного LLM‑шота** |
| **Checkpoint** | При падении инфраструктуры | Таймаут, ошибка сервера | Возобновление с последнего узла |

### Шаблоны и примеры  

* **Создание клиента** – пример 5‑9.  
* **Запрос с контрактом** – пример 5‑10:  
  ```python
  result = client.create(
      messages=[{"role":"user","content":"Generate an image prompt …"}],
      response_model=ImagePrompt,
      max_retries=policy.max_retries,
      temperature=0.2,
  )
  ```

### Ошибки и предупреждения  

| Ошибка | Почему плоха | Как избежать |
|--------|---------------|--------------|
| Отключить `Instructor` и полагаться только на Pydantic‑gate | При каждом ошибочном JSON‑ответе требуется отдельный запрос → двойные затраты | Включайте `Instructor` для всех моделей, где нужен «structured output». |
| Забыть задать `max_retries` | Возможен бесконечный цикл генерации | Установите небольшое значение (например, 3) в политике. |
| Писать кастомный парсер вместо `response_model` | Потеря типовой обратной связи | Всегда передавайте Pydantic‑модель в `response_model`. |

### Где нам пригодится  

- **Запросы** — при работе с LLM, где нужен строгий JSON‑output (подготовка промптов, схем, запросов к API).  
- **Проверка** — быстрая обратная связь LLM без отдельного узла‑фиксатора.  
- **Помощники** — инструктор может автоматически «перепрашивать» у модели недостающие поля.

## 5. MCP — универсальный протокол взаимодействия с инструментами (стр. не указаны)

### Главная мысль  
Model Context Protocol (MCP) задаёт лёгкий, единственный интерфейс для **вызова инструментов, доступа к данным и взаимодействия с приложениями**. С помощью MCP ваш агент может пользоваться любыми tool‑серверами (внутренними или сторонними) без изменения кода, а политика‑контроль размещается в самом сервере.

### Как делать  

1. **Определите Pydantic‑модели запросов/ответов** (например, `ReadFileRequest`, `WriteFileRequest`).  
2. **Создайте сервер MCP через `FastMCP`**  
   ```python
   mcp = FastMCP("FileManager")
   @mcp.tool()
   def read_file(request: ReadFileRequest) -> str: …
   @mcp.tool()
   def write_file(request: WriteFileRequest) -> dict: …
   @mcp.tool()
   def list_files(request: ListFilesRequest) -> list[str]: …
   if __name__ == "__main__":
       mcp.run(transport="stdio")   # локальная разработка
   ```
3. **Для продакшн‑развёртывания выберите транспорт** (HTTP, WebSocket, gRPC, stdio).  
4. **Подключите клиент MCP к LangGraph:**  
   ```python
   client = MultiServerMCPClient({
       "file_manager": {
           "command": "python",
           "args": [os.path.abspath("file_manager_server.py")],
           "transport": "stdio",
       }
   })
   tools = await client.get_tools()
   ```
5. **Встроьте полученные инструменты в граф LangGraph** (см. пример 5‑14).  
6. **Для обнаружения внешних MCP‑инструментов используйте сервисы‑агрегаторы** (Composio, Docker‑MCP).  

### Правила и числа  

| Параметр | Рекомендация |
|----------|--------------|
| Транспорт для локальной разработки | `stdio` |
| Транспорт для продакшн‑сервера | HTTP/WS / gRPC (в зависимости от нагрузки) |
| Параллельные вызовы | Ограничьте `max_parallel_calls` в `GovernancePolicy` (пример 6‑1) |
| Бюджет вызовов | `max_total_calls_per_task` — по умолчанию 20, в примере 2 — 2 вызова |

### Шаблоны и примеры  

* **Pydantic‑модели** – пример 5‑11.  
* **MCP‑сервер** – пример 5‑12 (`@mcp.tool()` функции).  
* **Клиент MCP** – пример 5‑13 (`MultiServerMCPClient`).  
* **Интеграция в граф** – пример 5‑14 (`call_model` + `ToolNode`).  

### Ошибки и предупреждения  

| Ошибка | Последствия | Как исправить |
|--------|-------------|---------------|
| Протокол `stdio` в продакшн‑среде | Нет возможности масштабировать, нет сетевого изоляции | Перейти на HTTP/WS/gRPC. |
| Не использовать типизацию входов/выходов | Появляются «тихие» ошибки при несовпадении типов | Обязательно описывайте запрос/ответ через `BaseModel`. |
| Писать глобальные соединения к БД без `WAL` | Конкурентные запросы могут блокировать друг друга | Включить SQLite `WAL` mode, использовать атомарные обновления. |
| Отсутствие политики‑контроля в MCP‑сервере | Агент может вызвать любой инструмент без ограничений | Внедрите `GovernancePolicy` и проверку в каждом `@mcp.tool`. |

### Где нам пригодится  

- **Запросы** – любой вызов внешних API (файлы, БД, SaaS‑сервисы) через типизированные контракты.  
- **Проверка** – гарантирует, что каждый инструмент получает корректные типы и структуру.  
- **Память** – `policy_hash` и `schema_hash` сохраняются в чекпоинтах, позволяя воспроизводить состояние.  
- **Помощники** – позволяют агенту «искать» нужный инструмент в реальном времени, а не жестко кодировать их.

## 6. Безопасное исполнение и управление инструментами (стр. не указаны)

### Главная мысль  
После того как система стала предсказуемой, нужно контролировать **саму возможность выполнения** действий. Агент может «взять и выполнить» любые инструменты, если ему не закрыть эту возможность, что приводит к тихим, но серьёзным инцидентам (перезапись файлов, утечка credentials). Для этого вводятся **политики‑ограничения**, **бюджет‑трекинг**, **разделение этапов обнаружения/исполнения**, а также **протокол A2A (Agent‑to‑Agent)** как слой управления.

### Как делать  

1. **Определите структуру политики (`GovernancePolicy`).**  
   - Параметры: ограничения по общему числу вызовов, параллелизму, времени выполнения, тайм‑ауту MCP‑вызова, возможности создавать соединения, возможность «discovery + execution» в одном запросе и набор разрешённых типов артефактов.  
   - Пример 6‑1: `SEPARATION_POLICY` (разделяет discovery и execution).  
2. **Создайте объект‑трекинг `BudgetTracker`.**  
   - При старте задачи фиксируется время, счётчики вызовов, флаги «был выполнен‑step‑discovery», «был выполнен‑step‑execution», пауза и т.д.  
   - На каждый запрос проверяется:  
     * Не превышен ли `max_total_calls_per_task`.  
     * Не превысил ли `max_parallel_calls`.  
     * Не нарушено ли правило `connection_and_execution_in_same_run`.  
   - При нарушении – **отклонить** запрос, вернуть сообщение об ошибке.  
3. **Внедрите A2A как «контрольную плоскость»:**  
   - Агент формирует **intent** (что хочет сделать).  
   - A2A‑губернатор проверяет intent против текущей `GovernancePolicy`.  
   - Если intent допускается → передаёт в MCP‑выполнение. Если нет → отклоняет или требует Human‑in‑the‑Loop (HITL)‑одобрения.  
4. **Определите «Product Requirement Prompt (PRP)»:**  
   - Чётко описывает контекст (пути, версии зависимостей), паттерны кода и набор валидирующих команд, которые агент может выполнить.  
   - PRP передаётся вместе с intent, позволяя агенту понять, какие ограничения у него есть.  
5. **Встроите в граф A2A‑губернатор как отдельный узел (перед вызовами MCP).**  
   - На вход получает `tool_call` и текущий `BudgetTracker`.  
   - Выдаёт `approval_granted: bool` +, при необходимости, `human_approval_needed`.  
6. **Логируйте каждое решение (`policy_decision`, `tool_call_log`, `approval_log`).**  
   - Храните вместе с `run_id`, `policy_hash`, `schema_hash`.  
   - Обеспечивает **аудит** и возможность «trace‑back» после инцидента.  

### Правила и числа  

| Параметр | Значение в примерах |
|----------|---------------------|
| `max_total_calls_per_task` | 20 (общий), 2 (в `SEPARATION_POLICY`) |
| `max_parallel_calls` | 3 |
| `max_runtime_seconds` | 300 (общий), 60 (в `SEPARATION_POLICY`) |
| `mcp_call_timeout_seconds` | 20 |
| `allow_connection_creation` | `True` (в `SEPARATION_POLICY`) |
| `connection_and_execution_in_same_run` | `False` (запрещено одновременное discovery + execution) |
| `allowed_artifact_types` | `{policy_decision, tool_call_log, approval_log, …}` |

### Шаблоны и примеры  

* **Политика** – пример 6‑1 (`GovernancePolicy` + `SEPARATION_POLICY`).  
* **Трекер бюджета** – пример 6‑2 (`BudgetTracker` с полями `total_calls`, `active_calls`, `did_connection_step`, …).  
* **A2A‑губернатор** – логика проверяет `tool_policies` (регексп‑соответствия) и текущие счётчики, затем возвращает либо `allow`, либо `reject`/`request_human`.  
* **PRP** – структура: `{context: {paths, versions}, patterns: [...], validation_cmds: [...]}` (описано в тексте).  

### Ошибки и предупреждения  

| Ошибка | Почему опасна | Как избежать |
|--------|---------------|--------------|
| Позволить `connection_and_execution_in_same_run` | Агент может сразу после «дискавери» выполнить вредоносный запрос | Установить `connection_and_execution_in_same_run=False`. |
| Отключить `max_total_calls_per_task` | Возможен бесконечный цикл генерации запросов → большие расходы | Установить ограничение (например, 20) и фиксировать в трекере. |
| Не вести журнал артефактов | Потеря доказательств в случае инцидента | Записывайте каждое `policy_decision`, `tool_call_log`, `approval_log`. |
| Писать «hard‑coded» список разрешенных инструментов в агенте | При добавлении новых инструментов нужно будет менять код | Делайте список динамически через MCP‑дискавери + A2A‑политику. |
| Пропускать Human‑in‑the‑Loop для дорогих или опасных операций | Автоматически исполняются критические действия (удаление БД) | Настраивайте `human_approval_needed=True` в `ToolPolicy`. |

### Где нам пригодится  

- **Запросы** – любые действия, где нужен контроль затрат (LLM‑запросы, генерация изображений, обращения к базе).  
- **Проверка** – проверка, что инструмент вызывается в рамках политик (не более N вызовов, не одновременно с discovery).  
- **Память** – `run_id`, `policy_hash`, `schema_hash` сохраняются в базе/чекпоинте, позволяя воспроизводить каждый run.  
- **Помощники** – можно «попросить» у ассистента объяснить, почему запрос отклонён, используя логи `policy_decision`.

## 6. Глубокие агенты (Deep Agents) — планирование перед исполнением (стр. не указаны)

### Главная мысль  
Большие агентные системы становятся непредсказуемыми, когда сразу начинают выполнять инструменты. **Deep Agents** вводят отдельный слой планирования, после которого только проверенный план (с учётом политики, бюджета, суб‑агентов) отправляется в исполнение. Это уменьшает стоимость, предотвращает «tool‑sprawl» и обеспечивает изоляцию контекста.

### Как делать  

1. **Установите `deepagents` (MIT‑лицензия).**  
2. **Определите **sub‑agents** (изолированные контексты) для тяжёлых операций (поиск в интернете, работа с файлом, запрос к базе).**  
3. **Создайте **system prompt** — задать правила планирования, ограничения, цель задачи.**  
4. **Задайте **tools** (как обычные MCP‑инструменты, так и пользовательские).**  
5. **Определите **middleware** для:**  
   - Инъекции инструментов.  
   - Применения политик (выбор `allowed`/`forbidden`).  
   - Хранения промежуточных артефактов (audit‑log).  
6. **Опишите **execution contracts** (`SKILL.md`, `AGENTS.md`):**  
   - `SKILL.md` — какие умения/операции разрешены (например, писать код, отправлять email).  
   - `AGENTS.md` — тон, стиль, требования к качеству вывода.  
7. **Включите **Human‑in‑the‑Loop** (по желанию) для особо опасных sub‑agents.**  

### Правила и числа  

| Параметр | Пример/рекомендация |
|----------|---------------------|
| Максимальное количество **sub‑agents** | 3‑5 (чтобы не раздут контекст) |
| Длина **system prompt** | ≥ 200 симв., чтобы покрывать требования к планированию |
| Число **tool‑calls** в одном sub‑agent | ≤ 5 (чтобы не переполнить контекст) |
| Бюджет **LLM‑запросов** (tokens) | ≤ 500 – 800 токенов на план/подготовку, затем отдельные вызовы на исполнение |

### Шаблоны и примеры  

* **Таблица 5‑4** — преимущества `deepagents` (планирование, изоляция, аудит, композируемость).  
* **Фигуры 5‑4/5‑5** — визуальная схема компонентов (LLM, system prompt, tools, middleware, sub‑agents).  
* **Суб‑агент** — внутри него свой `model`, `tools`, `system prompt`; передаёт только конечный результат в главный агент.  

### Ошибки и предупреждения  

| Ошибка | Последствия | Как избежать |
|--------|-------------|--------------|
| Выдавать агенту доступ к *всем* инструментам без фильтрации | Появляется «tool‑sprawl», рост стоимости, безопасность | Применяйте `MCP` + `GovernancePolicy` к каждому инструменту. |
| Слишком большой **system prompt** | Переполнение окна контекста, деградация качества | Делите правила на **SKILL.md** (hard constraints) и **AGENTS.md** (soft). |
| Не отделять **plan** от **execution** | Ошибки в планировании не могут быть откатаны без повторного генерирования | Чётко фиксируйте две стадии: `plan → execute`. |
| Оставлять **sub‑agents** без собственного **checkpoint** | При падении теряется весь промежуточный контекст | Сохраняйте состояние каждого sub‑agent в отдельный чекпоинт (можно использовать тот же `InMemorySaver`). |

### Где нам пригодится  

- **Запросы** – при построении комплексных пайплайнов (исследование → написание текста → генерация изображения).  
- **Проверка** – проверка, что план соответствует бюджету и политике перед запуском.  
- **Память** – каждый sub‑agent сохраняет свои артефакты, позволяя откатить только часть работы.  
- **Помощники** – позволяют быстро переключаться между моделями/провайдерами, не меняя планировщик.

## Общее резюме — что взять в свой «арсенал»

| Тема | Что внедрить в свой продакшн‑поток |
|------|-----------------------------------|
| **Контракты + валидация (Pydantic)** | Определять типы и ограничения при любой передаче данных; делать `fail‑fast`. |
| **Конфигурация + OmegaConf** | Хранить правила (strict/lenient) в YAML, менять их «на лету». |
| **Фабрика моделей** | Динамически генерировать Pydantic‑схемы под текущую политику. |
| **Checkpoint‑механизм** | Сохранять `thread_id`, `policy_hash`, `schema_hash`, `run_id`. |
| **Instructor** | Делать «внутреннюю» валидацию в генерации LLM, минимизировать количество запросов. |
| **MCP + FastMCP** | Открытый протокол для всех инструментов, типизированные запросы/ответы. |
| **A2A + GovernancePolicy** | Управлять, какие tool‑calls разрешены, сколько их может быть, и где требуется HITL. |
| **BudgetTracker** | Отслеживать реальное потребление ресурсов (вызовы, время, параллелизм). |
| **Deep Agents** | Планировать, затем исполнять; использовать sub‑agents для тяжёлых задач. |
| **Audit‑лог** | Записывать `policy_decision`, `tool_call_log`, `approval_log` вместе с хешами. |

Эти блоки образуют **три уровня защиты**:

| Уровень | Что защищает | Как реализовано |
|---------|--------------|-----------------|
| **Контрактный (жесткий)** | Формат данных, типы, границы валидации | Pydantic + OmegaConf + Instructor |
| **Операционный (граничный)** | Количество вызовов, тайм‑ауты, разделение discovery/execute | GovernancePolicy + BudgetTracker + A2A |
| **Системный (реализационный)** | Интеграция внешних сервисов, переживание сбоев | MCP + FastMCP + LangGraph + Checkpoint |

С этими инструментами ваш единственный предприниматель‑одиночка сможет **строить, отлаживать и поддерживать** надёжные, бюджет‑контролируемые и безопасные агентные системы без постоянного вмешательства в код.
