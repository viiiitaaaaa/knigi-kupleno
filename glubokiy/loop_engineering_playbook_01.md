## 📖 ЧАСТЬ I – Revolution of the Loop (стр. 5‑12)

### Глава 1 – The Loop Revolution  *(стр. 6‑12)*
- **Главная мысль** – Вместо цепочек запрос‑ответ, система AI должна работать в *автономных циклах*: наблюдать → рассуждать → действовать → проверять цель.  
- **Как делать**  
  1. Определить **MAX_STEPS** – максимальное число итераций.  
  2. Внутри цикла:  
     - `observation = await gather_context(state)`  
     - `reasoning = await llm.reason(observation)`  
     - `action = await llm.decide_action(reasoning)`  
     - `result = await execute(action)`  
     - `state = update_state(state, result)`  
     - `if state["resolved"]: return …`  
  3. После выхода из цикла – `escalate_to_human(state)` (fallback).  
- **Правила и числа**  
  - **MAX_STEPS** — порог завершения, иначе бесконечный цикл (пример = `MAX_STEPS`).  
  - **Стоимость**: каждый шаг добавляет стоимость API‑вызова; при **MAX_STEPS = 20** и $0.05 за шаг → $1 за «запуск», но при 10 000 конкурентных запросах → $10 000 в минуту.  
  - **Идемпотентность**: каждый записывающий запрос должен проверять *идентификатор* (fingerprint) и не выполнять дубль.  
- **Шаблоны / примеры**  
  ```python
  async def handle_refund(request):
      state = {"request": request, "resolved": False}
      for step in range(MAX_STEPS):
          observation = await gather_context(state)
          reasoning   = await llm.reason(observation)
          action      = await llm.decide_action(reasoning)
          result      = await execute(action)
          state = update_state(state, result)
          if state["resolved"]:
              return state["resolution"]
      return escalate_to_human(state)
  ```
- **Ошибки / предупреждения**  
  - **Отсутствие MAX_STEPS** → бесконечный цикл.  
  - **Отсутствие идемпотентных проверок** → финансовый «runaway» (пример – 2 400 дублированных возвратов, $340 к).  
  - **Твёрдое try/catch** в традиционных системах не спасает Loop‑системы (нужна *самокоррекция*).  
- **Где пригодится** – При построении любого агента‑обработчика (поддержка, код‑ревью, email‑триage), когда нужен цикл до выполнения цели.

### Глава 2 – The Agent Landscape in 2026  *(стр. 13‑20)*
- **Главная мысль** – На 2026 г. рынок свернулся вокруг нескольких моделей и фреймворков; выбор **модели + фреймворка** диктует стоимость, надёжность и масштабируемость Loop‑систем.  
- **Как делать**  
  1. Оценить требования проекта (граф‑выполнение, multi‑agent, исследование, простая цепочка).  
  2. По требованию выбрать **фреймворк** (см. дерево‑выбора).  
  3. Выбрать **модельный уровень** (Tier 1 – дешёвый, Tier 2 – сбалансированный, Tier 3 – премиум).  
  4. Рассчитать **проектную стоимость** (формула ниже).  
- **Правила и числа**  
  - **Точность вызова функций** ≥ 95 % (Claude, GPT‑4.1, Gemini 2.5 Pro).  
  - **Контекст** ≥ 100 K токенов → количество итераций без потери согласованности.  
  - **Таблица сравнения фреймворков**  

    | Фреймворк | Лучшее для | Слабости | Зрелость |
    |-----------|------------|----------|----------|
    | LangChain | Линейные цепочки, RAG | Сложный контроль‑поток | Высокая |
    | LangGraph | Состояния, ветвления | Кривая обучения | Высокая |
    | CrewAI    | Командные multi‑agent | Сложности отладки | Средняя |
    | AutoGen   | Конверсационные | Управление стоимостью | Средняя |
    | Custom    | Уникальные требования | Поддержка | Varied |

  - **Стоимость моделей (per 1K tokens) – Q4 2026**:  
    - *cheapest* = $0.025, *mid* = $0.80, *frontier* = $7.50.  
  - **Расчёт стоимости цикла**:  

    ```
    monthly_cost = (daily_requests) *
                   (avg_iterations) *
                   (tokens_per_iteration/1000) *
                   (model_cost_per_1K) * 30
    ```

    Пример: 10 000 запросов/день, 4 итерации, 3 000 токенов, Tier 2 $0.01/1K → **$3 600/мес**.  
  - **MAX_STEPS**: ставьте в 95‑й перцентиль + 30 % «запаса» (см. *PRODUCTION TIP*).  
- **Шаблоны / примеры**  

  **Выбор фреймворка**  

  ```python
  def choose_framework(req):
      if req.needs_graph_execution: return "LangGraph"
      if req.needs_multi_agent:    return "CrewAI"
      if req.needs_research:       return "AutoGen"
      if req.needs_simple_chain:   return "LangChain"
      return "custom"
  ```

  **Выбор модели по tier**  

  ```python
  MODELS = {
      "tier_1_cheap": {"model":"claude-3.5-haiku","cost_per_1k":0.001},
      "tier_2_balanced": {"model":"gpt-4.1-mini","cost_per_1k":0.01},
      "tier_3_premium": {"model":"claude-opus-4","cost_per_1k":0.075},
  }
  ```

- **Ошибки / предупреждения**  
  - **Framework‑trap**: если >30 % кода – обходные пути фреймворка → переход к кастом‑решению.  
  - **Dependency creep**: >20 % кода адаптирует фреймворк → экономический ущерб.  
  - **Пере‑/недо‑выбор модели** → избыточные токены (пример – ​80‑90 % экономии, заменив классификатор на Haiku).  
- **Где пригодится** – При выборе стека (модель + фреймворк) для любого нового агента, особенно когда нужен чёткий расчёт бюджета и контролируемый масштаб.

### Глава 3 – The Loop Engineer Mindset  *(стр. 21‑28)*
- **Главная мысль** – Инженер‑loop мыслит **траекториями** (путём последовательных состояний) вместо функций; ключевыми элементами являются контроль‑цикл, состояние и наблюдение за отклонениями.  
- **Как делать**  
  1. **Определить 4‑элементный контроль‑цикл**:  
     - *Sensor* – что наблюдает (API, пользователь).  
     - *Controller* – LLM‑рассуждение и решение.  
     - *Actuator* – инструменты (API, БД).  
     - *Feedback* – сигнал «близок‑ли к цели».  
  2. **Смоделировать агент как конечный автомат** (State‑Machine).  
  3. **Установить MAX_STEPS** и **budget** (стоимость).  
  4. **Логировать каждую траекторию**; проверять *конвергенцию* (качество должно расти).  
  5. При отклонении – ищите причину: контекст‑окно, неверный сигнал оценки, осцилляцию.  
- **Правила и числа**  
  - **CREED (Кодекс Loop‑инженера)**  
    1. *MAX_STEPS* обязателен.  
    2. Каждый *action* логируется.  
    3. Любой сбой — восстанавливается или эскалацируется.  
    4. Стоимость — первоклассное ограничение.  
    5. Цикл считается «готовым» только после продакшн‑мониторинга.  
  - **Триггер дивергенции** – проверка: контекст‑окно (≈ 100 K токенов), оценка (неправильный reward), осцилляция (повторяющиеся состояния).  
- **Шаблоны / примеры**  

  **Контроль‑цикл (термостат)**  

  ```python
  class AgentThermostat:
      def __init__(self, goal, tolerance=0.1):
          self.goal = goal
          self.tolerance = tolerance
      def loop(self, initial_state):
          state = initial_state
          for i in range(self.max_steps):
              reading = self.sense(state)          # Sensor
              error   = self.compare(reading,self.goal)  # Feedback
              if abs(error) < self.tolerance:
                  return state                     # Success
              action = self.decide(error)          # Controller
              state  = self.act(action)            # Actuator
          return self.timeout_handler(state)
  ```

  **State‑Machine**  

  ```python
  class AgentStateMachine:
      VALID_TRANSITIONS = {
          IDLE: [THINKING],
          THINKING: [ACTING, SUCCEEDED, FAILED],
          ACTING: [EVALUATING, FAILED],
          EVALUATING: [THINKING, SUCCEEDED, ESCALATED],
      }
  ```

- **Ошибки / предупреждения**  
  - **Транзакционный мышление** – проверять только финальный результат; пропускает 80 % ошибок в промежуточных шагах.  
  - **Отсутствие траекторного логирования** → незаметные сбои.  
  - **Отсутствие ограничения шагов** → потенциальный финансовый урон.  
- **Где пригодится** – При проектировании любой автономной системы (боты, автоматизация, CI/CD), где важна предсказуемость и контроль расходов.

## 📖 ЧАСТЬ II – Core Loop Patterns (стр. 29‑45)

### Глава 4 – The ReAct Pattern  *(стр. 30‑40)*
- **Главная мысль** – Основной паттерн **ReAct** = *Reason → Action → Observation* (мысли‑действия‑наблюдения). Он обеспечивает самокоррекцию и повышает точность инструментов.  
- **Как делать** *(пошагово)*  
  1. **Инициализировать** LLM, набор `tools`, `MAX_STEPS`.  
  2. В каждом шаге:  
     - LLM генерирует **THOUGHT** (обоснование).  
     - При наличии **ACTION** → вызываем соответствующий **tool**.  
     - Получаем **OBSERVATION** и добавляем её в историю.  
  3. Если нет `tool_call` → считаем, что получен **FINAL_ANSWER**.  
  4. При достижении `MAX_STEPS` возвращаем частичный ответ.  
- **Правила и числа**  
  - **Трасса размышления (Thought)** добавляет 50‑100 токенов ≈ $0.001 за шаг (при $0.01/1K). Это «дешёвый» способ улучшить точность (+20‑30 % снижения ошибок).  
  - **Deduplication**: хранить `call_sig = tool_name + JSON_args`; если повтор – вернуть сообщение *“You already tried this exact call. Try a different approach.”*  
  - **Budget guard**: проверять `cost > 0.9 * budget` **до** каждого LLM‑вызова; оставлять 10 % для финального ответа.  
  - **MAX_STEPS**: обязателен; рекомендуется ставить чуть выше 95‑й перцентиль (см. глава 1).  
- **Шаблоны / примеры**  

  **Базовый ReAct‑агент**  

  ```python
  class ReActAgent:
      def __init__(self, llm, tools, max_steps=10):
          self.llm, self.tools, self.max_steps = llm, {t.name:t for t in tools}, max_steps
      def run(self, query):
          msgs = [{"role":"system","content":REACT_PROMPT},
                  {"role":"user","content":query}]
          for step in range(self.max_steps):
              resp = self.llm.chat(msgs)
              if resp.has_tool_call:
                  tool = self.tools[resp.tool_name]
                  result = tool.execute(resp.tool_args)
                  msgs.append({"role":"tool","content":result})
              else:
                  return resp.text
          return "Max steps reached. Partial answer: " + self.summarize(msgs)
  ```

  **Production‑grade ReAct (Anthropic)** – содержит budget‑check, deduplication, обработку ошибок, системный промпт (см. стр. 31‑34).  

- **Типичные сбои (таблица)**  

    | Сбой                | Симптом                     | Причина                               | Fix |
    |---------------------|----------------------------|---------------------------------------|-----|
    | **Повторный ловушк**| Один и тот же `tool`‑вызов 3+ раз | Игнорирование ошибки инструмента | Хеш‑проверка + инъекция “try different” |
    | **Преждевременный ответ**| Ответ без достаточных доказательств | Модель «экономит» шаги | Требовать минимум доказательств перед FINAL_ANSWER |
    | **Фиксация инструмента**| Использует один инструмент | Приоритет в системном промпте | Перетасовать порядок, добавить “consider all tools” |
    | **Галлюцинированный инструмент**| Вызов несуществующего инструмента | Путаница в названиях | Проверять название перед выполнением |
    | **Переполнение контекста**| Качество падает после N шагов | Превышение окна | Суммировать/сжать состояние |
    | **Сквозное расширение**| Уходит в сторонние темы | Неясные инструкции, “curiosity bias” | Добавить “stay focused on original question” |

- **Ошибки / предупреждения**  
  - **ANTI‑PATTERN: REPETITION TRAP** – отсутствие хеш‑проверки → runaway‑cost.  
  - **Не использовать Thought** → повышенный риск неверных tool‑calls.  
  - **MAX_STEPS = 10 или 20 без анализа** → лишние токены, потенциальные утечки.  
- **Где пригодится** – Агент, который комбинирует несколько инструментов (поиск, калькулятор, базу, файловую систему) и нужен гибкий, самокорректирующийся процесс (например, поддержка, исследовательский бот, аналитика данных).

### Глава 5 – Plan‑and‑Execute  *(стр. 41‑45)*
- **Главная мысль** – Разделить *стратегию* и *тактику*: сначала создать детальный план, затем последовательно выполнять шаги (часто внутри шагов используют ReAct). План позволяет поддерживать глобальную согласованность, а пере‑планирование реагирует на неожиданности.  
- **Как делать**  
  1. **Planner** (модель Opus‑class) генерирует *полный* план (нумерованный список).  
  2. **Executor** (модель Sonnet‑class) обрабатывает каждый пункт, используя, при необходимости, внутр. ReAct‑цикл.  
  3. После **каждого** шага проверять необходимость **replan** (модель Haiku‑class).  
  4. **Синтезировать** конечный результат после всех шагов.  
- **Правила и числа**  
  - **Тиринг моделей**:  
     - *Plan creation* — Tier 3 (Opus) (дорого, но нужен глобальный контекст).  
     - *Step execution* — Tier 2 (Sonnet) (достаточно для большинства задач).  
     - *Replan decision* — Tier 1 (Haiku) (двоичная «continue / replan”).  
  - **Размер плана**: оптимально 3‑7 шагов, каждый в 1 предложении, с чётким критерием успеха.  
  - **Стоимость**: переход к более дешёвому tier для большинства шагов экономит ~50 % без потери качества.  
- **Шаблоны / примеры**  

  **Классический Plan‑and‑Execute**  

  ```python
  class PlanAndExecute:
      def __init__(self, planner_llm, executor_llm):
          self.planner, self.executor = planner_llm, executor_llm
      def run(self, goal):
          plan = self.planner.create_plan(goal)   # список шагов
          results = []
          for i, step in enumerate(plan.steps):
              result = self.executor.execute(step, context=results)
              results.append(result)
              if result.requires_replan:
                  remaining = plan.steps[i+1:]
                  plan = self.planner.replan(goal, completed=results,
                                            remaining=remaining,
                                            reason=result.replan_reason)
          return self.synthesize(results)
  ```

  **Prompt для пере‑планирования** (стр. 43)  

  ```
  CONTINUE - proceed with the existing plan
  REPLAN - followed by the updated remaining steps
  ```

- **Ошибки / предупреждения**  
  - **ANTI‑PATTERN: STALE PLAN EXECUTION** – игнорировать результаты, противоречащие плану → “garbage” и перерасход бюджета. Нужно проверять после **каждого** шага.  
  - **Слишком детальный план** → ломается при первой неожиданности.  
  - **Слишком общий план** → исполнитель теряется, растет количество LLM‑вызовов.  
- **Где пригодится** – Сложные бизнес‑процессы (миграция данных, составление отчётов, многоэтапные исследования), где порядок шагов известен, но детали могут меняться в ходе выполнения.

### 📌 Как применять полученные правила в ежедневной работе предпринимателя‑одиночки

| Ситуация | Какой паттерн | Что взять из конспекта |
|----------|---------------|------------------------|
| **Автоматическое чтение и ответ на входящие email** | ReAct (с бюджетным планом) | Установить **MAX_STEPS = 95‑й percentile + 30 %**, добавить **идемпотентный чек** (про‑email обработан), использовать **дешёвый Haiku‑class** для простых писем, **GPT‑4** – только для «сложных» (пример в Scored Walkthrough 1.2). |
| **Генерация еженедельных отчётов из Jira** | План‑и‑Выполнить (с ReAct внутри) | Спланировать 4‑5 шагов (сбор данных, синтез, проверка качества, отправка), **Tier 3** только для финального синтеза, **Tier 2** для шагов, **Tier 1** для решения «продолжить/перепланировать». |
| **Быстрый прототип клиентского чат‑бота** | Фреймворк **LangChain** (если < 4 недели) | Оценить **TIMELINE < 4 нед**, **TEAM = 1‑3**, **PATTERN = linear**, дальше обернуть в абстракцию, чтобы можно было сменить фреймворк. |
| **Обучающий агент, который ищет научные статьи** | ReAct + Reflection (для точности) | Добавить **Reflection** после каждого tool‑call (2× токенов), но только если требуется высокая точность; иначе оставлять базовый ReAct. |
| **Автоматическая проверка финансовых транзакций** | ReAct + строгая **идемпотентность** | Хранить **fingerprint** транзакции, проверять перед каждым `refund`‑вызовом; установить **MAX_STEPS** = 5‑7, **budget‑guard** = 90 % от лимита. |

**Краткие напоминания для ИИ‑помощника Claude**

1. **Всегда** задавай `MAX_STEPS` и проверяй бюджет **до** обращения к LLM.  
2. **Логируй** каждый `THOUGHT`, `ACTION`, `OBSERVATION`.  
3. **Проверяй идемпотентность** в любой операции записи (refund, write‑file и т.п.).
