**Часть 9 из 11 – «RAG with Python Cookbook» (Dominik Polzer)  
Раздел 9.5 — Оптимизация графа знаний для систем RAG**  
*Стр. 297‑298*  

- **Главная мысль**  
  Добавление заранее подготовленных сводок, агрегатов и эмбеддингов в граф знаний позволяет сократить затраты и задержки, переместив тяжёлую работу с времени запросов на время загрузки данных.

- **Как делать**  
  1. Сначала построить базовый граф без оптимизаций и измерить его производительность.  
  2. При необходимости добавить:  
     - **Сводки клаузул** (summary) — для быстрой фильтрации большого количества клаузул;  
     - **Агрегаты** (count, flags) — для повторного использования уже посчитанных величин;  
     - **Эмбеддинги уровня SLA** — для поиска целых контрактов целиком.  
  3. После каждой оптимизации проверять, что запросы стали быстрее, а расход токенов не увеличился, и ответы остаются точными.  
  4. Обязательно хранить оригинальный текст клаузул и использовать его в финальном ответе.

- **Правила и числа** *(стр. 297)*  
  - Не добавляйте все оптимизации сразу — начните с базовой модели, измерьте метрики и только тогда внедряйте нужные улучшения.  
  - Поддержание синхронности: суммари, агрегаты и эмбеддинги должны быть актуальны при изменении данных (это основной «trade‑off» — увеличение объёма хранилища и времени ingest).  

- **Шаблоны и примеры** *(стр. 297)*  
  ```cypher
  MATCH (c:Company)-[:HAS_SLA]->(:SLA)-[:HAS_CLAUSE]->(cl:Clause)-[:OF_TYPE]->(t:ClauseType)
  WITH c, t, count(cl) AS num_clauses
  SET c[t.name + '_count'] = num_clauses
  ```

- **Ошибки и предупреждения**  
  - Не заменяйте оригинальный текст суммарными данными — они лишь фильтруют/ранжируют.  
  - Слишком раннее добавление всех оптимизаций может привести к избыточному хранению и усложнённому обслуживанию без реальной пользы.  

- **Где нам пригодится**  
  *Для ускорения запросов к графу, снижения токен‑расхода и подготовки к масштабной генерации ответов в системах RAG.*

## **Глава 10 — Оценка (Evaluating) систем RAG**  

### **10.0 Введение в оценку RAG (стр. 299‑300)**  
- **Главная мысль** – Оценка необходима, иначе улучшения в системе становятся догадками.  
- **Ключевые детали**  
  - RAG не обучается; он лишь извлекает и генерирует. Поэтому метрики отличаются от традиционных ML‑метрик.  
  - Тестовые вопросы должны отражать реальные намерения пользователя, но не быть дословно в данных.  

### **10.1 Выбор правильных метрик оценки RAG‑систем (стр. 303‑304)**  

- **Главная мысль**  
  Подбирайте метрики в зависимости от того, какие «заземлённые» (ground‑truth) данные у вас есть, и используйте небольшое, сбалансированное набор (2‑3) метрик, покрывающих разные части пайплайна.  

- **Как делать**  
  1. Определите тип имеющихся аннотированных данных:  
     - **Ответы‑референсы** → используйте метрики сравнения ответов (семантическое сходство, LLM‑based correctness).  
     - **Аннотированные куски** (question ↔ relevant document) → используйте метрики извлечения (precision, recall).  
     - **Нет ни того, ни другого** → применяйте внутренние метрики генерации (faithfulness, relevancy, coherence).  
  2. Выберите минимум **две метрики**: одну для извлечения, одну для генерации.  
  3. При необходимости добавьте специальные метрики (например, для text‑to‑SQL).  

- **Правила и числа** *(стр. 303‑304)*  
  - Обычные группы метрик: **Generation**, **Retrieval**, **General** (latency, token usage).  
  - Примерные категории:  
    - Generation — faithfulness, correctness, coherence, fluency, safety.  
    - Retrieval — recall, precision, F1.  
    - General — latency, токен‑расход.  

- **Шаблоны / примеры**  
  - Нет конкретных код‑шаблонов в этом кусочке текста, но указано, что в репозитории GitHub книги находятся готовые примеры.  

- **Ошибки / предупреждения**  
  - Не оценивайте только одну часть пайплайна – иначе можно ухудшить другую, не заметив этого.  

- **Где пригодится**  
  *Для построения тестового набора и автоматической проверки изменений в любой RAG‑системе.*  

### **10.2 Оценка RAG‑систем людьми (стр. 307‑309)**  

- **Главная мысль**  
  Сбор обратной связи от реальных пользователей (thumbs‑up/down, рангирование) необходим для измерения субъективных качеств (тон, ясность, полезность), которые автоматические метрики упустить не могут.  

- **Как делать**  
  1. Если есть большая тестовая аудитория, показывайте **две версии** (старую и новую) и просите ранжировать ответы (pairwise).  
  2. При единственном показе используйте **thumbs‑up / thumbs‑down** плюс, при отрицательном отклике, открытое текстовое поле для комментария.  
  3. Собирать **пассивные сигналы**: временные метки, идентификаторы пользователей, время отклика, лог запросов, список полученных документов, LLM‑ответы.  
  4. Для измерения латентности используйте модуль `time` в Python и фиксируйте метки на каждом этапе пайплайна.  

- **Правила и числа** *(стр. 307‑309)*  
  - При парных сравнениях показывайте пользователям **два ответа одновременно**.  
  - Для пассивного мониторинга собирайте **тайм‑стемпы** и **идентификаторы**.  
  - Пример формы (рис. 10‑6) включает: thumb, полe для бесплатного текста, быстрые метки‑лейбы.  

- **Шаблоны / примеры**  
  - Streamlit‑модуль `st.feedback` (см. документацию).  

- **Ошибки / предупреждения**  
  - Человек — дорог и медлен; использовать только для **целевых** ревью (после крупных изменений), а не для каждой коммиты.  
  - Оценка может быть непоследовательна – разные люди дают разные оценки.  

- **Где пригодится**  
  *Для измерения пользовательского удовлетворения и тональных аспектов, когда меняются ответы, модели или UI.*  

### **10.3 Создание синтетических данных для автоматизированного тестирования (стр. 310‑315)**  

- **Главная мысль**  
  С помощью LLM генерировать вопросы‑ответы **из собственных фрагментов** знаний, получая масштабный, полностью автоматический набор тестов.  

- **Как делать**  
  1. Загрузить набор фрагментов (пример: *RAG mini‑Wikipedia* из Hugging Face).  
  2. Выбрать случайные текст‑чанки (например, `random.sample(docs_list, 5)`).  
  3. Сформировать **prompt**: инструкция + контекст. Инструкция требует задавать **естественные, фактологические** вопросы, без ссылок на «контекст».  
  4. Отправить запрос к LLM (в примере – `gpt‑5.2`) с **response_format** — Pydantic‑модель `QuestionAnswerPairs`.  
  5. Сохранить вывод: `question`, `answer`, `context`.  

- **Правила и числа** *(стр. 310‑315)*  
  - Минимум **50‑100** синтетических пар для надёжной оценки.  
  - При прототипировании достаточно **5** пар (как в примере).  
  - После генерации вручную проверьте **10‑20** пар на естественность и точность.  

- **Шаблоны / примеры**  
  ```python
  QA_generation_prompt = """
  Your task is to generate a question and its corresponding answer
  based on the provided context.
  ...
  Context: {context}
  Output:"""
  class QuestionAnswerPairs(BaseModel):
      question: str = Field(description="A factoid question about the context.")
      answer: str   = Field(description="The answer to the factoid question.")
  ```
  Код цикла генерации показан в строках 313‑319.  

- **Ошибки / предупреждения**  
  - Синтетические вопросы **очень просты** и могут не отразить реальную «длинную хвостовую» часть запросов.  
  - Не использовать их для оценки **тона, ясности, многократного диалога**.  
  - При крупном обновлении знаний нужно **перегенерировать** набор.  

- **Где пригодится**  
  *Для быстрых регрессионных тестов и контроля целостности пайплайна после изменений кода/модели.*  

### **10.4 Оценка шага извлечения: Context Precision@k (стр. 316‑322)**  

- **Главная мысль**  
  **Context Precision@k** измеряет, какая доля из k‑выбранных фрагментов действительно полезна для формирования ответа.  

- **Как делать**  
  1. Выбрать случайный вопрос из тестового набора.  
  2. Выполнить запрос через RAG‑систему, собрать **generated answer** и **retrieved chunks**.  
  3. Для каждого чанка вызвать LLM‑judge, который сравнивает **question + answer + chunk** и возвращает **verdict (1/0)** и **reason**.  
  4. Подсчитать **precision**:  

     \[
     \text{Context precision@k} = \frac{\sum_{i=1}^{k} \text{verdict}_i}{k}
     \]

  5. При необходимости использовать уточнённую формулу из текста (с учётом весов vk).  

- **Правила и числа** *(стр. 316‑322)*  
  - **k** — общее число возвращённых чанков (в примере 3).  
  - **vk** — бинари‑флаг релевантности (1 = релевантен).  
  - При расчёте добавить небольшую **ε = 1e‑10**, чтобы избежать деления на ноль.  

- **Шаблоны / примеры**  
  - Pydantic‑модель `Verification` (стр. 317‑319).  
  - Пример кода проверки релевантности (стр. 318‑321).  
  - Пример вывода: два релевантных чанка → verdict 1, один нерелевантный → verdict 0 (рис. 10‑12).  

- **Ошибки / предупреждения**  
  - Не использовать только **строковые** метрики (BLEU/ROUGE) – они не отражают семантическую релевантность.  
  - При слишком большом **k** могут «затирать» полезные чанки шумом; используйте precision для подбора оптимального k.  

- **Где пригодится**  
  *Для отладки и настройки ранжирования векторных поисков, а также контроля стоимости токенов.*  

### **10.5 Оценка Faithfulness (правдоподобия) генерации с LLM‑as‑Judge (стр. 323‑329)**  

- **Главная мысль**  
  **Faithfulness** измеряет, насколько сгенерированный ответ **привязан** к извлечённому контексту (отсутствие «галлюцинаций»).  

- **Как делать**  
  1. **Декомпозировать** ответ на отдельные утверждения (claims) с помощью LLM (prompt «break down answer into statements»).  
  2. Для каждого утверждения вызвать LLM‑judge, который проверяет, поддерживается ли оно контекстом, возвращая **verdict (1/0)** и **reason**.  
  3. Вычислить **faithfulness score** = (число поддержанных утверждений) / (общее число утверждений).  

- **Правила и числа** *(стр. 323‑329)*  
  - Целевой уровень ‑ **≥ 80 %** в продакшене; **< 70 %** — серьёзные галлюцинации.  
  - При расчёте используйте `pandas` для подсчётов (стр. 328).  

- **Шаблоны / примеры**  
  - Pydantic‑модель `Statements` (стр. 324‑325).  
  - Prompt для разбиения ответа (`statement_prompt`).  
  - Prompt для оценки правдоподобия (`faithfulness_judge_prompt`).  
  - Пример кода расчёта процента (стр. 328‑329).  

- **Ошибки / предупреждения**  
  - Высокий faithfulness **не гарантирует** релевантность ответа (может быть точным, но не отвечать на вопрос).  
  - При слишком консервативных настройках модель может утаивать нужную информацию; балансировать с **answer relevancy**.  

- **Где пригодится**  
  *В задачах с высокими рисками (медицина, финансы, юридические документы), где недопустимы выдуманные факты.*  

### **10.6 Оценка релевантности ответа (Answer Relevancy) (стр. 330‑333)**  

- **Главная мысль**  
  **Answer relevancy** измеряется тем, насколько сгенерированный ответ соответствует **исходному вопросу**; рассчитывается через сравнение эмбеддингов оригинального вопроса и искусственно сгенерированных вопросов, основанных на ответе.  

- **Как делать**  
  1. Запустить вопрос через RAG‑систему → получить **answer**.  
  2. С помощью LLM сгенерировать **N = 3** (по умолчанию) «искусственных» вопросов, которые можно задать, чтобы получить тот же ответ.  
  3. Вычислить эмбеддинги для оригинального вопроса (**E₀**) и для каждого искусственного вопроса (**Eᵢ**).  
  4. Для каждого **Eᵢ** посчитать **косинусное сходство** с **E₀**.  
  5. Среднее значение сходств → **answer relevancy score**.  

- **Формула** *(стр. 330‑331)*  

  \[
  \text{Answer relevancy} =
  \frac{1}{N}\sum_{i=1}^{N}\cos\!\bigl(E_{gi},E_{0}\bigr)
  \]

- **Правила и числа** *(стр. 332‑333)*  
  - **Noncommittal score** = 1, если сгенерированный вопрос получает «эвфемерный» ответ (например, «I’m an AI, I don’t feel …»).  
  - Примерные значения в таблице 10‑2:  
    - Вопрос «Capital of France?», ответ «Paris» → 0 (полностью отвечает).  
    - Вопрос «How are you feeling?», ответ «I’m an LLM…» → 1 (не отвечает).  

- **Шаблоны / примеры**  
  - Prompt `response_relevance_prompt` (стр. 332).  
  - Pydantic‑модель `GeneratedQuestion` + `GeneratedQuestions` (стр. 332‑333).  
  - Функция `create_embeddings` с моделью `text-embedding-3-small` (стр. 333).  

- **Ошибки / предупреждения**  
  - Не полагайтесь только на релевантность; необходимо также проверять **faithfulness** и **context precision**.  
  - Слишком высокие пороги сходства могут маскировать случаи, когда ответ **не охватывает** вопрос полностью.  

- **Где пригодится**  
  *Для автоматической проверки того, что ответ действительно решает задачу пользователя, особенно при изменении prompts или моделей.*
