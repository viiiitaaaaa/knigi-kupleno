## Глава 10 «Память в многопоточных/многопользовательских агентных системах» (стр. —)

### Главная мысль  
Память (как краткосрочная, так и долгосрочная) превращает агент‑инструмент в **постоянного специалиста**, способного сохранять контекст между вызовами и – в результате – выполнять более сложные задачи без потери информации.

### Как делать  

1. **Определите режим‑постоянства** для каждого суб‑агента (см. Таблицу 10‑6).  
2. **Соберите схему состояния** (TypedDict) для оркестратора и для рабочего (sub‑)агента.  
3. **Оркестратор** передаёт **только текущий запрос** (`current_input`) в суб‑агент, чтобы изолировать контекст.  
4. **Суб‑агент** сохраняет **свою собственную историю сообщений** (`messages`) и сам её использует для вывода фактов.  
5. При компиляции графа задайте **checkpointer** в зависимости от выбранного режима:  
   * `None` – без памяти (per‑invocation)  
   * `True` – поток‑уровневая память (per‑thread)  
   * `False` – stateless без чекпоинтов.  
6. **Тестируйте**: запустите несколько «туров» и проверьте, какие факты сохраняются (см. Таблицу 10‑7).  

### Правила и числа  

| Режим | Поведение памяти | Поведение агента |
|------|-------------------|------------------|
| **Per‑invocation (None)** | Нет памяти между вызовами | Статeless‑функция |
| **Per‑thread (True)** | Память накапливается | Постоянный агент с историей |
| **Stateless (False)** | Нет постоянства/восстановления | Чистое выполнение, без прерываний |

*Таблица 10‑6* (стр. —).  
*Таблица 10‑7* (стр. —) демонстрирует, как в разных режимах меняются известные факты (`Known`) и количество видимых сообщений (`Msgs`) после 3‑х туров.

### Шаблоны и примеры  

* **Оркестратор (пример 10‑17)**  

```python
class ParentState(TypedDict):
    current_input: str
    answer: str

def make_parent_app(worker_app):
    def call_worker(state: ParentState, config: RunnableConfig):
        out = worker_app.invoke(
            {"messages": [HumanMessage(content=state["current_input"])]},
            config=config,
        )
        return {"answer": out["messages"][-1].content}
    builder = StateGraph(ParentState)
    builder.add_node("call_worker", call_worker)
    builder.add_edge(START, "call_worker")
    return builder.compile(checkpointer=InMemorySaver())
```

* **Рабочий агент (пример 10‑18)** – извлекает из своей истории факты о дублировании оплаты, тарифе и возврате.  

* **Сборка рабочего с разными режимами (пример 10‑19)**  

```python
def build_worker(mode: str):
    builder = StateGraph(WorkerState)
    builder.add_node("billing_worker", billing_worker_node)
    builder.add_edge(START, "billing_worker")
    if mode == "per_invocation":   return builder.compile()
    if mode == "per_thread":      return builder.compile(checkpointer=True)
    if mode == "stateless":        return builder.compile(checkpointer=False)
    raise ValueError(f"Unknown mode: {mode}")
```

### Ошибки и предупреждения  

* **Неправильный checkpointer**: `checkpointer=True` работает **только для вложенных суб‑графов**; попытка задать его на корневой граф выдаст ошибку.  
* **Перепутать режимы** – в `stateless` отключаются все возможности прерывания и восстановления, поэтому такие агенты не смогут, например, ожидать ввода пользователя.  
* **Отсутствие валидации памяти** → «потеря фактов», «застаревшие» или противоречивые ответы (см. раздел *Memory Requires Verification*).

### Где пригодится  

* При построении **гибридных систем**: оркестратор – контекст‑изолированный, суб‑агенты – по желанию сохраняют локальную историю (для кода, биллинга, диалогов).

## Глава 11 «От вычислений к затратам: проектирование экономичных агентных систем» (стр. —)

### Главная мысль  
Для агентных систем **стоимость** – ключевой ограничитель; многократные шаги, повторные запросы к LLM и перемещения данных быстро умножают токены и расходы. Нужно проектировать архитектуру с учётом **мультипликатора затрат**, **кеширования**, **выбора инфраструктуры** и **оптимизации внимания**.

### Как делать  

1. **Оцените базовую стоимость**:  
   * рассчитайте вероятность успеха отдельного агента (`p≈0.60`).  
   * если нужна надежность ≈ 99 %, понадобится `n=5` попыток → **5‑кратный рост токен‑бюджета**.  

2. **Разбейте стоимость по компонентам** (мультишаговый мультипликатор):  
   - роутинг, поиск, рассуждение, рефлексия, guard‑rails.  

3. **Сократите повторяющиеся префиксы** с помощью **prompt‑caching** (кешировать системный запрос, описания инструментов, few‑shot примеры).  

4. **Выберите уровень инфраструктуры** (гиперскейлер vs. неоклауд) в зависимости от регуляций и объёма:  
   - Таблица 11‑1 (типы деплоя).  

5. **Учитывайте KV‑кеш** модели:  
   - *Prefill* – заполняет KV‑кеш (память растёт с длиной входа).  
   - *Autoregressive* – использует KV‑кеш для следующего токена, экономя вычисления, но требуя пропускную способность памяти.  

6. **Оптимизируйте внимание**:  
   - используйте **FlashAttention** (версии 1‑4) – только нужные плитки данных проходят через on‑chip память; минимизируют трафик HBM.  
   - На длинных контекстах (>1 M токенов) предпочтителен **FlashAttention‑4** (GPU Blackwell B200).  

7. **Применяйте мемоизацию** (кеширование состояний планировщика):  
   - построьте **FactStore** (пример 11‑1) → собирает факты, считает версии, классифицирует изменения (added, reinforced, conflict, duplicate).  
   - создайте **WorldView** (пример 11‑2) – неизменяемый снимок фактов + доказательства.  
   - сформируйте **PlannerContext** (пример 11‑3) – полный набор условий (задача, мир, доступные инструменты, «застрявшие» инструменты).  
   - реализуйте **TieredCache** (пример 11‑4 – 11‑7) с **трёхуровневым** поиском: точный, нормализованный, семантический (embedding‑поиск).  
   - задайте **порог семантической схожести τ** (пример 11‑8).  

8. **Тестируйте и мониторьте**:  
   - измеряйте **hit‑rate** кеша, но проверяйте, приводит ли он к **прогрессу** (избегайте «застреваний»).  
   - собирайте статистику вызовов (см. Таблица 11‑3).  

### Правила и числа  

| Параметр | Значение / правило |
|----------|--------------------|
| **Успешность одного вызова** | `p = 0.60` (пример) |
| **Кол‑во повторов для ~99 %** | `n = 5` → токен‑расход *5×* |
| **Таблица 11‑1** – уровни деплоя (типы, где лучше применять) |
| **Таблица 11‑2** – соответствие FlashAttention‑версий GPU |
| **Таблица 11‑3** – ожидаемые LLM‑вызовы per запрос: роутинг 1, retrieval 0.6, reasoning 0.7, reflection 0.5, guard‑rails 2.0 |
| **Токен‑префикс** – типичный систем‑промпт ≈ 5 000 токенов; без кеша каждый шаг добавляет их заново. |
| **Semantic similarity threshold τ** – обычно 0.90 (пример в коде). |

### Шаблоны и примеры  

* **FactStore (пример 11‑1)** – управляет историей фактов, считает версию, возвращает тип изменения (`added`, `reinforced`, `conflict`, `duplicate`).  

* **WorldView (пример 11‑2)** – immutable `frozenset[Fact]` + `evidence`‑кортеж; позволяет хешировать состояние.  

* **PlannerContext (пример 11‑3)** – `@dataclass(frozen=True)` с полями `task`, `view`, `tools_available`, `stale_tools`; метод `make` сортирует списки для детерминированного хеша.  

* **Cache entry (пример 11‑4)** – хранит `fact_hash`, `normalized_hash`, `full_vec` (embedding), `decision`, контекстные guard‑значения.  

* **Exact / Normalized hash (пример 11‑5)** – SHA‑256 → 24‑симв. префикс (≈ 96 бит).  

* **Lookup (пример 11‑6)** – последовательный поиск: точный → нормализованный → семантический (cosine‑similarity). Возвращает `(decision, tier)`.  

* **Store (пример 11‑7)** – формирует текстовое представление, получает embedding, сохраняет в кеш.  

* **SwarmPlanner init (пример 11‑8)** – подключает `TieredCache`, задаёт HTTP‑заголовки для API.  

### Ошибки и предупреждения  

* **Кеш‑хиты без прогресса** – 90 % хитов может означать «застревание» в старом решении; нужно отслеживать, меняет ли кеш состояние.  
* **Слишком низкий τ** → неверные семантические совпадения → галлюцинации в планах.  
* **Неправильный выбор уровня деплоя**: в регулируемых отраслях использовать Tier 3 (VPC + weights) или Tier 4, иначе рискуете нарушить юридические требования.  
* **Игнорировать KV‑кеш**: при контексте > 1 M токенов без FlashAttention‑4 GPU будет простаивать из‑за перемещения памяти.  
* **Не тестировать память**: без проверки «memory requires verification» агент может «забыть» важные факты после суммаризации.  

### Где пригодится  

* **Запросы/проверка**: при оценке стоимости конкретного workflow (сколько токенов займет каждый шаг).  
* **Память/контроль**: построение локального хранилища фактов и планировочного кеша для повторяющихся задач.  
* **Помощники/агенты**: создание гибридных систем (ориентатор + специалисты) с разными режимами постоянства.  
* **Данные**: поддержка регулятивных ограничений (данные должны оставаться в VPC).  
* **Учёба**: понимание влияния KV‑кеша, FlashAttention и мультипликатора затрат на масштабируемость.
