# Конспект по книге «Hands-On RAG for Production» (Часть 2)

## Введение в RAG: Потоки данных (стр. 31–33)
- **Главная мысль**: RAG состоит из двух основных процессов: **Ingestion** (загрузка и подготовка данных) и **Query Flow** (обработка запроса пользователя).
- **Как делать (Query Flow)**:
    1. Конвертация запроса пользователя в вектор (embedding).
    2. Семантический поиск в векторной БД для нахождения релевантных фактов.
    3. Формирование промпта: объединение найденных фактов и вопроса пользователя.
    4. Генерация ответа LLM на основе этого контекста.
    5. Применение «guardrails» (ограничителей) для проверки галлюцинаций и токсичности.
- **Правила и числа**: 
    - В продакшене простой семантический поиск часто недостаточен, требуются гибридный поиск или реранкинг (переранжирование) (стр. 31).
- **Термины**:
    - **Dataset (набор данных)** — сырые исходные файлы.
    - **Corpus (корпус)** — очищенные и организованные данные.
    - **Index (индекс)** — структура данных, оптимизированная для быстрого поиска.
    - **Semantic search (семантический поиск)** — поиск по смыслу (через векторы), а не по буквам.
    - **Lexical search (лексический поиск)** — поиск по точному совпадению слов.
- **Ошибки и предупреждения**: LLM может «придумать» ответ (галлюцинация), поэтому важна проверка соответствия ответа предоставленным фактам (стр. 32).
- **Где нам пригодится**: Создание архитектуры памяти для агентов и системы проверки ответов.

## Промышленный стек RAG (MLOps/LLMOps) (стр. 32–33)
- **Главная мысль**: Переход от прототипа к продакшену требует внедрения инженерных практик для обеспечения скорости, безопасности и качества.
- **Как делать (Инфраструктура)**:
    1. **CI/CD**: Автоматизация обновления данных и оценки качества.
    2. **Версионирование**: Хранить промпты, модели эмбеддингов и логику нарезки текста как код.
    3. **Observability**: Трассировка каждого запроса для отладки «плохих» ответов.
    4. **Безопасность**: Использовать RBAC (ролевой доступ), чтобы пользователь видел только разрешенные ему документы.
- **Правила и числа**: Данные должны быть зашифрованы как при хранении, так и при передаче (стр. 33).
- **Где нам пригодится**: Организация хранения своих скриптов, данных и управление доступом.

## Пример: RAG с LangChain (стр. 34–35)
- **Главная мысль**: Базовая реализация RAG включает загрузку PDF, разбивку на части, создание векторов и запуск цепочки «поиск $\rightarrow$ промпт $\rightarrow$ ответ».
- **Как делать (Процесс)**:
    1. Загрузка PDF $\rightarrow$ Парсинг в текст.
    2. Разделение текста на чанки (куски).
    3. Создание эмбеддингов $\rightarrow$ Сохранение в векторную БД (например, LanceDB).
    4. Создание цепочки: Ретривер (поиск топ-3 чанков) $\rightarrow$ Шаблон промпта $\rightarrow$ LLM $\rightarrow$ Парсер вывода.
- **Шаблоны и примеры**: Промпт: *«Answer the question based only on the following context: {context} Question: {question}»* (стр. 35).
- **Правила и числа**: В примере использован размер чанка `chunk_size=1000` и перекрытие `chunk_overlap=200` (стр. 34).
- **Где нам пригодится**: Готовый шаблон для написания своих скриптов на Python.

## RAG против других подходов (стр. 36–38)
- **Главная мысль**: RAG эффективнее простого «Чата с PDF» (из-за масштабируемости) и Fine-tuning (из-за стоимости и контроля доступа).
- **Сравнение**:
    - **«Chat with PDF»**: Просто закидывание всего текста в окно контекста. *Минусы*: дорого, медленно (latency), не масштабируется на тысячи документов (стр. 36).
    - **Fine-tuning (Дообучение)**: Изменение весов модели на своих данных. *Минусы*: нужен эксперт (риск переобучения), дорого (GPU), невозможно быстро обновлять данные, нет контроля доступа (все данные сливаются в один «blob») (стр. 37).
- **Ошибки и предупреждения**: «Эффект Борга» при Fine-tuning — невозможно разделить знания, доступные разным пользователям (стр. 37).
- **Где нам пригодится**: Обоснование выбора RAG вместо дообучения модели для своих данных.

## Преимущества и кейсы RAG (стр. 38–46)
- **Главная мысль**: RAG дает масштабируемость, снижает галлюцинации, обеспечивает прозрачность (цитирование) и позволяет мгновенно обновлять знания.
- **Ключевые выгоды**:
    - **Объяснимость**: Возможность добавить ссылки `[1, 2]` на источник (стр. 39).
    - **Актуальность**: Достаточно обновить документ в БД, не переобучая модель (стр. 39).
- **Кейсы применения**:
    - Виртуальные ассистенты (поддержка клиентов, обучение студентов).
    - Корпоративный поиск (поиск по Notion, Jira, Google Drive).
    - Автоматизация контента (отчеты, статьи).
    - Персонализированная реклама (генерация оффера под текущий контекст пользователя).
    - Медицина и право (поиск по регламентам, историям болезни с обязательным участием человека — HITL) (стр. 45).
- **Где нам пригодится**: Идеи для создания своих агентов-помощников (учёба, бизнес).

## Продвинутый RAG (Advanced RAG) (стр. 46–48)
- **Главная мысль**: Эволюция RAG идет в сторону автономных агентов, работы с изображениями и графами знаний.
- **Три направления**:
    1. **Agentic RAG**: Агент может делать многошаговый поиск, использовать внешние инструменты (API, Web search) и переформулировать запрос (стр. 46).
    2. **Multimodal RAG**: Работа с таблицами и схемами. Либо через перевод всего в текст, либо через VLM (зрительно-языковые модели), которые «видят» страницу (стр. 47).
    3. **Knowledge Graphs (Графы знаний)**: Извлечение сущностей и связей. Позволяет делать «multi-hop reasoning» (связывать факты из разных документов) (стр. 47).
- **Где нам пригодится**: Планирование развития своих систем (переход от простого поиска к агентам).

## Базовый стек RAG: Потоки (стр. 49–52)
- **Главная мысль**: Техническая реализация RAG делится на Ingestion (подготовка) и Query (выполнение) потоки.
- **Процесс Ingestion (Загрузка)**:
    1. **Parsing (Парсинг)**: Извлечение текста из PDF/DOCX, очистка от мусора, OCR для картинок (стр. 50).
    2. **Chunking (Чанкинг)**: Нарезка длинных текстов на куски (чтобы влезть в окно LLM и повысить точность поиска) (стр. 51).
    3. **Embedding (Эмбеддинг)**: Преобразование текста в вектор чисел, отражающий смысл (стр. 51).
    4. **Indexing (Индексация)**: Организация векторов в БД для быстрого поиска (стр. 52).
- **Процесс Query (Запрос)**:
    - **Query Rewriting (Переписывание)**: Трансформация запроса пользователя (например, отделение команды «напиши стих» от сути поиска «поездки в 2025»), чтобы поиск был точнее (стр. 52).
- **Где нам пригодится**: Пошаговый план реализации своего пайплайна обработки данных.
