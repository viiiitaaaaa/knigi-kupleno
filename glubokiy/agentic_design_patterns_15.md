## 2. Глоссарий — основные определения (стр. 449‑452)  

### 2.1 Prompt (стр. 449)  
- **Главная мысль** – запрос — ввод, который пользователь даёт модели (вопрос, инструкция, утверждение).  
- **Как делать** – формулируйте чётко, задавайте цель, указывайте ограничения.  
- **Правила/числа** – «качество и структура промпа сильно влияют на вывод модели».  
- **Пример** – *«Сгенерируй план запуска продукта за 30 дней»*.  
- **Ошибки** –‑‑ «нечёткие, многозначные промпты → плохие ответы».  
- **Где пригодится** – при построении всех ваших запросов к LLM.

### 2.2 Context Window (стр. 449)  
- **Главная мысль** – максимальное количество токенов, которое модель может обработать за один проход.  
- **Как делать** – следите, чтобы важная информация помещалась в окно; при превышении отбрасывайте старый контент.  
- **Правила** – «информация за пределами окна игнорируется».  
- **Ошибки** –‑‑ *переполнение* окна → потеря контекста.  
- **Где пригодится** – при построении длительных диалогов / архивов.

### 2.3 In‑Context Learning (стр. 449)  
- **Главная мысль** – модель умеет учиться новому заданию, получая примеры внутри самого промпа, без дообучения.  
- **Как делать** – добавляйте в запрос 1‑3 примера желаемого поведения.  
- **Пример** – *«Пример 1: … Пример 2: … Теперь реши задачу‑3»*.  
- **Ошибки** –‑‑ слишком мало примеров → плохая генерализация.  
- **Где пригодится** – быстрый прототип новых функций без переобучения.

### 2.4 Zero‑Shot / One‑Shot / Few‑Shot Prompting (стр. 451)  
- **Главная мысль** – уровни количества примеров в запросе (0, 1, few). Чем больше примеров, тем точнее модель.  

### 2.5 Multimodality (стр. 451)  
- **Главная мысль** – способность модели работать с разными типами данных (текст, изображение, аудио).  

### 2.6 Grounding (стр. 452)  
- **Главная мысль** – привязывание вывода модели к проверяемым источникам (RAG), чтобы уменьшить галлюцинации.  

### 2.7 Core AI Model Architectures (стр. 452‑453)  

| Архитектура | Кратко | Пример применения |
|------------|--------|-------------------|
| **Transformers** | Самая популярная, использует self‑attention для обработки длинных последовательностей. | Большие LLM‑ы (GPT‑4, Claude). |
| **RNN** | Последовательная обработка, «память» о предыдущих входах. | Ранние модели для речи, текстов. |
| **MoE (Mixture of Experts)** | Динамический роутер выбирает несколько «экспертов»‑моделей, экономя вычисления. | Огромные модели с 1 Т параметров. |
| **Diffusion Models** | Генерация изображений через «шум‑обратный процесс». | DALL‑E 2, Stable Diffusion. |
| **Mamba** | Selective State Space Model (SSM)‑архитектура, эффективна для очень длинных контекстов. | Альтернатива трансформеру при работе с десятками тысяч токенов. |

- **Ошибки** – попытка использовать трансформер для токенов > контекстное окно без отрезки → падение качества.

## 3. Жизненный цикл разработки LLM (стр. 454‑458)

### 3.1 Основные стадии (стр. 455)  
1. **Pre‑training** – обучение на огромном корпусе интернета (общие знания, язык, мир).  
2. **Fine‑tuning** – дообучение на специализированных наборах данных (конкретные задачи).  
3. **Alignment** – корректировка поведения, чтобы вывод был «полезным, безопасным, согласованным с человеческими ценностями».  

### 3.2 Техники Pre‑training (стр. 456‑457)  
- **Causal Language Modeling (CLM)** – предсказывает следующее слово.  
- **Masked Language Modeling (MLM)** – заполняет скрытые слова.  
- **Denoising Objectives** – восстанавливает испорченный ввод.  
- **Contrastive Learning** – различает похожие/непохожие пары.  
- **Next Sentence Prediction (NSP)** – определяет, следуют ли два предложения друг за другом.  

### 3.3 Техники Fine‑tuning (стр. 458)  
1. **Supervised Fine‑Tuning (SFT)** – обучение на метках «ввод‑вывод».  
2. **Instruction Tuning** – фокус на следовании инструкциям.  
3. **Parameter‑Efficient Fine‑Tuning (PEFT)** – меняются только небольшие части модели:  
   - **LoRA (Low‑Rank Adaptation)** – добавляет небольшие матричные «адаптеры».  
   - **QLoRA** – память‑оптимизированный вариант LoRA.  

### 3.4 Retrieval‑Augmented Generation (RAG) (стр. 459)  
- **Главная мысль** – подключение внешнего источника знаний во время инференса/файн‑тюна, чтобы модель могла «запрашивать» факты.  

### 3.5 Правила и числа  
- **Никаких конкретных чисел** в описании, только перечисления техник.

### 3.6 Ошибки/предупреждения  
- **Переобучение** на узком наборе данных → потеря «общих» знаний.  
- **Отсутствие alignment** → модель может генерировать опасный контент.

## 4. Техники выравнивания и обеспечения безопасности (стр. 460‑461)

- **RLHF (Reinforcement Learning from Human Feedback)** – обучает модель с помощью «reward‑model», часто с **PPO**‑оптимизатором.  
- **DPO (Direct Preference Optimization)** – упрощённый метод без отдельной reward‑модели.  
- **KTO (Kahneman‑Tversky Optimization)** – упрощённый сбор данных для обучения.  
- **Guardrails** – финальный слой фильтрации вывода, блокирующий вредоносные действия в реальном времени.  

**Где применимо** – при выпуске публичных ботов, когда нужен контроль над токсичностью.

## 5. Фреймворки рассуждения и планирования (стр. 461‑464)

| Фреймворк | Что делает | Ключевая идея |
|-----------|-----------|----------------|
| **Chain‑of‑Thought (CoT)** | «Думать вслух»: модель пошагово объясняет рассуждения перед ответом. | Повышает точность в задачах с логикой. |
| **Tree‑of‑Thoughts (ToT)** | Параллельный поиск нескольких рассуждательных ветвей, выбор лучшей. | Позволяет решать более сложные задачи, сравнивая варианты. |
| **ReAct (Reason and Act)** | Цикл «рассуждение → действие (вызов инструмента) → новое рассуждение». | Интеграция инструментов в процесс мышления. |
| **Planning** | Делит большую цель на подпункты, формирует план выполнения. | Позволяет агенту управлять длительными процессами. |
| **Deep Research** | Автономный поиск, синтез и генерация новых вопросов для глубокого изучения темы. | Подходит для исследовательских агентов. |
| **Critique Model** | Специальный агент‑критик, оценивающий выводы других агентов. | Автоматическое улучшение качества. |

- **Ошибки** – отсутствие «self‑correction» → модель может «залипнуть» в ошибочном пути.  
- **Где пригодится** – построение сложных ботов‑ассистентов, требующих последовательного мышления (например, финансовый советник, планировщик проекта).

## 7. Часто задаваемые вопросы (FAQ) (стр. 477)

| Вопрос | Краткий ответ | Где использовать |
|--------|---------------|-----------------|
| **Что такое «agentic design pattern»?** | Переиспользуемое решение типичной проблемы при построении автономных систем. | При проектировании новых агентов – выбираете готовый паттерн. |
| **Главная цель руководства?** | Практическое введение в построение агентных систем, с готовыми архитектурными чертежами. | Для быстрого старта без теоретических «водоворотов». |
| **Кому предназначено?** | Разработчикам ИИ, инженерам‑программистам, архитекторам систем, желающим перейти от простых запрос‑ответ к автономным агентам. | Оценка целевой аудитории вашего продукта. |
| **Ключевые паттерны?** | *Reflection*, *Planning*, *Tool Use*, *Multi‑Agent Collaboration*, *Human‑in‑the‑Loop*. | При построении пайплайна агента выбираете нужные блоки. |
| **Зачем планирование?** | Делит сложную задачу на подзадачи, поддерживает стратегию, отслеживает прогресс, предотвращает «застревание». | В любой долгосрочной задаче (например, запуск продукта). |
| **Разница «инструмент» vs «навык»?** | Инструмент — внешний API/служба (погода, калькулятор). Навык — интегрированная способность, часто сочетает несколько инструментов. | При построении агентных функций («записать встречу» = навык, использующий календарный API). |

- **Ошибки/предупреждения** – не путать «инструмент» и «навык», иначе агент будет перегружать внешние сервисы лишними вызовами.
