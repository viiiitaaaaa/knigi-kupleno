## 1 . Статическое vs. динамическое агентное взаимодействие  

### Главная мысль  
LLM‑модель сама по себе умеет лишь предсказывать токены (stateless). Чтобы превратить её в настоящего агента, нужно добавить **планирование, память и инструменты**, а также организовать **stateful‑цикл** «рассуждение → действие → адаптация».  

### Как делать  
1. **Определить инструменты** (функции, к которым модель будет обращаться).  
2. **Декорировать их** `@tool`‑декоратором LangChain – обязательна точная сигнатура и описательная docstring.  
3. **Привязать инструменты** к LLM через `bind_tools(..., tool_choice="auto")`.  
4. **Запускать цикл**:  
   - вызвать модель с текущим списком сообщений;  
   - если в ответе есть `tool_calls` – выполнить их, добавить `ToolMessage`;  
   - повторять, пока нет вызовов или не превысим шаговый лимит.  
5. **Добавить завершающую инструкцию**, чтобы гарантировать финальный ответ.  

### Правила и числа  
| Правило | Примечание (стр.) |
|--------|-------------------|
| Обязательная **docstring** у каждой функции‑инструмента (иначе LangChain бросает ошибку). | (стр. —) |
| Ограничение количества шагов в цикле (по умолчанию 8) – защита от бесконечных петлей. | (стр. —) |
| При биндинге `tool_choice="auto"` модель сама решает, нужен ли инструмент. | (стр. —) |
| Для безопасного калькулятора запрещены глобальные переменные, оставлены только константы `pi`, `e`. | (стр. —) |

### Шаблоны и примеры  

*Определение инструмента*  

```python
@tool("internet_search")
def internet_search(query: str) -> str:
    """Search Google via SerpAPI for up-to-date information."""
    serp_api_key = os.environ["SERPAPI_API_KEY"]
    search = SerpAPIWrapper(params={"engine":"google"}, serpapi_api_key=serp_api_key)
    return search.run(query)
```

*Биндинг инструментов*  

```python
llm = ChatOpenAI(model="gpt-4o", temperature=0, max_tokens=800)
llm = llm.bind_tools([internet_search, calculator], tool_choice="auto")
```

*Мини‑цикл без состояния*  

```python
def run_once(prompt: str, max_steps: int = 8) -> str:
    messages = [HumanMessage(content=prompt)]
    for _ in range(max_steps):
        ai = llm.invoke(messages)
        messages.append(ai)
        calls = getattr(ai, "tool_calls", None) or []
        if not calls:               # нет вызовов → финальный ответ
            return messages[-1].content
        for call in calls:
            result = tool_map[call["name"]].invoke(call.get("args", {}))
            messages.append(ToolMessage(content=str(result), name=call["name"]))
    # если превысили лимит – принудительно завершаем
    messages.append(HumanMessage(content="Finish now. Give a short final answer…"))
    final_ai = llm.invoke(messages)
    return final_ai.content
```

### Ошибки и предупреждения  
- **Отсутствие docstring** → ошибка при построении схемы инструмента.  
- **Неочевидный/размытый docstring** → модель может генерировать некорректные вызовы.  
- **Неограниченный цикл** → возможны «runaway loops», поэтому нужен жёсткий `max_steps`.  

### Где нам пригодится  
Для **быстрого прототипа**: выполнить запросы к внешним API (поиск, вычисления) без сохранения состояния между запусками.

## 2 . Построение **stateful**‑агента (LangGraph)  

### Главная мысль  
Для многократных интеракций необходимо хранить **структурированное состояние** (сообщения, результаты инструментов, контрольные точки) и **переходы** между узлами‑логикой, а не просто сбрасывать всё после каждого вызова.  

### Как делать  

1. **Определить тип состояния** (`TypedDict`/`Pydantic`), включающий, минимум, список сообщений.  
2. **Создать узлы**:  
   - `llm_node` – вызывает LLM, добавляет её сообщение.  
   - `tool_node` – исполняет все `tool_calls` из последнего сообщения.  
3. **Определить роутер** (функцию `route`) — если в последнем сообщении есть `tool_calls`, перейти к `tool_node`, иначе завершить.  
4. **Собрать граф** (`StateGraph`): добавить узлы, задать старт (`START`) и конечные (`END`) ребра, подключить условные переходы.  
5. **Скомпилировать граф** с чекпоинтером (`MemorySaver`) для сохранения состояния между запросами.  
6. **Назначить `thread_id`** – уникальный идентификатор ветки (разные ветки → разные диалоги).  
7. **(Опционально) Добавить трассировку** – функции `_short`, `print_state_snapshot`, `run_with_tracing` выводят компактный лог‑трассы.  

### Правила и числа  

| Правило | Примечание (стр.) |
|--------|-------------------|
| `MemorySaver` — in‑memory чекпоинтер, сохраняет состояние per‑thread. | (стр. —) |
| `thread_id` — идентификатор ветки, позволяет параллельно вести несколько разговоров без пересечения. | (стр. —) |
| **Шаговый лимит** (по умолчанию 20) в `run_with_tracing` – защита от бесконечных рекурсий. | (стр. —) |
| При форматировании сообщений в `_short` используется `max_len = 140` символов. | (стр. —) |

### Шаблоны и примеры  

*Определение состояния и узлов*  

```python
class AgentState(TypedDict):
    messages: Annotated[List[BaseMessage], add_messages]

def llm_node(state: AgentState) -> AgentState:
    ai = llm.invoke(state["messages"])
    return {"messages": [ai]}

tool_node = ToolNode(tools=tools)   # готовый узел из LangGraph
```

*Граф и роутер*  

```python
graph = StateGraph(AgentState)
graph.add_node("llm", llm_node)
graph.add_node("tools", tool_node)
graph.add_edge(START, "llm")

def route(state: AgentState):
    last = state["messages"][-1]
    calls = getattr(last, "tool_calls", None) or []
    return "tools" if calls else END

graph.add_conditional_edges("llm", route,
                            {"tools": "tools", END: END})
graph.add_edge("tools", "llm")
```

*Компиляция и запуск*  

```python
checkpointer = MemorySaver()
app = graph.compile(checkpointer=checkpointer)
cfg = {"configurable": {"thread_id": "nyc-weather-session"}}
```

*Трассировка*  

```python
def run_with_tracing(app, input_state, config, title):
    for event in app.stream(input_state, config=config, stream_mode="updates"):
        for node, upd in event.items():
            print(f"[enter {node}] updated: {list(upd.keys())}")
            if "messages" in upd:
                print(f"  {_short(upd['messages'][-1])}")
            print(f"[leave {node}]")
```

### Ошибки и предупреждения  

- **Не сохранять сообщения** в состоянии → каждый запрос будет «stateless», потеряется контекст.  
- **Не задавать `thread_id`** → все запросы будут объединяться в одну ветку, что приводит к конфликтам при параллельных сценариях.  
- **Неправильный роутер** (возврат неверного узла) → цикл может «зависнуть» в бесконечном переходе.  

### Где нам пригодится  

Для **многократных интерактивных задач**: запросы к базе, пошаговый расчёт, работа с пользовательскими скриптами, где нужен кеш результатов и возможность ветвления диалогов.

## 3 . «Deus Ex Machina»: реальные возможности современных агентов  

### Главная мысль  
Сегодняшние агенты – это **инженерные системы** со строго ограниченными зонами свободы: они могут выбирать между предопределёнными ветвями, вызывать инструменты и рефлексировать, но не могут перепроектировать собственный граф или создавать новые инструменты без человеческого вмешательства.  

### Как делать  
1. **Определить набор фиксированных путей** (узлы‑действия, инструменты).  
2. **Ограничить LLM** лишь в выборе между этими путями (router‑узел, guard‑условия).  
3. **Встроить защитные механизмы** (ограничения по времени/шагам, валидацию вывода инструмента).  

### Правила и числа  

| Правило | Примечание (стр.) |
|--------|-------------------|
| Агент может *перемещаться* только по **предзаданным путям** (router → node). | (стр. —) |
| Агент **не может** самостоятельно *перепроектировать* граф, создавать новые инструменты. | (стр. —) |
| Автономия оценивается как **орchestrated** (внутри границ), а не **full** – полная. | (стр. —) |

### Шаблоны и примеры  

Таблица 1‑2 (в тексте) сравнивает «Что могут» vs «Что не могут» агенты; она служит шаблоном для оценки требуемой автономии в проекте.  

### Ошибки и предупреждения  

- **Иллюзия полной автономии** → переоценка возможностей, риск небезопасного поведения.  
- **Отсутствие контролирующего роутера** → агент может застрять в бесконечном цикле или вызвать нежелательные инструменты.  

### Где нам пригодится  

При **проектировании безопасных продуктов**: чётко сформулировать, какие действия агент может выполнять, и где нужен человеческий контроль (approval‑gate, коррекции).

## 4 . Кейс — *AI Scientist v2* (ограниченная автономия)  

### Главная мысль  
AI Scientist v2 демонстрирует, как **орchestrated autonomy** позволяет полностью автоматизировать исследовательский цикл (генерация гипотез, код, эксперимент, написание статьи). Однако даже при таком успехе остаются ограничения: низкая новизна, необходимость валидации человеком, ошибки в цитировании и визуализации.  

### Как делать (упрощённый пайплайн)  

1. **Tree‑search** (генерация гипотез).  
2. **Эксперимент‑менеджмент** (запуск кода, отладка).  
3. **Vision‑Language feedback** (анализ результатов).  
4. **Сборка рукописи** (автогенерация текста, ссылки).  

### Правила и числа  

| Правило | Примечание (стр.) |
|--------|-------------------|
| Система смогла **подать 3 статьи** на ICLR 2025 workshops; **одна** принята. | (стр. —) |
| Приёмка ограничена **workshop‑уровнем**, не main‑conference. | (стр. —) |
| Ошибки: «citation errors», «misleading figure descriptions». | (стр. —) |

### Шаблоны и примеры  

*Формулировка запроса к модели (пример из кода)*
```python
"Generate three distinct approaches for a developer blog on: {topic}"
```

*Структура вывода (JSON)*
```json
{
  "options": [
    {"title": "...", "audience": "...", "angle": "...", "outline": [...], "rationale": "..."},
    ...
  ]
}
```

### Ошибки и предупреждения  

- **Методология** полученных статей часто «поверхностна», требует глубокого экспертного анализа.  
- **Автогенерация кода** может привести к скрытым багам; нужен человеческий дебаг.  

### Где нам пригодится  

Для **автоматизации рутинных исследовательских шагов**: генерация идей, быстрая проверка гипотез, подготовка черновиков отчётов/статей.

## 5 . Итоги главы 1  

### Главная мысль  
Переход от **статических предикторов** к **динамическим агентам** достигается через:  
- **Концепцию состояния (FSM/HSM → LangGraph)**,  
- **Планирование/рефлексию (CoT, ToT, ReAct)**,  
- **Инструменты** (поиск, вычисления, API),  
- **Контролируемую автономию** (router‑узлы, ограничения).  

### Как делать (коротко)  

1. Оформить инструменты (`@tool`).  
2. Привязать их к LLM (`bind_tools`).  
3. Выбрать **stateless**‑проtotyping (цикл 1‑4).  
4. Перейти к **stateful**‑архитектуре (LangGraph).  
5. Добавить **трассировку** и **чекпоинты**.  
6. Оценить уровень автономии и установить границы.  

### Правила и числа  

| Правило | Примечание (стр.) |
|--------|-------------------|
| **step‑bound** (по умолчанию 8) – защита от «runaway loops». | (стр. —) |
| **max_tokens** = 800 (пример привязки модели). | (стр. —) |
| **temperature** = 0 — детерминированность для инструментов. | (стр. —) |
| **recursion_limit** = 20 (вызов `run_with_tracing`). | (стр. —) |

### Шаблоны и примеры  

- **Мини‑граф** из двух узлов (LLM ↔ Tools).  
- **Функция `_short`** для компактного лог‑вывода.  

### Ошибки и предупреждения  

- Не использовать **вью‑поток** без ограничения шагов → возможен дедлайн.  
- Пропуск **docstring** → ошибка сборки схемы.  

### Где нам пригодится  

Для **быстрого перехода** от простых запросов к **многошаговым, запоминающимся агентам**, которые могут работать с вашими скриптами и данными в рамках одной сессии.

## 6 . Глава 2 — «Architectures and Patterns: Planning, Reactivity, and Multi‑Agent Systems»  

### Главная мысль  
Архитектура определяет, как агент планирует, реагирует и взаимодействует с другими агентами. Основные паттерны: **Chain‑of‑Thought (CoT)**, **Tree‑of‑Thought (ToT)** и **ReAct** (Reason + Act). Плюс — механизмы «human‑in‑the‑loop» (approval‑gates, коррекции, прерывания) для надёжности и выравнивания целей.  

### Как делать (по каждому паттерну)  

#### 6.1 CoT (Chain‑of‑Thought)  
1. Ввести **system‑prompt**, задающий модель «думать вслух» и выводить финальный ответ только после завершения цепочки.  
2. При необходимости добавить **sandbox‑инструмент** (например, `PyodideSandboxTool`) для выполнения кода.  
3. Запустить агента через `create_react_agent(...)`.  

#### 6.2 ToT (Tree‑of‑Thought) – лёгкая инженерная версия  
1. **Узел‑пропозер** (маленькая LLM) генерирует фиксированное количество вариантов (обычно 3).  
2. **Узел‑рефлектор** (более мощная LLM) оценивает варианты, выбирает лучший и формирует JSON‑выбор.  
3. **Последующие узлы** (research, draft) работают уже с выбранным ветром.  
4. Сконструировать граф в **LangGraph**, задав последовательные ребра `propose → reflect → research → draft → END`.  

#### 6.3 ReAct (Reason + Act)  
1. **Состояние** – список сообщений (`AgentState`).  
2. **Модель** привязывается к набору инструментов (`model.bind_tools(TOOLS)`).  
3. **Policy‑node** (`call_model`) получает весь контекст и выдаёт **либо** мыслительный шаг, **либо** вызов инструмента.  
4. **Tool‑node** исполняет каждый запрошенный инструмент, добавляя `ToolMessage`.  
5. **Условный роутинг** (`should_continue`) решает, перейти ли к `tools` или завершить.  

### Правила и числа  

| Правило | Примечание (стр.) |
|--------|-------------------|
| **CoT‑prompt** требует явного разделения финального ответа (только после полного анализа). | (стр. —) |
| В ToT **branching factor** = 3 (для экономии и читаемости). | (стр. —) |
| **max_len** = 140 в функции `_short` (для журналов). | (стр. —) |
| **temperature** = 0 в примерах ReAct (детерминированность). | (стр. —) |
| **recursion_limit** = 20 (для потоковых запусков). | (стр. —) |

### Шаблоны и примеры  

*CoT‑prompt (пример 2‑1)*

### Ошибки и предупреждения  

- **CoT** без явного финального шаблона → модель может отдать частичный вывод.  
- **ToT** с слишком большим branching factor → экспоненциальный рост затрат.  
- **ReAct** без правильного `should_continue` → может зациклиться в бесконечном «think‑act» → нужен жёсткий лимит шагов.  
- **Sandbox** (Pyodide) — не поддерживает все библиотеки (например, `matplotlib`), нужно планировать ограниченный набор (pandas, SVG‑вывод).  

### Где нам пригодится  

- **CoT** – для **прозрачного аудита** (аналитика данных, отладка, доказательство срока).  
- **ToT** – когда нужно **сравнить несколько стратегий** (контент‑план, варианты дизайна).  
- **ReAct** – для **интерактивных запросов**, где требуется чередовать запросы к API/поиску и объяснения (например, «узнать погоду», «сделать расчёт», «вывести график»).
