## Prompt Chaining — Разбиение сложных задач на последовательные подсказки (стр. 26‑35)

### Главная мысль
Разбивая многократные запросы на цепочку небольших, специализированных подсказок, — можно превратить сложный многошаговый процесс (поиск, извлечение, синтез, проверка) — в надёжный, управляемый и легко отлаживаемый рабочий поток.

### Как делать — общий алгоритм (пошагово)

1. **Выделить подзадачи** – определить логически независимые части исходного запроса.  
2. **Сформулировать отдельные подсказки** для каждой подзадачи (Prompt 1, Prompt 2 …).  
3. **Выполнять их последовательно**: результат предыдущей подсказки передаётся как вход следующей (prompt chaining).  
4. **Параллельно обрабатывать независимые шаги**, если они не зависят друг от друга (пример — одновременный парсинг нескольких статей).  
5. **Собирать и синтезировать** полученные данные в финальный ответ.  
6. **Опционально** добавить внешние инструменты (калькулятор, OCR‑модуль) между шагами.  

### Правила и числа (стр. 33‑34)

| Правило | Краткое содержание |
|--------|---------------------|
| **Rule of thumb** | Применять, когда задача слишком сложна для одного запроса, требует нескольких фаз обработки, использует внешние инструменты или нужна сохранённость состояния. |
| **Почему** | Одна монолитная подсказка перегружает модель → теряется контекст, увеличивается количество ошибок. |
| **Что** | Prompt Chaining → деление задачи на цепочку малых, сфокусированных шагов (иногда называют “Pipeline”). |

### Шаблоны и примеры (из текста)

* **Complex Query Answering** – 4‑шаговая цепочка:  
  1. *Prompt 1*: «Определи подпра­вры в запросе».  
  2. *Prompt 2*: «Исследуй причины краха 1929 года».  
  3. *Prompt 3*: «Исследуй реакцию правительства».  
  4. *Prompt 4*: «Синтезируй ответ».  

* **Data Extraction & Transformation** – условный цикл:  
  - *Prompt 1*: «Извлеки поля (имя, адрес, сумма) из счета».  
  - *Processing*: проверка полноты/формата.  
  - *Prompt 2 (Conditional)*: «Найди недостающие/ошибочные поля».  

* **Content‑Generation Workflow** – генерация идеи → план → черновики → ревизия (5 подшагов).  

* **Code Generation & Refinement** – псевдокод → стартовый код → статический анализ → исправление → документация/тесты (5 шагов).  

* **Multimodal Reasoning** – 3‑шаговая цепочка: извлечение текста из изображения → сопоставление с метками → интерпретация через таблицу.  

* **LCEL‑пример (Python)** – два‑шаговый pipeline:  
  ```python
  extraction_chain = prompt_extract | llm | StrOutputParser()
  full_chain = {"specifications": extraction_chain} | prompt_transform | llm | StrOutputParser()
  ```

### Ошибки и предупреждения
- **Перегрузка одной подсказки** → потеря контекста, «забывание» инструкций (стр. 33).  
- **Недостаточная проверка** промежуточных результатов → ошибки в итоговом ответе (см. цикл в Data Extraction).  
- **Неправильный порядок**: попытка синтезировать до завершения всех параллельных извлечений приводит к неполным данным.  
- **Неправильный тип внешнего инструмента** (например, арифметика внутри LLM) → неточности; лучше делегировать калькулятору.  

### Где нам пригодится
Для запросов предпринимателя, требующих **многократного поиска, объединения данных, генерации кода или контента**, а также при **обработке неструктурированных входов (PDF, email, OCR)**.

## Routing — Динамический выбор следующего действия (стр. 36‑49)

### Главная мысль
Маршрутизация вводит условную логику в агентный поток: система сначала классифицирует запрос/состояние, а затем направляет выполнение к подходящему инструменту, цепочке или под‑агенту, делая работу адаптивной к меняющимся условиям.

### Как делать (пошаговый шаблон)

1. **Анализ входа** – с помощью LLM, правил, эмбеддингов или обученного классификатора определить тип/намерение.  
2. **Выбрать путь** – сопоставить полученный маркер (например, «order_status», «product_info», «technical_support», «unclear») с конкретным обработчиком/цепочкой.  
3. **Делегировать** запрос выбранному обработчику (sub‑agent, tool, отдельный chain).  
4. **(Опционально) Обновить состояние** – сохранить результат/контекст для последующего использования.  
5. **(Опционально) Обратная связь** – если выбран «unclear», запросить уточнение и начать цикл заново.  

### Правила и числа (стр. 37‑38)

| Правило | Содержание |
|--------|-------------|
| **LLM‑based Routing** | LLM получает инструкцию «выведи только одну метку» и выдаёт её → система читает метку и направляет поток. |
| **Embedding‑based Routing** | Преобразовать запрос в вектор, сравнить с векторами‑прототипами маршрутов (семантическое сравнение). |
| **Rule‑based Routing** | Прямые if/else‑условия по ключевым словам – быстрее, но менее гибко. |
| **ML‑model‑based Routing** | Тренированный классификатор (supervised) выдает метку; LLM может генерировать синтетические данные, но сам не участвует в реальном времени. |
| **Rule of Thumb** | Применять, когда агент должен выбирать между **≥2** различными ветвями в зависимости от **интента**, **состояния** или **результата предыдущего шага**. |

### Шаблоны и примеры

* **LLM‑router Prompt** (стр. 36‑37)  
  ```
  Analyze the following user query and output only the category: 
  'Order Status', 'Product Info', 'Technical Support', or 'Other'.
  ```

* **LangChain + RunnableBranch** (стр. 40‑42) – код‑пример:  
  ```python
  coordinator_router_prompt = ChatPromptTemplate.from_messages([
      ("system", """Analyze the user's request and determine which specialist handler 
      should process it. Output one word: 'booker', 'info' or 'unclear'."""),
      ("user", "{request}")
  ])
  coordinator_router_chain = coordinator_router_prompt | llm | StrOutputParser()
  
  branches = {
      "booker": RunnablePassthrough.assign(output=lambda x: booking_handler(x['request'])),
      "info":   RunnablePassthrough.assign(output=lambda x: info_handler(x['request'])),
      "unclear":RunnablePassthrough.assign(output=lambda x: unclear_handler(x['request']))
  }
  
  delegation_branch = RunnableBranch(
      (lambda x: x['decision'].strip() == 'booker', branches["booker"]),
      (lambda x: x['decision'].strip() == 'info',   branches["info"]),
      branches["unclear"]
  )
  ```

* **Google ADK‑router** (стр. 43‑46) – описание «Coordinator» агент с инструкцией делегировать запросы к «Booker» или «Info» через **Auto‑Flow**.

### Ошибки и предупреждения
- **Неправильная классификация** → запрос попадает в неподходящий обработчик (например, запрос о бронировании попадает в инфо‑агент).  
- **Пересечение маршрутов** (один запрос подходит под несколько правил) – требуется приоритет/дисциплина в определении меток.  
- **Зависимость от качества эмбеддингов**: плохие векторы → неверный семантический маршрут.  
- **Отсутствие fallback‑маршрута** («unclear») → система «зависает» без ответа.  

### Где нам пригодится
Для **триггеров выбора между разными скриптами/инструментами** (например, запрос «сгенерировать финансовый отчёт» → роут в модуль расчётов, а запрос «рассчитать налог» → роут в калькулятор), а также при построении **диалоговых помощников**, где нужно различать типы пользовательских запросов.

## Parallelization — Параллельное выполнение независимых подпроцессов (стр. 50‑57)

### Главная мысль
Когда отдельные шаги в агентном workflow не зависят друг от друга, их можно выполнять одновременно, что существенно снижает время отклика (особенно при работе с медленными внешними API) без потери точности результата.

### Как делать (пошаговый шаблон)

1. **Идентифицировать независимые подпроцессы** (поиск, суммирование, генерация вопросов и т.п.).  
2. **Оформить каждый подпроцесс как отдельную «runable»‑цепочку** (LLM‑prompt + парсер).  
3. **Собрать их в `RunnableParallel`** (или аналог в выбранном фреймворке).  
4. **Передать исходные данные** (например, тему) всем цепочкам одновременно.  
5. **Ожидать завершения** всех параллельных задач.  
6. **Синтезировать результаты** в финальный вывод при помощи отдельного LLM‑шаблона.  

### Правила и числа (стр. 51‑53)

| Правило | Содержание |
|--------|------------|
| **Идентификация независимых частях** | Любой шаг, чей вход не зависит от выхода другого шага, можно ставить в параллель. |
| **Асинхронность ≠ истинный параллелизм** | В Python GIL ограничивает истинный параллелизм; `asyncio` даёт *конкурентность* (одновременное ожидание сетевых запросов). |
| **Rule of Thumb** | Применять, когда есть ≥2 независимых внешних вызова (API, поиск, аналитика) – экономия времени в 2‑5× и более. |

### Шаблоны и примеры

* **LangChain + RunnableParallel** (стр. 54‑56)  
  ```python
  summarize_chain = ChatPromptTemplate.from_messages([...]) | llm | StrOutputParser()
  questions_chain = ChatPromptTemplate.from_messages([...]) | llm | StrOutputParser()
  terms_chain     = ChatPromptTemplate.from_messages([...]) | llm | StrOutputParser()
  
  map_chain = RunnableParallel({
      "summary":   summarize_chain,
      "questions": questions_chain,
      "key_terms": terms_chain,
      "topic":    RunnablePassthrough()
  })
  
  synthesis_prompt = ChatPromptTemplate.from_messages([
      ("system", """Based on the following information:
      Summary: {summary}
      Related Questions: {questions}
      Key Terms: {key_terms}
      Synthesize a comprehensive answer."""),
      ("user", "Original topic: {topic}")
  ])
  
  full_parallel_chain = map_chain | synthesis_prompt | llm | StrOutputParser()
  ```
  Запуск (асинхронно):
  ```python
  response = await full_parallel_chain.ainvoke("The history of space exploration")
  ```

* **Пример применения** (стр. 52‑53) – агент‑исследователь, одновременно собирает:
  - новости,
  - котировки акций,
  - соц‑медиа,
  - данные из базы компаний.

### Ошибки и предупреждения
- **Синхронизационные зависимости**: если один подпроцесс неожиданно начинает использовать результат другого, параллелизм станет ошибочным.  
- **Перегрузка API‑квот**: одновременный запрос к нескольким внешним сервисам может превысить лимиты.  
- **Неочевидные исключения** в одном из параллельных потоков → «застревание» всей цепочки, если не обрабатывать ошибки явно.  
- **Плохое масштабирование** в однопоточном исполнении (Python GIL) – соблюдать, что «параллельность» здесь ≈ одновременное ожидание, а не истинное вычислительное распараллеливание.  

### Где нам пригодится
Для **быстрого сбора и агрегирования данных из нескольких источников** (цена акций, погода, новости) при построении **дашбордов, аналитических отчётов или стратегических рекомендаций** у одиночного предпринимателя.

**Краткое сравнение трёх паттернов**

| Паттерн | Когда использовать | Ключевая техника |
|--------|-------------------|-------------------|
| **Prompt Chaining** | Одна сложная задача → требуется последовательный анализ/синтез, часто с внешними инструментами. | Последовательные подсказки + промежуточная валидация. |
| **Routing** | Неизвестно, какой из нескольких путей подходит; необходимо классифицировать запрос/состояние. | Условный переход (LLM‑router, правила, эмбеддинги, обученный классификатор). |
| **Parallelization** | Задача делится на независимые подпроцессы, каждый из которых может работать независимо. | `RunnableParallel`/async‑вызовы, затем объединяющий шаг. |

Эти три шаблона образуют базовый набор при построении **агентных систем** для вашего личного ассистента Claude:  
- **Prompt Chaining** — структурирует глубокие «запрос‑ответ» цепочки.  
- **Routing** — решает, к какому **sub‑агенту** или **инструменту** обратиться.  
- **Parallelization** — ускоряет сбор данных и одновременную генерацию разных артефактов.  

Используйте их последовательно: сначала разбейте задачу (chaining), затем решите, какие ветки нужны (routing), а где возможно – запустите их параллельно (parallelization). Это позволит вашему единственному предпринимателю эффективно управлять скриптами, данными и процессом обучения без лишних человеческих ошибок.
