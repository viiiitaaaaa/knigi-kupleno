## Что такое ИИ-агент? (стр. 218–223)

**Главная мысль:** ИИ-агент — это развитие RAG (поиска по документам). Если обычный RAG просто ищет ответ на вопрос, то агент использует LLM как «мозг» для планирования: он сам понимает, каких знаний ему не хватает, выбирает нужные инструменты, вызывает их в правильном порядке и синтезирует итоговый ответ.

### Агентный стек (Agentic Stack) — из чего состоит агент (стр. 219–221)
1. **Рассуждающая LLM (Мозг):** Понимает намерения пользователя, разбивает сложную цель на шаги, принимает решения и пишет финальный ответ.
2. **Оркестрация (Нервная система):** Прослойка (например, LangChain, CrewAI), которая передает команды от «мозга» к инструментам и возвращает результаты обратно.
3. **Инструменты (Руки):** API внешних сервисов, доступ к базам данных (text2SQL), поиск в интернете, доступ к календарю или почте.

### Типы систем: Один агент vs Много агентов (стр. 221–223)
- **Одиночный агент (Single-agent):** 
    - *Для чего:* Простые, сфокусированные задачи (например, базовый чат-бот поддержки).
    - *Плюсы:* Работает быстрее на 30–50%, дешевле по токенам.
- **Мультиагентные системы (Multi-agent):** 
    - *Для чего:* Сложные рабочие процессы (например, один агент ищет данные, второй анализирует цифры, третий пишет отчет).
    - *Топологии:* 
        1. **Супервайзер:** Главный агент-менеджер распределяет задачи подчиненным.
        2. **Коллаборативная:** Агенты общаются друг с другом напрямую (Peer-to-Peer).
    - *Минусы:* «Налог на сложность» — выше задержки, больше затрат на токены, риск зацикливания.

**Когда переходить на мультиагентную систему?**
- Нужны разные уровни безопасности для разных задач.
- Слишком много инструментов (один агент начинает путаться и галлюцинировать — «размытие инструментов»).
- Разные команды разработчиков поддерживают разные части логики.

**Рекомендация:** Начинайте с одного хорошо настроенного агента. Если нужно больше — используйте паттерн «Оркестратор $\rightarrow$ Рабочие» (подчиненные не общаются между собой).

**Где нам пригодится:** Для создания автономных помощников, которые не просто отвечают, а выполняют действия (записи, расчеты, поиск).

## Кейсы использования (Agentic Use Cases) (стр. 224–228)

**Главная мысль:** Агенты превращают рутинные процессы из жестких сценариев «если-то» в гибкие интеллектуальные системы.

- **Клиентский сервис:** Переход от скриптов к персонализированным помощникам (например, банковский агент, который видит историю счетов клиента). *Предупреждение:* Критически важна борьба с галлюцинациями.
- **Финансы:** Автоматизация инвестиционных меморандумов (сбор данных из новостей и отчетов) и анализ новых регуляторных норм.
- **Здравоохранение:** Автоматическое создание заметок врача по аудиозаписи приема, поиск пациентов для клинисследований. *Правило:* Окончательное решение всегда за лицензированным врачом.
- **Кодинг:** Переход от подсказок кода к полноценным агентам (Cursor, Claude Code), которые могут запускать терминал и тесты. Роль программиста меняется с «кодера» на «директора кода/ревьюера».

**Предупреждения:**
- Агенты плохо справляются с «задачами с длинным горизонтом» (много шагов подряд), так как ошибки накапливаются.
- В регулируемых сферах (деньги, здоровье) обязателен принцип **Human-in-the-loop** (человек должен подтвердить действие перед его выполнением).

**Где нам пригодится:** Для автоматизации своих скриптов, анализа данных и ускорения разработки своих продуктов.

## Агентный цикл (The Agentic Loop) (стр. 202–205)

**Главная мысль:** Работа любого агента — это бесконечный цикл из трех стадий.

1. **Наблюдение (Observation):** Получение запроса пользователя или результата работы предыдущего инструмента.
2. **Рассуждение и планирование (Reasoning and planning):** Мозг анализирует контекст, память и решает, какой инструмент вызвать и с какими параметрами.
3. **Действие (Action):** Оркестратор вызывает инструмент и возвращает результат обратно в цикл.

### RAG как инструмент (стр. 203)
Есть два подхода к работе с документами:
- **Retrieval-as-a-tool:** Инструмент просто дает куски текста $\rightarrow$ агент сам думает и синтезирует ответ (больше контроля и прозрачности).
- **RAG-as-a-tool:** Инструмент сам ищет и возвращает готовый ответ с цитатами (более стабильно и единообразно).

### Вызов инструментов / Tool Calling (стр. 204–205)
Это способность LLM генерировать структурированный запрос (обычно JSON) для вызова функции.
- **Рекомендация по именованию:** Не называйте функцию `data_lookup` (слишком общо), используйте семантические имена (например, `get_weather`), четко описывайте типы аргументов и границы работы инструмента.
- **Параллельный вызов:** Современные модели могут вызвать несколько инструментов за один раз (например, запросить выручку компании за 2021, 2022 и 2023 годы одновременно).

**Где нам пригодится:** Для отладки агентов (если агент ошибся, нужно понять, на какой стадии цикла: наблюдение $\rightarrow$ план $\rightarrow$ действие).

## Протоколы связи: MCP и A2A (стр. 206–210)

**Главная мысль:** Чтобы не писать уникальный код для каждого нового инструмента или агента, нужны единые стандарты связи.

### Model Context Protocol (MCP) (стр. 206–209)
Стандарт, который отделяет «мозг» агента от реализации инструментов.
**Три основы MCP:**
1. **Инструменты (Tools):** Функции для действий или динамического чтения данных.
2. **Ресурсы (Resources):** Слой данных (например, ссылки на файлы или БД через URI), чтобы не передавать огромные тексты в каждом ответе.
3. **Промпты (Prompts):** Шаблоны инструкций для повторяющихся задач.

**Архитектура:** Хост (приложение) $\rightarrow$ Клиент MCP $\rightarrow$ Сервер MCP (адаптер) $\rightarrow$ Инструмент/Данные.

### Agent-to-Agent (A2A) (стр. 236–237)
Протокол для общения агентов между собой. Позволяет объединять агентов от разных вендоров (например, агент в Google Cloud общается с агентом в Salesforce).
- **Agent Card (Карточка агента):** Цифровой профиль, где описаны навыки агента. С помощью карточек один агент находит другого подходящего помощника для задачи.

**Где нам пригодится:** При масштабировании системы, когда нужно подключать разные сторонние API или создавать команду специализированных помощников.

## Практика: Агент на LangChain (стр. 237–239)

**Главная мысль:** Реализация агента по методу ReAct (Reason + Act).

**Процесс создания:**
1. Создается стандартный RAG-конвейер (загрузка PDF $\rightarrow$ разбиение на чанки по 1000 симв. с перекрытием 100 $\rightarrow$ векторное хранилище FAISS).
2. RAG-конвейер оборачивается в функцию (инструмент) с описанием: «Используй этот инструмент для ответов по статье GPT-2».
3. Создается ReAct-агент, которому передается LLM и список инструментов.
4. Агент получает сложный вопрос $\rightarrow$ сам разбивает его на два простых под-запроса $\rightarrow$ вызывает RAG-инструмент дважды $\rightarrow$ объединяет ответы.

**Где нам пригодится:** Шаблон для создания собственного «умного» поиска по своим документам и учебным материалам.
