## 1. Введение — что такое память агента (стр. –)  
- **Главная мысль** – Агент — это конечный автомат без «по‑умолчанию» памяти. Чтобы он мог помнить имя, предпочтения и прошлый опыт, память нужно добавить намеренно.  
- **Как делать**  
  1. Определить, какие типы информации должны сохраняться (контекст разговора, факты, эпизоды, инструкции).  
  2. Спроектировать слой хранения (коротк‑‑ и долгосрочная память).  
  3. Встроить чтение/запись в узлы графа или сервисный слой.  
- **Правила и числа** – На рисунке 10‑1 показана “time‑travel”‑отладка через контрольные точки.  
- **Шаблоны / примеры** – Пример 10‑1: `build_checkpointer()` и `build_store()` → создаются in‑memory‑сэйвер и векторный индекс.  
- **Ошибки / предупреждения** – Без памяти каждый запрос начинается с нуля → невозможность персонализации и накопления опыта.  
- **Где пригодится** – При построении любого агента‑помощника, который должен помнить предпочтения пользователя.

## 2. Короткосрочная (рабочая) память и «time travel» (стр. –)  
- **Главная мысль** – Короткосрочная память хранит состояние текущего диалога (сообщения, промежуточные значения) и позволяет «перематывать», ветвить и отлаживать исполнение.  
- **Как делать**  
  1. Создать `checkpointer` (см. пример 10‑1).  
  2. При построении графа передать `checkpointer` в `compile()`.  
  3. При каждом запуске указывать `thread_id` в `RunnableConfig`.  
  4. Для отладки использовать `get_state_history()` → выбрать нужную точку и вызвать `update_state()` / `invoke()` (примеры 10‑4).  
- **Правила и числа** – Пример 10‑3 выводит количество сохранённых чекпоинтов: `len(list(persist_demo.get_state_history(ps_cfg)))`.  
- **Шаблоны / примеры** –  
  - `InMemorySaver()` → простейший чекпоинтер.  
  - Производственный вариант: `SqliteSaver(conn)` или `PostgresSaver.from_conn_string(url)`.  
  - Пример 10‑4: «fork»‑и‑«replay» из ранее сохранённого шага.  
- **Ошибки / предупреждения** – Не забывать задавать уникальный `thread_id`; иначе чекпоинты разных диалогов перемешаются.  
- **Где пригодится** – Отладка цепочек рассуждений, аудит решений, возможность «переписать» ошибочный ход.  

---

## 3. Долгосрочная память – превращаем агента в профессионала (стр. –)  
- **Главная мысль** – Долгосрочная память сохраняет — факты, эпизоды, процедуры — между сессиями, создавая у агента «опыт».  
- **Как делать**  
  1. Выделить три «ножки стула» памяти: **короткосрочная**, **долгосрочная (семантическая, эпизодическая)** и **процедурная**.  
  2. Для каждой «ножки» использовать отдельный namespace (см. пример 10‑5).  
  3. Оборудовать слой доступа (пример 10‑6) – один сервисный объект, который использует единый `store`.  
- **Правила и числа** – Таблица 10‑2 сравнивает короткосрочную и долгосрочную память (напр., «Persistence → Ephemeral vs Persistent storage»).  
- **Шаблоны / примеры** – `UserMemoryService` с методами `list_semantic`, `upsert_semantic`, `set_procedural`.  
- **Ошибки / предупреждения** – Писать в память по‑молчанию без проверки → возможность «memory poisoning».  
- **Где пригодится** – Любой агент, который должен помнить предпочтения клиента (UI‑тема, язык), историю запросов, правила компании.

## 4. Пространства имен (namespaces) и сервисный слой (стр. –)  
- **Главная мысль** – При многопользовательском приложении необходимо изолировать данные по пользователю, организации и типу памяти.  
- **Как делать**  
  1. Описать `AppContext(org_id, user_id, is_admin)`.  
  2. Реализовать функции‑генераторы namespace, напр. `ns_user(ctx, kind)` и `ns_org_shared(org_id, kind)`.  
  3. Обернуть низкоуровневый `store` в класс‑обёртку (`UserMemoryService`).  
  4. При записи проверять, что `user_id` пришёл из проверенного JWT (см. *Verify Your User ID*).  
- **Шаблоны / примеры** –  
  ```python
  NS_SEMANTIC = "semantic"
  ns_user(ctx, NS_SEMANTIC)  # → ("org123", "alice", "semantic")
  ```  
- **Ошибки / предупреждения** – Если `user_id` берётся из клиентского поля, любой может подменить его и писать в чужую память.  
- **Где пригодится** – В SaaS‑приложениях, где несколько организаций и пользователей делят один бек‑енд.

## 5. Эпизодическая память (стр. –)  
- **Главная мысль** – Хранит конкретные прошедшие события (задачи + результаты) и позволяет агенту использовать их как «few‑shot» примеры.  
- **Как делать**  
  1. При начале/завершении задачи вызвать `episodic_record_event(store, ctx, task, outcome)`.  
  2. Поиск похожих эпизодов через `episodic_search(store, ctx, query, limit)`.  
- **Шаблоны / примеры** – Пример 10‑7: `store.put(ns_user(ctx, NS_EPISODIC), key, {...})`.  
- **Ошибки / предупреждения** – Не хранить слишком мелкие эпизоды без агрегирования – может вызвать «memory bloat».  
- **Где пригодится** – При построении аналитических агентов, которым важно смотреть, как решалась похожая задача ранее.  

---

## 6. Семантическая память (стр. –)  
- **Главная мысль** – Хранит факты — допустимые, долговечные знания (настройки, справочная информация).  
- **Как делать**  
  1. Проверять факт перед записью (`validate_durable_memory_text`).  
  2. Записывать через `semantic_upsert_fact(store, ctx, key, fact, extra, transient=False)`.  
  3. Поиск через `semantic_search(store, ctx, query, limit)`.  
- **Шаблоны / примеры** – Пример 10‑8: формирование `payload` с полем `mem_ix = f"{text}\u200ckey:{key}"`.  
- **Ошибки / предупреждения** – Хранить «transient»‑факты без маркировки → они могут «загрязнить» долговременную память.  
- **Где пригодится** – При построении «knowledge‑base»‑агентов, использующих RAG‑подобный поиск.  

---

## 7. Процедурная память (стр. –)  
- **Главная мысль** – Является «живым руководством»: набор инструкций, правил и улучшений, которые агент вызывает каждый раз.  
- **Как делать**  
  1. При первом запуске инициализировать дефолтные инструкции (`procedural_ensure_default`).  
  2. При изменении поведения вызвать `procedural_put_structured(..., fields)`.  
  3. Чтение через `procedural_get_item`.  
- **Шаблоны / примеры** – Пример 10‑9: обновление полей `"style", "workflow", "safety", "task_policies"` только если они переданы.  
- **Ошибки / предупреждения** – Не обновлять инструкцию → агент будет работать по устаревшему сценарию.  
- **Где пригодится** – При динамической адаптации бизнес‑процессов (например, смена формата отчётов).

## 8. Единый «унифицированный» агент (весь стек) (стр. –)  
- **Главная мысль** – Показано, как собрать все типы памяти в одну рабочую систему, поддерживая несколько пользователей и потоков.  
- **Как делать** (по шагам, пример 10‑10)  
  1. Сформировать `RunnableConfig` с `thread_id`.  
  2. Обернуть пользовательский ввод в `HumanMessage(id=uuid4())`.  
  3. Передать `AppContext` (org, user, is_admin) в `agent_app.invoke`.  
  4. Вызывать «слеш‑команды» (`/memory list`, `/thread summarize`, `/memory compact`).  
  5. При необходимости менять память (добавлять предпочтения, эпизоды, процедуры).  
- **Шаблоны / примеры** – Выводы из кода:  
  - `run_turn(..., "remember: I use dark mode …")` → запись в семантику.  
  - `run_turn(..., "episode: billing dispute …")` → запись в эпизод.  
  - `run_turn(..., "/memory list")` → список текущих записей.  
- **Ошибки / предупреждения** – Не проверять `is_admin` → пользователь может изменить глобальные правила организации.  
- **Где пригодится** – Прототип личного ассистента с поддержкой нескольких пользователей и мульти‑тредов.

## 9. Шифрование чекпоинтов (стр. –)  
- **Главная мысль** – Данные чекпоинтов могут содержать конфиденциальную информацию, их следует защищать шифрованием.  
- **Как делать** (пример 10‑11)  
  1. Установить переменную окружения `LANGGRAPH_AES_KEY` (64 hex‑символа).  
  2. Создать `EncryptedSerializer.from_pycryptodome_aes()`.  
  3. Передать её в `InMemorySaver(serde=serde)`.  
  4. Скомпилировать граф с этим чекпоинтером и выполнить один‑два запроса.  
- **Ошибки / предупреждения** – При отсутствии корректного ключа код пропустит шифрование (сообщение «Encrypted demo skipped»).  
- **Где пригодится** – При работе с ПДн, медицинскими данными, финансовой информацией.

## 10. Гигиена памяти (Memory Hygiene) (стр. –)  

### 10.1. Политика удержания (Retention) – таблица 10‑4  
- **Механизмы**  
  - **Time‑based pruning** – удалять записи старше N дней.  
  - **Importance‑based retention** – держать только «ценные» записи (ошибки, нарушения, высоко‑достоверные события).  
  - **Compression** – суммировать эпизоды, сокращать размер.  

### 10.2. Сокращение диалога (Summarize & compact) – пример 10‑12  
- **Как делать**  
  1. Сформировать список сообщений, исключив команду‑сокращение.  
  2. Сконкатенировать их в один `transcript`.  
  3. Попросить LLM‑модель (`memory_llm.invoke`) вернуть до 8 буллетов.  
  4. Сгенерировать `RemoveMessage`‑операции для всех старых сообщений.  
  5. Добавить новое `HumanMessage` с суммарием.  
- **Шаблон вывода** – `Prior conversation (summarized):\n- …`  

### 10.3. Компактификация семантической памяти – пример 10‑13  
- **Как делать**  
  1. Получить список фактов (`semantic_list_items`).  
  2. Объединить их в строку `facts`.  
  3. Попросить LLM слить, де‑дуплицировать, убрать противоречия.  
  4. Записать результат под фиксированным ключом `CONSOLIDATED_KEY`.  
  5. Удалить исходные отдельные записи.  
- **Результат** – Возвращает консолидированный текст и количество удалённых записей.  

### 10.4. Валидация перед записью – пример 10‑14  
- **Как делать** (функция `validate_durable_memory_text`)  
  - Ограничить длину (`max_chars`).  
  - Запретить паттерны SSN, номера кредитных карт, PEM‑приватные ключи, AWS‑ключи, OpenAI‑секреты.  
  - При несоответствии бросить `ValueError`.  
- **Где пригодится** – Защита от случайного или злонамеренного загрязнения памяти.  

### 10.5. Обновление памяти с учётом противоречий и дубликатов – пример 10‑15  
- **Как делать** (функция `apply_updates`)  
  1. Скопировать текущий `current_memory`.  
  2. Удалить записи из `factsToRemove` и те, которые «supersedes».  
  3. По категориям, где режим `replace`, удалить всё старое.  
  4. Вычислить нормализованный ключ (`_fact_key`) для новых фактов → отсеять дубликаты.  
  5. Оставить только факты выше `fact_confidence_threshold`.  
  6. Если общее количество > `max_facts`, отсортировать по уверенности и оставить `max_facts`.  
- **Ошибки / предупреждения** – При масштабировании возможны коллизии ID (см. ниже).  

### 10.6. Риски коллизий ID  
- **Главная мысль** – При генерации коротких UUID‑hex (`[:10]`) может случиться совпадение, особенно в системах с млн записей. Необходимо мониторить и при необходимости увеличить длину.  

### 10.7. Стоимость решения о хранении (Parallel Tax)  
- **Торговля‑офф** – Вызов LLM‑модели для каждой оценки «должно ли запомниться» удваивает количество запросов.  
- **Альтернативы** –  
  - **Regex / правила** – 0 дополнительных вызовов, ~70 % точности, бесплатно.  
  - **Embedding similarity** – GPU‑инференс, ~85 % точности, низкая стоимость.  
  - **Encoder‑only классификатор** – GPU, ~90 % точности, небольшие затраты.  
  - **Полный LLM‑judge** – 1 вызов / шаг, ~95 % точности, удваивает счётчик.  
- **Таблица 10‑5** – Сводит подходы, количество extra‑вызовов, точность и стоимость.  

### 10.8. Детерминированное устранение противоречий – пример 10‑16  
- **Как делать** (`deterministic_reconcile_profile_facts`)  
  1. Сформировать набор пар конфликтующих паттернов (например, «dark mode» vs «light mode»).  
  2. Сравнить каждую пару фактов, взять более новый (по `updatedAt`/`createdAt`).  
  3. Сформировать набор `to_remove` и вернуть память без этих записей.  

- **Где пригодится** – При поддержке профилей, где пользователь может менять настройки, а старые записи нужно отбрасывать автоматически.

## 11. Топология памяти в многопользовательских/мульти‑агентных системах (стр. –)  

| Топология | Описание | Плюсы | Минусы |
|-----------|----------|-------|--------|
| **Локальная (per‑agent)** | Каждый агент хранит свою память в отдельном namespace/сторе. | Модульность, отсутствие «шума» от чужих агентов. | Дублирование знаний, дрейф согласованности. |
| **Глобальная (shared)** | Все агенты читают/пишут в один общий слой памяти. | Единый источник правды, лёгкая координация. | Шум, рост токен‑использования, необходимость синхронизации. |
| **Гибридная** | Агент имеет локальную память + доступ к общему слою (для системных фактов, агрегированных результатов). | Лучшее сочетание изоляции и общих знаний, масштабируемо. | Сложнее реализовать (нужен слой агрегации/компрессии). |

- **Рисунки** – 10‑4 (локальная vs общая) и 10‑5 (гибрид).  
- **Практический совет** – В продакшн‑системах обычно выбирают гибрид: локальный чекпоинтер + общий векторный/ключ‑значный store.

### Сводка «Где нам пригодится каждая часть?»

| Раздел | Применение в работе единственного предпринимателя |
|--------|---------------------------------------------------|
| Введение в память | Определение, какие данные нужны вашему личному ассистенту. |
| Короткосрочная память | Отладка цепочек запросов, возможность «переписать» прошлый шаг. |
| Долгосрочная память | Сохранение предпочтений (язык, UI‑тема), истории проектов. |
| Namespaces | Разделить память по клиенту/компании (если работает с несколькими клиентами). |
| Эпизодическая память | Сохранять результаты прошлых запусков скриптов, чтобы «по‑учитывать» их в новых задачах. |
| Семантическая память | Хранить справочные факты (кодовые шаблоны, ссылки), быстрый поиск. |
| Процедурная память | Динамически менять правила (например, «сейчас использовать формат JSON»). |
| Унифицированный агент | Объединить всё в один сервис‑ассистент, который умеет переключаться между пользователями. |
| Шифрование чекпоинтов | Защищать конфиденциальные данные (пароли, токены). |
| Гигиена памяти | Предотвратить «разрастание» хранилища, держать только актуальные сведения. |
| Топология памяти | Выбрать правильную архитектуру (гибрид) для масштабирования и совместной работы нескольких скриптов/агентов. |

**Кратко:** Для построения собственного помощника (Claude + один пользователь) достаточно реализовать короткосрочную память (чекпоинтер) + долгосрочную (семантика + эпизоды + процедуры) через `UserMemoryService`, использовать **namespaces** по‑пользовательски, поддерживать **гигиену** (валидацию, сжатие, дедупликацию), а при необходимости **шифровать** чекпоинты. При росте до нескольких агентов или клиентов — перейти к гибридной топологии, где каждый агент имеет локальную память, а общие факты живут в глобальном store.
