### 1.5 Создание первой RAG‑приложения (стр. 27‑31)  
- **Главная мысль** – Минимальный RAG‑pipeline состоит из четырёх шагов: разбиение текста, получение эмбеддингов, хранение в векторной базе, запрос‑генерация.  
- **Как делать**  
  1. **Разбиение** (chunking) текста на куски ~1000 символов с перекрытием ≈ 200 симв.:

     ```python
     def chunk_text(text, size=1000, overlap=200):
         chunks, start = [], 0
         while start < len(text):
             end = min(start + size, len(text))
             if end < len(text):
                 bp = text.rfind("\n\n", start, end) or text.rfind(". ", start, end)
                 if bp > start:
                     end = bp + 1
             chunk = text[start:end].strip()
             if chunk:
                 chunks.append(chunk)
             start = end - overlap if end < len(text) else end
         return chunks
     ```
  2. **Эмбеддинг**: используем OpenAI `text-embedding-3-small`. Пакетируем запросы по 100 кусков, собираем векторные представления.  
  3. **Хранение**: `chromadb.PersistentClient(path="chroma_db")`, создаём (или получаем) коллекцию, добавляем `ids`, `documents`, `embeddings`, `metadatas`.  
  4. **Поиск**: по запросу превращаем вопрос в эмбеддинг, ищем `top_k` схожих кусков (`collection.query`).  
  5. **Генерация**: формируем промпт  

     ```
     Answer the question using only the context below.
     Context:
     {retrieved_chunks}
     Question:
     {question}
     Answer:
     ```
     и вызываем OpenAI `gpt-5-mini`.  
- **Правила и числа** – Параметры chunk‑size = 1000, overlap = 200; Batch‑size = 100 кусков; `top_k` = 3 (по умолчанию).  
- **Шаблоны и примеры** – Промпт в функции `answer`; код загрузки эмбеддингов в `embed_and_store`.  
- **Ошибки и предупреждения**  
  - Если ретривер возвращает нерелевантные куски → отладка на этапе поиска, а не генерации.  
  - При множественном запуске может возникнуть конфликт ID; удалите `chroma_db` или измените имя коллекции.  
  - Простой pipeline не подходит для многократных шагов рассуждения или комбинированных источников (SQL + вектор).  
- **Где нам пригодится** – Быстрая проверка идеи: построить чат‑бота над своей коллекцией (например, договоры, техническая документация) и интегрировать с Claude как генератор.

### 1.6 Выбор фреймворков и библиотек для RAG (стр. 32‑34)  
- **Главная мысль** – Существует два подхода: **ориентированные фреймворки** (LangChain, LangGraph, LlamaIndex) и **низкоуровневые библиотеки** (FAISS, NumPy). Фреймворки ускоряют разработку, но добавляют зависимостей.  
- **Как делать** – Таблица 1‑2 (стр. 33) классифицирует типы библиотек:  
  - **Orchestration** – LangChain, LangGraph, LlamaIndex.  
  - **LLM/Embeddings** – OpenAI, Anthropic, HuggingFace Transformers, Sentence‑Transformers.  
  - **Vector storage** – Chroma, FAISS, Pinecone, Milvus, Weaviate.  
  - **Data processing** – pandas, NumPy, PyPDF2, python‑docx, Unstructured, openpyxl, scikit‑learn.  
  - **Multimodal** – Pillow, pytesseract, MoviePy, pdf2image, opencv‑python.  
  - **NLP** – NLTK, Transformers, Rank‑BM25, BeautifulSoup4.  
  - **Evaluation** – Ragas, Phoenix, LangSmith, Prometheus‑Eval.  
  - **Web / deployment** – Streamlit, Gradio, Flask, Django.  
  - **DB / storage** – SQLAlchemy, Psycopg2, SQLite3.  
- **Правила и числа** – Зависимостей у типичного проекта с фреймворком ≈ 100 +; без фреймворка ≈ 5‑10.  
- **Шаблоны и примеры** – Figure 1‑9 (обзор библиотек) и Figure 1‑10 (дерево зависимостей Text Splitter из LangChain).  
- **Ошибки и предупреждения** – При большом количестве зависимостей повышается риск конфликтов, уязвимостей, необходимости частых обновлений. Не подключайте фреймворк, если проект прост (только векторный поиск + LLM).  
- **Где нам пригодится** – При планировании архитектуры RAG‑проекта: решаем, нужен ли нам LangChain для сложных цепочек запросов или достаточно чистого кода с Chroma и OpenAI.
