## 9.1 Why multi‑agent? (стр. 272‑273)  
- **Главная мысль** – Один агент со всеми ролями и инструментами быстро теряет эффективность; лучше разбить задачу на несколько специализированных агентов, каждый со своим коротким промптом и набором инструментов.  
- **Как делать**  
  1. Выделить отдельные роли из общего задания (например, Researcher, Coder, Writer, Reviewer).  
  2. Для каждой роли создать отдельный агент – задать короткий системный промпт, подобрать только нужные инструменты.  
  3. Осуществить взаимодействие между агентами (см. дальше — паттерны сотрудничества).  
- **Правила и числа** – При более чем 10 инструментов LLM всё чаще выбирает неверный инструмент (стр. 273). Чем больше «лишней» информации в контекстном окне, тем труднее LLM сосредоточиться на задаче.  
- **Шаблоны и примеры** – Пример системного промпта, объединяющего четыре роли (стр. 273):  

  ```text
  You are a technical blog writing assistant.
  [Research Role] … 
  [Coding Role] …
  [Writing Role] …
  [Review Role] …
  Available tools: search_web, execute_python, …
  ```  

- **Ошибки и предупреждения** – Длинный промпт путает LLM; слишком много инструментов → частые ошибки выбора.  
- **Где нам пригодится** – При построении запросов‑посредников, когда нужно разделить работу над данными/скриптами/контентом между несколькими специализированными агентами.  



## 9.2 Three collaboration patterns (стр. 274‑275)  
- **Главная мысль** – Существует три способа организации взаимодействия агентов: *Workflow* (разработчик задаёт порядок), *Agent as Tool* (LLM решает, какой агент вызвать, но главный агент остаётся «директором») и *Transfer* (LLM полностью передаёт управление другому агенту).  
- **Как делать**  
  1. Определить, **кто решает порядок** (разработчик — Workflow, LLM — Agent as Tool/Transfer).  
  2. Определить, **делится ли контекст** (общий — Transfer, изолированный — Agent as Tool).  
  3. Выбрать паттерн по правилам:  
     - Если порядок известен заранее → **Workflow**.  
     - Если нужен координатор‑делегатор, а LLM выбирает экспертов → **Agent as Tool**.  
     - Если запрос полностью принадлежит одному эксперту и нужно «перевести» пользователя → **Transfer**.  
- **Правила и числа** – Таблица 9.1 (стр. 275) сравнивает три паттерна:  

  | Паттерн | Кто решает порядок | Как делится контекст | Лучший случай |
  |---------|-------------------|----------------------|---------------|
  | Workflow | Разработчик | По выбору разработчика | Предсказуемый пайплайн |
  | Agent as Tool | LLM | Изолированный | Синтез нескольких экспертных результатов |
  | Transfer | LLM | Общий | Чётко разделённые области |  

- **Шаблоны и примеры** – Пример кода — Workflow (стр. 276):  

  ```python
  workflow = run_sequential(agents=[researcher, coder, writer, reviewer])
  ```  

  Пример регистрации агента‑инструмента (стр. 276):  

  ```python
  assistant = Agent(
      instructions="Answer user questions",
      tools=[AgentTool(researcher), AgentTool(calculator)]
  )
  ```  

  Пример маршрутизатора Transfer (стр. 277):  

  ```python
  router = Agent(
      name="router",
      instructions="Analyze the request and route to the appropriate expert",
      sub_agents=[code_expert, math_expert, writing_expert]
  )
  ```  

- **Ошибки и предупреждения** – Не перепутать **Agent as Tool** (контроль остаётся у главного агента) и **Transfer** (контроль переходит к специалисту).  
- **Где нам пригодится** – При построении «умных» помощников, где часть запросов обрабатывается сразу (Workflow), а часть требует динамического выбора инструмента (Agent as Tool) или переадресации к конкретному эксперту (Transfer).  



## 9.3 Agent workflow: Defining order in code (стр. 276‑283)  

### 9.3.1 Workflow design principles (стр. 277)  
- **Главная мысль** – Чтобы объединять разные типы рабочих процессов (Sequential, Parallel, Loop), каждый из них должен наследоваться от базового `Agent` и реализовывать метод `run()`. Это позволяет вкладывать один workflow в другой.  
- **Как делать**  
  1. Создать классы `SequentialWorkflow`, `ParallelWorkflow`, `LoopWorkflow`, наследуя их от `Agent`.  
  2. Реализовать в каждом `run()` единый интерфейс, принимающий `user_input`, `context`, `verbose`.  
  3. При необходимости вложить один workflow в другой, просто передать его в список `agents`.  
- **Шаблоны** – Пример наследования (стр. 278):  

  ```python
  class SequentialWorkflow(Agent):
      async def run(...):
          ...

  class ParallelWorkflow(Agent):
      async def run(...):
          ...

  class LoopWorkflow(Agent):
      async def run(...):
          ...
  ```  

- **Где нам пригодится** – При построении сложных цепочек обработки данных, где каждый этап – отдельный агент (исследование → анализ → написание → редактура).  

### 9.3.2 Sequential: Step‑by‑step execution (стр. 278‑280)  
- **Главная мысль** – Последовательный workflow запускает агентов один за другим, передавая контекст от текущего к следующему.  
- **Как делать** (по коду Listing 9.5)  
  1. При первом агенте передать и `user_input`, и `context`.  
  2. Для остальных агентов — только `context`.  
  3. Перед каждой новой итерацией очистить `context.final_result` и `context.current_step`.  
  4. После выполнения агента взять `result.context` и передать его дальше.  
- **Шаблоны** – Пример создания и запуска (стр. 280):  

  ```python
  workflow = SequentialWorkflow(agents=[researcher, writer, editor])
  result = await workflow.run("Write a post about the latest trends in AI agents")
  ```  

- **Ошибки** – Не передавать `user_input` повторно, иначе получаем дублирующие запросы.  

- **Где пригодится** – Прямые пайплайны, где каждый шаг логически следует за предыдущим (research → write → review).  

### 9.3.3 Parallel: Concurrent execution (стр. 281‑283)  
- **Главная мысль** – Параллельный workflow одновременно запускает несколько агентов на одинаковый ввод и затем объединяет их результаты в один контекст.  
- **Как делать** (Listing 9.6)  
  1. Зафиксировать количество уже существующих событий (`existing_event_count`).  
  2. Запустить все агенты одновременно через `asyncio.gather`.  
  3. Создать новый `merged_context`.  
  4. Скопировать существующие события из исходного контекста.  
  5. Добавить только **новые** события от каждого агента, при этом:  
     - Удалить дублирующие пользовательские сообщения (`seen_user_event`).  
     - Сохранить автора события (`event.author`) для различения.  
  6. Сформировать итоговый вывод, объединяя результаты с заголовками `[agent_name]`.  
- **Шаблоны** – Пример агентов‑перспектив (стр. 283):  

  ```python
  optimist = Agent(..., instructions="Analyze from a positive perspective …")
  pessimist = Agent(..., instructions="Analyze focusing on risks …")
  realist = Agent(..., instructions="Analyze practical feasibility …")
  workflow = ParallelWorkflow(agents=[optimist, pessimist, realist])
  result = await workflow.run("Evaluate my AI‑based education platform startup idea")
  ```  

- **Ошибки** – Не забыть убрать повторные пользовательские события; иначе контекст «засоряется».  

- **Где пригодится** – Когда нужны независимые оценки (риски/возможности), параллельные проверки кода (безопасность, производительность, читабельность).  

### 9.3.4 Loop: Iterative execution (стр. 284‑286)  
- **Главная мысль** – Циклический workflow повторно запускает набор агентов, пока не выполнится условие остановки (например, достижение качества).  
- **Как делать** (Listing 9.7)  
  1. Определить `stop_condition` — функцию `(result, iteration) -> bool`.  
  2. Установить `max_iterations` (по‑умолчанию 10) во избежание бесконечного цикла.  
  3. Внешний цикл `for iteration in range(1, max_iterations+1)`.  
  4. Внутри – последовательный запуск агентов, как в Sequential, с тем же управлением `is_first_agent`.  
  5. После каждой итерации проверить `stop_condition`; если `True` — прервать.  
- **Шаблоны** – Пример `Review`‑модели и функции‑условия (стр. 284‑285):  

  ```python
  class Review(BaseModel):
      content: str
      score: int   # 0‑100
      feedback: str

  def quality_reached(result, iteration):
      return isinstance(result.output, Review) and result.output.score >= 80
  ```  

  Запуск:  

  ```python
  workflow = LoopWorkflow(
      agents=[writer, reviewer],
      stop_condition=quality_reached,
      max_iterations=5,
  )
  result = await workflow.run("Write marketing copy")
  ```  

- **Другие варианты stop‑условий** (стр. 285): поиск ключевого слова «APPROVED», минимум 3 итераций и длина > 1000 символов.  

- **Где пригодится** – Автоматическое доработывание текста, тестирование кода до прохождения всех тестов, перевод с многократным улучшением.  

### 9.3.5 Composing workflows (стр. 286‑287)  
- **Главная мысль** – Поскольку все три workflow‑класса наследуют `Agent`, их можно вкладывать друг в друга, получая гибкие гибридные пайплайны.  
- **Как делать** – Составить вложенный список агентов, например:  

  ```python
  workflow = SequentialWorkflow(
      agents=[
          researcher,
          ParallelWorkflow(agents=[optimist, pessimist, realist]),
          LoopWorkflow(
              agents=[writer, reviewer],
              stop_condition=quality_reached,
              max_iterations=3,
          ),
          editor,
      ]
  )
  result = await workflow.run("Write an AI market analysis report")
  ```  

- **Где пригодится** – Когда требуется сочетать предсказуемый порядок (Sequential) с параллельными оценками и итеративным улучшением.  



## 9.4 Agent as Tool: Calling agents as tools (стр. 284‑290)  

### 9.4.1 Making agents into tools (стр. 286)  
- **Главная мысль** – Любой агент можно «упаковать» в инструмент, чтобы LLM могла вызывать его так же, как обычный API‑инструмент.  
- **Шаблон листа инструментов** (стр. 286):  

  ```json
  {
    "tools": [
      {"name": "web_search", "description": "..."},
      {"name": "calculator", "description": "..."},
      {"name": "researcher", "description": "..."},
      {"name": "coder", "description": "..."}
    ]
  }
  ```  

- **Где пригодится** – При динамической маршрутизации, когда LLM сама решает, нужен ли исследователь или кодировщик.  

### 9.4.2 Implementing AgentTool (стр. 287‑288)  
- **Главная мысль** – `AgentTool` – адаптер, который делает любой `Agent` совместимым с системой инструментов.  
- **Как делать** (по коду Listing 9.8)  
  1. В `__init__` взять имя и описание агента, сформировать `tool_definition`.  
  2. Если передан `input_schema` — вывести JSON‑схему из Pydantic‑модели; иначе создать параметр `request: string`.  
  3. В `execute`:  
     - При наличии `input_schema` валидировать вход через Pydantic, собрать JSON‑строку.  
     - Иначе взять `request` из `kwargs`.  
     - Запустить дочерний агент `await self.agent.run(request)`.  
     - Вернуть только `result.output`.  
- **Шаблон применения** – Регистрация агента‑инструмента (стр. 287):  

  ```python
  tools = [web_search, calculator,
           AgentTool(researcher), AgentTool(coder)]
  ```  

- **Ошибки** – Если `input_schema` не совпадает с ожидаемым форматом, `execute` выдаст ошибку валидации.  

### 9.4.3 Context isolation (стр. 289‑290)  
- **Главная мысль** – В паттерне *Agent as Tool* дочерний агент работает в **изолированном** контексте, передавая главному только конечный результат.  
- **Преимущества** (стр. 289‑290):  
  1. **Абстракция** – главный агент не видит внутренний процесс (кол‑во запросов, промежуточные шаги).  
  2. **Эффективность контекста** – в родительский контекст добавляется лишь одна строка результата, экономя место в окне.  
  3. **Независимость** – сбои и инструменты дочернего агента не влияют напрямую на родителя.  
- **Недостатки** – При отладке нужно отдельно смотреть внутрь дочернего агента; если нужен промежуточный статус, лучше использовать *Workflow*.  
- **Где пригодится** – Когда нужен быстрый вызов специализированного агента как функции, без передачи внутрішних деталей (например, поиск и сразу получить резюме).  

### 9.4.4 Practical example: Researcher + Coder (стр. 290‑291)  
- **Главная мысль** – Пример оркестратора, который через `AgentTool` вызывает исследователя и кодировщика, комбинируя их результаты.  
- **Код** (сокращённо, из текста):  

  ```python
  researcher = Agent(model=llm, name="researcher",
                     description="Search the web and summarize findings",
                     tools=[search_web])

  coder = Agent(model=llm, name="coder",
                description="Write and execute Python code",
                tools=[code_execution_tool])

  orchestrator = Agent(
      model=llm,
      name="coordinator",
      instructions="Delegate to researcher or coder as needed and combine results",
      tools=[AgentTool(researcher), AgentTool(coder)]
  )
  ```  

- **Где пригодится** – Автоматическая подготовка отчётов с поиском информации и генерацией кода‑примеров.  



## 9.5 Agent Transfer pattern (стр. 291‑298)  

### 9.5.1 Differences between Agent as Tool and Transfer (стр. 291‑292)  
- **Главная мысль** – *Transfer* передаёт **управление** другому агенту, а контекст остаётся **общим**; *Agent as Tool* оставляет контроль у главного агента, а дочерний работает в изолированном контексте.  
- **Таблица различий** (стр. 291):  
  - **Location of control** – Tool → главный остаётся; Transfer → контроль переходит.  
  - **Context sharing** – Tool → изолированный; Transfer → общий.  
  - **Conversation continuity** – Tool → результат возвращается, главный отвечает; Transfer → специалист отвечает напрямую.  
- **Где пригодится** – При обслуживании клиентов: обычный агент отвечает, но при техническом запросе переводит к технической поддержке (Transfer).  

### 9.5.2 Transfer is also a tool (стр. 292‑293)  
- **Главная мысль** – Реализовать Transfer удобно, добавив в набор инструментов агента специальный инструмент `transfer_to_agent`.  
- **Как делать** –  
  1. При запуске `run()` собрать список **transfer‑targets** (дочерние, родитель, при необходимости соседи).  
  2. Сгенерировать инструмент `transfer_to_agent` (см. ниже).  
  3. Добавить его в `context.transfer_tools`.  
- **Где пригодится** – Позволяет LLM динамически решать, когда переключиться на более подходящего специалиста.  

### 9.5.3 Agent tree (стр. 294‑295)  
- **Главная мысль** – Для Transfer требуется **дерево агентов**, в котором каждый агент знает своих дочерних, родителя и (по желанию) соседей.  
- **Как делать** (из Listing 9.10‑9.12)  
  1. При инициализации `Agent` передать `sub_agents`‑список.  
  2. Автоматически установить `parent` у каждого под‑агента (`_validate_and_set_sub_agents`).  
  3. Проверить **уникальность имён** и отсутствие **дублирующих родителей**.  
  4. Метод `_get_transfer_targets` формирует список доступных целей: дети + родитель + (если `disallow_transfer_to_peers=False`) соседи.  
- **Шаблон проверки** – Ошибка при дублировании имени (стр. 294):  

  ```python
  raise ValueError(f"Duplicate sub-agent name: '{sub.name}'")
  ```  

- **Где пригодится** – При построении сложных иерархий: «супервизор → менеджеры → специалисты» или сети взаимных запросов между агентами.  

### 9.5.4 Implementing the transfer tool (стр. 296‑298)  
- **Главная мысль** – `create_transfer_tool` генерирует функцию‑инструмент, которая записывает в `context.transfer_to` выбранное имя агента.  
- **Как делать** (Listing 9.14)  
  1. Сформировать список `target_names`.  
  2. Составить строку `agent_info` со сведениями о каждом агенте (имя + краткое описание).  
  3. Декорировать функцию `transfer_to_agent` с `@tool(...)`.  
  4. Внутри функции:  
     - Проверить, что `agent_name` в `target_names`.  
     - Если `context.transfer_to` == None → записать цель, вернуть сообщение о передаче.  
     - Иначе – вернуть сообщение «Transfer already requested».  
  5. Добавить в параметр `agent_name` **enum** с `target_names` (стр. 298).  
- **Шаблон JSON‑определения инструмента** (стр. 298):  

  ```json
  {
    "name": "transfer_to_agent",
    "description": "Transfers work to another agent...",
    "parameters": {
      "type": "object",
      "properties": {
        "agent_name": {
          "type": "string",
          "enum": ["math", "search"]
        }
      },
      "required": ["agent_name"]
    }
  }
  ```  

- **Где пригодится** – Для любой системы, где LLM может «передать» задачу другому специалисту, сохранив весь диалог.  

### 9.5.5 Implementing agent transfer (стр. 298‑…)  
Текст заканчивается в середине реализации `run()`. Основные идеи (из приведённого фрагмента):  

- В начале `run()` регистрировать transfer‑tool, если он ещё не в `context.transfer_tools`.  
- При получении результата проверять `context.transfer_to`; если оно не None, найти целевой агент через `_find_agent` и вызвать его `run()` с тем же `context`.  
- После завершения, вернуть итоговый `AgentResult`.  

*(Поскольку в части текста дальнейшая реализация не предоставлена, детали шагов нельзя добавить.)*  

- **Где пригодится** – В системах с динамической переадресацией запросов (например, чат‑бот поддержки, где запрос первого уровня может быть передан в отдел продаж, а потом обратно в сервис).

| **Parallel** | Параллельный анализ разных гипотез/моделей (например, несколько метрик качества одновременно). |
| **Loop** | Итеративный процесс улучшения модели: генерировать, тестировать, дорабатывать до порога качества. |
| **Agent as Tool** | Динамический вызов «специалистов» в зависимости от пользовательского запроса (например, «построй график», «посчитай статистику», «сгенерируй код»). |
| **Transfer** | Переключать диалог между «общим помощником» и «экспертом‑по‑моделям», сохраняя контекст всей беседы. |
| **AgentTool** | Оборачивать любые функции (SQL‑запрос, API‑вызов) как инструменты, чтобы LLM могла их вызывать без ручной маршрутизации. |
| **Agent tree** | Организовать иерархию: «Главный оркестратор» → «Подразделы аналитики» → «Модели», позволяя легко добавлять новые специализации. |
| **Transfer tool** | Позволяет LLM сама решать, когда переключать управление, например, от вопроса о бизнес‑стратегии к расчётам финансовой модели. |

Эти конструкции помогут построить гибкую, расширяемую систему, где каждый скрипт и каждый набор данных останутся в чётко определённой «области ответственности», а взаимодействие между ними будет управляться предсказуемыми (Workflow) и динамическими (Agent as Tool, Transfer) паттернами.
