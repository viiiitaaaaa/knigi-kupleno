## 1.4.2 Условия применения агентов  (стр. 31‑32)

### Главная мысль
Агенты нужны только тогда, когда задача требует **многошагового рассуждения и работы с инструментами**; иначе хватает одного вызова LLM.

### Как делать (пошагово)

1. Оценить задачу:  
   a. Сколько шагов предвидится?  
   b. Нужно ли искать внешние данные, выполнять расчёты, использовать инструменты?  
2. Сравнить **стоимость**, **задержку** и ** риск ошибок** между:
   * одним вызовом LLM,  
   * агентским циклом (много вызовов).  
3. Принять решение, если одновременно выполняются **три критерия** (см. ниже).

### Правила и числа  (стр. 31)

| Критерий | Что проверять |
|----------|----------------|
| **Сложность задачи** | Непредсказуемое число шагов → агент полезен. |
| **Ценность результата** | Выигрыш должен покрывать более высокие затраты и задержку. |
| **Стоимость/детектируемость ошибок** | Если ошибка может иметь критические последствия — агент может быть плохим выбором. |

### Шаблоны‑примеры
- **Пример задачи, требующей агента**: «Сколько времени уэлиду Кипчоге понадобится, чтобы пробежать от Земли до Луны, если он будет держать рекордный марафонский темп?».  
  Требуется: поиск биографии, поиск рекорда, поиск расстояния, расчёт.
- **Пример задачи, где агент избыточен**: запрос «Кто президент Франции?». Один вызов LLM достаточно.

### Ошибки и предупреждения
- **Тренд‑ловушка**: использовать агенты «просто потому, что они новые».  
- **Переоценка ценности**: если выгода от результата мала, лишние вызовы LLM лишь повышают расходы.  

### Где пригодится
Для **выбора** (запросов/скриптов) – решить, нужен ли цикл с инструментами или достаточно одного LLM‑вызова.

## 1.4.3 GAIA — агентский «тренировочный зал»  (стр. 32‑33)

### Главная мысль
**GAIA** – набор вопросов, каждый из которых требует мультишагового рассуждения, веб‑поиска, вычислений и т.п.; идеально подходит для практики разработки агентов.

### Как делать (циклический процесс)

1. **Определить** задачу → проверить, подходит ли она под GAIA.  
2. **Разработать прототип** агента.  
3. **Наблюдать неудачи**, анализировать причину.  
4. **Улучшать** агент и повторять (observe‑analyze‑improve).

### Правила и числа (стр. 32)

- **Ясные ответы** → быстрый фидбэк и возможность измерять прогресс.  
- **Лёгкость отработки** → процесс разработки (observe‑analyze‑improve) полностью реализуем на GAIA.  
- **Отсутствие предметных знаний** → задачи сконцентрированы на поиске и синтезе, не требуют медицины, права и т.д.

### Шаблоны‑примеры
- Вопрос из GAIA: «Сколько людей живёт в регионе A?» – прост.  
- Сложный пример: «Как LLM‑агенты изменят будущее?» – требует сбора разных источников, синтеза.

### Ошибки и предупреждения
- **Только измерять** (один раз) недостаточно – нужны итерации.  
- **Слишком сложные вопросы** в начале могут демотивировать; выбирайте уровень сложности постепенно.

### Где пригодится
Для **тестирования** и **отладки** новых функций агента (поиск, расчёт, планирование) в вашем собственном проекте.

## 1.5 Контекст‑инжиниринг (стр. 33‑36)

### Главная мысль
Контекст — это всё, что LLM «видит» при генерации ответа (системный промпт, сообщения, результаты инструментов, документы). **Контекст‑инжиниринг** — умелое снабжение модели нужной информацией в нужный момент.

### Как делать (общий процесс)

1. **Определить** какие данные нужны для конкретного шага задачи.  
2. **Сформировать** их в нужном виде (текст, JSON, структура).  
3. **Добавить** в контекст **только** релевантные куски и **удалить** лишнее (reduce).  
4. При необходимости **сохранить** часть контекста во внешнее хранилище (write) для последующего использования.  
5. При работе с несколькими инструментами **изолировать** их среды (isolate).

### Правила и числа (стр. 34‑35)

| Факт | Вывод |
|------|-------|
| Большие окна контекста (до 1 млн токенов) | Не всегда лучше – «контекст‑рот» (деградация качества). |
| «Lost in the middle» | Модели чаще «теряют» информацию в середине длинных контекстов. |
| **Контекст‑rot** → Доля релевантных токенов должна быть высокой. |

### Шаблоны‑примеры
- **Контекст‑окно** (рис. 1.5):  
  `System prompt → Tools → User message → Tool result → LLM`.  
- **Сокращение**: Суммировать старый чат в 2‑3 предложения вместо полного листа сообщений.

### Ошибки и предупреждения
- Заполнять **весь** контекст «всем доступным» материалом → деградация, потеря ключевой информации.  
- Игнорировать **позицию** информации (важные детали в середине могут быть проглочены).

### Где пригодится
При **проектировании** запросов к LLM в ваших скриптах‑агентах: какие данные добавить, какие удалить.

## 1.5.1 Почему агенты падают  (стр. 33)

### Главная мысль
Провалы агентов вызываются **недостаточным интеллектом модели** или **недостатком информации** в контексте.

### Как делать (диагностика)

1. При ошибке проверить:  
   a. Было ли у модели достаточно «мозговой мощности» (сложные вычисления, логика).  
   b. Был ли в контекст включён необходимый факт/документ.  
2. Если проблемa в (a) → сменить/обновить модель.  
   Если в (b) → добавить нужные данные в контекст.

### Правила и числа
- **Информационный дефицит** – главная причина реальных провалов.  

### Шаблоны‑примеры
- Запрос «Какая у нас политика отпуска?», а в контекст не загружен документ политики → ошибка.

### Ошибки и предупреждения
- Пытаться «исправить» плохой контекст заменой модели – бессмысленно.

### Где пригодится
Для **отладки** текущих агентов: быстро понять, виноват ли LLM или контекст.

## 1.5.2 От промпт‑инжиниринга к контекст‑инжинирингу  (стр. 34‑35)

### Главная мысль
Раньше сосредотачивались только на **промптах** (текстовых инструкциях). Сейчас, когда агент использует инструменты, **контекст** динамически меняется, и надо управлять им целиком.

### Как делать (операции)

1. При каждом вызове инструмента **добавлять** результат в контекст.  
2. При необходимости **преобразовать** результаты (например, превратить HTML‑страницу в чистый текст).  
3. **Контролировать объем** – решать, сколько истории сохранять, а что отбрасывать.

### Правила и числа
- Инструменты → новые данные → **рост** контекста.  
- Нужно **постоянно** поддерживать «только необходимую» часть.

### Шаблоны‑примеры
- После поиска в вебе: `Tool result` помещается сразу после сообщения пользователя.

### Ошибки и предупреждения
- Позволять контексту «заполняться» без отбора → «контекст‑rot» и рост расходов.

### Где пригодится
При **реализации** механизмов обхода веб‑поиска, код‑выполнения, доступа к базе данных.

---

## 1.5.3 Больше контекста — не всегда лучше  (стр. 34‑36)

### Главная мысль
С ростом **длины контекста** модель часто ухудшает качество (эффект «контекст‑rot», «lost in the middle»).

### Как делать (управление длиной)

1. **Отбирать** только релевантные фрагменты.  
2. При достижении предела окна **суммировать** старую историю (reduce).  
3. Проверять **метрики** качества (например, Levenshtein‑score) при разных длинах.

### Правила и числа (стр. 34‑35)

- Современные LLM поддерживают **от сотен тысяч до миллиона токенов**.  
- При росте длины **снижается** нормализованный Levenshtein‑score (см. рис. 1.6).  

### Шаблоны‑примеры
- Вместо загрузки полного PDF‑файла (10 000 токенов) – извлечь **ключевые абзацы** (500 токенов).

### Ошибки и предупреждения
- Предположить, что «заполнить всё окно» даст лучшую точность – ошибочно.  

### Где пригодится
Для **оптимизации** расходов и скорости вашего агента (особенно при длительных диалогах).

## 1.5.4 Пять стратегий контекст‑инжиниринга  (стр. 35‑36)

### Главная мысль
Контекст‑инжиниринг делится на **5 категорий**; каждая реализуется в отдельной главе книги.

| Стратегия | Что делает | Где раскрыто |
|-----------|------------|--------------|
| **Generate** | Включает в контекст вывод LLM (планы, рефлексия) | Гл. 7 |
| **Retrieve** | Приносит внешнюю информацию (поиск, БД, файлы) | Гл. 3, 5, 6 |
| **Write** | Сохраняет данные из контекста во внешнее хранилище (долгосрочная память, scratch‑pad, файлы) | Гл. 6, 8 |
| **Reduce** | Сокращает контекст (суммирование, удаление) | Гл. 6 |
| **Isolate** | Разделяет задачи/инструменты в отдельные среды (песочницы, отдельные агенты) | Гл. 8, 9 |

### Как делать (пример для каждой)

1. **Generate** – попросить LLM сгенерировать план и добавить его в историю.  
2. **Retrieve** – выполнить веб‑поиск, взять первые‑три ссылки, добавить их содержимое.  
3. **Write** – сохранить результаты вычислений в файл‑scratchpad и записать путь в контекст.  
4. **Reduce** – каждый N‑й диалог суммировать в 2‑3 предложения, удалить детали.  
5. **Isolate** – запускать код пользователя в отдельном контейнере, а не в основной среде агента.

### Правила и числа
- **Strategy = hub**: Гл. 6 объединяет Retrieve, Write, Reduce (память).  

### Шаблоны‑примеры
- Таблица 1.1 (стр. 35‑36) – краткое перечисление стратегий.  

### Ошибки и предупреждения
- Смешивать стратегии без контроля → **переполнение** и **потерю** важной информации.  

### Где пригодится
Для **проектирования** модульных компонентов вашего агента (поиск, память, планирование).

## 1.5.5 От контекст‑инжиниринга к «harness engineering»  (стр. 36‑37)

### Главная мысль
Контекст‑инжиниринг — часть **harness (платформы)** агента. **Harness engineering** — это всё, что окружает модель: память, инструменты, рабочая среда, безопасность и т.д. Формула:  

**Agent = Model + Harness**.

### Как делать (строительство harness)

1. **Определить** какие компоненты нужны (memory, tools, sandbox, multi‑agent).  
2. **Встроить** контекст‑инжиниринг как один из слоёв harness.  
3. **Развивать** harness по мере роста требований (см. главы 5‑9).

### Правила и числа
- Примеры требований:  
  * Персонализация поведения (memory, skills).  
  * Безопасное исполнение кода (sandbox).  
  * Координация нескольких агентов (multi‑agent).

### Шаблоны‑примеры
- Выражение: «Agent = Model + Harness» (стр. 36).

### Ошибки и предупреждения
- Считать, что **harness** уже готов – нужно **постепенно** добавлять части.

### Где пригодится
При **разработке** полной среды для вашего агента (например, в домашнем проекте с код‑генерацией и доступом к файлам).

## 2 Мозг AI‑агентов: LLM (стр. 40‑52)

### 2.1 Выбор LLM для агентов  (стр. 40‑43)

#### 2.1.1 Закрытые LLM (стр. 41‑42)

**Главная мысль**  
Закрытые модели (OpenAI GPT, Anthropic Claude, Google Gemini) позволяют быстро экспериментировать без собственного инфракструктурного кода.

**Плюсы закрытых моделей**  

| Преимущество | Что даёт |
|-------------|----------|
| **Быстрая проверка гипотез** | API‑ключ → сразу писать код. |
| **Идентичная среда** | Прототип = продакшн – нет расхождений. |
| **Лучшие текущие возможности** | Более сильные в рассуждениях и вызовах инструментов. |
| **Фичи “из коробки”** | tool‑calling, structured output, token‑caching, batch‑processing. |

#### 2.1.2 Открытые LLM (стр. 41‑42)

**Главная мысль**  
После валидации идеи на закрытых LLM можно переключиться на открытые (Llama, Mistral, Qwen, DeepSeek) для экономии и контроля.

**Ключевые причины**  

| Причина | Что значит |
|---------|------------|
| **Оптимизация расходов** | При большом объёме трафика локальный запуск дешевле. |
| **Стабильность и контроль** | Нет зависимости от внешних API‑отказов; данные остаются в компании. |
| **Гибридный подход** | Основное рассуждение – закрытый LLM; простые задачи – открытый. |

#### 2.1.3 Обязательные возможности LLM для агентов (стр. 42‑44)

- **Tool calling (function calling)** – способность выбрать и вызвать внешний инструмент.  
- **Structured output** – генерация JSON/доменных схем.  
- **Long context support** – окна до сотен тысяч токенов (но помнить о «контекст‑rot»).  
- **Гибкость к изменяющемуся рынку** – быстро менять модель, проверять новые версии (источники: Artificial Analysis, LM Arena, официальные анонсы).

**Выбранный в книге LLM** – **OpenAI GPT‑5 mini** (экономичный, стабилен, поддерживает tool‑calling).  

### 2.2 Базовые LLM‑API для построения агентов  (стр. 44‑50)

#### 2.2.1 Настройка окружения (стр. 44‑45)

1. **Клонировать репозиторий**:

#### 2.2.2 Простой вызов OpenAI API (стр. 45‑46)

```python
from openai import OpenAI
client = OpenAI()
response = client.chat.completions.create(
    model="gpt-5-mini",
    messages=[
        {"role":"system","content":"You are a helpful assistant."},
        {"role":"user","content":"What is the capital of France?"}
    ]
)
print(response.choices[0].message.content)
```

- **Роли сообщений**: `system` (ранее `developer`), `user`, `assistant`.  
- **Параметр `temperature`**: 0‑0.3 → детерминировано; 0.7‑1.0 → креативно.  
- **`max_tokens`** ограничивает длину вывода.

#### 2.2.3 Unified API через LiteLLM (стр. 46‑47)

```python
from litellm import completion

# OpenAI
completion(model="gpt-5-mini", messages=[{"role":"user","content":"Hello!"}])

# Anthropic
completion(model="claude-sonnet-4-5", messages=[{"role":"user","content":"Hello!"}])
```

- Один `completion`‑функция → единый формат ответа (OpenAI‑style).  
- Ключи читаются из `.env` автоматически.

#### 2.2.4 Управление диалогом (stateless API) (стр. 47‑48)

- **API без состояния** → каждый запрос需要 полный контекст.  
- **Хранить историю** в списке `messages`, каждый элемент `{role, content}`.  
- Пример добавления ответов в историю (`assistant` роль) показан в листинге 2.6.

#### 2.2.5 Структурированный вывод (стр. 48‑49)

- Используем **Pydantic** для описания схемы JSON.  
```python
from pydantic import BaseModel
class ExtractedInfo(BaseModel):
    name: str
    email: str
    phone: str | None = None

response = completion(
    model="gpt-5-mini",
    messages=[{"role":"user","content":"My name is John Smith, my email is john@example.com, and my phone is 555-1234."}],
    response_format=ExtractedInfo
)
result = response.choices[0].message.content   # уже объект ExtractedInfo
```

- Позволяет **валидацию** и быстрый парсинг (важно для tool‑calling).

#### 2.2.6 Асинхронные запросы (стр. 49‑50)

```python
import asyncio, litellm

async def get_response(prompt):
    resp = await litellm.acompletion(
        model="gpt-5-mini",
        messages=[{"role":"user","content":prompt}]
    )
    return resp.choices[0].message.content

prompts = ["2+2?", "Capital of Japan?", "Who wrote Romeo?"]
results = await asyncio.gather(*[get_response(p) for p in prompts])
```

- **`num_retries`** → автоповтор при ошибках (exponential backoff).  
- **`asyncio.Semaphore`** → ограничение одновременных запросов (пример 2.9).  

### 2.3 Улучшение интеллекта агента: Prompt engineering  (стр. 50‑52)

#### 2.3.1 Роль системных промптов (стр. 51)

- **System prompt** = «постоянные» инструкции, задающие:
  - **Идентичность** продукта (напр., «вы — Claude 4.5, версия Opus/…»).  
  - **Формат и стиль** вывода (избегать лишних буллетов, использовать естественные предложения).  
  - **Ограничения поведения** (не давать советы по химическому/ядерному оружию, не генерировать вредоносный код).  
  - **Лимиты знаний** (отмечать дату cutoff, предлагать использовать web‑search при необходимости).  

#### 2.3.2 Рекомендации по промптам для агентов (стр. 52)

| Принцип | Как реализовать в системном промпте |
|--------|--------------------------------------|
| **Автономность** | «Если намерение пользователя ясно, действуй сразу без подтверждения». |
| **Запросы‑неоднозначности** | «Только при неясном запросе задай уточняющий вопрос». |
| **Стратегическое использование инструментов** | Чётко описать когда и какие инструменты разрешено вызывать. |
| **Границы** | Перечислить типы запросов, которые агент обязан отказать (дети, оружие, вредоносный код, финансовый совет). |
| **Понимание ограничений** | При запросах за пределами cutoff – честно ответить «не знаю», предложить поиск. |

### Ошибки и предупреждения (раздел 2.3)

- **Недостаточно строгий system prompt** → агент может «заблудиться», использовать неподходящие инструменты.  
- **Слишком многословные инструкции** → модель может игнорировать детали; лучше лаконичные, чёткие правила.  

### Где пригодится
- При **создании** собственного system prompt для вашего агента‑помощника (настраиваемая личность, ограничения и политики tool‑calling).
