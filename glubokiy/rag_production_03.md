## Общий поток RAG-стека (стр. 53–54)
- **Главная мысль**: Процесс превращения запроса пользователя в ответ включает переписывание запроса, поиск (retrieval), переранжирование (reranking) и генерацию.
- **Как делать (процесс поиска)**:
    1. **Переписывание запроса**: Создание «запроса для поиска» (retrieval query), чтобы LLM не искала лишние инструкции, а фокусировалась на сути данных.
    2. **Поиск (Retrieval)**:
        - *Семантический (Dense)*: перевод в векторы $\rightarrow$ поиск похожих векторов через скалярное произведение (dot product).
        - *По ключевым словам (Sparse)*: прямое сопоставление строк (TF-IDF, BM25).
        - *Гибридный*: объединение обоих методов для точности (редкие токены, опечатки).
    3. **Переранжирование (Reranking)**: Дополнительная фильтрация топ-результатов.
- **Правила и числа**: 
    - Для нормализованных векторов (длиной 1) скалярное произведение равно косинусному сходству (стр. 53).
    - Алгоритм MMR (Maximum Marginal Relevance) с 1998 года используется для борьбы с избыточностью данных в выдаче (стр. 53).
- **Ошибки и предупреждения**: Простого ранжирования по сходству векторов часто недостаточно для LLM, поэтому нужен этап переранжирования (reranking).
- **Где нам пригодится**: Для проектирования общей логики агентов и цепочек запросов.

## Парсинг документов (Document Parsing) (стр. 54–63)
- **Главная мысль**: Превращение файлов разных форматов (PDF, DOCX, HTML) в чистый текст, отделяя полезные знания от разметки и оформления.
- **Как делать**:
    1. **PDF**: Сложный формат (текст хранится как координаты символов). Использовать библиотеки `PyMuPDF`, `pdfminer.six` или API Adobe. Для сканов — OCR (Tesseract, Azure/Google OCR).
    2. **DOCX/HTML**: Проще, так как это XML-структуры. Использовать `python-docx` или `Beautiful Soup`.
    3. **VLM (Vision-Language Models)**: Использование моделей типа GPT-5.x для парсинга сложных макетов (слайды, инфографика) как крайняя мера.
- **Шаблоны и примеры**: 
    - *Метаданные*: Чтобы не терять контекст в чатах (кто сказал фразу), сохранять теги в JSON: `{"who": "AI"}` (стр. 56).
    - *Стратегия*: «Сначала самый дешевый успешный парсер» (Библиотеки $\rightarrow$ OCR $\rightarrow$ VLM) (стр. 57).
- **Ошибки и предупреждения**: 
    - PDF не имеют логической структуры; простое извлечение может перемешать текст из двух колонок (стр. 55).
    - VLM склонны к галлюцинациям и стоят дорого (стр. 56).
- **Где нам пригодится**: Для подготовки данных из своих документов, скриптов обработки PDF/DOCX.

## Чанкинг текста (Text Chunking) (стр. 63–69)
- **Главная мысль**: Разбиение длинных текстов на части («чанки»), чтобы они помещались в контекстное окно LLM и моделей эмбеддингов, а также для повышения точности поиска.
- **Как делать (Стратегии)**:
    1. **Фиксированный размер**: Резка по количеству символов/токенов. Рекомендуется использовать *нахлест* (overlap), чтобы не терять смысл на границах.
    2. **С учетом контента**: Разбиение по абзацам (`\n\n`) или предложениям (через NLP-библиотеки `spaCy`, `NLTK`).
    3. **Рекурсивный**: Иерархическое деление (абзац $\rightarrow$ предложение $\rightarrow$ фраза). Пример: `RecursiveCharacterTextSplitter` в LangChain.
    4. **По структуре документа**: Использование заголовков Markdown (#, ##).
    5. **Семантический**: Группировка предложений по смысловой близости (через кластеризацию).
- **Правила и числа**:
    - Контекстные окна: GPT-5.1 (400k), Claude Sonnet 4.5/Gemini 3 (1M) (стр. 64).
    - Окна эмбеддингов гораздо меньше: OpenAI/Gemini $\approx$ 8k токенов (стр. 65).
    - Время ответа (TTFT) растет квадратично от длины контекста (стр. 64).
- **Ошибки и предупреждения**: 
    - «Lost in the middle»: LLM лучше помнит начало и конец контекста, чем середину (стр. 67).
    - Фиксированный чанкинг может разрывать слова, создавая шум для эмбеддингов (стр. 68).
- **Где нам пригодится**: Для настройки памяти помощников и оптимизации стоимости/скорости запросов.

## Модели эмбеддингов (Embedding Models) (стр. 69–75)
- **Главная мысль**: Перевод текста в векторы (наборы чисел), чтобы компьютер мог находить смысловое сходство, даже если слова разные (например, «США» и «Америка»).
- **Как делать (Выбор модели)**:
    1. Проверить рейтинг в MTEB (Massive Text Embedding Benchmark).
    2. Определить размерность вектора (баланс между точностью и затратами ресурсов).
    3. Сопоставить размер чанка с окном модели (чтобы избежать скрытой обрезки текста).
- **Правила и числа**:
    - Окна моделей: Qwen3 (32k), OpenAI/Gemini (8k), BGE-M3 (1k) (стр. 71).
    - MRL (Matryoshka Representation Learning): позволяет обрезать вектор до меньшей размерности без большой потери смысла (стр. 71).
- **Ошибки и предупреждения**: 
    - JSON-формат для передачи векторов неэффективен (занимает больше места и может терять точность). Рекомендуется Base64 (стр. 72).
    - Если чанк длиннее окна модели, библиотека (например, HuggingFace) молча обрежет его $\rightarrow$ потеря данных (стр. 72).
- **Где нам пригодится**: Для настройки семантического поиска по своим данным.

## Векторные базы данных и поиск (стр. 75)
- **Главная мысль**: Инструменты для хранения векторов, которые позволяют быстро находить наиболее похожие объекты без перебора всего списка (brute-force).
- **Как делать**:
    - Для малых данных: хранение в RAM и прямой перебор (сложность $O(n)$).
    - Для больших данных: использование специализированных векторных БД.
- **Правила и числа**: Скалярное произведение (dot product) — основной метод измерения сходства. При нормализации векторов это превращается в косинусное сходство (стр. 75).
- **Где нам пригодится**: Для организации долгосрочной памяти ИИ-агентов.
