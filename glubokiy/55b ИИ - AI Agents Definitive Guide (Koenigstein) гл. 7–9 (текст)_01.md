## Chapter 7. Deploying Agents in Real Products (стр. —)  

### Главная мысль  
Для перехода от прототипа к реально работающему продукту нужны системные подходы — механизмы отката, абстракция инференса, обратные связи, обработка отказов и интеграция в организацию.  

### Как делать  
1. **Определить стадию зрелости** — по модели MVP → alpha → hardening → production → scale (табл. 7‑1).  
2. **Создать диагностическую среду** — быстрый UI (Streamlit/Gradio), PaaS‑развёртывание (DigitalOcean, Heroku, Render).  
3. **Встроить наблюдение** — логировать поведение агентов, стоимость, задержки, трассировку, ошибки (табл. 7‑2).  
4. **Хардить инфраструктуру** — checkpoint‑снимки, обрезка контекста, circuit‑breaker (табл. 7‑3).  
5. **Организовать fallback‑механизм** — многоуровневая проверка структуры вывода (табл. 7‑5).  
6. **Выбрать и настроить backend инференса** — TGI, vLLM или SGLang; учитывать холодный старт, кеши, масштабирование (табл. 7‑8).

## 1. From MVP Vibes to Production Setup (стр. —)  

### Главная мысль  
MVP — это не только «минимальный продукт», а диагностическая лаборатория, где проверяются нестабильные поведения агентов.  

### Как делать (шаги)  
1. Сконструировать лёгкий UI (Streamlit/Gradio).  
2. Деплоить на управляемый PaaS (Git‑деплой 5‑15 мин).  
3. Собирать обратную связь о задержках, стоимости, ошибках.  

### Правила и числа  
* Автоматический репо‑деплой ≈ 5–15 минут (параграф «Платформы… позволяют…»).  

### Шаблоны и примеры  
* UI‑слой → Streamlit / Gradio.  
* PaaS → DigitalOcean App Platform, Heroku, Render.  

### Ошибки и предупреждения  
* Не полагаться только на «deploy to endpoint» — это создаёт vendor lock‑in.  

### Где нам пригодится  
* При построении быстрой тестовой среды для новых агентов‑единственников.

## 3. Monitoring Your Agents (стр. —)  

### Главная мысль  
Мониторинг — обязательная часть продакшена, позволяющая закрыть цикл обратной связи между стоимостью, латентностью, поведением и надёжностью.  

### Как делать (шаги)  
1. Логировать **поведение агентов** (соблюдение ролей, схем, использование инструментов).  
2. Отслеживать **стоимость** (токены, API‑расход).  
3. Собрать **латентность** (время ответа модели, задержки инструментов).  
4. Вести **трассировку** (цепочки решений, вызовов инструментов).  
5. Записывать **логи** (ошибки, повторные попытки, артефакты).  

### Правила и числа (табл. 7‑2)  
| Dimension | Что наблюдать | Зачем |  
|-----------|----------------|-------|  
| Agent behavior | Role adherence, style, schema, tool usage | Выявить дрейф |  
| Cost | Token usage, API spend, infra overhead | Найти «потоковые» расходы |  
| Latency | Model response, tool delay | Найти узкие места |  
| Tracing | Decision paths, tool calls | Дебаг |  
| Logging | Failures, retries, edge cases | Форе́нзика |  

### Шаблоны и примеры  
* `AgentSession` — структура для логирования состояния (пример 7‑1).  

### Ошибки и предупреждения  
* Трассировка дорогая — нужно ограничивать объём (см. раздел 4).  

### Где нам пригодится  
* Для построения панели контроля над агентами в SaaS‑приложении.

## 4. Monitoring Granularity (стр. —)  

### Главная мысль  
Трассировать всё — дорого; нужен баланс между полнотой данных и бюджетом.  

### Как делать (правила)  
- **До включения трассировки**: задать правила редактирования (PII, PCI, токены).  
- **В разработке**: логировать 100 % трасс.  
- **В продакшене**: логировать 100 % ошибок + 10‑25 % успешных запросов.  
- **При инцидентах**: временно поднять долю до 100 % для полной видимости.  

### Правила и числа (прямо из текста)  
* Сэмплинг = 10‑25 % успешных запросов (прод).  
* 100 % ошибок всегда.  

### Шаблоны и примеры  
* Псевдо‑код: `if error: log(trace) else if random()<0.2: log(trace)`  

### Ошибки и предупреждения  
* Не редактировать чувствительные данные → утечка PII.  

### Где нам пригодится  
* При построении сервисов с ограниченным бюджетом на хранение логов.

## 5. Hardening the Backbone (стр. —)  

### Главная мысль  
Переход к FastAPI‑бэкенду требует инфраструктурных паттернов — контроль контекста, ограничители, резервные модели.  

### Как делать (шаги)  
1. Перевести UI‑логику в отдельный FastAPI‑сервис (Docker + MCP).  
2. Внедрить **streaming** (WebSocket / SSE) вместо обычных POST‑запросов.  
3. Добавить **checkpoint‑снимки**, **обрезку контекста**, **circuit‑breaker** (табл. 7‑3).  
4. Реализовать **сохранение/восстановление** состояния (пример 7‑4).  

### Правила и числа (табл. 7‑3)  
| Pattern | Focus | Mechanism | Why |  
|---------|-------|-----------|-----|  
| Checkpointing | Надежность | Снимки в диск/DB | Возобновление после краша |  
| Context pruning | Производительность | Обрезка токенов | Предотвратить рост стоимости |  
| Circuit breaker | Безопасность | Ограничения по ходам/бюджету | Остановить бесконечные циклы |  

### Шаблоны и примеры  
* **Checkpoint** – `save_checkpoint(session)` (пример 7‑4).  
* **Контекст‑janitor** – `prune_history()` (пример 7‑2).  
* **CircuitBreaker** – `check_circuit_breaker()` (пример 7‑3).  

### Ошибки и предупреждения  
* Не запускать долгие задачи через обычный REST — может привести к таймауту 30 сек.  

### Где нам пригодится  
* При построении собственного API‑слоя для агентов‑одиночек.

## 6. Streaming Versus Polling (стр. —)  

### Главная мысль  
Для длительных агентных задач нужен потоковый ответ (WebSocket/SSE), а не опрос.  

### Как делать  
* В FastAPI использовать `WebSocket` или `Server‑Sent Events` для передачи промежуточных состояний.  

### Ошибки и предупреждения  
* Стандартный POST с таймаутом ≈ 30 сек — не подходит.  

### Где нам пригодится  
* При реализации интерактивного чат‑бота в веб‑интерфейсе.

## 7. Checkpointing (стр. —)  

### Главная мысль  
Снимки состояния позволяют возобновлять работу после падения без потери контекста.  

### Как делать (шаги)  
1. Определить сериализуемый объект (`AgentSession`).  
2. После каждой итерации вызывать `save_checkpoint`.  
3. При запуске искать последний чекпоинт `load_checkpoint`.  

### Правила и числа  
* Чекпоинты сохраняются в временной папке (`tempfile.mkdtemp`).  

### Шаблоны и примеры  
* `AgentSession` — класс с полями `session_id`, `history`, `turn_count`, `total_usd` и др. (пример 7‑1).  
* Функции `save_checkpoint`, `load_checkpoint`, `list_checkpoints` (пример 7‑4).  

### Ошибки и предупреждения  
* Не сохранять чувствительные данные без редактирования.  

### Где нам пригодится  
* При длительных сценариях поддержки, где пользователь может прервать сессию.

## 8. Context Pruning (стр. —)  

### Главная мысль  
Слишком длинный диалог → рост латентности и стоимости; нужно удалять «мёртвый» контекст, сохраняя последние сообщения и системный промпт.  

### Как делать (шаги)  
1. Подсчитать токены в истории (`count_tokens`).  
2. Если превышен лимит → сохранить системный промпт, последние N сообщений, а остальное суммировать в системное сообщение‑резюме.  

### Шаблоны и примеры  
* `prune_history()` — функция с параметрами `max_tokens=4000`, `keep_recent=6` (пример 7‑2).  

### Ошибки и предупреждения  
* Не удалять системный промпт.  
* Не удалять последние сообщения — они нужны для актуального вывода.  

### Где нам пригодится  
* При работе с моделями с небольшим контекстным окном (GPT‑3.5, LLaMA‑2).

## 9. Circuit Breaker (стр. —)  

### Главная мысль  
Защита от бесконечных циклов и превышения бюджета — необходима для контроля расходов и пользовательского опыта.  

### Как делать (шаги)  
1. Ввести **бюджетный предохранитель** — проверка `session.total_usd >= budget_cap`.  
2. Ввести **ограничитель по ходам** — проверка `session.turn_count >= max_turns`.  
3. При срабатывании бросать `CircuitBreakerTripped`, обрабатывая её в FastAPI.  

### Правила и числа (пример 7‑3)  
* `budget_cap = 0.50 USD` (по умолчанию).  
* `max_turns = 12`.  

### Шаблоны и примеры  
* `CircuitBreakerTripped` — исключение с полем `session`.  
* `check_circuit_breaker(session, budget_cap, max_turns)` (пример 7‑3).  

### Ошибки и предупреждения  
* Не полагаться лишь на ограничения провайдера — нужно локальное ограничение.  

### Где нам пригодится  
* При работе с клиентскими запросами, где важен контроль стоимости (например, SaaS‑платформа).

## 10. The Need for a Fallback Guy (стр. —)  

### Главная мысль  
Любая модель может «сломаться» (таймаут, неверный синтаксис, семантический дрейф). Нужно заранее предусмотреть резервную модель/путь.  

### Как делать (шаги)  
1. Выбрать **первичную** модель.  
2. Описать **fallback‑модель** (вторая по приоритету).  
3. Тестировать оба пути (primary + fallback) через одинаковый пайплайн.  

### Правила и числа  
* Не использовать только «budget caps» — нужен **budget fuse** + **turn fuse** (см. circuit breaker).  

### Шаблоны и примеры  
* Трёхуровневая стратегия (табл. 7‑5).  

### Ошибки и предупреждения  
* Ожидать, что fallback будет генерировать корректный JSON — нужно проверять.  

### Где нам пригодится  
* При построении критически важных сервисов (поддержка, обработка заявок).

## 11. Structured Output Enforcement Tiers (стр. —)  

### Главная мысль  
Для надёжного получения структурированного вывода необходима многоуровневая проверка: строгая схема, клиентская валидация, и, в крайнем случае, «промптовая» канонизация.  

### Три уровня (табл. 7‑5)  

| Tier | Подход | Механизм | Примечание |
|------|--------|----------|-----------|
| **1** | Strict JSON Schema | Constrained decoding на уровне токенов (provider) | Гарантирует только форму JSON, не смысл. |
| **2** | Instructor + Pydantic | Клиентская валидация, автоматические ретраи | Работает с любой моделью, проверяет поля. |
| **3** | Prompt‑only + canonicalization | Описание схемы в промпте, пост‑обработка | Наименее надёжный, используется в прототипах. |

### Как делать (шаги)  
1. Дать провайдеру **JSON‑schema** (`response_format`) → **Tier 1** (пример 7‑11).  
2. Встроить **Instructor** + **Pydantic** модель (`response_model=SupportTicket`) → **Tier 2** (пример 7‑12).  
3. Если оба не сработали, выполнить **деградированный запрос** с жёстким промптом → **Tier 3** (пример 7‑13).  

### Правила и числа  
* При **Tier 1**: `strict: True` в `response_format`.  
* При **Tier 2**: `max_retries=2` в клиенте Instructor.  
* При **Tier 3**: запрос без `response_format`, только системный промпт (`DEGRADED_SYSTEM`).  

### Шаблоны и примеры  
* **Schema** — `SUPPORT_TICKET_SCHEMA` (пример 7‑6).  
* **Pydantic** — `SupportTicket` (пример 7‑7).  
* **Instructor client** — `instructor.from_openai(...)` (пример 7‑8).  

### Ошибки и предупреждения  
* **Tier 1** не защищает от дрейфа значений (priority, sentiment).  
* **Tier 2** требует корректного `field_validator`.  
* **Tier 3** может вернуть несовместимые поля – следует делать канонизацию.  

### Где нам пригодится  
* При построении конвейера трансляции пользовательских запросов в тикет‑систему.

## 12. Model Drift (стр. —)  

### Главная мысль  
Разные модели называют одинаковые понятия разными лексемами; без нормализации происходит скрытый дрейф поведения.  

### Как делать (шаги)  
1. Составить **карты нормализации** (пример 7‑5).  
2. В `field_validator` применять карты (пример 7‑7).  
3. При отсутствии соответствия – задавать консервативный дефолт или выполнять инференс приоритета из контекста.  

### Шаблоны и примеры  
* `CATEGORY_MAP`, `PRIORITY_MAP`, `SENTIMENT_MAP` (пример 7‑5).  

### Ошибки и предупреждения  
* Не использовать только строгую схему — значения всё равно могут «дрейфовать».  

### Где нам пригодится  
* При переключении между провайдерами (OpenAI ↔ Anthropic ↔ Minimax).

## 13. Inference Backends: Cold Starts, Caching, and Deployment Physics (стр. —)  

### Главная мысль  
Самостоятельный запуск моделей (TGI, vLLM, SGLang) влечёт за собой холодные старты, кеш‑эффекты и ограничения памяти, которые влияют на латентность и стоимость.  

### Как делать (шаги)  
1. Выбрать бэкенд **vLLM / TGI / SGLang** в зависимости от нагрузки.  
2. При **scale‑to‑zero** хранить веса в постоянном хранилище (S3, GCS) — чтобы не скачивать каждый раз.  
3. Настроить **prefix‑caching** и **KV‑cache** для ускорения повторяющихся промптов.  
4. При необходимости **монтировать** постоянный диск в контейнере (Modal, Docker).  

### Правила и числа (табл. 7‑8)  

| Concern | Что происходит | Влияние |
|---------|----------------|--------|
| Cold start | Загрузка весов в GPU | 30–120 сек задержка первой заявки |
| Scale to zero | Отключение инференса при отсутствии трафика | Каждый «разогрев» → холодный старт |
| KV cache | Пересчёт ключей‑значений для каждого токена | Увеличивает время первого токена |
| Prefix caching | Повторное использование KV‑кэша | Ускоряет 2‑5× |
| Cache invalidation | Изменение префикса → сброс кэша | Латентность резко растёт |
| Memory pressure | Рост KV‑кэша при длинных контекстах | Увеличивает tail‑latency, падает батчинг |

### Шаблоны и примеры  
* **vLLM** — PagedAttention, линейная масштабируемость.  
* **TGI** — CUDA‑ядра, совместим с OpenAI‑API.  
* **SGLang** — поддержка мультимодальных моделей.  

### Ошибки и предупреждения  
* Хранить веса только в облачном бакете без монтирования → каждый воркер скачивает гигабайты → высокая стоимость.  

### Где нам пригодится  
* При построении собственного локального сервера LLM‑агентов (например, SaaS‑приложение с закрытыми данными).  

---

### Общее резюме для ИИ‑помощника Claude  

* **План**: пройти стадии зрелости (табл. 7‑1), начиная с MVP‑лаборатории, постепенно добавляя наблюдение, хард‑инжиниринг, fallback‑механизмы и масштабирование.  
* **Инструменты**: Streamlit/Gradio → PaaS → FastAPI → Docker → Kubernetes/Ray.  
* **Ключевые паттерны**: checkpointing, context pruning, circuit breaker, multi‑tier output validation, normalization maps, inference‑backend selection.  
* **Что проверять**: стоимость (USD), латентность (сек), корректность JSON‑схемы, соответствие бизнес‑правилам (приоритет, категория).  
* **Где ошибки**: бесконечные циклы, дрейф при смене модели, скрытая потеря токенов, холодные старты, отказ инструментов.  

Эти пункты позволят быстро подготовить, протестировать и надёжно запустить агента‑единственника в продакшн‑условиях, минимизируя риски для бюджета и пользовательского опыта.
