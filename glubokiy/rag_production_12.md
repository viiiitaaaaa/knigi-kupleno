# Конспект: Мультимодальный RAG (Работа с таблицами, изображениями и медиа)

## Работа с таблицами в документах (стр. 264–275)
**Главная мысль:** Таблицы — это «микро-документы» с высокой плотностью данных. Обычная нарезка текста (chunking) их ломает, поэтому таблицы нужно извлекать, нормализовать и подавать в LLM в структурированном виде (JSON/DataFrame).

### Как делать (Процесс извлечения):
1. **Экстракция:** Поиск таблицы как отдельного объекта (по сетке, выравниванию, пробелам) с помощью Vision-моделей.
2. **OCR и семантика:** Поячеечное распознавание текста (чтобы данные не «перетекали» из колонки в колонку) и определение ролей (где заголовок, где данные).
3. **Нормализация:** Очистка данных от шума (например, удаление символов валют или приведение «$ (1,000)» к числу).

### Инструменты (стр. 266):
- **Облачные (платные, для сканов/рукописей):** Amazon Textract, Azure Document Intelligence, Google Cloud Document AI.
- **Гибридные:** LlamaParse (выдает Markdown).
- **Open Source (бесплатные, локальные, для цифровых PDF):** 
    - `Docling` (от IBM) и `Unstructured` — понимание структуры, JSON/HTML.
    - `Gmft` — специализируется только на экстракции таблиц.

### Правила и числа:
- **Проблема «безголовых» чанков:** При обычном разделении текста заголовок таблицы остается в первом чанке, а данные — в следующих. LLM теряет смысл цифр (стр. 268–269).
- **Решение:** Преобразовывать таблицу в JSON (список строк, где ключи — названия колонок) $\rightarrow$ создавать краткое резюме таблицы $\rightarrow$ индексировать резюме $\rightarrow$ при запросе подавать в LLM **всю** таблицу целиком (стр. 269–270).
- **Лимит:** Если таблица огромная, нужно фильтровать колонки перед подачей в LLM (стр. 270).

### Склейка многостраничных таблиц (стр. 272–274):
**Проблема:** Парсеры видят одну таблицу на 6 страницах как 6 разных таблиц.
**Как лечить:** 
1. Проверить, что таблицы идут на соседних страницах.
2. Сравнить количество колонок и типы данных.
3. Удалить повторяющиеся заголовки на новых страницах.
4. Объединить в один DataFrame перед индексацией.

**Где пригодится:** Для анализа финансовых отчетов, прайс-листов, технических спецификаций и любых данных в PDF.

## Работа с изображениями и диаграммами (стр. 276–291)
**Главная мысль:** Изображения (схемы, графики) не имеют структуры текста. Есть два пути: либо превратить картинку в текст один раз при загрузке, либо использовать модель, которая «видит» картинку в момент ответа.

### Стратегия 1: Резюмирование изображений (Image Summarization) (стр. 278–284)
- **Суть:** VLM (GPT-4, Claude 3) описывает картинку $\rightarrow$ текст описания кладется в векторную базу.
- **Процесс:** 
    1. VLM создает детальный summary (4–6 предложений) $\rightarrow$ сохраняется как обычный чанк.
    2. Оригинал картинки хранится в S3, в метаданных чанка — ссылка на него.
    3. При ответе: либо подается текст summary, либо (если модель видит картинки) подается сам файл в Base64.
- **Плюсы:** Дешево при запросе, работает с простыми LLM.
- **Минусы:** Если summary упустило деталь, модель её никогда не найдет.

### Стратегия 2: Общее векторное пространство (Shared Embedding Space) (стр. 284–291)
- **Суть:** Использование моделей типа **CLIP, SigLIP, ImageBind**. Они переводят и текст, и картинку в один и тот же векторный код.
- **Процесс:** Картинка $\rightarrow$ Image Encoder $\rightarrow$ Вектор. Запрос «собака» $\rightarrow$ Text Encoder $\rightarrow$ Вектор. Поиск идет по косинусному сходству (стр. 286).
- **Плюсы:** Очень быстро, не нужно описывать каждую картинку текстом.
- **Минусы:** Плохо работает с точными данными (цифры в графиках, мелкий текст). Модель поймет, что это «график продаж», но не скажет точное число.

**Сравнение (где что использовать):**
- **Summarization:** Для технических схем, графиков, документов, где важны детали и цифры.
- **Shared Embeddings:** Для фото, каталогов товаров, визуальных стилей.

**Где пригодится:** Для анализа презентаций, инструкций с картинками, поиска по архивам фото/скриншотов.

## Аудио и Видео в RAG (стр. 291–267)
**Главная мысль:** Самый простой способ работы с медиа — высококачественная транскрибация в текст с сохранением метаданных о спикерах и времени.

### Как делать (Процесс):
1. **Транскрибация:** Использование моделей типа **Whisper** (OpenAI), **Chirp** (Google) или **Deepgram**.
2. **Диаризация (Speaker Diarization):** Обязательное разделение потока на разных спикеров (кто именно сказал фразу). Без этого контекст теряется (стр. 292).
3. **Привязка по времени (Timestamps):** Каждому фрагменту текста присваивается время начала и конца для создания «глубоких ссылок» на конкретную секунду видео/аудио.
4. **Чанкинг:** Группировка реплик спикеров в блоки (например, до 512 токенов), сохраняя границы предложений.

**Ошибки и предупреждения:**
- Плоская транскрибация (без имен спикеров) бесполезна для RAG, так как неясно, кто автор утверждения (стр. 292).

**Где пригодится:** Для анализа записей созвонов в Zoom, видео-уроков, интервью, голосовых заметок.
