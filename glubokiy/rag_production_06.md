# Конспект: Масштабирование и развертывание RAG в продакшене

## Исправление галлюцинаций (стр. 121)
- **Главная мысль**: Обнаружения галлюцинаций (ошибок в фактах) недостаточно; система должна уметь их исправлять, чтобы быть надежной.
- **Как делать**:
    1. Модель детектирования выявляет потенциальную галлюцинацию.
    2. Если вероятность ошибки высока, система либо отказывается отвечать («Я не знаю»), либо отправляет ответ в специальную **модель коррекции**.
    3. Модель коррекции берет подозрительный ответ и исходные фрагменты документов (контекст) и переписывает ответ правильно.
- **Ошибки и предупреждения**: Использование цепочки «детектор $\rightarrow$ корректор» увеличивает задержку (latency) ответа.
- **Где нам пригодится**: Для проверки ответов помощника и повышения их точности.

## Создание отличного пользовательского опыта (UX) в RAG (стр. 122–128)
- **Главная мысль**: Успех RAG зависит не только от точности, но и от того, как пользователь взаимодействует с системой и получает данные.
- **Как делать**:
    1. **Захват ввода**:
        - Использовать естественный язык (текст, голос, файлы).
        - Внедрить уточнение запросов (автодополнение, примеры вопросов).
        - Поддерживать многошатовые диалоги (память истории чата).
    2. **Презентация результатов**:
        - Интегрировать ссылки на источники прямо в текст (цитирование), а не списком в конце.
        - Использовать визуальную иерархию (цвета, шрифты) для разделения ответов ИИ и данных из документов.
        - Объяснять процесс: показывать индикаторы загрузки или «отчет о прогрессе» (что сейчас ищет система).
    3. **Контроль и обратная связь**:
        - Дать пользователю выбор источников (например, искать только в Google Drive, игнорируя Slack).
        - Добавить кнопки 👍/👎 и возможность комментировать части ответа.
        - Обрабатывать ошибки корректно: если данных нет, предложить альтернативный способ поиска.
- **Шаблоны и примеры**: Интерфейс `vectara-answer` (показывает статус поиска, цитируемые ссылки и «бейдж галлюцинации»).
- **Инструменты**: `assistant-ui` (React/TS), `Streamlit` и `Gradio` (Python — для прототипов), `vectara-answer` (готовый UI для Q&A).
- **Где нам пригодится**: При создании интерфейса для своих агентов и инструментов работы с данными.

## Заключение по главе 3 (стр. 128–129)
- **Главная мысль**: Переход к корпоративному RAG требует внимания к четырем столпам: надежный импорт данных $\rightarrow$ точный многошаговый поиск $\rightarrow$ защитные барьеры (guardrails) $\rightarrow$ детектирование/исправление галлюцинаций.
- **Где нам пригодится**: Общий чек-лист для проверки архитектуры системы.

## Развертывание RAG в продакшен (Глава 4) (стр. 130–149)
### Переход от POC к продакшену (стр. 130–132)
- **Главная мысль**: Создать Proof of Concept (POC — прототип) легко, но сделать систему масштабируемой, безопасной и быстрой — это сложная инженерная задача (DevOps, инфраструктура как код).
- **Где нам пригодится**: Понимание разницы между «скриптом на коленке» и полноценным сервисом.

### Проблемы качества ответов (стр. 132–135)
- **Главная мысль**: Низкое качество ответов обычно вызвано одной из четырех причин.
- **Причины и решения**:
    1. **Нет релевантных данных**: Система не находит ответ, так как документа нет в базе. *Решение*: Отслеживать запросы, обновлять базу, использовать «стейджинг» (проверка новых данных в тестовой коллекции перед переносом в основную).
    2. **Слабый поиск (Retrieval)**: Простой векторный поиск не справляется с большим объемом. *Решение*: Гибридный поиск и реранкеры (переранжирование результатов).
    3. **Галлюцинации LLM**: Модель додумывает ответы, если данные неполны. *Решение*: Выбор моделей с низким уровнем галлюцинаций и внедрение систем коррекции.
    4. **Плохой промпт**: Слишком простой запрос к модели. *Решение*: Добавлять четкие инструкции, например: *«Если ты не знаешь ответа, просто скажи, что не знаешь; не пытайся его выдумать»* (стр. 135).
- **Где нам пригодится**: Для диагностики, почему агент «тупит» или врет.

### Борьба с высокой задержкой (Latency) (стр. 135–141)
- **Главная мысль**: Пользователь ждет быстрый ответ, но сложный RAG-пайплайн работает медленно.
- **Целевые числа**:
    - Поиск (векторный/гибридный/реранкер): $\le 300$ мс в среднем (стр. 135).
    - Генерация LLM: от 2–3 секунд (малые модели) до 5–10 секунд (флагманские).
- **Как ускорять**:
    1. **Параллелизация**: Использовать архитектуру микросервисов с оркестратором. Оркестратор делает «fan-out» (одновременные запросы к векторной БД и текстовому поиску), чтобы общее время зависело от самого медленного источника, а не от их суммы.
    2. **Оптимизация моделей**: Использовать vLLM, TensorRT-LLM или TGI (поддерживают continuous batching и paged attention).
    3. **Индексация**: Использовать ANN-индексы (HNSW, IVFPQ).
    4. **Кэширование (Redis/Dragonfly)**:
        - *Полный ответ*: Кэш по хешу запроса.
        - *Результаты поиска*: Кэш по эмбеддингу запроса.
        - *Контент чанков*: Кэш самих текстов документов.
        - *Семантический кэш*: Поиск по сходству векторов (если вопрос сформулирован иначе, но смысл тот же). Порог сходства в примере: $0.85$ (стр. 140).
- **Ошибки и предупреждения**: Проблема инвалидации кэша (данные в базе изменились, а в кэше остался старый ответ). Решение: события (Pub/Sub) при обновлении документов.
- **Где нам пригодится**: Для оптимизации скорости работы своих скриптов и агентов.

### Безопасность и приватность данных (стр. 141–144)
- **Главная мысль**: Защита данных должна быть на всех этапах: импорт $\rightarrow$ хранение $\rightarrow$ генерация.
- **Как делать**:
    1. **Импорт**: Шифрование. Для персональных данных (PII) использовать **«типизированное маскирование»** (entity-aware redaction). Вместо удаления имени заменить его на `<PERSON>`, чтобы сохранить смысл предложения для ИИ.
    2. **Хранение**: Шифрование, RBAC (ролевой доступ) и принцип «минимума необходимых данных» (GDPR).
    3. **Утечки через доступ**: Интегрировать фильтр прав доступа в поток запроса, чтобы пользователь видел только те документы, к которым у него есть доступ.
    4. **Утечки через провайдера LLM**: Чтобы данные не ушли в OpenAI/Anthropic, использовать on-premises модели (Llama, Qwen, DeepSeek) в своем облаке (VPC).
    5. **Барьеры генерации**: Внедрять Guardrails для блокировки токсичного или запрещенного контента.
- **Где нам пригодится**: Для защиты своих данных и соблюдения приватности.

### Интеграция и «хаос вендоров» (стр. 145–149)
- **Главная мысль**: Сборка RAG из разных сервисов (парсинг PDF $\rightarrow$ БД $\rightarrow$ Реренкер $\rightarrow$ LLM) создает хрупкую архитектуру.
- **Предупреждение**: Каждый новый компонент увеличивает сложность поддержки, время задержки и риски безопасности.
- **Где нам пригодится**: Осторожность при добавлении новых библиотек и API в систему.
