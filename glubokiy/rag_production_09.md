# Конспект: Оценка RAG-приложений (Глава 6)

Эта часть посвящена тому, как понять, работает ли ваш RAG (поиск + генерация) хорошо или он «галлюцинирует» и выдает мусор.

## Метрики поиска (Retrieval Metrics) (стр. 195–198)
- **Главная мысль:** Нужно понять, находит ли система правильные куски данных (чанки) из базы для ответа на запрос.
- **Как делать:**
    1. Создать «золотой набор» (golden chunks) — список эталонных правильных чанков для каждого вопроса (вручную).
    2. Применить одну из метрик ниже.
- **Правила и числа:**
    - **Precision@k (Точность):** Какая доля из $k$ найденных чанков реально полезны. Важна, если у LLM маленькое «окно контекста» (стр. 195).
    - **Recall@k (Полнота):** Сколько из всех существующих в базе правильных чанков система смогла найти в топ-$k$ (стр. 196).
    - **F1-score@k:** Среднее между точностью и полнотой. Используется, когда важен баланс (стр. 196).
    - **Rank-aware метрики (учитывают порядок):**
        - **MRR (Mean Reciprocal Rank):** Считает только позицию первого правильного ответа. Идеально, если нужен один точный ответ (стр. 197).
        - **MAP (Mean Average Precision):** Средняя точность по всем найденным правильным чанкам. Штрафует за низкий ранг полезных данных (стр. 197).
        - **nDCG:** Самая мощная метрика. Позволяет давать чанкам разную степень полезности (например: 0 — бесполезно, 3 — идеально) (стр. 198).
- **Ошибки и предупреждения:** Между точностью и полнотой есть конфликт: если возвращать слишком много данных (высокий Recall), в них попадет много шума (упадет Precision) (стр. 196).
- **Где нам пригодится:** Для проверки качества скриптов поиска и настройки размера окна контекста.

## UMBRELA scores (стр. 199–201)
- **Главная мысль:** Метод оценки поиска без «золотых наборов» с помощью LLM в роли судьи (LLM-as-a-judge).
- **Как делать:**
    1. Подать запрос и найденный чанк в LLM-судью с помощью специального промпта.
    2. LLM присваивает балл от 0 до 3.
- **Правила и числа (Шкала UMBRELA):**
    - **0** = Не относится к делу.
    - **1** = Связано с темой, но ответа нет.
    - **2** = Есть ответ, но он нечеткий или спрятан в лишнем тексте.
    - **3** = Точный ответ на запрос (стр. 199).
- **Шаблоны:** В тексте приведен `UMBRELA_PROMPT`, который заставляет модель рассуждать по шагам: намерение $\rightarrow$ соответствие $\rightarrow$ надежность $\rightarrow$ итоговый балл (стр. 200).
- **Ошибки и предупреждения:** Невозможно вычислить Recall (полноту), так как пришлось бы прогонять через LLM вообще все данные в базе (стр. 199).
- **Где нам пригодится:** Для автоматической проверки качества данных, когда их слишком много, чтобы размечать вручную.

## Метрики генерации (Generation Metrics) (стр. 201–204)
- **Главная мысль:** Проверка того, насколько эффективно LLM превращает найденные чанки в итоговый ответ.
- **Основные метрики:**
    - **Context Utilization (Использование контекста):** Насколько полно использованы факты из чанков. Метод **AutoNuggetizer** разбивает данные на «наггеты» (атомарные факты): *Vital* (критичные) и *OK* (дополнительные), а затем проверяет их наличие в ответе (стр. 201–202).
    - **Answer Accuracy (Точность ответа):** Сравнение с эталонным ответом (Similarity) и проверка релевантности вопросу (стр. 202).
    - **Faithfulness (Верность/Достоверность):** Главный инструмент борьбы с галлюцинациями. Проверяет, можно ли каждое утверждение в ответе подтвердить найденными чанками (стр. 202).
    - **Citation Accuracy (Точность ссылок):** Проверяет, действительно ли ссылка ведет на текст, подтверждающий утверждение (стр. 203).
    - **Response Consistency (Стабильность):** Выдаст ли система один и тот же ответ на один и тот же запрос при разных запусках (стр. 203).
- **Безопасность:** Использование моделей-фильтров (**Llama Guard**, **ShieldGemma**) для отсева хейт-спича или опасного контента (стр. 204).
- **Red Teaming:** Метод «красной команды» — намеренный поиск уязвимостей и предвзятости системы человеком (стр. 204).
- **Где нам пригодится:** Для борьбы с галлюцинациями и обеспечения безопасности помощника.

## Инструменты оценки (RAG Evaluation Offerings) (стр. 205–208)
- **Главная мысль:** Обзор готовых библиотек для автоматизации всех вышеописанных метрик.
- **Варианты:**
    1. **Open RAG Eval:** Бесплатный, делает упор на reference-free метрики (без золотых наборов): UMBRELA, AutoNuggetizer, HHEM (галлюцинации) (стр. 205).
    2. **Ragas:** Популярный фреймворк, может сам генерировать синтетические тестовые наборы (стр. 207).
    3. **DeepEval:** Подход как в юнит-тестах (pytest). Можно писать тесты на конкретные случаи (стр. 208).
    4. **Amazon Bedrock:** Облачный сервис (AWS), всё «из коробки», включая оценку безопасности (стр. 208).
- **Где нам пригодится:** Для выбора библиотеки под свои скрипты (Open RAG Eval — если нет эталонов, DeepEval — если нужен строгий контроль).

## Обратная связь от людей (Human Feedback) (стр. 209–210)
- **Главная мысль:** Автоматика может ошибаться, поэтому нужны «лайки/дизлайки» от реальных пользователей.
- **Как делать:**
    1. Добавить кнопки $\text{👍}/\text{👎}$ в интерфейс.
    2. Считать **User Satisfaction Rate** (количество 👍 / общее количество голосов) (стр. 209).
    3. Анализировать ошибки: какие темы (категории) собирают больше всего дизлайков $\rightarrow$ править данные в этой категории (стр. 209).
- **Где нам пригодится:** Для финальной проверки того, доволен ли пользователь результатом.

## Интеграция в продакшн (Integrating RAG Evaluation) (стр. 211–218)
- **Главная мысль:** Оценка должна быть частью цикла разработки (Measurement $\rightarrow$ Tuning), а не разовым действием.
- **Процессы:**
    - **Offline evaluation:** Тесты на фиксированном наборе данных перед обновлением кода/данных («ворота качества») (стр. 212).
    - **Online evaluation:** Мониторинг живого трафика. Рекомендуется делать **асинхронно** (в фоне), чтобы не тормозить ответ пользователю, и использовать **сэмплирование** (проверять 5–10% запросов для экономии денег) (стр. 213).
- **Системные метрики (стр. 213–214):**
    - **Latency (Задержка):** Время от запроса до ответа (следить за P95/P99).
    - **Throughput (Пропускная способность):** Запросов в секунду (QPS).
    - **Uptime (Доступность):** Цель $\ge 99.9\%$.
    - **Cost (Стоимость):** Учет токенов за генерацию + токенов за работу LLM-судьи.
- **Где нам пригодится:** Для планирования бюджета и настройки скорости работы агентов.
