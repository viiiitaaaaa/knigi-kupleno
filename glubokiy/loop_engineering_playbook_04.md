## Глава 12 – «Ошибка → Восстановление» (стр. 144‑160)

### 1. Категории ошибок агентов (стр. 144)  
- **Главная мысль:** Ошибки делятся на 5 категорий, каждая требует собственного способа восстановления.  
- **Категории и стратегии:**  

| Категория | Примеры | Что проверяем | Как восстанавливаем | Время/шаги |
|---|---|---|---|---|
| 1. Транзиентные | API‑таймаут, rate‑limit, сетевой сбой | Тип исключения + HTTP‑статус | Повтор с экспоненциальным backoff | сразу |
| 2. Инструментальные | Неправильные аргументы, недоступный инструмент | Валидация инструмента + парсинг ответа | Коррекция аргументов, переход к запасному инструменту | сразу |
| 3. Модельные | Галлюцинации, противоречивый вывод, отказ | Валидация вывода + проверка схемы | Перепрос (re‑prompt) с исправлением, корректировка temperature, 1‑2 шагa | 1‑2 |
| 4. Состояния | Переполнение контекста, устаревшие данные | Инварианты состояния | Откат к чек‑пойнту, обновление контекста | несколько шагов |
| 5. Логические | Плохой план, циклическое рассуждение, «scope creep» | Мониторинг прогресса + анализ траектории | Пересмотр плана, эскалация человеку | много шагов |

- **Правило “Опасность”** (стр. 144): Транзиентные – самые лёгкие, логические – самые опасные. На категории 3‑5 следует тратить ≈ 80 % усилий по‑резилентности.  

### 2. Шаблон 1 – Retry с экспоненциальным backoff (стр. 144‑146)  
- **Главная мысль:** При временных ошибках нужно повторять запрос, увеличивая задержку, плюс *jitter* (для избежания «thundering herd»).  
- **Шаги (код‑пример):**  

1. Обернуть функцию декоратором `retry_with_backoff`.  
2. При `retryable_exceptions` (по умолчанию `TimeoutError, ConnectionError`) пробовать выполнить до `max_retries+1` раз.  
3. Вычислить задержку: `delay = min(base_delay * 2**attempt, max_delay)`.  
4. Если `jitter=True`, умножить на случайный множитель `0.5 + random.random()`.  
5. При исчерпании попыток бросить последнюю ошибку.  

- **Параметры:** `max_retries` (по умолчанию 3), `base_delay` = 1 сек., `max_delay` = 60 сек., `jitter` = True. (стр. 144‑145)  

#### Шаблон кода  
```python
@retry_with_backoff(max_retries=3,
                   retryable_exceptions=(TimeoutError, ConnectionError, RateLimitError))
def call_llm(prompt, model="claude-sonnet-4"):
    return client.messages.create(model=model,
                                 messages=[{"role":"user","content":prompt}])
```  

#### Ошибки/предупреждения  
- **ANTI‑PATTERN:** повторять НЕ‑идемпотентную операцию без проверки (стр. 146). Каждое действие должно иметь *idempotency‑key* и проверку результата перед новым запросом.  

### 3. Матрица решений о повторе (стр. 147)  
| Ошибка | Ретрай? | Макс‑ретрай | Backoff | Примечание |
|---|---|---|---|---|
| HTTP 429 (Rate limit) | ✅ | 5 | Использовать заголовок `Retry‑After` | (стр. 147) |
| HTTP 500 | ✅ | 3 | Экспон. + jitter | (стр. 147) |
| HTTP 401 | ❌ | 0 | – | Исправьте креденшелы |
| HTTP 400 | ❌ | 0 | – | Исправьте запрос |
| Timeout | ✅ | 2 | Линейный + упрощение ввода | (стр. 147) |
| Connection reset | ✅ | 3 | Экспон. + jitter | (стр. 147) |
| Model refusal | ⚠️ (может) | 1 | Нет | Переформулировать запрос |
| Hallucinated tool | ✅ | 2 | Нет | Перепрос с доступным инструментом |

### 4. Шаблон 2 – Fallback‑цепочки (стр. 147‑148)  
- **Главная мысль:** Если повторы не спасают, переключаемся на запасные стратегии.  
- **Шаги:**  

1. Создать `FallbackChain` с упорядоченным списком `(имя, callable)`.  
2. При `execute` пробовать стратегии последовательно, записывая в `execution_log`.  
3. При успехе вернуть результат, иначе бросить `AllStrategiesFailedError`.  

- **Пример:**  
```python
search_chain = FallbackChain([
    ("google_search", lambda q: google_api.search(q)),
    ("bing_search",   lambda q: bing_api.search(q)),
    ("cached_knowledge", lambda q: llm.answer_from_training(
        f"Based on your training data, answer: {q}"))
])
```  

### 5. Шаблон 3 – Самокоррекция (рефлексия) (стр. 148‑149)  
- **Главная мысль:** При модельных ошибках агент сам проверяет и исправляет вывод.  
- **Процесс:**  

1. `self_correct(agent, task, initial_output, max_rounds=2)`  
2. **Критика:** LLM получает инструкцию «проверь вывод на ошибки…» (стр. 149).  
3. Если в критике есть «APPROVED», возвращаем текущий вывод.  
4. Иначе вызываем LLM с запросом «применить исправления» и заменяем `current`.  

- **Стоимость:** Один проход‑критика ≈ стоимость оригинального генератора; две раунда ≈ тройная стоимость (стр. 149). Рекомендуется только для критически важных артефактов.  

### 6. Шаблон 4 – Circuit Breaker (стр. 149‑151)  
- **Главная мысль:** Предотвращаем бесконечные вызовы падающего сервиса.  
- **Состояния:** `CLOSED` (норм), `OPEN` (отклонять), `HALF_OPEN` (тестировать восстановление).  
- **Параметры** (по умолчанию): `failure_threshold=5`, `recovery_timeout=60 сек.`, `half_open_max=2`. (стр. 150)  
- **Алгоритм:**  

1. При `OPEN` проверять, прошёл ли `recovery_timeout`; если да → `HALF_OPEN`.  
2. При успешном вызове в `HALF_OPEN` увеличить `half_open_successes`; при достижении `half_open_max` перейти в `CLOSED`.  
3. При любой ошибке вызвать `_on_failure()`, увеличить `failure_count`; если `>= failure_threshold` → `OPEN`.  

- **Пример использования:**  
```python
search_breaker = CircuitBreaker(failure_threshold=3, recovery_timeout=30)
def safe_search(query):
    return search_breaker.call(google_api.search, query)
```  

### 7. Шаблон 5 – Graceful Degradation (стр. 152‑154)  
- **Главная мысль:** Если всё восстановление провалилось, агент отдаёт лучший‑возможный ответ с явным указанием ограничений.  
- **Таблица сценариев** (стр. 152):  

| Полный функционал | Деградированный ответ | Коммуникация пользователю |
|---|---|---|
| Search API | Исследование в живых источниках | «Based on my training data (may be outdated)…» |
| Code execution | Проверенный код | «I could not verify this code. Please test before using.» |
| Бюджет | Полный многошаговый анализ | «Budget reached. Here is what I found so far…» |
| Переполнение контекста | Анализ ключевых секций | «Document too large. Analyzed sections 1‑5 of 20.» |
| Основная модель упала | Ответ Haiku с оговоркой | «Using a faster model. Quality may be reduced.» |

- **Scored Walkthroughs** (стр. 152‑154) показывают, как правильно ответить на платёжный сбой, недоступный поиск, зацикливание инструмента.  

### 8. Никогда не глотать ошибки молча (стр. 155‑156)  
- **Главная мысль:** Ошибку нельзя просто игнорировать; необходимо: (1) восстановить с логированием, (2) эскалировать человеку, (3) триггерить деградацию.  

### 9. Слой безопасности агента (стр. 155‑157)  
- **Таблицы параметров:**  

| Блокируемые действия | Требуют подтверждения |
|---|---|
| `delete_file`, `send_email`, `make_payment`, `modify_permissions`, `deploy_to_production`, `update_database`, `create_account` | Да |
| `format_disk`, `drop_database`, `rm_rf`, `disable_firewall`, `expose_credentials` | **Блокируется навсегда** |

- **Лимит экспорта данных:** `MAX_DATA_EXPORT_BYTES = 10 000 000` (10 МБ). (стр. 155)  
- **Проверки до/после действия:** обнаружение prompt‑инъекций (стр. 156‑157) по 8‑строчным паттернам (например, “ignore previous instructions”).  

### 10. Дерево решений по ошибкам (стр. 158)  
1. Транзиентная? → Retry с backoff (max 3).  
2. Есть fallback? → Включить fallback, логировать деградацию.  
3. Можно ли отдать частичный результат? → Делать с дисклеймером.  
4. Известный режим отказа? → Применить фикс, добавить регрес‑тест.  
5. Иначе → Эскалировать человеку с полным трейсом.  

### 11. Практические упражнения (стр. 159)  
- Реализовать `retry_with_backoff`.  
- Построить `FallbackChain` для LLM‑переходов.  
- Тестировать `CircuitBreaker`.  
- Создать цикл самокоррекции.  
- Запустить хаос‑тестинг, чекпоинт‑систему, карту деградаций.  

### 12. Краткое содержание (стр. 160)  
- 5 категорий ошибок → разные стратегии.  
- Retry + jitter, Decision Matrix, Fallback Chains, Self‑Correction, Circuit Breaker, Graceful Degradation.  
- Никогда не игнорировать ошибки, использовать слой безопасности, дерево решений.  

**Где пригодится:** При построении любого автономного агента‑одиночки – для отлова и восстановления ошибок, логирования, планов эскалации и создания безопасных «запасных» стратегий.

## Глава 13 – «Оптимизация затрат» (стр. 161‑175)

### 1. Введение – стоимость как главный барьер (стр. 161‑162)  
- **Главная мысль:** Самый дорогой агент – тот, что работает бесконечно; правильный подбор модели и кеширование позволяют сократить расходы до 20 % от наивного варианта.  

### 2. Ландшафт цен моделей (стр. 162‑163)  

| Модель | Цена ввода $/M токенов | Цена вывода $/M токенов | Качество | Лучшее применение |
|---|---|---|---|---|
| Claude Opus 4 | 15 | 75 | Frontier | Сложные рассуждения, оценка |
| Claude Sonnet 4 | 3 | 15 | High | Основные рассуждения, инструменты |
| Claude Haiku 3.5 | 0.8 | 4 | Fast | Классификация, экстракция, роутинг |
| GPT‑4o | 2.5 | 10 | High | Общие задачи, мультимод |
| GPT‑4o mini | 0.15 | 0.6 | Fast | Массовый простой поток |
| Gemini 2.0 Flash | 0.10 | 0.40 | Fast | Самый высокий объём, низкая цена |

- **Факт:** Opus‑вывод стоит 187 раз дороже, чем Gemini Flash (стр. 163).  

### 3. Уравнение стоимости (стр. 163‑164)  
`total_cost = (input_tokens * price_in + output_tokens * price_out) * iterations`.  
Функция `calculate_task_cost` (стр. 163‑164) выводит детали: стоимость за итерацию, процент расходов на ввод/вывод, месячный бюджет при 1 k/10 k запросов в день.  

### 4. Анти‑паттерн: считать токены вывода бесплатными (стр. 164)  
- **Главная мысль:** Выводные токены часто в 5‑10 раз дороже ввода; ограничьте `max_tokens` под каждый тип задачи.  

### 5. Стратегия 1 – Маршрутизация моделей (стр. 164‑165)  
- **Главная мысль:** Отправлять каждую подзадачу к наиболее экономичной модели.  
- **Таблица роутинга:**  

| Тип задачи | Модель | max_tokens | temperature |
|---|---|---|---|
| classify | Claude Haiku 3.5 | 100 | 0 |
| extract | Claude Haiku 3.5 | 500 | 0 |
| route | Claude Haiku 3.5 | 50 | 0 |
| search_query | Claude Haiku 3.5 | 200 | 0.3 |
| summarize | Claude Sonnet 4 | 1000 | 0.3 |
| reason | Claude Sonnet 4 | 2000 | 0.5 |
| plan | Claude Sonnet 4 | 1500 | 0.3 |
| synthesize | Claude Sonnet 4 | 3000 | 0.5 |
| judge | Claude Opus 4 | 500 | 0 |

- **Оценка экономии:** `estimate_savings` сравнивает стоимость роутинга vs. всё‑Sonnet (стр. 165).  

### 6. Стратегия 2 – Кеширование (стр. 165‑167)

#### a) Exact‑Match Cache (стр. 165‑166)  
- Хеш SHA‑256 от полного входа, TTL = 3600 сек.  
- Статистика `hits/misses/expired`.  

#### b) Semantic Cache (стр. 166‑167)  
- Хранит векторные эмбеддинги, порог схожести 0.95 (стр. 170).  
- При запросе ищет лучшую схожесть > threshold, возвращает кеш.  

#### Пример использования (стр. 166‑167):  

```python
semantic_cache.set(query, value)
result = semantic_cache.get(query)   # возвращает None, если нет похожего
```  

### 7. Стратегия 3 – Prompt Caching (стр. 168)  
- Anthropic позволяет кэшировать системный промпт (до 90 % экономии).  
- Пример: система с 5000‑токенным `LONG_SYSTEM_PROMPT` вызывается 1000 раз → без кеша $15, с кешем $1.5 (стр. 168).  

### 8. Стратегия 4 – Бюджетные гарды (стр. 168‑170)  

| Параметр | Описание |
|---|---|
| `per_run_budget` | Максимальный расход за один запуск (по умолчанию $1) |
| `daily_budget` | Общий дневной лимит (по умолчанию $500) |
| `check_budget(estimated_cost)` | Возвращает `allowed: False` + причину (`per_run_budget_exceeded` / `daily_budget_exceeded`). |

- При превышении: `force_synthesis` (принудительно перейти к генерации итогового вывода) или `queue_for_tomorrow`.  

### 9. Треугольник Cost‑Quality‑Speed (стр. 170‑171)  

| Оптимизация | Влияние на стоимость | Влияние на качество | Влияние на скорость |
|---|---|---|---|
| Model routing | 40‑70 % | Среднее/низкое | Быстрее (меньшие модели) |
| Prompt caching | 15‑40 % | Нет | Небольшой прирост |
| Response caching (exact) | 20‑50 % | Нет / низкое (semantic) | Очень быстро (cache‑hits) |
| Prompt compression | 10‑30 % | Низко‑средний риск | Быстрее (меньше токенов) |
| Early termination | 15‑25 % | Средний риск | Быстрее (меньше итераций) |
| Batch processing | 30‑50 % | Нет | Медленнее (задержка батча) |
| Fine‑tuning | 50‑80 % | Лучше на целевом домене | Значительно быстрее |

- **PRODUCTION TIP** (стр. 171): Устанавливайте порог семантического кеша 0.95 (ошибки < 1 %); 0.90 даёт 12 % больший хит‑рейт, но 8 % ложных положительных.  

### 10. Scored Walkthrough 13.1 – Сокращение затрат на 60 % (стр. 171‑172)  
- **Ключевые шаги:**  
  1. Model routing (Haiku → Sonnet → Opus).  
  2. Prompt caching (6 k‑токенный системный промпт).  
  3. Semantic cache (cos‑similar > 0.95).  
  4. Сократить среднее число итераций (6 → 4).  
- **Результат:** экономия ≈ 65 % → стоимость за запуск ≈ $0.88, месяц ≈ $132 k.  

### 11. Scored Walkthrough 13.2 – Бюджетный гард (стр. 172‑173)  
- **Шаги:**  
  1. Делить бюджет: план 10 %, исследование 60 %, синтез 20 %, буфер 10 %.  
  2. Перед каждым LLM‑вызовом оценивать стоимость (ввод + вывод).  
  3. Если оставшийся бюджет < стоимости следующей итерации → переключить в `synthesis mode`.  
  4. Жёстко разрывать при $1.00 (стр. 172).  

### 12. Scored Walkthrough 13.3 – Выбор кеша (стр. 173‑174)  
- **Решение:** Слои: Exact‑Match (TTL 1 ч, 0 $), затем Semantic (0.95, TTL 24 ч, $0.0001/запрос).  
- **Ожидаемый хит‑рейт:** 10‑15 % (Exact) + 15‑20 % (Semantic) → 25‑35 % запросов из кеша.  
- **Экономия:** $0.25/кеш‑запрос → $22 k/мес, стоимость инфраструктуры $300 → чистый доход $21.7 k.  

### 13. Финальное резюме (стр. 175)  
- Правильный подбор модели – до 70 % экономии.  
- Prompt‑caching – до 90 % экономии ввода.  
- Кеширование ответов – 20‑50 % экономии LLM‑вызовов.  
- Бюджетные гарды гарантируют, что агент не выйдет за пределы расходов.  
- Первые 50 % экономии почти бесплатны; дальше – компромисс качества.  

**Где пригодится:** При построении любого одиночного агента‑скрипта, где важно контролировать расходы (ценовые модели, кеш‑стратегии, бюджетные ограничения).

## Глава 14 – «Кодинг‑агенты» (стр. 176‑190)

### 1. Общий контекст (стр. 176‑177)  
- **Главная мысль:** Современные кодинг‑агенты умеют генерировать, тестировать, отлаживать и деплоить код автономно; ключевой паттерн – *write‑test‑fix* loop.  

### 2. Write‑Test‑Fix Loop (стр. 177‑180)  

| Шаг | Описание |
|---|---|
| 1. Понимание | `_gather_context(task)` собирает релевантные файлы (структура проекта, упомянутые файлы, импорт‑граф, grep‑результаты). |
| 2. План | `_create_plan` формирует план реализации. |
| 3‑5. Итеративный цикл (max_attempts, по умолчанию 3) | a) **Write** – `_implement(plan, context)` генерирует изменения.<br>b) **Test** – `_run_tests(changes)` запускает тесты.<br>c) **Fix** – если тесты не пройдены, `plan = _revise_plan(...)` и повтор. |
| 6. Завершение | При всех тестах → успех; иначе → результат с ошибками. |

- **Ключевое наблюдение (стр. 181):** Большинство сбоев связано не с генерацией, а с **выбором контекста**.  

### 3. Сравнение стратегий редактирования (стр. 181‑182)  

| Стратегия | Как работает | Плюсы | Минусы | Лучшее применение |
|---|---|---|---|---|
| Whole‑file rewrite | Выдаёт весь файл целиком | Простой, без конфликтов | Высокие токены, риск удаления | Новые/малометражные файлы (<200 строк) |
| Search‑and‑replace | Находит старый текст, заменяет | Точно, мало токенов, сохраняет остальной код | Хрупко, если текст не уникален | Точечные правки в больших файлах |
| Line‑range edit | Меняет строки N‑M | Точно по номерам | Номера смещаются после правок | Нужны фикс‑позиции |
| AST‑based edit | Модифицирует абстрактное синтаксическое дерево | Семантически осознанно, сохраняет формат | Языко‑специфично, сложно реализовать | Автоматический рефакторинг |
| Diff/patch | Генерирует unified‑diff | Стандартный, удобен для ревью | Трудно генерировать корректно | Code‑review пайплайны |

- **Рекомендация (стр. 182):** По‑умолчанию использовать **search‑and‑replace**; whole‑file только для новых файлов; избегать line‑range; AST‑based только при наличии специализированных реализаций.  

### 4. Управление контекстом в больших кодовых базах (стр. 182‑184)  

| Приоритет | Описание | Доля токен‑бюджета |
|---|---|---|
| 1. `task_mentions` | Файлы, явно упомянутые в задаче | 30 % |
| 2. `import_graph` | Файлы, импортируемые упомянутыми | 25 % |
| 3. `grep_results` | Файлы, содержащие релевантные паттерны | 20 % |
| 4. `test_files` | Тесты для всех меняемых файлов | 15 % |
| 5. `architecture_map` | Высоко‑уровневая карта проекта | 10 % |

- **Правила:** никогда не читать файл, который не будет использован; предпочитать функции/сигнатуры вместо полного кода; всегда включать тест‑файл для каждой модификации. (стр. 183)  

- **Анти‑паттерн:** чтение целых файлов, когда нужна только функция (стр. 184).  

### 5. Шаблоны системных промптов (стр. 184‑185)  

| Тип задачи | Шаблон (коротко) |
|---|---|
| Bug‑fix | `BUG_FIX_PROMPT` – сначала написать failing‑test, потом минимальное исправление, запуск всех тестов. |
| Feature | `FEATURE_PROMPT` – читаем архитектуру, соблюдаем конвенции, пишем тесты, обновляем доку. |
| Refactor | `REFACTOR_PROMPT` – запуск тестов до начала, небольшие инкрементные изменения, откат при падении. |

Каждый шаблон включает **правила** (номерованные) и **контекст‑файлы** (`{context}`).  

### 6. Кейc‑стади : Claude Code (стр. 185‑186)  

1. **Incremental context expansion** – начинает с карты проекта, читает файлы по мере надобности.  
2. **Search‑and‑replace editing** – генерирует операции «найти‑заменить».  
3. **Test‑driven iteration** – после каждой группы изменений запускает тесты и корректирует только провалившиеся части.  
4. **Self‑imposed limits** – следит за токен‑бюджетом, суммирует раннее содержание.  

- **Лимит итераций:** после 3‑х неудачных попыток отчитывается, а не зацикливается (стр. 186).  

### 7. Scored Walkthrough 14.1 – Агент‑исправитель багов (стр. 186)  
- **5‑фазный цикл:** парсинг бага → локализация → тест‑first → минимальное исправление → проверка всех тестов (максимум 3 revision).  

### 8. Scored Walkthrough 14.2 – Большие монорепозитории (стр. 186‑187)  
- **Три адаптации:**  
  1. Таргетированный сбор контекста (AST‑поиск, граф зависимостей).  
  2. Инструмент *codebase map* (структура, границы модулей).  
  3. Search‑and‑replace вместо whole‑file.  

### 9. Scored Walkthrough 14.3 – Выбор стратегии редактирования (стр. 187‑188)  
- При массовом переименовании (47 файлов) использовать **search‑and‑replace с AST‑осведомлённостью** вместо полного перезаписывания.  

### 10. Принцип «Test‑First» (стр. 188)  
- **Главная мысль:** писать тест до исправления гарантирует, что баг действительно устранён и создаёт регрессионный тест бесплатно.  

### 11. Production Tip (стр. 188)  
- При трёх неудачных попытках **добавлять полный дифф** в контекст следующей итерации – уменьшает повторные ошибки с 70 % до < 20 %.

### 13. Кейc‑стади : Cursor автокомплит (стр. 190)  
- **4‑этапный микролуп:** (1) сбор контекста ≈ 50 мс, (2) классификация интента ≈ 20 мс, (3) генерация ≈ 200‑400 мс (fast‑model Haiku‑class + speculative decoding), (4) фильтрация ≈ 30 мс (парсинг, тип‑проверка, существование символов).  
- **Оптимизационный вывод:** экономия 50 мс и $0.001 за запрос критична при > 100 запросов/минуту.  

**Где пригодится:** При построении собственного код‑генератора, авто‑рефакторинга, автодокументирования, CI‑агентов, а также в инструментальных сценариях (Git‑hooks, PR‑боты).
