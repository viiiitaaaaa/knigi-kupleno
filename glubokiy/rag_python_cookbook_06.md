## 1. Поиск в IVF‑индексе (стр. 186‑186)

- **Главная мысль** – При поиске в IVF‑индексе сначала находят ближайший центр (центроид) раздела, а затем ищут ближайший вектор внутри этого раздела; однако соседний раздел может содержать более близкий объект.
- **Как делать**
  1. Найти центр (centroid) самого близкого раздела (partition).  
  2. Внутри найденного раздела сравнить запрос‑вектор с векторами‑данными (обычно через метрику `<=>` – расстояние).  
  3. Выбрать вектор с минимальным расстоянием как «nearest neighbor».  
  4. При желании можно проверить границы соседних разделов (необязательно, обычно игнорируется).
- **Правила и числа**
  - Точность – небольшая потеря по сравнению с полной переборкой, но ускорение – значительное (стр. 186).  
- **Шаблоны и примеры** – На рисунке 6‑11 показан запрос (синий пункт) и поиск внутри выбранного раздела.  
- **Ошибки и предупреждения** – Возможна ошибка, если нужный вектор лежит в соседнем разделе, близко к границе (стр. 186).  
- **Где нам пригодится** – При построении быстрых векторных поисков в PostgreSQL (pgvector) или в FAISS, когда нужны компромиссы между скоростью и точностью.

## 2. HNSW‑индекс (стр. 186‑187)

- **Главная мысль** – HNSW = многослойный граф, где верхний слой — «монаполосные» «автосети», а нижний слой — плотные локальные связи; такой граф даёт быстрый поиск как «шорткаты» (высокие слои) и детальную навигацию (нижние слои).
- **Как делать** (концептуально)
  1. Построить несколько слоёв графа; каждый слой имеет всё меньше узлов, но с более «длинными» ребрами.  
  2. При запросе стартовать с верхнего слоя, где перемещаемся большими шагами, потом спускаться к деталям.  
- **Правила и числа** – Когда‑то сравнивают с национальной дорожной картой: верхний слой – “highways”, нижний – “city streets” (рис. 6‑12).  
- **Шаблоны и примеры** – На рисунке 6‑12 визуализирована иерархия слоёв.  
- **Ошибки и предупреждения** – Никаких конкретных в тексте; просто помнить, что HNSW требует больше памяти, чем простые IVF‑центроиды.  
- **Где нам пригодится** – При работе с pgvector (поддержка HNSW), FAISS, Milvus, когда нужен более точный поиск в больших пространствах.

## 3. Гибридный поиск (ключевые слова + семантика) (стр. 188‑190)

### 3.1 Общая идея (стр. 188‑188)

- **Главная мысль** – Объединить полнотекстовый (keyword) поиск и векторный (semantic) поиск в один набор результатов, используя взвешенное суммирование их оценок.
- **Как делать** (полный процесс)
  1. **Подготовка таблицы**  
     ```sql
     DROP TABLE IF EXISTS test_embedding_table;
     CREATE TABLE test_embedding_table AS
       SELECT *, to_tsvector(text_chunk) AS tsv
       FROM job_description_table;
     ```  
  2. **Получить embedding запроса** через OpenAI (модель `text-embedding-3-small`).  
  3. **Запустить один SQL‑запрос**, который одновременно считает:  
     - `text_score` = `ts_rank(tsv, plainto_tsquery('PostgreSQL'))` – оценка полнотекстового поиска;  
     - `vector_score` = `1 - (embedding <=> query_embedding)` – косинусное сходство (чем ближе → больше);  
     - `hybrid_score` = `text_score*0.5 + vector_score*0.5` (вес 0,5/0,5) – итоговая комбинированная оценка.  
  4. **Фильтрация** – `WHERE tsv @@ plainto_tsquery('PostgreSQL')` (только документы, содержащие ключевые слова).  
  5. **Сортировка** – `ORDER BY hybrid_score DESC` и `LIMIT 10`.  
  6. **Получить результаты** через `cur.fetchall()`.  
- **Правила и числа**
  - Вес keyword = 0.5, вес вектор = 0.5 (стр. 189).  
  - При необходимости изменить, например 0.7 / 0.3 (стр. 189).  
- **Шаблоны и примеры** – Пример SQL‑запроса (стр. 189‑190) и вывод `hybrid_score`.  
- **Ошибки и предупреждения**  
  - Плохой полнотекстовый индекс ухудшит гибридный результат (стр. 190).  
  - Не использовать гибридный поиск, если смысл запроса важнее точных слов (стр. 190).  
- **Где нам пригодится** – В проектах, где нужны и точные совпадения терминов (юриспруденция, мед‑записи, техническая документация), и семантическое совпадение (стр. 190).

### 3.2 Когда использовать/не использовать (стр. 190‑190)

- **Подходит** – юридические тексты, тех. документация, медицинские записи, запросы с именами собственными/сокращениями.  
- **Не подходит** – разговорные запросы, общие знания, если индекстекст плох.

## 4. Техника 7.1 – Метаданные‑фильтрация (стр. 191‑198)

- **Главная мысль** – Хранить метаданные (например, тему — «football», «tennis») рядом с embedding‑ами; перед векторным поиском отфильтровать строки по этим метаданным, тем самым сузив пространство поиска.
- **Как делать**
  1. **Создать расширение и таблицу**  
     ```sql
     CREATE EXTENSION IF NOT EXISTS vector;
     CREATE TABLE embeddings_table_with_metadata (
       id SERIAL PRIMARY KEY,
       text_chunk TEXT,
       embedding VECTOR(1536),
       metadata JSONB
     );
     ```  
  2. **Заполнить таблицу**: для каждой строки сформировать embedding через OpenAI, добавить метаданные (JSON `{"topic":"tennis"}` и т.п.).  
  3. **Сформировать запрос**:  
     ```sql
     SELECT text_chunk,
            1 - (embedding <=> %s::vector) AS similarity
     FROM embeddings_table_with_metadata
     WHERE metadata->>'topic' = %s
     ORDER BY similarity DESC
     LIMIT 5;
     ```  
  4. **Передать параметры** – `query_embedding` и `topic_filter` (например `'football'`).  
  5. **Получить результаты** (см. рис. 7‑5).  
- **Правила и числа**  
  - Размер embedding = 1536 (стр. 195–196).  
  - В примере ограничение `LIMIT 5` (стр. 197).  
- **Шаблоны и примеры** – Код Python + SQL (стр. 196‑197).  
- **Ошибки и предупреждения**  
  - Не использовать, если данные однородны по теме или нет метаданных (стр. 198).  
  - Сбор метаданных требует усилий, но дает более лёгкую оценку (стр. 198).  
- **Где нам пригодится** – При сегментации пользователей/контента (спорт, продукты, темы), когда запрос неоднозначен без контекста (стр. 194‑197).

## 5. Техника 7.2 – HyDE (Hypothetical Document Embeddings) (стр. 198‑187)

- **Главная мысль** – Сначала LLM генерирует «гипотетические» документы, стилистически похожие на ваш корпус, а затем эти гипотетические тексты встраиваются и используются для поиска настоящих документов.
- **Как делать**
  1. **Получить запрос** от пользователя.  
  2. **Сгенерировать N гипотетических документов** с помощью LLM (prompt см. стр. 200).  
  3. **Определить схему ответа** через Pydantic (`class HypotheticalDocuments(BaseModel): documents: list[str]`).  
  4. **Вызвать LLM** (`gpt-5-mini`, `client.beta.chat.completions.parse`) – получить список гипотетических текстов.  
  5. **Получить embeddings** этих гипотетических документов (OpenAI `text-embedding-3-small`).  
  6. **Поиск в векторной базе** с этими embedding‑ами → возврат реальных документов.  
  7. **Не включать гипотетические документы в финальный запрос**; использовать только найденные реальные.
- **Правила и числа**
  - Кол‑во гипотез = 3 (стр. 200).  
  - Пример модели = `gpt-5-mini` (стр. 200).  
  - Установка: `pip install openai pydantic` (стр. 200).  
- **Шаблоны и примеры** – Prompt в стр. 202, пример гипотетических документов (рис. 7‑7).  
- **Ошибки и предупреждения**  
  - Гипотетический текст может быть неверным → привести к плохим результатам (стр. 187).  
  - Не использовать, если стилистика запросов уже совпадает со стилем корпуса или если дополнительная задержка/стоимость неприемлемы (стр. 187).  
- **Где нам пригодится** – При разнице стиля запросов и документов (напр., пользователи задают «как починить машину», а база содержит «автомобильный сервисный бюллетень»), когда нужен «стилевой мост» (стр. 186‑187).

## 6. Техника 7.3 – Multi‑query Retrieval (стр. 188‑191)

- **Главная мысль** – Одному запросу сопоставить несколько альтернативных формулировок, выполнить векторный поиск по каждому и объединить результаты, тем самым повышая полноту (recall).
- **Как делать**
  1. **Сгенерировать 2‑3 альтернативные формулировки** из исходного запроса (LLM, prompt см. стр. 204).  
  2. **Для каждой формулировки выполнить векторный поиск** (по отдельности).  
  3. **Объединить все найденные документы** (слияние, потом‑можно ранжировать).  
  4. **Передать объединённый набор LLM‑модели** для генерации окончательного ответа.  
- **Правила и числа**
  - Кол‑во вариантов ≈ 3 (стр. 204).  
  - В примере 4 поисковых запросов (3 варианта + оригинальный) (стр. 205).  
- **Шаблоны и примеры** – Prompt в стр. 204, вывод (рис. 7‑9).  
- **Ошибки и предупреждения**  
  - Увеличивает latency и стоимость почти в N‑раз (стр. 205).  
  - Не применять, если запрос уже узко‑специфичен или лимит по времени строг (стр. 205).  
- **Где нам пригодится** – При широких, неоднозначных вопросах (например, “польза возобновляемой энергии”), когда нужно покрыть несколько аспектов (стр. 205).

## 7. Техника 7.4 – Система маршрутизации запросов (Query Routing) (стр. 206‑209)

- **Главная мысль** – Автоматически определять, какой из нескольких источников данных (векторный магазин, SQL‑БД, API и т.п.) лучше всего отвечает на конкретный запрос, и направлять запрос именно туда.
- **Как делать**
  1. **Определить список доступных «инструментов»** (функций) — каждый представляет отдельный источник (football‑vector, tennis‑vector, SQL‑football‑results).  
  2. **Создать схему Pydantic**, ограничив вывод лишь названием выбранного источника (`Literal[...]`).  
  3. **Сформировать системный prompt** (стр. 207‑208) – попросить LLM выбрать лучший источник для конкретного вопроса.  
  4. **Вызвать LLM** (`gpt-5-mini`) с запросом пользователя; получить строку‑метку (`data_source`).  
  5. **На основании метки выполнить соответствующую функцию** (`search_vector_db`, `query_sql_db` и т.д.).  
- **Правила и числа**
  - Установка зависимостей: `pip install openai pydantic` (стр. 207).  
  - В примере 3 источника (`Literal["general_football_knowledge","general_tennis_knowledge","latest_football_results_sql"]`) (стр. 208).  
- **Шаблоны и примеры** – Код `RouterDecision` и пример вывода (рис. 7‑11).  
- **Ошибки и предупреждения**  
  - Добавляет latency ≈ 0.5‑2 сек. (стр. 195).  
  - Не нужен, если есть только один источник (стр. 195).  
  - При сильной неоднозначности классификация может падать (стр. 195).  
- **Где нам пригодится** – Когда у вас несколько баз (векторные, SQL, внешние API) и запросы явно различаются (стр. 206‑209).

## 8. Техника 7.5 – Авто‑слияние (Auto‑Merging Retriever) (стр. 211‑214)

- **Главная мысль** – Хранить мелкие «leaf»‑чункты (≈250 символов) и их родительские «parent»‑чункты (≈1 000 символов). При поиске по leaf‑чункам, если ≥ 2 leaf‑чунка из одного parent‑чунка попали в топ‑результаты, возвращать весь parent‑чунк, давая LLM больше контекста.
- **Как делать**
  1. **Разбить документ**:  
     - `leaf_node_size = 250` символов;  
     - `parent_merge = 4` leaf‑чунков → один parent‑чунк (≈1 000 символов).  
  2. **Создать таблицу** (стр. 212) с полями: `leaf_node_id`, `leaf_chunk`, `parent_node_id`, `parent_chunk`, `leaf_chunk_embedding VECTOR(1536)`.  
  3. **Заполнить таблицу**: для каждого leaf‑чунка вычислить embedding (OpenAI `text-embedding-3-small`) и вставить.  
  4. **Поиск**: выполнить векторный поиск по `leaf_chunk_embedding`.  
  5. **Подсчёт совпадений**: если у какого‑то `parent_node_id` найдено более 2 leaf‑чунков в топ‑результатах, запросить `parent_chunk` и отдать его LLM.  
- **Правила и числа**
  - `leaf_node_size = 250` (стр. 212).  
  - `parent_merge = 4` → `parent_node_size = 1000` (стр. 212).  
  - Порог «два» leaf‑чунка для слияния (стр. 199).  
- **Шаблоны и примеры** – Фрагмент кода создания таблицы и вставки (стр. 212‑213).  
- **Ошибки и предупреждения**  
  - Не использовать, если документы плоские без иерархии (стр. 214).  
  - Увеличивает объём хранилища (двойной набор‑чунков).  
- **Где нам пригодится** – Книги, исследования, руководства с чёткой иерархией (главы/разделы), когда отдельные чунки часто требуются вместе (стр. 214).

## 9. Техника 7.6 – Окно‑предложений (Sentence Window Retriever) (стр. 215‑217)

- **Главная мысль** – После нахождения релевантного небольшого чунка (≈250 токенов) добавить к нему несколько соседних чунков (пред- и пост‑чунки) для передачи LLM более полной контекстной информации.
- **Как делать**
  1. **Создать таблицу** с полями `chunk_id SERIAL`, `chunk TEXT`, `chunk_embedding VECTOR(1536)`; обеспечить, чтобы `chunk_id` возрастает в порядке появления в оригинальном документе (стр. 216).  
  2. **При загрузке** разбить документ на чунки одинаковой длины (≈250 токенов).  
  3. **Запрос**: найти наиболее похожий чунк (по embedding).  
  4. **Определить окно** – взять N чунков до и после найденного (обычно N = 1, можно 2).  
  5. **Объединить их** (≈750 токенов) и передать в LLM.  
- **Правила и числа**
  - Окно обычно = 3 чунка (основной + по одному с обеих сторон) (рис. 7‑15).  
  - Чанк‑размер ≈ 250 токенов (стр. 216).  
- **Шаблоны и примеры** – Рис. 7‑14 и 7‑15 иллюстрируют процесс.  
- **Ошибки и предупреждения**  
  - Не использовать, если чунки уже большие (> 500 токенов) или если документы «FAQ» (самостоятельные ответы) (стр. 217).  
  - Увеличивается размер промпта (стр. 217).  
- **Где нам пригодится** – Юридические тексты, технические руководства, нарративные документы, где важен контекст вокруг ключевых предложений (стр. 216‑217).

## 10. Техника 7.7 – Перепозиционирование (Reranking) (стр. 218‑205)

- **Главная мысль** – После объединения результатов из разных источников (мультимодельные запросы, HyDE, Multi‑query, инструменты) выполнить дополнительный LLM‑ранжирующий проход, который оценивает релевантность каждого документа и оставляет топ‑N.
- **Как делать**
  1. **Собрать все найденные документы** в один список (стр. 218).  
  2. **Сформировать prompt**: перечислить документы, задать вопрос, запросить оценки релевантности от 1 до 5 (стр. 219).  
  3. **Вызвать LLM‑ранжер** (OpenAI, `gpt‑5‑mini`) с Pydantic‑схемой для получения структурированного ответа.  
  4. **Отсортировать по оценкам** и, при желании, оставить только лучшие N (часто 3) для финального промпта.  
- **Правила и числа**
  - Оценка от 1 до 5 (стр. 219).  
  - Пример: остаёмся с топ‑3 после ранжирования (стр. 205).  
- **Шаблоны и примеры** – Prompt в стр. 219, вывод (рис. 7‑17).  
- **Ошибки и предупреждения**  
  - Добавляет задержку (очередной LLM‑вызов) и стоимость (стр. 205).  
  - Не использовать, если уже получен достаточный recall и критерий качества удовлетворён (стр. 205).  
- **Где нам пригодится** – Когда совокупный набор результатов большой/шумный (мульти‑запросы, HyDE, агентные системы) и нужен отбор действительно полезных фрагментов перед генерацией (стр. 205).
