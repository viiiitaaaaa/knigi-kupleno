## Оценка мульти‑модальных агентов с помощью **AgentVista** (стр. —)  

### Главная мысль  
Оценка агентов должна выходить за рамки простого сравнения финального вывода: нужно измерять, какие инструменты использовались, сколько ходов потребовалось и как изменялась траектория взаимодействия. Такие «рабочие» метрики дают реальную основу для выбора модели, изменения системы и решений о релизе.  

### Как делать (пошагово)  

1. **Подготовить список моделей** (`MODELS`).  
2. **Для каждой модели**:  
   1. Заменить символ «/» в названии модели на «__», получив `safe_name`.  
   2. Сформировать путь к каталогу вывода `output_dir = os.path.join(BASE_OUTPUT_DIR, safe_name)`.  
   3. Создать каталог, если его ещё нет: `os.makedirs(output_dir, exist_ok=True)`.  
3. **Скопировать текущие переменные окружения** в `env` и задать имена моделей для рассуждения и верификации:  
   ```python
   env["REASONING_MODEL_NAME"] = model_name
   env["VERIFIER_MODEL_NAME"] = model_name
   ```  
4. **Сформировать команду запуска `infer.py`** со следующими параметрами:  
   ```python
   cmd = [
       "python", "infer.py",
       "--input-file", INPUT_FILE,
       "--image-folder", IMAGE_FOLDER,
       "--output-dir", output_dir,
       "--max-turns", "10",           # максимум 10 диалоговых ходов
       "--max-images", "20",          # максимум 20 изображений за задачу
       "--max-total-tokens", "24000",# предел общего количества токенов
       "--skip-completed",           # пропустить уже завершённые задачи
   ]
   ```  
5. **Запустить команду** (в ноутбуке обычно через `subprocess.run(cmd, env=env)` — не показано в тексте).  
6. После завершения **просмотреть созданный каталог** `agentvista_multi_model_runs`:  
   - файлы метрик (кол‑во ходов, использованные инструменты и т.п.);  
   - траектории (полные журналы взаимодействия).  
7. **Сравнить результаты** всех моделей при помощи вспомогательной функции из ноутбука. В примере лучшей оказалась модель GPT 5.4.  

### Правила и числа (стр. —)  

| Параметр | Значение | Примечание |
|----------|----------|------------|
| `--max-turns` | **10** | Ограничение количества диалоговых ходов. |
| `--max-images`| **20** | Максимум изображений, которые агент может загрузить за одну задачу. |
| `--max-total-tokens`| **24000** | Общий лимит токенов (ввод + вывод) для всех ходов. |
| `--skip-completed`| **установлено** | Не пересчитывать уже завершённые запросы. |
| `os.makedirs(..., exist_ok=True)`| **True** | Создаёт каталог, если его нет, без ошибки. |

### Шаблоны и примеры  

* **Шаблон названия каталога вывода**  
  ```python
  safe_name = model_name.replace("/", "__")
  output_dir = os.path.join(BASE_OUTPUT_DIR, safe_name)
  ```  

* **Пример команды** (из кода выше) – полностью готовый `cmd`‑список.  

* **Функция сравнения** – упомянута в ноутбуке, детали не раскрыты, но её цель — агрегировать метрики по всем моделям.  

### Ошибки и предупреждения  

| Возможная проблема | Как избежать |
|--------------------|--------------|
| Не создался каталог вывода → `FileNotFoundError` | Обязательно вызвать `os.makedirs(..., exist_ok=True)` перед запуском. |
| Превышение лимита токенов → отклонение запросов LLM | Следить за `--max-total-tokens` = 24000; при необходимости уменьшить. |
| Неучтённые уже завершённые задачи → двойные подсчёты | Оставьте `--skip-completed`, иначе результаты будут смещены. |
| Неправильные пути к `INPUT_FILE`/`IMAGE_FOLDER` | Проверяйте существование файлов/папок перед запуском. |

### Где нам пригодится  

- **Запросы**: формировать метрики для разных моделей перед их внедрением.  
- **Проверка**: регрессионный тестинг изменений в пайплайне (промпты, оркестрация).  
- **Память**: хранить траектории, чтобы потом проанализировать «почему» ошиблись.  
- **Помощники**: автоматизированный скрипт для сравнения новых вариантов моделей.  
- **Данные**: использовать полученные метрики как часть обучающего набора для мета‑модели, выбирающей лучшую стратегию.  
- **Учёба**: пример практического построения benchmark‑suite из реального продакшн‑трафика.

## Заключение (стр. —)  

### Главная мысль  
Переходим от случайного наблюдения к систематической, воспроизводимой оценке поведения агентов: превращаем продакшн‑трейсы в benchmark‑кейсы, комбинируем детерминистические проверки с LLM‑оценкой открытых задач, и строим регрессионные воркфлоу для сравнения моделей, промптов и изменений оркестрации ещё до их деплоя.  

### Как делать (ключевые шаги)  

1. **Собрать продакшн‑трейсы** → превратить в набор входных файлов.  
2. **Запустить детерминистические проверки** (правильные шаги, вызванные инструменты).  
3. **Запустить LLM‑оценку** открытых задач (качество ответа, соответствие инструкциям).  
4. **Свести сигналы в единую оценку** (метрики, ранжирование).  
5. **Построить регрессионный воркфлоу**: при каждом изменении модели/промпта сравнивать новые результаты с базой.  
6. **Для кодирующих агентов** добавить тесты из собственного репозитория в benchmark; результат — «проходит / не проходит», а не субъективная оценка.  
7. **Для мульти‑модальных и долгих задач** анализировать траектории, а не только финальный успех.  

### Правила и числа (стр. —)  

- **Не использовать только spot‑check** (периодические, случайные проверки) — они дают слабую основу.  
- **Регрессия** должна запускаться после **каждого** изменения кода/промпта.  

### Шаблоны и примеры  

- **Benchmark‑case** – файл с полным диалогом (вход, инструменты, ответы).  
- **Regression‑report** – таблица: модель | промпт | метрика | примечание.  

### Ошибки и предупреждения  

- **Слишком малый набор тестов** → не обнаружит скрытых regressions.  
- **Оценка только по финальному выводу** → упускает ошибки в промежуточных шагах, особенно в мульти‑модальных сценариях.  

### Где нам пригодится  

- **Запросы**: быстро проверять новые идеи/промпты перед их внедрением.  
- **Проверка**: автоматический CI‑pipeline для агентов.  
- **Память**: сохранять результаты, чтобы видеть деградацию со временем.  
- **Помощники**: Claude может генерировать новые benchmark‑кейсы из логов.  
- **Данные**: собранные метрики служат обучающим сигналом для meta‑модели.  
- **Учёба**: пример полного цикла оценки от сбора логов до регресс‑отчётов.
