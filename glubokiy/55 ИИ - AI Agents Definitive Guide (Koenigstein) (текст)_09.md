## Часть 15. Глава 8 — Оценка и наблюдение за агентными системами (стр. —)

### 1. Введение — «Оценка и наблюдение» (стр. —)  
- **Главная мысль** – Оценка нужна уже на этапе разработки: раннее тестирование позволяет обнаружить слабости до того, как они превратятся в дорогостоящие баги в продакшене.  
- **Как делать**  
  1. Делим цикл оценки на три уровня: публичные бенчмарки → поведенческий стресс‑тест → кастомные бенчмарки.  
  2. Проводим два параллельных трека: *поведенческий* и *угрозный* (вредоносный).  
  3. После деплоя продолжаем мониторинг и превращаем наблюдения в новые кастомные тесты.  

---

### 2. Публичные бенчмарки (стр. —)  
- **Главная мысль** – Позволяют быстро сравнить модели по «универсальным» способностям (логика, код, работа с инструментами).  
- **Правила** – Бенчмарк — только первый сигнальный шаг; не гарантирует стабильную работу в вашем конкретном пайплайне.  

---

### 3. Оценка (Evaluation) (стр. —)  
- **Главная мысль** – После того как модель интегрирована в агентную архитектуру, нужно измерять её реальное поведение: трассировать действия, фиксировать провалы, искать отклонения.  
- **Как делать**  
  1. Собирать логи выполнения (модельный вывод, вызовы инструментов, статус запросов).  
  2. Анализировать метрики (latency, token usage, tool‑calls).  
  3. Выявлять «неожиданное» поведение, которое не проявилось в публичных тестах.  

---

### 4. Кастомные бенчмарки (Custom benchmarking) (стр. —)  
- **Главная мысль** – На основе выводов из оценочного трека формируются задачи, отражающие ваш бизнес‑контекст (доменные edge‑кейсы, специфические ошибки).  
- **Как делать**  
  1. Описать набор сценариев, отражающих ваш процесс (типы запросов, особые условия).  
  2. Использовать их для регресс‑тестов при изменении моделей, промптов, инструментов.  

---

### 5. Стресс‑тестирование перед деплоем (Evaluation Before Deployment) (стр. —)  
- **Главная мысль** – Публичные бенчмарки не дают полной картины; нужно проверять модель в точных условиях вашего пайплайна.  
- **Ошибка** – Положиться только на общие бенчмарки → ложное чувство уверенности.  

---

### 6. Ложное чувство уверенности (False Confidence) (стр. —)  
- **Главная мысль** – Хорошие результаты на публичных наборах не гарантируют надёжность в вашем сценарии, потому что модель и система **вероятностны**.  
- **Предупреждение** – Не откладывайте проверку на «позднюю» стадию: архитектурные ошибки могут уже быть внедрены.  

---

### 7. Два ранних трека оценки (таблица 8‑1) (стр. —)  

| Трек | Фокус | Типичные инструменты | Что измеряется |
|------|-------|----------------------|----------------|
| **Поведенческий стресс‑тест** | Реальные рабочие сценарии, edge‑кейсы | Наборы сценариев + harness + эксперты‑домены | Правильность поведения, покрытие, отсутствие нелепых выводов |
| **Раннее тестирование на угрозы** | Безопасность, уязвимости | Red‑teaming‑фреймворки, адверсариальные промпты, чек‑лист OWASP | Пробой защита от инъекций, превышения прав, опасных вызовов инструментария |

---

### 8. Поведенческий стресс‑тест: ролевая игра (стр. —)  
- **Главная мысль** – Начинаем с набора «ожидаемых» пользовательских запросов и целевых ответов; при отсутствии готового датасета генерируем его через LLM и проверяем экспертами.  
- **Шаги**  
  1. **Собрать/создать** набор сценариев (можно автоматически генерировать).  
  2. **Определить** критерии оценки (правила, метрики).  
  3. **Имплементировать** лёгкий harness (см. ниже).  
  4. **Запускать** сценарии массово, собирать результаты.  
  5. **Отдавать** их на рецензию экспертам (SME).  
- **Где пригодится** – При построении MVP, быстрой проверки промптов и инструментов.

### 9. Как писать эффективные сценарии оценки (стр. —)  

| Аспект | Что делать |
|--------|------------|
| **Ясно определить успех** | Описать, какой результат считается правильным (формат, ограничения). |
| **Учесть edge‑кейсы** | Включить неясные, спорные, стрессовые запросы. |
| **Персоны** | Указать, кто пользователь, его уровень знаний, настроение. |
| **Поток диалога** | Описать не один запрос, а последовательность ходов (уточнения, эскалация, восстановление). |

**Шаблон сценария** (просто пример):  
```
Persona: Технический специалист, раздражённый (эмоция = frustration)  
Goal: Получить инструкцию по возврату товара.  
Stress dimension: ambiguity (недостаток информации).  
Expected flow: 1) запрос → уточнение → 2) предоставление политики возврата → 3) подтверждение действия.
```

#### Таблица 8‑2 — Стресс‑измерения (примерные)

| Стресс‑измерение | Пример |
|-------------------|--------|
| Срочность | Пользователь требует ответ «сейчас». |
| Неоднозначность | Не хватает ключевой информации, нужен уточняющий вопрос. |
| Эмоциональное раздражение | Пользователь злится, требует быстрого решения. |
| Несоответствие знаний | Пользователь неверно понимает ограничения системы. |
| Враждебный замысел | Пользователь пытается обойти ограничения. |

### 10. Пример кода — структурный harness (стр. —)  

#### 10.1 Схемы входов/выходов (пример 8‑1)  

```python
class TicketScenario(BaseModel):
    scenario_id: str
    ticket_text: str
    product: str
    priority: str = "normal"
    stress_dimension: str = "ambiguity"
    required_terms: List[str] = []
    scenario_group_id: Optional[str] = None
    candidate_id: int = 0

class TicketOutput(BaseModel):
    category: str
    urgency: str
    summary: str
    root_cause_hypothesis: str
    resolution_steps: List[str]
    customer_reply: str
```

#### 10.2 Правила проверки стресс‑измерений (пример 8‑2)  

```python
def stress_dimension_violation(output, stress_dim):
    text = " ".join([output.summary,
                     output.customer_reply,
                     " ".join(output.resolution_steps)]).lower()
    if stress_dim == "urgency":
        return 0 if output.urgency.lower() in {"high", "critical"} else 1
    if stress_dim == "ambiguity":
        markers = ["clarify","please provide","which","could you share"]
        return 0 if any(m in text for m in markers) else 1
    # … (другие измерения)
    return 0
```

#### 10.3 Генерация одного сценария (пример 8‑3) – **Шаги**  
1. Захватить семафор (ограничение конкуренции).  
2. Сформировать `user_prompt` из полей `TicketScenario`.  
3. Вызвать агент (`await agent.ainvoke`).  
4. Преобразовать ответ в `TicketOutput` (валидация схемы).  
5. Вычислить детерминированный скор (например, покрытие ключевых слов).  
6. Вычислить `stress_violation`.  
7. Вернуть словарь с полным набором метрик (время, скоры, ошибки).  

#### 10.4 Параллельный запуск и батч‑скейлинг (пример 8‑4)  

- **Параметры из текста**: `concurrency = 4`, `score_batch_size = 3`.  
- **Алгоритм**  
  1. Создать `asyncio.Semaphore(concurrency)`.  
  2. Запустить все `generate_one`‑задачи асинхронно.  
  3. По мере завершения обновлять прогресс‑колбэк.  
  4. Отфильтровать успешные результаты, разбить на батчи `score_batch_size`.  
  5. Вызвать `judge_batch` (LLM‑оценка) для каждого батча.  
  6. Скомбинировать детерминированный скор (40 %) и LLM‑скор (60 %) → `final_score`.  

#### 10.5 Экспорт трасс (пример 8‑5)  

```python
def add_rtturn_trace_columns(df):
```

### 11. Ошибки и предупреждения при стресс‑тесте  

| Ошибка | Предупреждение |
|--------|----------------|
| Тестировать только один сценарий | Не охватывает вариативность реального потока. |
| Писать сложные правила оценки | Трудно поддерживать, вводит субъективность. |
| Не ограничивать конкурентность | Может «перегрузить» модельный эндпоинт и исказить результаты. |
| Игнорировать операторные метрики (latency, cost) | Скрывает экономические проблемы. |

### 12. Раннее тестирование на угрозы (Early Threat Testing) (стр. —)  

- **Главная мысль** – Нужно проверять безопасность уже на этапе разработки, иначе уязвимости могут стать частью архитектуры.

#### 12.6 Callback‑функция с `RTTurn` (пример 8‑10)  

```python
def model_callback(attack_input: str):
    final_state = agent.invoke({
        "messages":[HumanMessage(content=attack_input)],
        "tool_budget":2,
        "approved_email":False,
        "executed_tools":[],
        "blocked_tools":[],
    })
    final_text = extract_final_text(final_state["messages"])
    executed = final_state.get("executed_tools", [])
    blocked   = final_state.get("blocked_tools", [])
    return RTTurn(
        role="assistant",
        content=final_text,
        tools_called=[ToolCall(name=n) for n in executed] +
                     [ToolCall(name=f"BLOCKED::{n}") for n in blocked]
    )
```

- **Зачем** – Позволяет увидеть в трассе *скрытые* вызовы инструментов (выполненные, но заблокированные).  

#### 12.7 Обнаружение «пассивных» провалов  

> Если агент пишет «не могу получить политику», но в трассе видно, что `search_kb` был вызван, значит нарушение *least‑privilege* (агент попытался, но был остановлен).  

#### 12.8 Запуск проверки ASI02 (пример 8‑11)

```python
    framework=OWASP_ASI_2026(categories=["ASI_02"]),
    attacks_per_vulnerability_type=1,

```

#### 12.9 Ошибки/предупреждения при red‑тестах  

| Ошибка | Предупреждение |
|--------|----------------|
| Не использовать `RTTurn` | Пропустите скрытые действия, оценка будет неполной. |
| Оставлять `tool_budget` слишком высоким | Возможна бесконечная рекурсия вызовов. |
| Не проверять `blocked_tools` | Не увидите, что защита сработала, но агент всё‑таки попытался. |

### 13. Пост‑деплоймент оценка (Post‑Deployment Evaluation) (стр. —)  

- **Главная мысль** – После выпуска система сталкивается с неожиданными запросами; необходимо непрерывно собирать метрики и превращать их в новые кастомные тесты.  
- **Ключевые сигналы** (таблица 8‑6)  

| Сигнал | Почему важен |
|--------|----------------|
| Latency / response time | Выявление медленных вызовов инструментов, узких мест. |
| Token usage & cost | Предотвращение «runaway»‑циклов и внезапных расходов. |
| Tool usage patterns | Обнаружение избыточных или ошибочных вызовов. |
| Execution traces | Поиск ошибок в рассуждениях и оркестрации. |
| Sessions / multi‑turn flows | Анализ дрейфа намерений, эскалаций. |
| User segmentation | Определение групп, генерирующих сбои. |
| User feedback | Прямой показатель качества ответа. |
| Human annotation | Создание новых наборов данных из реального поведения. |

- **Как применять**  
  1. Подключить платформу наблюдения (Langfuse, LangSmith, либо OpenTelemetry‑совместимую).  
  2. Настроить алерты по порогам latency / cost.  
  3. Периодически экспортировать трассы, генерировать новые сценарии и запускать их в «custom benchmark»‑цикле.

## Краткие рекомендации для единоличного предпринимателя  

| Задача | Где применить из этой части |
|--------|------------------------------|
| **Быстрая проверка модели в своем пайплайне** | Публичные бенчмарки → поведенческий стресс‑тест (Раздел 5‑8). |
| **Создание набора тестов для собственного продукта** | Шаблоны сценариев, таблица 8‑2 (Раздел 9). |
| **Автоматический запуск тысяч сценариев** | Асинхронный harness с `semaphore`, `score_batch_size` = 3 (Раздел 10). |
| **Проверка безопасности (инъекции, злоупотребление инструментами)** | OWASP ASI Top 10, DeepTeam, `RTTurn` (Раздел 12). |
| **Мониторинг в продакшене** | Сигналы из таблицы 8‑6, интеграция с LangSmith/Telemetry (Раздел 13). |
| **Оптимизация стоимости** | Трек «Token usage & cost», контекст‑прюнинг, квантизация (упомянуто в начале главы 7, но актуально здесь). |

---  

**Итого:**  
- Структурированный **harness** (определения схем, проверка стресс‑измерений, параллельный запуск, экспорт трасс) — основа раннего обнаружения ошибок.  
- **OWASP ASI Top 10** — чек‑лист, который следует прогонять через Red‑Team (DeepTeam) → получать отчёты о PASS/FAIL.  
- **Пост‑деплоймент** — постоянный цикл наблюдения, сбор метрик, обратная связь в кастомные бенчмарки.  

Следуя этим рекомендациям, вы сможете построить надёжный агентный сервис, который быстро выявляет и исправляет как **поведенческие** недостатки, так и **безопасностные** уязвимости, а также удерживает **операционные расходы** под контролем.
