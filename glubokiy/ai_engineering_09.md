## 1. Оценочный workflow (стр. 357‑358)

### Главная мысль  
Оценка модели – циклический четырёхшаговый процесс, позволяющий отсеять неподходящие варианты и постоянно улучшать модель в продакшене.

### Как делать  
1. **Фильтрация по жёстким атрибутам** – исключить модели, не удовлетворяющие обязательным требованиям (например, только API‑доступ, отсутствие возможности локального хостинга).  
2. **Отбор по публичной информации** – использовать бенчмарки и лидерборды, подбирая модели, которые могут сбалансировать качество, задержку и стоимость.  
3. **Эксперименты на своём пайплайне** – запустить собственные тесты, снова учитывая все цели (качество + латентность + цена).  
4. **Мониторинг в продакшене** – следить за сбоями, собирать обратную связь и переоценивать модель.

*Эти шаги повторяются, т.к. новые данные могут заставить вернуться к предыдущему пункту.*

### Правила и числа  
*Нет конкретных цифр, только упоминание, что 70 % успеха — разбиение задачи на два шага (стр. 357).*

### Шаблоны и примеры  
- **Figure 4‑5** (не в тексте) – визуальная схема четырёх шагов.  

### Ошибки и предупреждения  
- Не считать выбранную модель «финальной» – процесс итеративный.  
- Не игнорировать жёсткие атрибуты, иначе модель станет unusable в продакшене.

## 2. Build vs Buy: открытый vs коммерческий доступ (стр. 359‑363)

### Главная мысль  
Выбор между использованием **модельных API** (коммерческих) и **самостоятельным хостингом** открытых моделей резко ограничивает набор кандидатов и определяется лицензией, доступностью весов и вашими политиками.

### Как делать  

#### 2.1 Понять, что значит «open source»  
1. **Open weight** – весы модели публичны, но обучающие данные могут быть закрыты.  
2. **Open model** – весы + данные открыты.  

#### 2.2 Оценить лицензию  
Для каждой модели спросить:  
- Разрешено ли коммерческое использование?  
- Есть ли ограничения на количество активных пользователей (пример – Llama‑2 > 700 млн MAU требует отдельной лицензии)?  
- Можно ли использовать вывод модели для дальнейшего обучения/дистилляции?  

#### 2.3 Выбор инфраструктуры  
- **Model API** – инференс‑служба уже запущена; вы получаете готовый endpoint.  
- **Self‑hosted** – вы берёте на себя развёртывание, масштабирование, безопасность.  

### Правила и числа  
- **Llama‑2**: > 700 млн MAU → специальная лицензия (стр. 361).  
- **Mistral‑7B**: изначально не разрешал дистилляцию, позже изменил (стр. 361).  
- **Meta Llama‑2 / Llama‑3** – Community License Agreement (стр. 361).  

### Шаблоны и примеры  
| Тип модели | Пример лицензии | Ключевые ограничения |
|-----------|------------------|-----------------------|
| Open‑weight | Apache 2.0 (Gemma, Mistral‑7B) | Коммерческое использование разрешено, но проверить ограничения на до‑обучение. |
| Open‑model | Нет в текущем тексте (почти нет полностью открытых моделей). | Требует открытых данных. |
| Коммерческий API | OpenAI, Anthropic, Azure OpenAI | Доступ только через API, возможны ограничения на лог‑пробы, финетюнинг. |

### Ошибки и предупреждения  
- Путать **open source** и **open data** – лицензия может закрывать данные.  
- Не проверять **корректность лицензии** – может привести к юридическим рискам.

## 3. Семь осей выбора модели (стр. 364‑371)

### Главная мысль  
Решать, использовать API или хостить модель, нужно по **семи критериям**: приватность данных, происхождение данных, производительность, функциональность, стоимость, контроль и возможность запуска на устройстве.

### Как делать (по оси)

| Ось | Что проверять | Как измерять |
|-----|----------------|--------------|
| **Data privacy** | Можно ли отправлять данные наружу? Наличие политики использования пользовательских данных. | Пример – скандал Samsung → ChatGPT (стр. 364‑365). |
| **Data lineage & copyright** | Есть ли прозрачность тренировочных данных? Возможные юридические риски. | Проверить публикацию данных (пример – Google Gemini без раскрытия). |
| **Performance** | Сравнение по публичным бенчмаркам (MMLU, etc.). | Тренд: разрыв между открытыми и проприетарными моделями сокращается (стр. 367). |
| **Functionality** | Поддерживает ли API функции типа **function calling**, **structured outputs**, **log‑probs**? | Log‑probs часто скрыты у коммерческих API (стр. 369‑370). |
| **API cost vs engineering cost** | Сравнить цену за запрос с затратами на разработку и поддержку собственного инференса. | При больших объёмах API может стать дороже, чем self‑host. |
| **Control, access, transparency** | Возможность заморозить модель, видеть версии, менять ограничения. | Коммерческие модели часто меняются бесшумно (стр. 372‑374). |
| **On‑device deployment** | Требуется ли работа без интернета? | Только self‑host может работать офлайн (стр. 374‑376). |

### Правила и числа  
- **Latency**: мягкий атрибут, если вы можете оптимизировать модель; жёсткий – при использовании чужих API (стр. 357).  
- **Risk of losing access**: коммерческий API может исчезнуть (стр. 374‑376).  

### Шаблоны и примеры  
- **Table 4‑4** (стр. 375‑376) – сравнение «Model APIs» vs «Self‑hosting» по каждому из пунктов.  

### Ошибки и предупреждения  
- Переоценка **функциональности API** – могут отсутствовать важные возможности (log‑probs, finetuning).  
- Игнорировать **изменения в политике использования данных** (пример – Zoom 2023).

## 4. Навигация по публичным бенчмаркам (стр. 377‑384)

### Главная мысль  
Публичные бенчмарки – богатый, но **неполный и часто загрязнённый** источник. Нужно выбирать, агрегировать и понимать их корреляцию, иначе выбор модели будет ошибочным.

### Как делать  

1. **Собрать набор подходящих бенчмарков** (от 400+ в `lm-evaluation-harness` до 500+ в OpenAI Eval).  
2. **Определить, какие бенчмарки важны** для вашего приложения (например, кодинг, правовые вопросы).  
3. **Сформировать собственный leaderboard**:  
   - Выбрать метрики для каждого бенчмара (accuracy, F1, BLEU, …).  
   - Присвоить вес (см. ниже) → агрегировать.  
4. **Агрегировать**:  
   - **Среднее арифметическое** – все бенчмарки одинаковый вес (HF, стр. 384).  
   - **Mean win‑rate** – доля побед модели над другими (HELM, стр. 384).  

### Правила и числа  

| Платформа | Кол‑во бенчмарков (пример) | Примеры бенчмарков |
|-----------|---------------------------|--------------------|
| **EleutherAI lm‑evaluation‑harness** | 400+ | – |
| **OpenAI evals** | 500+ | – |
| **Hugging Face Open LLM Leaderboard (2023)** | 6 (ARC‑C, MMLU, HellaSwag, TruthfulQA, WinoGrande, GSM‑8K) | (стр. 380‑381) |
| **HELM Lite** | 10 | (MATH, LegalBench, MedQA, WMT‑2014, NarrativeQA, OpenBookQA, Natural Questions ×2) (стр. 381‑382) |

- **Корреляция**: сильно коррелируют ARC‑C, MMLU, WinoGrande (ρ ≈ 0.86‑0.90) (стр. 383‑384).  

### Шаблоны и примеры  

- **Пример оценки**: среднее по 6 HF‑бенчмаркам → 0.78 → рейтинг модели.  
- **Mean win‑rate**: модель A выигрывает у модели B в 70 % сценариев → win‑rate = 0.7.  

### Ошибки и предупреждения  

- **Слишком малый набор** – не покрывает все способности модели (HG пример: только 4 бенчмарка в 2023).  
- **Не учитывать корреляцию** – сильные корреляции могут «перекручивать» итоговый рейтинг.  
- **Считать все бенчмарки одинаковыми** – может недооценить, например, TruthfulQA (стр. 384).

## 5. Пользовательские (private) leaderboards (стр. 385‑386)

### Главная мысль  
Для конкретного продукта нужны **собственные бенчмарки** – они позволяют отфильтровать модели, учитывая уникальные требования (код, креативное письмо и т.п.).

### Как делать  

1. **Собрать список публичных бенчмарков**, релевантных вашему кейсу.  
2. **Проверить надёжность**: убедиться, что бенчмарк действительно измеряет нужную метрику (не “скрытый” тест).  
3. **При необходимости добавить свои** (например, набор вопросов из вашего домена).  

### Правила и числа  
- **Обновлять** список по мере появления новых бенчмарков (стр. 385).  

### Шаблоны и примеры  
- **Код‑агент**: берём `HumanEval`, `MBPP`, `CodeXGLUE`.  
- **Писатель‑ассистент**: берём `StoryCloze`, `BLEU‑based creative writing`.  

### Ошибки и предупреждения  

- **Публичные бенчмарки могут быть «загрязнены»** (см. глава 6).  
- **Не проверять репрезентативность** – может выбрать модель, которая «обучалась» на ваш тест.

*В Claude: «Сгенерировать список подходящих публичных бенчмарков для задачи X».*

## 6. Контаминация данных (стр. 387‑392)

### Главная мысль  
**Контаминация** – модель обучалась на том же наборе, по которому её сейчас оценивают. Это приводит к завышенным метрикам и обманутому выбору модели.

### Как происходит  

1. **Неумышленный скрейпинг** публичных бенчмарк‑данных в тренировочный корпус.  
2. **Тренировочные наборы и бенчмарки берут данные из одного источника** (например, учебники).  
3. **Умышленное до‑обучение** на бенчмарках, чтобы повысить показатели (полезно, но делает оценку несправедливой).  

### Как обнаружить  

| Метод | Описание | Плюсы | Минусы |
|------|----------|-------|--------|
| **n‑gram overlap** | Ищем совпадения длиной ≥ 13 токенов между тренировочным и тестовым корпусом. | Высокая точность. | Требует полного доступа к тренировочным данным, дорогой. |
| **Perplexity** | Оцениваем perplexity модели на тестовых примерах; аномально низкие значения → возможна контаминация. | Быстро, без доступа к тренировочным данным. | Менее точный. |

### Действия по очистке  

1. **Удалить загрязнённые примеры** из тренировочного корпуса (если доступно).  
2. При публикации результатов **указать**:  
   - Доля тестовых примеров, попавших в тренировочный набор.  
   - Метрики на «чистой» подсети и на полном наборе.  
3. При создании публичных бенчмарков **оставлять часть данных закрытой** и предоставлять хелпер‑скрипт для оценки на hold‑out‑set (стр. 392).  

### Пример из текста  
- **GPT‑3**: 13 бенчмарков ≥ 40 % их данных присутствовали в тренировочном наборе, разница в результатах между чистой и полной выборкой показана на Figure 4‑10 (стр. 392).  

### Ошибки и предупреждения  

- **Полагаться только на n‑gram** без доступа к тренировочным данным невозможно.  
- **Игнорировать небольшую долю загрязнения** – даже 5‑10 % могут сильно искажать позиции в лидерборде.  

### Где пригодится  

*Для Claude: «Проверь, есть ли в моём тренировочном наборе строки из benchmark X».*

## 7. Построение собственного пайплайна оценки (стр. 393‑398)

### Главная мысль  
Надёжный пайплайн оценки – это **структурированный набор шагов**, который измеряет как конечный результат, так и каждый компонент системы, а также чётко прописанные критерии и шкалы оценивания.

### Шаги (с детализацией)

1. **Оценка всех компонентов**  
   - Разделить приложение на отдельные части (например, PDF→text, затем extraction).  
   - Оценивать каждый блок независимо (симилярность текста, точность извлечения).  
   - Оценивать как **по‑turn**, так и **по‑задаче** (количество ходов до решения).  

2. **Создание Evaluation Guideline** (руководства)  
   - Описать **что должно делаться** и **что не должно** (например, ответы на вне‑тематику).  
   - Установить границы «out‑of‑scope» и правила реагирования.  

3. **Определение критериев качества**  
   - Примеры: **Relevance**, **Factual consistency**, **Safety** (стр. 398).  
   - Подготовить набор реальных запросов (можно собрать у пользователей).  

4. **Создание шкалы оценок и рубрики**  
   - Выбрать тип шкалы: бинарный (0/1), 1‑5, или 0‑1.  
   - Для каждого уровня привести **конкретные примеры** (что считается 1, что 0).  
   - **Валидация рубрики** людьми (сами, коллеги) – если непонятно – доработать.  

5. **Автоматизация**  
   - Интегрировать рубрики в тест‑скрипты (можно в Claude вызвать `evaluate(responses, rubric)`).  

### Правила и числа  

- **Среднее количество критериев** в реальных проектах ≈ 2.3 (стр. 398).  

### Шаблоны и примеры  

- **Рубрика для factual consistency**  
  - 0 – противоречит контексту.  
  - 0.5 – частично соответствует.  
  - 1 – полностью соответствует.  

- **Таблица Turn‑based vs Task‑based** (стр. 394‑395) – показывает, как сравнивать количество ходов и завершённость задачи.  

### Ошибки и предупреждения  

- **Не писать «чёрный ящик»**: без чёткого гайдлайна метрики теряют смысл.  
- **Слишком абстрактные критерии** (например, только «полезность») → трудности в автоматизации.  
- **Не учитывать «out‑of‑scope» запросы** – могут инфицировать метрики.  

### Где пригодится  

*Для Claude: «Сгенерировать rubrics для оценивания ответов чат‑бота по критериям relevance, factual, safety».*
