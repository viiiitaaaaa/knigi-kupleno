### Централизованное хранилище состояния execution · Использовать структуру `ExecutionContext` (содержащую ID сессии, историю событий, счетчик шагов и гибкое хранилище state) для централизованного хранения состояния, что упрощает передачу контекста и отладку · Сохранение всех шагов агента как `Event` в `ExecutionContext` (стр. 106–107).

### Универсальный интерфейс инструментов base tool · Наследовать все инструменты от абстрактного базового класса `BaseTool`, который определяет имя, описание, схему (`tool_definition`) и асинхронный метод `execute` с обязательным принятием контекста · Реализация базового класса `BaseTool` (стр. 108).

### Автоматическое определение контекста в функциях · Проверять сигнатуру функции при инициализации через `FunctionTool`: если функция ожидает параметр `context`, передавать его, а если нет — опускать · Реализация `FunctionTool` с проверкой сигнатуры через `inspect` (стр. 109–110).

### Интеграция внешних MCP-инструментов · Оборачивать инструменты из внешних MCP-серверов в функции через клиентскую сессию и конвертировать их в `FunctionTool` для бесшовного использования наряду с локальными инструментами · Функция `load_mcp_tools` и адаптер `_create_mcp_tool` (стр. 111–112).

### Разделение слоев коммуникации с LLM · Изолировать логику с помощью трех компонентов: `LlmRequest` (пакетирование запроса), `LlmClient` (общение с API через LiteLLM) и `LlmResponse` (стандартизация ответа) · Архитектура коммуникационного слоя (стр. 113–115).

### Безопасная обработка ошибок API · Перехватывать исключения при вызове LLM или инструментов и сохранять сообщения об ошибках внутри объектов ответа (`LlmResponse.error_message` или статус `error` в `ToolResult`), вместо того чтобы аварийно завершать работу агента · Обработка исключений в `LlmClient.generate()` и `Agent.act()` (стр. 115, 124).

### Защита от бесконечных циклов · Ограничивать максимальное число шагов агента с помощью параметра `max_steps` в конструкторе `Agent` · Использование `max_steps` в цикле `run()` и проверка счетчика в `ExecutionContext` (стр. 107, 120).

### Структурированный вывод через инструменты-модификаторы · Реализовывать возвращаемые структурированные данные (Pydantic-модели) путем динамического создания специального инструмента `final_answer` через декоратор `@tool`, что заставляет LLM строго следовать требуемой схеме · Динамическое создание `final_answer` в `_setup_tools()` (стр. 125–127).

### Ограничение параллельных запросов для экономии и безопасности · Использовать `asyncio.Semaphore` при запуске агента для оценки или массовых задач, чтобы контролировать параллелизм и не перегружать API-лимиты · `SEMAPHORE = asyncio.Semaphore(3)` при вызове `solve_problem` (стр. 130).

### Отладка с помощью трассировки выполнения · Использовать полный контекст выполнения (`ExecutionContext`) и утилиту `display_trace()` для визуализации шагов агента (размышлений и вызовов инструментов) при разборе сбоев · Использование `display_trace(result.context)` для отладки (стр. 130–131).
