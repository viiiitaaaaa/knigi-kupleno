### Ограничение цикла · Устанавливать максимальное количество шагов (bounded loop) для каждого агента, чтобы избежать бесконечного выполнения и сжигания токенов. · Пример: стандартное значение для продакшена — 10–25 шагов с простым счетчиком и возвратом фолбэка при достижении лимита. · (стр. 284)

### Ранний выход · Завершать работу агента сразу при достижении цели, не выполняя запланированные «на всякий случай» шаги. · Пример: добавление явной проверки достижения цели после каждого шага и прерывание цикла, если ответ уже достаточен. · (стр. 284)

### Автоматический выключатель по стоимости · Останавливать цикл, когда расходы на токены превышают заданный бюджет. · Пример: отслеживание суммарных токенов (вход + выход) и прерывание цикла при достижении порога (например, $0.50 за запуск) с возвратом лучшего результата. · (стр. 284)

### Проверка сходимости · Останавливать итерации агента, если его вывод перестает существенно меняться. · Пример: сравнение двух последовательных выводов с помощью семантического сходства (косинусное расстояние эмбеддингов), и если они похожи на 95%+, останавливать вычисления. · (стр. 284)

### Детектор осцилляции · Прерывать зацикливание агента между двумя состояниями путем принудительного выбора нового подхода. · Пример: хеширование состояния агента после каждого шага; если хеш повторяется среди последних 5 состояний, внедряется инструкция «вы должны выбрать другой подход». · (стр. 284)

### Цикл с экспоненциальной задержкой (Backoff) · Увеличивать задержку между итерациями при возникновении ошибок (с добавлением случайного джиттера). · Пример: старт с мгновенной повторной попытки, затем 1, 2, 4 секунды (до максимума в 30 секунд). · (стр. 284)

### Контроль времени выполнения (Timeout Guard) · Устанавливать независимый от шагов тайм-аут по реальному времени для защиты от зависаний на API. · Пример: прерывание работы через 5 минут вне зависимости от состояния агента и возврат лучшего частичного результата. · (стр. 285)

### Вложенные циклы · Использовать внешнее кольцо для главной цели и внутренние циклы с отдельными лимитами для подзадач. · Пример: декомпозиция проблемы внешним циклом, где каждая подзадача получает собственный лимит шагов и бюджет, чтобы сложная подзадача не исчерпала весь ресурс. · (стр. 285)

### Параллельный цикл · Запускать независимые итерации одновременно (асинхронно) для сокращения времени ожидания. · Пример: использование `asyncio.gather()` для одновременного исследования трех разных источников. · (стр. 285)

### Проверка качества напоследок (Cooldown Loop) · Запускать финальную верификацию после завершения основного цикла для отлова пропущенных ошибок. · Пример: дополнительная итерация исключительно для проверки фактов, консистентности и валидации формата. · (стр. 285)

### Адаптивный лимит шагов · Динамически корректировать оставшийся лимит шагов в зависимости от оценки текущего прогресса агента. · Пример: если за 5 шагов агент выполнен на 80%+, снизить лимит до 3; если меньше чем на 20% — увеличить до 25. · (стр. 286)

### Маршрутизатор инструментов · Использовать легкую модель (класса Haiku) для выбора подходящего инструмента до запуска главной модели, экономя контекст и токены. · Пример: маршрутизатор видит только имена и описания инструментов, выбирая нужный без передачи полного контекста. · (стр. 287)

### Фолбэк инструментов · Автоматически переключаться на резервный инструмент или базу знаний при сбое первичного. · Пример: при падении API веб-поиска переходить к альтернативному провайдеру или использовать обучающие данные с дисклеймером. · (стр. 287)

### Валидация аргументов инструментов · Проверять типы, диапазоны и форматы параметров до вызова функции инструмента. · Пример: возврат понятного сообщения об ошибке с правильным форматом до того, как будет потрачен вызов API. · (стр. 287)

### Кэширование результатов инструментов · Сохранять результаты вызовов инструментов для идентичных входных данных (на основе хеша имени и аргументов). · Пример: кэширование поисковых запросов и обращений к БД, повторяющихся в разных запусках агента. · (стр. 287)

### Песочница для инструментов (Tool Sandboxing) · Изолировать выполнение инструментов для обеспечения безопасности продакшена. · Пример: запуск кода в Docker-контейнерах, ограничение файловых операций специальной директорией и использование только read-only подключений к БД. · (стр. 287)

### Сначала чтение (Read-Only First) · Обязывать агента собирать информацию и читать текущее состояние перед выполнением любых записывающих действий. · Пример: чтение содержимого файла или записей БД перед их модификацией для предотвращения слепых перезаписей. · (стр. 288)

### Идемпотентность инструментов · Проектировать инструменты так, чтобы их повторный вызов приводил к тому же результату без дублирования сущностей. · Пример: повторный вызов `create_user(email=x)` должен возвращать существующего пользователя вместо создания дубликата. · (стр. 288)

### Суммирование результатов инструментов · Сжимать объемные ответы инструментов (например, сотни строк из БД) до ключевых метрик перед добавлением в контекст. · Пример: выделение только существенной информации для экономии 60–80% токенов контекста. · (стр. 288)

### Инструмент подтверждения (Confirmation Tool) · Использовать специальный мета-инструмент для запроса одобрения пользователя перед необратимыми действиями. · Пример: вызов `confirm_action` с описанием удаляемых файлов и ожидание клика-подтверждения. · (стр. 288)

### Скользящее окно памяти (Sliding Window) · Хранить в контексте только последние N взаимодействий, отбрасывая старые. · Пример: сохранение последних 5–10 сообщений для коротких задач, где не нужна глубокая история. · (стр. 290)

### Память по ключевым точкам (Landmark Memory) · Помечать критические моменты (смену плана, ошибки, важные открытия) как «вехи», которые никогда не удаляются, а рутину сжимать. · Пример: сохранение ключевых решений в неизменяемом виде при сжатии остального диалога. · (стр. 290)

### Сжатие памяти · Периодически (каждые 5–10 шагов) с помощью недорогой модели компрессировать историю диалога в маркированный список фактов и решений. · Пример: сокращение размера контекста на 60–80% с минимальной потерей важной информации. · (стр. 290)

### Хранилище предпочтений · Вести отдельный key-value файл или профиль с персональными настройками пользователя и подгружать их в системный промпт. · Пример: сохранение привычек вроде «всегда использовать метрическую систему» при старте сессии. · (стр. 290)

### Кэш фактов · Сохранять единожды проверенные агентом утверждения вместе с источниками, чтобы не повторять поиск. · Пример: кэширование факта вроде «Компания X основана в 2015 г.» для будущих запросов. · (стр. 291)

### Бюджетирование контекста · Жестко распределять лимиты контекстного окна по категориям памяти (например, 40% — рабочая память, 20% — вехи, 20% — извлеченный контекст, 20% — системный промпт). · Пример: при превышении бюджета в конкретной категории очищать или сжимать только её элементы. · (стр. 291)

### Валидация и откат состояния · Использовать типизированные объекты (вместо свободного текста), проверять их на непротиворечивость после каждого шага и откатывать стек при ошибках. · Пример: при обнаружении повреждения состояния возвращаться к последнему сохраненному контрольному чек-поинту (rollback). · (стр. 291)

### Самокритика (Self-Critique) · Добавлять финальный шаг, на котором агент оценивает свой собственный ответ на наличие ошибок и неточностей. · Пример: использование сфокусированного промпта для проверки фактов, логики и полноты перед возвратом ответа пользователю. · (стр. 294)

### Рубрицированное оценивание · Оценивать выходные данные по предопределенным критериям (точность, полнота, ясность) по шкале от 1 до 10. · Пример: применение числовой шкалы с конкретными уровнями для принятия решения о возврате или доработке ответа. · (стр. 294)

### Проверка цитирования (Citation Verification) · Автоматически сверять каждое утверждение в тексте с указанным источником. · Пример: извлечение фактов из ответа и проверка их наличия в исходных материалах с удалением неподтвержденных данных. · (стр. 294)

### Маскировка персональных данных (PII Scrubbing) · Удалять или заменять личную информацию (email, телефоны, адреса) специальными токенами перед логированием или сохранением. · Пример: использование регулярных выражений и NER-моделей для сокрытия чувствительных данных клиентов. · (стр. 294)

### Ведение аудиторского лога (Audit Log) · Создавать неизменяемую запись каждого действия агента, вызова инструмента и изменения состояния с таймстаймом и trace ID. · Пример: логирование шагов для последующего дебага, комплаенса и разбора инцидентов. · (стр. 295)

### Защита от резких изменений (Rate-of-Change Guard) · Приостанавливать работу агента и запрашивать подтверждение, если он пытается изменить слишком много элементов за раз. · Пример: пауза, если за один шаг удаляется больше 5 файлов или модифицируется свыше 20 строк в БД. · (стр. 295)

### Имитация работы (Dry Run) · Выполнять полный цикл рассуждений агента, но перехватывать и симулировать все побочные эффекты (запросы инструментов) без реального коммита. · Пример: показ пользователю того, что планирует сделать агент, без реального изменения файлов или отправки данных. · (стр. 295)

### Многоуровневые модели (Model Tiering) · Использовать дешевые модели для простых задач и дорогие — только для сложного анализа. · Пример: применение Haiku для классификации ($0.001), Sonnet для генерации ($0.01) и Opus для сложной логики ($0.05). · (стр. 296)

### Сжатие промптов (Prompt Compression) · Удалять из промптов лишние пробелы, сокращать повторяющиеся инструкции и использовать компактные форматы. · Пример: сокращение промпта с 2000 до 800 токенов для экономии 60% затрат на входные токены на каждой итерации. · (стр. 296)

### Семантическое кэширование · Искать в кэше похожие по смыслу запросы (через косинусное расстояние эмбеддингов с порогом > 0.95), а не только точные совпадения. · Пример: выдача готового ответа из кэша для часто повторяющихся вопросов в службе поддержки. · (стр. 296)

### Пакетная обработка (Batch Processing) · Объединять запросы в группы для сокращения накладных расходов на системные промпты и описания инструментов. · Пример: обработка элементов пачками по 10 штук вместо 100 отдельных запусков агента (экономия до 90% служебных токенов). · (стр. 296)

### Ленивое вычисление (Lazy Evaluation) · Загружать данные, инструменты или запускать анализ только тогда, когда это реально потребовалось на текущем шаге. · Пример: отказ от предзагрузки всех файлов или инструментов заранее, чтобы не тратить контекст впустую. · (стр. 296)

### Стриминг ответов (Streaming Response) · Передавать промежуточные результаты (статус мыслей, вызовы инструментов) по мере их появления через Server-Sent Events (SSE). · Пример: показ пользователю процесса «Ищу в 3 базах данных...», что увеличивает толерантность к ожиданию в 10 раз. · (стр. 296)

### Бюджет токенов по фазам · Жестко распределять токены между этапами работы агента (например, 30% — планирование, 50% — выполнение, 20% — синтез). · Пример: запрет фазе планирования расходовать лимит этапа выполнения. · (стр. 296)

### Повторное использование шаблонов промптов · Хранить общие инструкции (правила безопасности, схемы вывода) централизованно и подключать по ссылке. · Пример: единый системный промпт форматирования для всех агентов для снижения затрат на поддержку. · (стр. 296)

### Ограничение длины ответа (Response Truncation) · Жестко ограничивать максимальное число выходных токенов в зависимости от типа вопроса пользователя. · Пример: ограничение ответа до 100 токенов для вопросов «да/нет» и до 500 для кратких выжимок. · (стр. 296)

### Параллельные вызовы инструментов · Вызывать независимые инструменты одновременно (через `asyncio`) вместо последовательного перебора. · Пример: одновременный поиск в базе данных и запрос погоды для уменьшения задержки вдвое. · (стр. 297)

### Предварительная загрузка данных (Prefetch) · Загружать необходимые данные параллельно или заранее до того, как агент явно запросит их. · Пример: подтягивание истории заказов и тикетов поддержки клиента параллельно с началом анализа его профиля. · (стр. 297)

### Прогрессивное раскрытие информации (Progressive Disclosure) · Показывать пользователю краткую сводку по умолчанию, скрывая детали в раскрывающихся блоках. · Пример: вывод одноабзацного итога работы агента с возможностью развернуть лог рассуждений и сырые данные. · (стр. 298)

### Поддержка отмены действий (Undo Support) · Делать каждое записывающее действие агента обратным с помощью сохранения истории транзакций и возможности отката в один клик. · Пример: отмена создания файла или обновления базы данных по кнопке интерфейса. · (стр. 298)

### Режим объяснения (Explanation Mode) · Предоставлять пользователю простой перевод цепочки рассуждений агента по первому требованию («почему ты это сделал?»). · Пример: демонстрация логики решения на базе системных логов отладки в понятном человеку виде. · (стр. 298)

### Сохранение контекста между сессиями · Запоминать проект, предпочтения и статус работы пользователя при его возвращении на следующий день. · Пример: возобновление работы с того же места без необходимости объяснять всё с нуля. · (стр. 298)

### Перевод технических ошибок · Превращать системные трейсы и ошибки в понятные человеку сообщения с планом дальнейших действий. · Пример: преобразование `ConnectionRefusedError: port 5432` в фразу «База данных временно недоступна, я повторю попытку через 30 секунд». · (стр. 298)

### Петля обратной связи · Собирать оценки (лайки/дизлайки) от пользователя для каждого ответа и автоматически создавать на их основе тестовые кейсы (evals) для улучшения системы. · Пример: превращение каждого дизлайка в новый тест для проверки качества работы агента. · (стр. 299)

### Корректный перепас человеку (Graceful Handoff) · Передавать диалог оператору-человеку с полным контекстом (что спрашивал пользователь, что пробовал агент, почему произошел сбой), если задача превысила возможности ИИ. · Пример: передача тикета без требования к пользователю повторять вводные данные заново. · (стр. 299)
