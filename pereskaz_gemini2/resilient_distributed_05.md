### Клиентский ключ идемпотентности (Client Idempotency Key) · Использовать уникальный UUID, генерируемый клиентом, чтобы сервер мог проверить по нему, обрабатывался ли запрос ранее. Передавать его в обязательном порядке (например, в HTTP-заголовке `Idempotency-Key`), а при повторном запросе возвращать сохраненный ответ. · Платежные API вроде Stripe, Adyen и Worldpay используют заголовок `Idempotency-Key` для безопасных повторов. · (стр. 6)

### Защита от подмены параметров при повторах · Обрабатывать повторные запросы с тем же ключом идемпотентности, но измененным телом запроса как ошибку валидации, чтобы клиент не отправлял разные данные с одинаковым ключом. · В API AWS повторный запрос с тем же ключом идемпотентности, но другими параметрами в теле вызывает ошибку валидации. · (стр. 8)

### Серверный фингерпринтинг запросов (Server-Side Request Fingerprinting) · Генерировать хэш (например, MD5-чексумму) на основе параметров запроса на стороне сервера, если клиент не может передавать ключ идемпотентности (устаревшее ПО). · Сервер создает MD5-хэш от строки параметров запроса для обнаружения дубликатов, но это чревато ложными срабатываниями. · (стр. 7)

### Ограничение времени жизни фингерпринта · Задавать период валидности (time limit / TTL) для серверных фингерпринтов, чтобы одинаковые запросы, пришедшие спустя долгое время (например, регулярные платежи), не считались дубликатами. · Если два одинаковых платежа приходят с разницей в несколько секунд — это дубликат, но если через неделю — новый платеж. · (стр. 7)

### Декларативное проектирование для идемпотентности · Использовать декларативный стиль программирования (описание желаемого результата, а не пошаговых инструкций), так как он по определению является идемпотентным. · Запуск скрипта Ansible второй раз ничего не меняет, если машина уже находится в ожидаемом состоянии. · (стр. 8)

### Тестирование повторов и идемпотентности · Проверять механизмы идемпотентности с помощью функциональных автотестов, а для тестирования повторов внедрять искусственный джиттер в сеть для симуляции таймаутов. · Использование искусственного джиттера в сети вызывает таймауты и провоцирует повторы запросов для тестирования. · (стр. 8)

### Избыточное резервирование (Overprovisioning) · Создавать избыточную емкость (дополнительные инстансы), чтобы оставшиеся узлы могли выдержать пиковую нагрузку при падении одного из инстансов. · Добавление пятого инстанса сервиса Pets вместо четырех снижает нагрузку на каждый узел с 120 до 96 запросов, предотвращая каскадный сбой при падении одного из них. · (стр. 11)

### Ограничение скорости (Rate Limiting) · Настраивать отклонение избыточного трафика выше определенного лимита, чтобы система продолжала работать стабильно на уменьшенной мощности, а не падала целиком. · Если каждый инстанс сервиса Pets может отклонять трафик сверх своего лимита, сервис продолжает работать при сбое соседей. · (стр. 12)

### Управление желаемым состоянием (Desired State Management) · Использовать инструменты оркестрации (например, Kubernetes), которые автоматически отслеживают состояние инфраструктуры и поднимают замену упавшему инстансу. · Kubernetes автоматически обнаруживает выход из строя инстанса сервиса и запускает новый экземпляр взамен. · (стр. 12)

### Снижение частоты отказа компонентов · Повышать надежность оборудования (резервирование питания, дисков), однако помнить, что полностью исключить сбои оборудования невозможно. · Использование отказоустойчивых хранилищ (SAN) или резервных блоков питания уменьшает вероятность падения машины. · (стр. 13)

### Повышение отказоустойчивости кэша · Использовать кластеризованные решения кэширования (или управляемые облачные сервисы вроде AWS ElastiCache), чтобы выход из строя одной ноды кэша не приводил к падению системы.  · Применение кластеров кэша позволяет другим нодам продолжать обслуживание запросов при падении одной из них. · (стр. 14)

### Улучшение времени восстановления кэша (Snapshots) · Настраивать периодический сброс снимков кэша на диск (snapshotting), чтобы после перезагрузки ноды быстро восстановить данные в памяти и снизить нагрузку на бэкенд. · Redis и Memcached позволяют периодически записывать снимки данных на диск для быстрого восстановления кэша после перезапуска. · (стр. 14)

### Быстрое завершение работы вместо медленного (Fail Fast) · В случае аварии кэша или перегрузки временно останавливать прием новых запросов (или снижать лимиты), чтобы предотвратить каскадный отказ всей системы. · Временная остановка приема заказов или ограничение запросов к каталогу защищает систему от полного зависания при падении кэша. · (стр. 15)
