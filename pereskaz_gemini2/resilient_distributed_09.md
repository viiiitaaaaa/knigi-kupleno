### Жестко закодированные IP-адреса · Не используйте жесткое кодирование IP в коде; если это необходимо, выносите их в конфигурационные файлы или используйте динамический DNS. · Пример из текста: хранение IP-адреса конечной точки в конфигурации клиента, требующее ручного обновления при изменении адреса сервера. (стр. 132)

### Динамическое обнаружение сервисов · Используйте динамическое обнаружение для автоматического обновления сетевых адресов клиентов при смене или сбое машин. · Пример из текста: запуск нового экземпляра Pet, который автоматически регистрируется в службе реестра (Service Registry). (стр. 132)

### DNS с коротким TTL · Применяйте DNS для динамического обнаружения с коротким временем жизни (TTL), чтобы записи быстрее обновлялись, учитывая риск кеширования. · Пример из текста: использование RFC 1035 с низким TTL (вплоть до нуля) для ускорения распространения изменений IP-адресов. (стр. 134)

### Инструменты Consul и etcd · Используйте распределенные хранилища типа Consul или etcd с поддержкой алгоритма Raft и проверки здоровья (health checks) для надежного обнаружения сервисов. · Пример из текста: применение Consul или etcd на нечетном количестве узлов (минимум три) для предотвращения единой точки отказа. (стр. 135)

### Шаблон consul-template · Применяйте вспомогательные инструменты для автоматического обновления конфигурационных файлов на основе данных из реестра сервисов. · Пример из текста: использование `consul-template` для динамического обновления текстовых файлов конфигураций по всему миру без изменения самого кода программ. (стр. 135)

### Выбор подхода к обнаружению сервисов · Начинайте с DNS, применяйте etcd в Kubernetes и выбирайте Consul для гибридных сред с поддержкой устаревшего ПО. · Пример из текста: рекомендация использовать стандартный DNS для статических сред и etcd/Consul для динамических контейнерных платформ. (стр. 135)

### Серверная балансировка нагрузки · Используйте серверную балансировку для распределения входящего трафика по пулу узлов с автоматическим удалением неисправных экземпляров. · Пример из текста: направление клиентских запросов на конечную точку балансировщика (например, HAProxy или nginx), который маршрутизирует их на доступные инстансы. (стр. 137)

### Балансировка на уровне L7 для HTTP/2 · Применяйте балансировщики уровня 7 (L7) вместо уровня 4 (L4) при работе с протоколами вроде HTTP/2, чтобы видеть отдельные запросы внутри одного соединения. · Пример из текста: проблема, когда L4-балансировщик отправляет все параллельные потоки HTTP/2 внутри одного TCP-соединения на единственный экземпляр приложения. (стр. 138)

### Клиентская балансировка нагрузки · Реализуйте клиентскую балансировку (в коде или через Service Mesh), чтобы клиент сам выбирал узел назначения и избегал лишних сетевых переходов (hops). · Пример из текста: прямое взаимодействие клиента с целевым сервером на основе информации об имеющихся инстансах без промежуточного прокси. (стр. 139)

### Использование Service Mesh · Применяйте сервисную сетку (Service Mesh) с локальными прокси для реализации клиентской балансировки и сквозных функций без усложнения бизнес-кода. · Пример из текста: прокси на стороне клиента и сервера, осуществляющие поиск и балансировку прозрачно для самого приложения. (стр. 140)

### Управление желаемым состоянием (Desired State Management) · Используйте декларативное описание инфраструктуры и платформы постоянного контроля для автоматического восстановления нужного количества экземпляров при сбоях. · Пример из текста: спецификация Kubernetes, в которой явно указано требование поддерживать ровно три экземпляра сервиса Pet. (стр. 142)

### Предпочтение stateless-процессинга · Проектируйте системы без сохранения локального состояния (stateless), чтобы любой экземпляр сервиса мог обработать любой запрос. · Пример из текста: передача содержимого корзины и ID пользователя прямо в запросе оформления заказа, позволяющая распределить вызовы на любой узел. (стр. 143)

### Избегание stateful-сложности · Тщательно взвешивайте риски при использовании stateful-процессинга (сохранение состояния в памяти), так как это усложняет маршрутизацию (sticky sessions) и приводит к потере данных при падении узла. · Пример из текста: отправка запроса только на конкретный инстанс C, где локально хранится корзина пользователя, с риском потерять данные при падении этого инстанса. (стр. 144)

### Тестирование отказоустойчивости машин · Проверяйте жизнеспособность системы с помощью запуска тестов нагрузки одновременно с принудительным отключением отдельных машин через API или инструменты хаос-инжиниринга. · Пример из текста: выполнение нагрузочного тестирования параллельно с программным удалением экземпляров сервиса для валидации непрерывности работы. (стр. 145)
