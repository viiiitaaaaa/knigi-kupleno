### Проверка памяти перед развертыванием · Регулярно тестируйте поведение памяти на разных шагах и в реалистичных сценариях взаимодействия, чтобы удостовериться, что сохраненные данные остаются доступными и корректными, а агент не теряет информацию при суммаризации и не выдает устаревшие данные · Тестирование систем памяти в реальных условиях вместо предположений о их работоспособности · (стр. 18)

### Изоляция контекста в многоагентных системах · Передавайте рабочему агенту (subagent) только текущий шаг (current turn) вместо полной истории родительского разговора, чтобы избежать лишнего шума и изолировать контекст · Передача оркестратором только `current_input` во вложенный биллинговый воркер (`ParentState` / `call_worker`) · (стр. 18)

### Использование чекпоинтеров для вложенных подграфов · Применяйте параметр `checkpointer=True` для сохранения состояния вложенных подграфов, чтобы агенты понимали, какие файлы они уже проверяли или редактировали в многошаговых диалогах · Передача `checkpointer=InMemorySaver()` в компиляцию родительского графа (`builder.compile(checkpointer=InMemorySaver())`) · (стр. 18)

### Предупреждение об ограничении чекпоинтеров · Учитывайте, что параметр `checkpointer=True` валиден только для вложенных подграфов и вызовет ошибку, если применен к корневому графу · Ошибка при попытке применить `checkpointer=True` на корневом графе · (стр. 18)

### Разделение графа агентов по уровням чувствительности данных · Разделяйте компоненты мультиагентной системы по степени секретности данных: используйте управляемые API (managed APIs) для нечувствительных задач и изолированные/локальные модели для работы с PII и финансами · Суперагент занимается только маршрутизацией, а агент поиска работает с приватными данными · (стр. 18)

### Мониторинг токенов через платформу трекинга · Всегда отслеживайте потребление токенов с помощью платформы трассировки в дополнение к мониторингу затрат на API или GPU, так как цены провайдеров могут меняться · Сравнение расчетных оценок затрат с реальным потреблением токенов через трекинг · (стр. 18)

### Применение мемоизации решений планировщика · Заменяйте повторные рассуждения (reasoning) прямым извлечением решений из кэша, сохраняя и повторно используя действия агента при достижении эквивалентного состояния фактов · Кэширование решений планировщика (`TieredCache`) на основе хэшей состояния фактов (`PlannerContext`) · (стр. 18)

### Использование многоуровневого кэша состояний (Tiered Cache) · Реализуйте кэш с тремя уровнями поиска (точный хэш, нормализованный хэш и семантическое сходство по эмбеддингам), чтобы повторно использовать решения даже при поверхностных вариациях данных · Поиск через `TieredCache.lookup()`, проверяющий `exact`, `normalized` и `semantic` тиры · (стр. 18)

### Учет контекстных ограничений при семантическом кэшировании · Обязательно проверяйте совпадение полного контекста планировщика (доступные и устаревшие инструменты — `tools_available` и `stale_tools`) при использовании семантического сходства, иначе агент применит решение из неверного контекста · Сравнение `entry.stale_tools == ctx.stale_tools` перед выдачей результата из кэша · (стр. 18)

### Контроль качества кэш-хитов (Предупреждение о зацикливании) · Отслеживайте, приводят ли кэшированные решения к изменениям состояния; если высокий процент совпадений (например, 90%) состоит из устаревших хитов, агент застрял в логическом цикле и требуется принудительный вызов планировщика · Предупреждение о том, что высокий `cache hit rate` сам по себе не равен экономии, если агент повторяет старые ошибки · (стр. 18)

### Настройка порога семантического сходства (τ) · Подбирайте пороговое значение сходства эмбеддингов ($\tau$), чтобы избежать галлюцинаций логики: слишком низкий порог заставит агента повторно использовать решение для задачи лишь из-за смутно похожих эмбеддингов · Использование параметра `threshold = 0.90` в `TieredCache` · (стр. 18)

### Управление версиями в хранилище фактов (`FactStore`) · Увеличивайте внутренний счетчик версий (`_version`) только при добавлении новых ключей, конфликтах или подкреплении фактов из других источников, чтобы изменения состояния запускали пересчет планировщика выборочно, а не при каждом дубликате · Класс `FactStore` с классификацией записей на `added`, `reinforced`, `conflict`, `duplicate` · (стр. 18)
