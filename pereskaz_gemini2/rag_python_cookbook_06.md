### Гибридный поиск (Keyword и Similarity) · Использовать комбинированный поиск (текстовый + векторный) в PostgreSQL с весами (например, 0.5 на 0.5) для одновременного учета точных совпадений терминов и семантического смысла · При выполнении SQL-запроса через Psycopg2 вычислять `text_score`, `vector_score` и `hybrid_score`, используя `ts_rank` для ключевых слов и косинусное сходство (`<=>`) для векторов · (стр. 188–189).

### Выбор весов для гибридного поиска · Настраивать веса текстового и векторного поиска в зависимости от домена (по умолчанию 0.5/0.5) · Если пользователи жалуются на нехватку точных терминов — увеличить вес текста до 0.7; если результаты уходят от сути — увеличить вес векторов до 0.7 · (стр. 190).

### Фильтрация по метаданным (Metadata Filtering) · Применять фильтрацию по метаданным *до* запуска семантического поиска, чтобы сузить пространство поиска до релевантного подмножества данных · В PostgreSQL сохранять метаданные в колонке типа `JSONB` и добавлять условие `WHERE metadata->>'topic' = %s` в SQL-запрос · (стр. 180–183).

### Использование HyDE (Hypothetical Document Embeddings) · Улучшать поиск путем генерации гипотетических документов (псевдодокументов), стилистически похожих на реальный контент в базе, с последующим созданием эмбеддингов для них · Использовать модель (например, `gpt-5-mini`) и схему Pydantic (`HypotheticalDocuments`), чтобы сгенерировать текст-ответ на запрос, а затем искать похожие векторы в базе по этому гипотетическому тексту · (стр. 184–187).

### Мультизапросный поиск (Multiquery Retrieval) · Создавать несколько альтернативных формулировок (вариаций) исходного запроса пользователя для преодоления ограничений поиска по расстоянию и повышения полноты поиска (recall) · Генерировать альтернативные подзапросы с помощью LLM (используя Pydantic-схему `QueryVariations`), выполнять для каждого из них векторный поиск, а затем объединять результаты · (стр. 188–191).

### Проектирование системы маршрутизации запросов (Query Routing) · Создавать роутер на основе LLM, который анализирует сложный вопрос пользователя и направляет его к наиболее подходящему источнику данных или инструменту · Определять через Pydantic схему `RouterDecision` со списком допустимых источников (`Literal`), чтобы заставить модель вернуть строго имя нужной функции/базы данных (например, `general_football_knowledge` или `latest_football_results_sql`) · (стр. 192–195).

### Автообъединяющийся ретривер (Auto-Merging Retriever) · Использовать мелкие текстовые фрагменты (дочерние `leaf chunks`) для точного векторного поиска, но передавать языковой модели более крупные родительские фрагменты (`parent chunks`) при нахождении достаточного числа релевантных детей · При превышении порогового значения релевантных дочерних элементов в одном родителе — извлекать и передавать в промпт весь родительский кусок текста · (стр. 197–199).

### Ретривер окон предложений (Sentence Window Retriever) · Использовать небольшие чанки для семантического поиска, но дополнять их соседними предложениями (до и после) из исходного документа для обеспечения достаточного контекста LLM · При создании таблицы сохранять строгую последовательность `chunk_id`, чтобы после нахождения релевантного чанка автоматически захватывать чанки до и после него · (стр. 200–202).

### Переранжирование результатов (Reranking) · Сортировать и фильтровать объединенные результаты из разных источников (векторный поиск, SQL, API) по степени их релевантности перед отправкой в финальный промпт · Использовать LLM с Pydantic-схемой для оценки каждого документа по шкале от 1 до 5 (промпт с оценкой релевантности), после чего отбирать только топ-3 лучших фрагмента для сокращения шума · (стр. 203–205).
