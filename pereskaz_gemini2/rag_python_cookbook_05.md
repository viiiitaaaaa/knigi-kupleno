### Использование классификации для маршрутизации запросов · Обучите классификатор (например, random forest) для предварительной фильтрации и сопоставления эмбеддингов с предопределенными категориями до запуска семантического поиска, чтобы сократить задержку и повысить точность. · `clf = RandomForestClassifier(); clf.fit(X, y)` · (стр. 153)

### Ограничения и критерии применения классификатора · Используйте классификацию при наличии четких стабильных категорий (спорт, политика, финансы) с достаточным количеством примеров (100–200 размеченных чанков на категорию); избегайте её при перекрывающихся доменах или наборе данных менее 10 000 документов. · Документы с вопросами о «спортивных ставках» охватывают спорт и право, поэтому для перекрывающихся доменов лучше использовать метаданные вместо классификатора. · (стр. 154)

### Гибридный поиск (комбинация ключевых слов и векторов) · Объедините полнотекстовый поиск по ключевым словам через BM25 с семантическим поиском по векторным эмбеддингам, а затем объедините их рейтинги с помощью рангового слияния (Reciprocal Rank Fusion, RRF). · `rrf_df["rrf_score"] = 1 / (k + rrf_df["keyword_rank"]) + 1 / (k + rrf_df["semantic_rank"])` · (стр. 155)

### Когда применять гибридный поиск · Используйте гибридный поиск, когда корпус документов содержит точные идентификаторы (наименования продуктов, SKU, артикулы, медицинские коды ICD-10, пути API), которые эмбеддинги не могут уловить надежно. · Вопрос: «Как настроить SSL для эндпоинта /api/v2/users?». · (стр. 158)

### Выбор векторного хранилища в зависимости от масштаба · Для автономных конвейеров и экспериментов используйте легкие библиотеки (FAISS, Annoy); для локальных прототипов — встраиваемые хранилища (Chroma); для живых систем с миллионами векторов — выделенные или управляемые базы данных (PostgreSQL с pgvector, Weaviate, Pinecone). · Использование Chroma для локальных RAG-прототипов и PostgreSQL/Pinecone для production. · (стр. 148)

### Использование FAISS для временного анализа · Применяйте FAISS для легких и быстрых поисков по сходству в памяти, когда не требуется персистентность между запусками, фильтрация по метаданным или разграничение доступа пользователей. · `index = faiss.IndexFlatL2(document_embeddings.shape[1])` · (стр. 154)

### Настройка клиента Chroma для прототипов · Используйте постоянный клиент Chroma (`PersistentClient`) с указанием пути к папке, чтобы данные сохранялись на диск и не терялись при перезапуске приложения. · `chroma_client = chromadb.PersistentClient(path=VECTOR_STORE_PATH)` · (стр. 155)

### Хранение векторов и бизнес-данных в PostgreSQL · Используйте расширение pgvector в PostgreSQL для хранения эмбеддингов в одной базе данных вместе со структурированными данными приложений и метаданными, что позволяет выполнять SQL-соединения и транзакции. · `CREATE EXTENSION IF NOT EXISTS vector;` · (стр. 163)

### Выполнение поиска по сходству в PostgreSQL · Выполняйте поиск по косинусному сходству с помощью оператора `<=>` (или по евклидову расстоянию через `<->`, скалярному произведению через `<#>`), комбинируя его с обычной SQL-фильтрацией в предложении `WHERE`. `1 - (embedding <=> '...')`. · `SELECT 1 - (embedding <=> '{embedded_query}') AS cosine_similarity, * FROM embeddings ORDER BY 1 - (...) DESC LIMIT 20;` · (стр. 165)

### Ускорение векторого поиска с помощью индексов в PostgreSQL · Создавайте индексы IVFFlat или HNSW в таблицах PostgreSQL с большим объемом данных (от 100 000+ строк), чтобы ускорить выполнение запросов по поиску векторов. · `CREATE INDEX ON test_embedding_table USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 200);` · (стр. 167)

### Настройка гиперпараметров HNSW-индекса · Настраивайте параметры индекса HNSW (`m`, `ef_construction`, `ef_search`) для баланса между скоростью поиска, потреблением памяти и качеством построения индекса. · `SET hnsw.ef_search = 50;` · (стр. 170)
