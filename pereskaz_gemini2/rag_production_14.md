### Выбор между обогащением и гибридным поиском · Оценивайте задачу перед выбором подхода: обогащение чанков подходит для семантических запросов и фактов (низкая латентность), а гибридно-грановый поиск — для структурных и реляционных задач (но требует text-to-Cypher и обработки галлюцинаций). · Пример: Обогащение чанков ищет актера для строки из фильма, а гибридный граф находит всех персонажей, взаимодействовавших с Бондом в более чем трех сценах. · (стр. 317–318)

### Обработка ошибок генерации Cypher · Реализуйте таймауты запросов и стратегии повторных попыток (retries) на случай, если языковая модель сгенерирует невалидный синтаксис при переводе естественного языка в запросы базы данных. · Пример: Защита text-to-Cypher конвейера от синтаксических галлюцинаций LLM. · (стр. 318)

### Архитектура хранения векторов в граде · Размещайте векторные эмбеддинги непосредственно в узлах графа с помощью встроенных векторных индексов (свойство `chunk.embedding`), чтобы выполнять семантический поиск и обход графа за одну транзакцию с атомарной консистентностью. · Пример: Хранение `chunk.embedding` в свойствах узла графовой базы данных. · (стр. 318–319)

### Синхронизация раздельного хранения · При раздельном хранении векторов (в векторной БД) и графа поддерживайте строгую синхронизацию идентификаторов `chunk_id`, чтобы приложение не падало при обращении к несуществующим в графе чанкам. · Пример: Использование `chunk_id` для поиска в графовой БД после получения чанка из векторного хранилища. · (стр. 319)

### Автоматизация извлечения сущностей и связей · Используйте единую языковую модель для автоматизации создания графа знаний через поиск ключевых сущностей, извлечение связей и сопоставление сущностей (entity linking). · Пример: Превращение неструктурированного текста в триплеты (Apple, FOUNDED_BY, Steve Jobs). · (стр. 320)

### Гибридная стратегия извлечения · Не полагайтесь только на LLM-пайплайн (он дает много шума), а применяйте гибридный подход: предложения LLM пропускайте через детерминированные эвристики (регулярные выражения для дат/ID), классические NLP-модели валидации и human-in-the-loop для критических сущностей. · Пример: Валидация извлеченных сущностей с помощью регулярных выражений и экспертного контроля. · (стр. 320)

### Решение проблемы синонимов через онтологии · Создавайте четкую онтологию с каноническими именами и псевдонимами сущностей, чтобы связывать разные вариации названий одного объекта с единым узлом вместо создания дубликатов. · Пример: Сопоставление «Tylenol» и «acetaminophen» с единой сущностью препарата через онтологию. · (стр. 321–322)

### Многоэтапный процесс сопоставления сущностей · Проводите нормализацию сырого текста (приведение к нижнему регистру, стандартизация суффиксов) и генерацию кандидатов с помощью метрик сходства для эффективного связывания сущностей. · Пример: Сравнение имен «Chris» и «Christopher» через расстояние Джаро–Винклера. · (стр. 321–322)

### Использование готовых онтологий и баз данных · Применяйте стандартные онтологии (например, FIBO) и лицензированные готовые базы знаний с каноническими идентификаторами (например, DrugBank, PermID), чтобы не строить граф с нуля и избежать провала более чем 50% таких проектов. · Пример: Связывание внутренних данных с «золотой записью» компании через стандартизированные идентификаторы. · (стр. 322–323)

### Оценка затрат на индексацию GraphRAG · Учитывайте огромные затраты токенов и времени на этап индексации GraphRAG (вызов LLM для каждого чанка, обнаружение сообщений и суммаризацию), предварительно тестируя затраты на небольшой выборке. · Пример: Расчет стоимости обработки 20 фильмов в $6.32 против более $500 для полного датасета. · (стр. 324–325, 328)

### Выбор локального поискового метода в GraphRAG · Используйте `local_search` (локальный поиск снизу вверх) для детальных вопросов, находящих точечные узлы и исследуя их ближайшее окружение (1–2 хопа). · Пример: Поиск контекста в локальной «окрестности» графа для ответа на специфичные вопросы. · (стр. 326)

### Выбор глобального поискового метода в GraphRAG · Используйте `global_search` (глобальный поиск сверху вниз) для исследовательских вопросов высокого уровня, требующих синтеза информации из несвязанных частей графа через суммирование сообществ. · Пример: Запрос об общих темах и нарративных паттернах во всех сценариях фильмов. · (стр. 326, 328)

### Ограничения применения GraphRAG · Отказывайтесь от GraphRAG на быстроменяющихся данных (новости, тикеты), задачах с жесткими требованиями к низкой латентности и там, где нужны точные цитаты (verbatim citations) из документов, из-за потерь информации при суммаризации. · Пример: Неприменимость суммаризованных отчетов сообществ для юридического аудита по точным фразам документов. · (стр. 328–329)

### Выбор инфраструктуры графовой базы данных · Подбирайте тип графовой БД под свои ресурсы: выделенный сервер (Neo4j/TigerGraph) — для строгого контроля и on-premises; управляемый сервис (AuraDB/Neptune) — при нехватке DevOps-ресурсов; встроенная библиотека (Kuzu/DuckDB) — для небольших (до 10–20 ГБ) в основном Read-Only графов, развертываемых через CI/CD. · Пример: Выбор сервера для глубокой кастомизации или встраиваемой библиотеки для статических данных в контейнерах. · (стр. 329–330)

### Обеспечение идемпотентности ETL-пайплайна графа · Проектируйте процесс импорта данных в граф идемпотентным (например, используя `MERGE` вместо `CREATE` в Cypher и пакетную коммит-фиксацию по 1000 узлов), чтобы избежать «ломания» базы при сбоях и перезапусках. · Пример: Проверка существования сущности перед добавлением для защиты от сбоев импорта метаданных. · (стр. 330)

### Контроль актуальности и «захоронение» фактов · При изменении данных реализуйте логику «захоронения» (tombstoning) устаревших связей (например, проставление статуса `inactive`), сохраняя исторический контекст вместо полного удаления. · Пример: Пометка старой связи работника с компанией как `status: "inactive"` вместо удаления ребра `WORKS_AT`. · (стр. 331–332)

### Чек-лист оправданности внедрения графа знаний · Применяйте чек-лист из 6 вопросов (наличие провалов на сложных запросах, жесткая необходимость детерминированного обоснования, готовые онтологии, графовая структура данных, сильная команда поддержки и четкий бизнес-ROI): если нет хотя бы 4 ответов «Да», откажитесь от графа из-за операционного налога. · Пример: Проверка окупаемости операционных расходов на поддержку сложного ETL-пайплайна. · (стр. 333)
