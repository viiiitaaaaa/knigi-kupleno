### Использование концепции «Vibe Coding» для старта · Используйте LLM для генерации черновых набросков, набросков сложной логики или создания быстрых прототипов, чтобы преодолеть проблему «чистого листа» и быстро перейти от абстрактной идеи к работающему коду. · Разработка начальных чертежей и прототипов при исследовании незнакомых API или новых архитектурных паттернов. · (стр. 404)

### Человеко-центрированное управление (Human-Led Orchestration) · Человек-разработчик выступает в роли тимлида и архитектора: он всегда находится в контуре, задает высокоуровневые цели, координирует рабочий процесс, выбирает агентов, предоставляет контекст и принимает финальные решения по любому сгенерированному результату. · Направление агента, предоставление контекста и проверка кода на соответствие стандартам проекта. · (стр. 404)

### Приоритет контекста (Primacy of Context) · Производительность агента напрямую зависит от качества и полноты контекста; избегайте автоматического извлечения контекста в стиле «черного ящика» и самостоятельно собирайте идеальный «инструктаж» (брифинг) для агента. · Создание специальной рабочей зоны (staging area) с полным исходным кодом, внешней документацией, требованиями и гайдами по стилю. · (стр. 405)

### Прямой доступ к фронтирным моделям · Используйте прямой доступ к передовым моделям (например, Gemini 2.5 Pro, Claude Opus 4) и избегайте промежуточных платформ, которые скрывают или усекают контекст, чтобы агенты работали на пике своих возможностей. · Настройка безопасных API-ключей для двух ведущих языковых моделей для перекрестного анализа и страховки от сбоев. · (стр. 405)

### Создание зоны подготовки контекста (Context Staging Area) · Организуйте для каждой задачи временную директорию (например, `task-context/`) с файлами разметки (markdown), где собраны цели, фрагменты кода и необходимые документы для точного инструктажа агента. · Создание папки с файлами `01_BRIEF.md` и `02_CODE/` перед запуском агента-исполнителя. · (стр. 406)

### Использование специализированных ролевых промптов (Specialist Agents) · Применяйте агентов с четко определенными ролями (Scaffolder, Test Engineer, Documenter, Optimizer, Process Agent) через таргетированные промпты для решения конкретных инженерных задач. · Запуск агента с промптом: «You are a senior software engineer. Based on the requirements in 01_BRIEF.md... implement the feature...». · (стр. 406)

### Двухэтапная проверка кода процессом-агентом (Process Agent Critique & Reflection) · Поручите агенту сначала выполнить детальный критический разбор кода (найти баги, нарушения стиля), а затем отрефлексировать собственную критику, отбросив незначительные замечания и выдав краткую, приоритизированную сводку для разработчика. · Промпт: «First, perform a detailed critique of the changes. Second, reflect on your critique to provide a concise, prioritized summary...». · (стр. 406)

### Реализация локального оркестратора контекста · Используйте легкие CLI-инструменты или локальные менеджеры агентов с конфигурационным файлом (например, `context.toml`), чтобы явно указывать файлы, директории и URL для формирования полезной нагрузки промпта. · Определение файлов проекта в конфиге `context.toml` для прозрачного контроля видимости данных моделью. · (стр. 407)

### Создание библиотек промптов с версионированием · Храните файлы промптов для каждого специализированного агента (например, `reviewer.md`, `tester.md`) в выделенной директории `/prompts` внутри Git-репозитория, чтобы совместно улучшать и версионировать инструкции. · Сохранение промптов ревьюера и документчика в виде markdown-файлов в репозитории кода. · (стр. 407)

### Интеграция рабочих процессов агентов с Git Hooks · Автоматизируйте проверки с помощью локальных Git-хуков (например, pre-commit), которые автоматически запускают агента-ревьюера для анализа подготовленных (staged) изменений прямо в терминале до фиксации коммита. · Настройка pre-commit хука для получения обратной связи от Reviewer Agent перед финальным коммитом. · (стр. 407)

### Поддержание архитектурного владения (Architectural Ownership) · Разработчик должен сохранять за собой стратегическое управление и проектирование архитектуры («что» и «почему»), используя агентов только для ускорения реализации («как»). · Выступление в роли финального арбитра дизайна и гаранта долгосрочного видения проекта. · (стр. 408)

### Ведение итеративного диалога с агентом · Если первоначальный результат агента несовершенен, не отбрасывайте его, а продолжайте диалог: давайте корректирующую обратную связь, добавляйте контекст и запрашивайте повторную попытку. · Уточнение инструкций и обсуждение отчета с Reviewer Agent для получения качественного результата. · (стр. 409)
