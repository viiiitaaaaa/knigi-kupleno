### Использование структурированных логов · Предпочитайте полностью структурированные логи полуструктурированным для упрощения их сбора, корреляции и запросов (например, в формате JSON). · Пример из текста: логирование в формате JSON с полями уровня логов, имени сервиса, ID клиента и суммы заказа вместо смешанного текста. · (стр. 9)

### Инструментация через OpenTelemetry · Используйте открытый стандарт OpenTelemetry (OTel) для сбора метрик, трейсов и логов без привязки к конкретному вендору. · Пример из текста: применение библиотек OTel для автоматического сканирования библиотек (например, в Java) или отправки данных через OTLP. · (стр. 10)

### Многомерный анализ данных (Slicing and Dicing) · Не полагайтесь только на статические дашборды; используйте инструменты, позволяющие детализировать и «нарезать» данные телеметрии для ответов на непредвиденные вопросы. · Пример из текста: отказ от статических дашбордов в пользу исследования данных через OpenTelemetry для поиска причин инцидентов. · (стр. 10)

### Мониторинг «золотых» сигналов · Собирайте для каждого сервиса четыре ключевых сигнала: насыщение (saturation), задержку (latency), частоту ошибок (error rates) и трафик (traffic). · Пример из текста: отслеживание использования CPU, времени отклика, кодов ошибок (например, HTTP 5xx) и запросов в секунду. · (стр. 11-12)

### Корреляция сигналов · Анализируйте метрики в комплексе, сопоставляя их друг с другом для выявления корневых причин проблем. · Пример из текста: сопоставление всплеска задержки с другими метриками за тот же период с помощью функции BubbleUp в Honeycomb. · (стр. 12)

### Определение Service Level Objectives (SLO) · Устанавливайте измеримые цели уровня обслуживания для команды, фокусирующиеся на пользовательском опыте в течение определенного периода. · Пример из текста: задание целевого показателя доступности сервиса на месяц или квартал. · (стр. 14)

### Использование Service Level Indicators (SLI) · Собирайте реальные данные о работе ПО (индикаторы), которые показывают, находится ли система в текущий момент в хорошем или плохом состоянии. · Пример из текста: измерение времени отклика при оформлении заказа и успешности операции. · (стр. 14)

### Управление бюджетом ошибок (Error Budgets) · Используйте допустимый предел погрешностей (вытекающий из SLO) для балансирования между рискованными изменениями (инновациями) и стабильностью системы. · Пример из текста: при доступности 99.9% в квартал допустимо 2 часа 11 минут простоев; при исчерпании лимита команда приостанавливает изменения и чинит надежность. · (стр. 14-15)
