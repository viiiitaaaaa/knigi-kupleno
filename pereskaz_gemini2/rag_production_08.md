### Борьба с нестабильностью судьи · Запускайте LLM-судью несколько лет (или прогонов) и усредняйте результаты, либо переходите от субъективного скоринга к структурированным попарным сравнениям (pairwise comparisons). · Применяйте множественные прогоны для компенсации стохастичности моделей. · (стр. 165)

### Борьба с самореферентной предвзятостью · Калибруйте LLM-судью по эталонному золотому тестовому набору (golden test set), созданному людьми, чтобы измерять реальную производительность, а не погоню за «AI-стилем». · Сравнивайте оценки модели с человеческими предпочтениями. · (стр. 166)

### Извлечение чистящего JSON из ответа судьи · Используйте регулярные выражения (`re.search`) для поиска и извлечения валидного JSON-объекта из ответа LLM, даже если модель обернула его в маркеры вроде \`\`\`json. · Реализуйте надежный парсинг ответов судьи в коде. · (стр. 193)

### Оптимизация ретривера до генератора · Всегда оптимизируйте ретривер перед генеративной LLM: если резыскание (recall) составляет 40%, никакой промпт-инжиниринг не спасет приложение. · Переходите на гибридный поиск (векторный + BM25) или добавляйте реранкер. · (стр. 158)

### Предотвращение устаревания контента (Content staleness) · Используйте уникальные идентификаторы сущностей (entity ID) и версию для каждого документа; при загрузке новой версии автоматически удаляйте все чанки предыдущих. · Запускайте проактивные тесты: если в системе есть две версии одного document ID, в пайплайне сбой. · (стр. 162)
