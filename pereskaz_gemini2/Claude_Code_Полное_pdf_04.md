* **TDD (Test-Driven Development):** Использовать цикл разработки через тестирование, пошагово запрашивая у ИИ написание теста (Red), реализацию под него (Green) и последующий рефакторинг с сохранением работоспособности тестов. · *Пример:* `> Напиши тест для функции formatCurrency(amount, currency): ... > Теперь напиши реализацию formatCurrency, которая проходит все тесты. Запусти тесты. > Тесты проходят. Теперь рефактори...` · (стр. 124).
* **Проектирование архитектуры базы данных:** Поставить ИИ бизнес-требования и технические ограничения (версия СУБД, нормализация, индексы, soft delete, аудит) для генерации готовой и продуманной схемы данных. · *Пример:* `> Спроектируй базу данных для системы бронирования отелей: Бизнес-требования: ... Требования: PostgreSQL 16, Нормализация до 3NF, Индексы...` · (стр. 129).
* **Пошаговое описание Git-коммитов:** Поручить ИИ проанализировать текущие изменения (`git diff`) и разбить их на логические коммиты в соответствии с conventional commits. · *Пример:* `> У меня незакоммиченные изменения в трёх разных фичах. Разбей их на отдельные коммиты: 1. Изменения в auth/ -> feat(auth): … 2. Исправления в api/ -> fix(api): … 3. Обновление конфигурации -> chore(config): …` · (стр. 147).

### Проверка результата · что делать (1–2 предложения) · пример из текста · (стр. N).
* **Анализ покрытия кода тестами:** Попросить ИИ настроить инструмент измерения покрытия (например, vitest) с заданными порогами или помочь довести текущий процент покрытия до целевого значения, начиная с критичных файлов. · *Пример:* `> Текущее покрытие: 45%. Помоги довести до 80%. Покажи файлы с наименьшим покрытием и напиши для них тесты, начиная с наиболее критичных.` · (стр. 126).
* **Mutation testing (Тестирование мутациями):** Настроить мутационное тестирование для проверки эффективности тестов на предмет реального отлова ошибок, а не простого покрытия строк кода. · *Пример:* `> Настрой mutation testing с Stryker. Покажи, насколько наши тесты действительно эффективны (не просто покрывают строки, а ловят ошибки).` · (стр. 127).
* **Аудит безопасности запросов к базе данных:** Попросить ИИ проверить код на наличие SQL-инъекций, использование параметризованных запросов, соблюдение прав доступа и шифрование конфиденциальных данных. · *Пример:* `> Проведи аудит безопасности запросов к БД: 1. Найди SQL-инъекции (строковая конкатенация в запросах) 2. Проверь использование параметризованных запросов...` · (стр. 137).
* **Автоматизированное Code Review:** Запустить проверку изменённых файлов (или конкретного PR) с помощью ИИ для выявления критических проблем, багов, уязвимостей и получения рекомендаций по улучшению кода. · *Пример:* `> Проведи code review для PR #42. Посмотри все изменённые файлы и оставь комментарии: – [!] Critical – баги, уязвимости – [~] Warning – потенциальные проблемы...` · (стр. 149).
