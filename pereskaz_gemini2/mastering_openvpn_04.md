### Управление каталогом PKI · Не удаляйте рабочие файлы вручную и доверьте управление хранилищем утилите (ssl-admin или Easy-RSA), так как удаление сертификата из папки `active` без перемещения в `revoked` потребует ручного и потенциально опасного редактирования файла `index.txt`, а папку `prog` с системными файлами OpenSSL нельзя трогать во избежание сбоя PKI. · `The active directory contains all the certificates... In order to utilize the OpenSSL utilities to revoke a certificate, the certificate must be present... It is suggested that the administrator leave the contents of the certificate store to the management of the utility.` · (стр. 110)

### Ограничения множественных CA · Избегайте использования нескольких CA для одного экземпляра OpenVPN без крайней необходимости (миграция, слияние компаний) и ни при каких обстоятельствах не используйте корневые CA веб-браузеров, так как это позволит любому пользователю из их иерархии подключиться к вашему VPN. · `Generally, it is not recommended to use multiple CA certificates for a single OpenVPN instance... Under no circumstances would it be ideal to use a web browser root certificate authority for an OpenVPN certificate chain.` · (стр. 111)

### Выбор аппаратных токенов · При выборе аппаратного токена или смарт-карты проверяйте их поддержку на уровне операционной системы и наличие PKCS#11 драйвера, а не совместимость с OpenVPN, и помните, что токен не требуется (и не рекомендуется) на сервере OpenVPN. · `Please note that OpenVPN depends purely on a working PKCS#11 driver. When selecting a hardware token, it will be important to verify whether the device is supported... Also, note that it is not required (or even recommended!) to use a hardware token on an OpenVPN server.` · (стр. 113)

### Проверка совпадения ID · После записи сертификата X.509 на токен обязательно проверьте, что идентификаторы (ID) закрытого ключа и сертификата совпадают, используя команду `pkcs11-tool --module <драйвер> --login -O`. · `We need to verify that the IDs of the private key and certificate match: pkcs11-tool --module libeTPkcs11.so --login -O` · (стр. 117)

### Получение сериализованного ID для токена · Чтобы узнать точный идентификатор токена, ожидаемый OpenVPN, используйте опцию `--show-pkcs11-ids` с путем к драйверу, а полученную строку заключайте в одинарные кавычки в конфигурации. · `In order to use a certificate and private key from a hardware token, you must first find out the hardware token ID that OpenVPN expects. This is done using the --show-pkcs11-ids option... please remember to use single quote mark.` · (стр. 118)

### Защита корневого ключа CA · Храните файлы PKI в отдельном защищенном месте (желательно на отдельном компьютере) и уделяйте особое внимание защите файла `ca.key`, так как его компрометация делает всю PKI небезопасной, требуя её полной замены. · `Special care should be taken to protect the ca.key file, as the entire security of your PKI is dependent on this file. If the ca.key file is compromised in any way, the entire PKI is rendered insecure, and should be abandoned.` · (стр. 122)

### Защита файла приватного ключа · Защитите файлы приватных ключей (`server.key` / `client.key`), сделав их доступными для чтения только пользователю root или администратору, поскольку любой с доступом к ним сможет расшифровать трафик OpenVPN. · `This file needs to be readable by the root (or administrator) user only, as anyone with read access to private keys can decrypt OpenVPN traffic.` · (стр. 128)

### Использование абсолютных путей · Всегда используйте абсолютные пути для указания файлов сертификатов, ключей и Diffie-Hellman параметров в конфигурационных файлах OpenVPN. · `It is advisable to use an absolute path for this file (as well as the other certificate and private key paths).` · (стр. 127)

### Предотвращение DoS-атак через tls-auth · Используйте директиву `tls-auth` со статическим пре-общим ключом для добавления дополнительного уровня аутентификации на TLS-контроллер, чтобы защитить сервер от DoS-атак (когда злоумышленник отправляет множество запросов на установку TLS-соединения). · `To address this possible vulnerability, OpenVPN introduced an extra authentication layer to the TLS control channel using the tls-auth option.` · (стр. 131)

### Направление ключа tls-auth · Задавайте разные направления (direction) для ключа `tls-auth`: параметр `0` на сервере и параметр `1` на всех клиентах для обеспечения двунаправленной безопасности. · `The direction flag needs to be set to 0 on one end and to 1 on the other end. In the client/server mode, this means that the server has the parameter 0 for the direction, and all clients have the direction parameter set to 1.` · (стр. 134)

### Проверка атрибутов назначения сертификатов (EKU) · Добавьте опции `remote-cert-tls client` на сервере и `remote-cert-tls server` на клиенте, чтобы проверять расширенное использование ключа (EKU) и предотвратить атаки с использованием поддельных сертификатов (например, когда злоумышленник ставит сервер на базе клиентского сертификата). · `This prevents a hacker from setting up a rogue OpenVPN server using a client certificate... prevents a malicious client from setting up a rogue OpenVPN server` · (стр. 133)

### Масштабирование серверной маршрутизации · Передавайте маршруты до серверных подсетей клиентам динамически с помощью директивы `push "route ..."` на сервере, а не прописывайте их вручную в каждом клиентском файле конфигурации, так как ручной подход не масштабируется. · `This is done using a push option, where the route configuration is pushed to the client. It could also be achieved by adding the route to the client configuration file itself, but this does not scale well.` · (стр. 138)
