### Стратегия повторных попыток с экспоненциальной задержкой и джиттером · Повторяйте запросы при временных сбоях (таймауты, ошибки сети), используя экспоненциальную задержку с добавлением случайного шума (джиттера), чтобы избежать проблемы лавинообразных запросов. · Пример из текста: `@retry_with_backoff(max_retries=3, retryable_exceptions=(TimeoutError, ConnectionError, RateLimitError))` · (стр. 144-145)

### Требование идемпотентности для повторных попыток · Никогда не повторяйте операции без проверки статуса (оплата, запись в БД, отправка email), если они не идемпотентны; каждая операция должна содержать ключ идемпотентности. · Пример из текста: Запрос статуса транзакции у платежного провайдера по ключу идемпотентности перед повторной попыткой. · (стр. 146)

### Цепочки резервных стратегий (Fallback Chains) · При сбое основного инструмента автоматически переключайтесь на альтернативные варианты (например, запасной поисковый API, кэш или базовые знания модели). · Пример из текста: `search_chain = FallbackChain([("google_search", ...), ("bing_search", ...), ("cached_knowledge", ...)])` · (стр. 147-148)

### Самокоррекция через рефлексию · Поручайте агенту проверять собственный результат на ошибки, логические провалы и галлюцинации, а затем применять исправления (используйте для критически важных задач). · Пример из текста: Функция `self_correct(agent, task, initial_output, max_rounds=2)` запускает проверку на наличие фактических ошибок или противоречий. · (стр. 148-149)

### Автоматический выключатель (Circuit Breaker) · Предотвращайте бесконечные обращения к падающему сервису: если инструмент слишком часто выдает ошибки, «размыкайте» цепь на время восстановления. · Пример из текста: `search_breaker = CircuitBreaker(failure_threshold=3, recovery_timeout=30)` · (стр. 150-151)

### Плавное ухудшение функционала (Graceful Degradation) · Если полное восстановление невозможно, возвращайте частичный результат с понятным предупреждением для пользователя вместо полного падения. · Пример из текста: Предоставление ответа из обучающих данных с пометкой: «На основе моих обучающих данных (могут быть устаревшими)...» при падении поискового API. · (стр. 152)

### Запрет на тихое проглатывание ошибок · Никогда не перехватывайте исключения молча; каждую ошибку нужно либо исправить с логированием, либо передать человеку, либо использовать для мягкого деградирования. · Пример из текста: Игнорирование ошибки на шаге 2 приводит к уверенно неверному результату на шаге 5. · (стр. 154)

### Слой безопасности агента (Pre/Post Action Checks) · Проверяйте действия агента до и после их выполнения: блокируйте опасные команды, требуйте подтверждения для чувствительных действий и отслеживайте попытки инъекций промптов. · Пример из текста: Класс `AgentSafetyLayer` с блокировкой деструктивных команд (`rm_rf`, `drop_database`) и проверкой на фразы вроде `ignore previous instructions`. · (стр. 155-157)

### Интеллектуальная маршрутизация моделей (Model Routing) · Используйте более дешевые и быстрые модели (например, Haiku) для простых задач вроде классификации и извлечения, а мощные (Sonnet, Opus) — только для сложного планирования и синтеза. · Пример из текста: Таблица маршрутизации задач `ROUTING_TABLE`, где для классификации используется `claude-haiku-3.5`, а для рассуждений — `claude-sonnet-4`. · (стр. 164)

### Многоуровневое кэширование (Exact & Semantic Cache) · Снижайте затраты на повторяющиеся запросы, используя точное совпадение (хэши) и семантическое кэширование через эмбеддинги. · Пример из текста: Классы `ExactMatchCache` и `SemanticCache` для переиспользования результатов похожих или идентичных запросов. · (стр. 165-167)

### Кэширование промптов (Prompt Caching) · Передавайте неизменяемые системные промпты и определения инструментов с флагом кэширования, чтобы сократить стоимость входных токенов на порядок. · Пример из текста: Настройка параметра `"cache_control": {"type": "ephemeral"}` для длинного системного промпта в API Anthropic. · (стр. 167-168)

### Бюджетные ограничения (Budget Guardrails) · Контролируйте расходы на уровне отдельных запусков и общие дневные лимиты, при исчерпании бюджета принудительно переключая агента в режим синтеза. · Пример из текста: Класс `BudgetGuard` с проверкой `per_run_budget` и `daily_budget`, переводящий агента в `force_synthesis` при превышении лимита. · (стр. 168-169)

### Цикл «написание — тестирование — исправление» (Write-Test-Fix Loop) · Для задач программирования агент должен не просто писать код, но и запускать тесты, анализировать падения и итеративно исправлять ошибки. · Пример из текста: Класс `CodingAgent`, выполняющий сбор контекста, планирование, написание кода и проверку тестами в цикле до 3 попыток. · (стр. 177-180)

### Выборочное извлечение контекста по частям · Не загружайте в контекст целые огромные файлы или репозитории целиком; используйте граф импортов, поиск по паттернам (grep) и извлечение функций через AST. · Пример из текста: Ограничение контекста правилом «предпочитай чтение сигнатур функций вместо полных реализаций» и разбиение бюджета токенов по приоритетам. · (стр. 182-184)

### Стратегия редактирования «Поиск и замена» (Search-and-Replace) · Избегайте перезаписи файлов целиком; используйте точечные операции поиска старого фрагмента и замены на новый, чтобы экономить токены и не удалять лишний код. · Пример из текста: Использование точных блоков поиска и замены вместо генерации всего файла при правке больших модулей. · (стр. 182)

### Принцип «Сначала напиши тест» (Test-First Principle для кода) · Всегда заставляйте агента сначала написать падающий тест на баг или новую фичу, и только потом писать исправляющий код. · Пример из текста: Правило в промпте для исправления багов: «Сначала напишите падающий тест, воспроизводящий ошибку, и запустите его для подтверждения». · (стр. 184, 188)

### Передача истории изменений при повторных попытках исправления кода · Если исправление кода не сработало с первого раза, передавайте агенту полный diff всех уже сделанных изменений, чтобы он не повторял ту же ошибку. · Пример из текста: Включение истории изменений в контекст при исчерпании попыток снижает количество повторных неверных правок с 70% до 20%. · (стр. 188)
